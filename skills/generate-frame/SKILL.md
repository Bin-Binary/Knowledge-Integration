# generate-frame — FrameNet 端到端框架语义学分析

## 1. 技能定位

将 FrameNet 框架语义学（Fillmore 理论传统；理论手册：*FrameNet II: Extended Theory and Practice*, Ruppenhofer et al., 2016）落地为可执行的端到端标注流水线。

**核心模型**：
- **Target**：框架触发词，激活一个独立完整事件；
- **Frame**：脚本式概念结构，描述某类情境/对象/事件及其参与者与道具；
- **FE（Frame Element）**：框架元素 = 抽象语义槽 = 语义角色——把事件中形形色色的参与者，按其在事件意义中承担的功能归类后打上的标签。FE 只标注"功能位"，不管"谁坐这个位"；
- **场景涌现**：`场景 = 框架结构（FE 角色定义）× 填充对象自带语义`；FE 的语义角色定义固定，但填充对象的变化带来不同的场景；场景是生成出来的，不是枚举出来的。

**一句话概括**：把任意领域语料转化为「入口框架 → 子框架 → 框架元素 → 框架关系」的语义结构，并同步产出**事实、缺口、误解**三类知识审计清单；**全部中间产物必须留存，禁止丢弃**。

**方法边界声明**（自知之明）：本方法产出的是"FrameNet 风格的主题知识结构化"，非严格 FrameNet 标注——框架由主题维度而非 LU 激活；LU 层（Target↔Frame 映射）暂不持久化，属已知局限。

## 2. 输入识别与预处理

| 输入类型 | 识别特征 | 预处理动作 |
|---|---|---|
| 主题 | 名词性领域词，如"Python异常体系"、"HTTP状态码" | 搜集该领域**权威原文**（官方文档优先），作为分析语料 |
| 语料地址 | URL / 文件路径 / 文档引用 | 读取原文，按片段顺序编号切分 |
| 命令 | 指令式表述，如"分析X的框架结构" | 解析出目标分析对象，归入上两类处理 |

> 语料选取原则：权威、可溯源（官方文档 > 教材 > 高质量技术文档）；每个片段必须可编号定位。

## 4. 微观七步法（句子级语料分析）

> 输入：一段原始自然语料段落。
> 前置规则：系动词 be 为 Cop 系动词，**不计入 Target**。
> 流程：①识别 Target → ②匹配 Frame → ③定位 FE → ④FE-GF-PT 三元组（仅表层句法依存）→ ⑤零实例化 NI + 特殊标注检查 → ⑥框架-框架关系 → ⑦业务洞察

### 4.1 识别 Target
- 逐句提取**可激活独立完整事件的谓词**；
- 每一个从句内的完整语义事件，独立作为一个 Target；
- 谓词、事件性名词、形容词均可成为 Target；
- 主动/被动形式的同语义谓词，各自独立 Target。

### 4.2 匹配 Frame
- 按每个 Target 的义项匹配 FrameNet 标准框架；
- 区分【核心 FE】（框架必需参与者）与【外围 FE】（可选补充参与者）；
- 记录每个 FE 的语义角色含义。

### 4.3 定位 FE 文本片段
- 在当前 Target 的**句法辖域内**找到每个 FE 对应的表层文本；
- 若 FE 概念存在但**无表层文本片段**：记录该状态，进入 4.5 零实例化判断。

### 4.4 FE-GF-PT 三元组表格（仅表层句法实现的 FE）
> 只填入拥有表层句法填充物的 FE；零实例化 FE 不进入本表。

| 字段 | 说明 |
|---|---|
| 文本片段 | 表层文本 |
| FE | 语义角色 |
| GF | Ext 外部论元 / Dep 依存论元 / Obj 宾语 / PP 介词短语 / Sfin 限定从句 |
| PT | 归属 Target-Frame 标记（格式：`词元 → 框架名`） |
| 归属Target | Target 词元（含词性，如 `bake.v`） |

### 4.5 零实例化 NI 判断 + 特殊标注检查
1. 零实例化三型（标记类型并写出语义解释）：
   - **INI**（不定零实例化）：FE 概念存在、无表层文本，指代集合内泛指实体；
   - **DNI**（定指零实例化）：无表层文本，但文中存在可恢复的先行语；
   - **CNI**（构式零实例化）：被构式（被动/中动/祈使）压制掉表层实现，概念上仍存在。
2. 特殊标注检查，逐一记录：FE 合并、非连续框架元素、Supp 支持谓词、Ctrlr 控制器。

### 4.6 框架-框架语义关系
- 判断多个 Target 之间的语义依赖；
- 严格使用 FrameNet 标准 9 种关系（全集与判定级联见 5.9）；
- 输出关系表：源框架｜FrameNet关系｜目标框架｜关系释义。

### 4.7 业务洞察（**严格只使用当前段落原文，禁止引入外部领域知识**）
- ✅ 确定事实：文本字面直接提取的客观断言；
- ⚠️ 信息缺口：本段原文未交代、缺少定义、边界模糊、INI 带来的信息空白；
- ❗ 易误解：基于文本表述，学习者容易脑补的错误推论，**每条须回溯原文文本**。

## 5. FrameNet 理论决策要点

### 5.1 框架切分清单（同框架词汇必须满足，按可操作性排序）
1. **相同 FE**：数量与类型一致（含显式与 NI 实现）；
2. **指称场景相同部分**；
3. **相同 FE profiling**：同一参与者视角被凸显（如 buy ≠ sell，须分帧）；
4. **相同关系**：FE 间互指关系一致、对背景框架的预设一致；
5. **类型相似**：Target 基本指称相似、FE 类型预指相似。

附加校验——**体一致性**：同框架 LU 必须蕴含相同的阶段与过渡；causative 与 inchoative 因多出一个致使子事件，须分帧（分帧后用 `Causative of` / `Inchoative of` 关联回来）。

> 适用性说明：本清单为"词归帧"判据；本方法的子框架属"事实归帧"，内聚性以入口框架维度槽（5.10）做粗粒度校验替代。

### 5.2 不作为切分依据的标准
- **语法差异**：被动、中动、时体构式、与外部主题 FE 的组合、纯词性差异（用 CNI 处理，不分帧）；
- **标量/极性反义**：反义词同框架；但**换位 converse**（buy/sell）与**逆反对**（tie/untie）须分帧；
- **用法差异**：指示、语域、方言、评价——用语义类型标记，不分帧。

### 5.3 FE 定义规则
- FE 是**抽象语义槽**，以语义角色命名，**禁止直接把事实文本当作 FE**；
- 事实仅作为 FE 的**填充值**进入框架表；
- 核心度三级：Core / Peripheral / Extra-Thematic（Duration、Frequency、Recipient、Beneficiary、Explanation、Condition、Concessive、Degree 等）；
- **核心度标注（v5 起，输出强制）**：每个 FE 在框架表中标注（核心）或（外围）。判定法：删除该槽后框架刻画是否仍完整——不完整→（核心）；仅补充语境/列举→（外围）；
- 同一语义槽的不同填充物本体类型不同时，拆分为两个 FE 并用 Excludes 关联。

### 5.4 FE 间关系（Frame-Internal FE Relations）

> 理论依据：Fillmore 框架语义学的核心主张——FE 不是松散独立的语义标签，而是通过概念的交互、凸显和约束**相互定义**的结构化网络。FE 间关系属于**框架内部标注**，与 §5.9 框架间关系属于不同层级，不进入框架关系表。

#### 5.4.1 概念上的相互依存性（Mutual Dependency）

一个 FE 的概念往往由另一个 FE 决定；缺少其中之一，另一方概念无法完整建立——这正是框架语义学区别于"独立特征列表"标记法的根本所在。

- 判定问题：**"删除 FE_A 后，FE_B 的概念是否退化为另一框架的 FE？"** 若是 → 两者存在相互依存关系；
- 在框架表中以注释形式标注：`` `FE_A` ↔ `FE_B`：相互依存 ``。

#### 5.4.2 核心集关系（CoreSet）

两个或多个核心 FE 在概念上可以**互相替代**来满足框架的核心语义——句子只要出现其中任意一个，框架的核心概念在认知上就是完整的。

- 判定问题：**"缺少 FE_A 时，FE_B 是否足以独立支撑框架核心概念？"** 若是 → 两者属同一 CoreSet；
- 标注格式：`CoreSet({FE_A}, {FE_B}, …)`，写在框架表的 FE 及填充列末尾；
- 典型案例：Motion 框架的 `Goal`、`Path`、`Source` 互属 CoreSet——出现任一即可完整刻画移动事件。

#### 5.4.3 排他关系（Excludes）

两个 FE 在概念上**互斥**，不可在同一认知视角下同时实现。

- 判定问题：**"FE_A 与 FE_B 是否描述同一概念位的不同互斥填充方式？"** 若是 → Excludes；
- 标注格式：`Excludes({FE_A}, {FE_B})`，写在框架表的 FE 及填充列末尾；
- 典型案例：行为的"不可控原因（Explanation）"与"主观目的（Purpose）"通常互斥；
- 与 5.3 已有规则衔接：同一语义槽因本体类型不同而拆分为两个 FE 时，必须用 Excludes 关联。

#### 5.4.4 要求关系（Requires）

一个 FE 的出现从概念上**强制要求**另一个 FE 的存在。

- 判定问题：**"FE_A 显式出现时，是否概念上必然隐含 FE_B？"** 若是 → Requires；
- 标注格式：`Requires({FE_A} → {FE_B})`，箭头方向为"出现 A 则必须出现 B"；
- 典型案例：出现"受赠者（Recipient）"则概念上隐含"赠予者（Donor）"。

#### 5.4.5 视角化与概念凸显（Perspective & Profiling）

不同的标示词（Lexical Unit）激活同一个框架，但通过操控 FE 之间的概念相对关系来表达不同视角——被凸显的 FE 成为句法上的主语/宾语，被背景化的 FE 降为零实例化。

- 判定问题：**"同一框架的不同 LU 是否对核心 FE 做了不同的前景/背景分配？"** 若是 → 存在视角化；
- 标注格式：在框架表 FE 列的对应 FE 填充后加 `[视角: 前景/背景]` 标记；
- 典型案例：Commercial_transaction 框架下，buy 凸显 Buyer+Goods（Seller 降为 DNI），sell 凸显 Seller+Goods（Buyer 降为 DNI）——buy 与 sell 因 profiling 不同须分帧（参见 5.1 第3条），但两者共享的抽象框架内部仍体现此 FE 间关系；
- 本方法适用：主题维度的子框架若对同一入口框架维度做了不同角度的刻画，应在 FE 列注明视角标记。

#### 5.4.6 FE 间关系输出格式

在框架表的 FE 及填充列末尾，以独立行（`<br>` 分隔）标注本框架内存在的 FE 间关系：

```
CoreSet({FE_A}, {FE_B}) | Excludes({FE_A}, {FE_B}) | Requires({FE_A} → {FE_B}) | `FE_A` ↔ `FE_B`：相互依存
```

> **范围界定**：若框架内无任何 FE 间关系（相互依存、CoreSet、Excludes、Requires 均不成立），则不标注，无需强行添加。视角化标记仅在适用时出现。

### 5.5 FE 语义角色与场景涌现（v5 新增）

**FE 的语义角色本质**：FE = 语义角色 = 把事件中形形色色的参与者，按其在事件意义中承担的功能归类后打上的标签。FE 只标注"功能位"，不管"谁坐这个位"。

**三条核心属性**：
1. **FE 的语义角色定义固定**：角色的职能定义是固定槽位，不随填充对象变化；
2. **FE 的填充对象本身可能自带语义**：填充对象本身可能是一个独立的认知实体，自带一套完整的属性和行为特征；框架和场景的关系是 1:N，由 FE 的填充对象激活不同场景；
3. **不同填充对象激活不同场景**：同一 FE 槽位上，不同填充对象因自带语义不同，会给框架带来完全不同的子场景。

**场景涌现公式**：`场景 = 框架结构（FE 角色定义）× 填充对象自带语义`

场景是**生成**出来的，不是**枚举**出来的——框架定义有限规则，填充对象使场景自动涌现；无需穷举所有可能的填充组合。

### 5.6 FE 角色职责的向上抽象助认知（v5 新增）

收敛后的内容依然可能面临无法描述 FE 角色职责的情况。直接描述说不清时，先向上抽象到认知上位，获得通用职责描述，再向下具体化回本 FE。

**认知路径**：
```
【类型集合】→ 描述不出来
     ↓ 向上抽象
  核心主体 → "负责承载实体的功能位置"（上位描述，通用）
     ↓ 向下具体化
【类型集合】→ "负责承载Python内建类型实体的功能位置"（具体描述，可用）
```

**原则**：上位标签是认知脚手架——帮人够到职责描述；够到后拆掉，FE 名称和最终描述都是自己的，不保留上位标签。任何 FE 都能获得职责描述，无需依赖灵光一现。

### 5.7 GF / PT 速查（理论背景）
- 动词 GF：Ext / Obj / Dep；名词 GF 另有 Gen / Quant / Appos；
- FrameNet PT 全集：NP、N、Poss、PP、VPfin、Sfin、Sinterrog、Swhether、Sing、Srel、Sto、Sforto、Sbrst、Sub、AJP、A、AVP、QUANT、QUO；
- 本流程表格规格以 4.4 节简化集合为准。

### 5.8 场景涌现落地路径（v5 新增）

需要 A（填充对象语义）和 B（FE 角色定义）才能生成场景，但 A 和 B 本身都很难直接获取。破法如下：

#### 5.8.1 起点反转——从语料事实出发，同时向 A 和 B 收敛

不求先有 A 和 B 再生成场景，而是从语料事实出发，同时向 A 和 B 收敛——能收敛多少就生成多少，收敛不了的标记为缺口。

**四步收敛**：
1. **语料→事实**（最容易）：语料说 "list是序列类型" → 事实：list属于序列分类。事实客观可提取，不需要理解就能记录。
2. **事实→FE 角色定义**（归纳）：多条事实都说 "X属于某分类" → 归纳出【类型集合】角色。FE 不是凭空设计的，是事实模式的共同点浮上来后命名的。
3. **事实→填充对象语义**（沉淀）：关于 list 的全部事实聚合 → list 的自带语义轮廓逐渐浮现（"序列"+"动态"+"有序"+"可迭代"+"非线程安全" → list≈动态数组）。语料说了多少就沉淀多少。
4. **缺口→定向补全**（驱动下一步）：语料没说 list 是否内存连续 → 缺口。缺口不是失败，是"当前认知边界"的诚实标记。

#### 5.8.2 向上抽象助认知

收敛后仍可能无法定义 FE 角色职责时，使用 §5.6 向上抽象法获得职责描述。

#### 5.8.3 JIT 语义提取——利用 LLM 作为高维语义空间编译器

对象自带语义的"按需运行时提取"（Just-In-Time Extractor）：当对象进入槽位时，利用 LLM 的通用常识或解析官方文档，只抽取与当前 FE 角色相关的特定语义切片，实现"语义投影"。不需要静态穷举对象的所有语义，只在它与特定 FE 发生碰撞时，才实时按需提取。

**工程落地**：通过专门的 Extractor Agent，给 LLM 输入 `(对象: X, 关注视角: Y)`，LLM 在海量知识库中坍缩出其自带语义。

#### 5.8.4 计算即涌现——LLM 充当"乘法算子"

有了填充对象语义和 FE 角色定义，两者相乘后的"场景涌现语义"仍然很难用规则代码拼出。利用 LLM 在高维向量嵌入空间中自动完成碰撞和乘法计算。

**但涌现≠正确**——LLM 做乘法算子可能产生"幻觉涌现"，因此涌现结果必须回校语料。完整闭环：

`[对象自带语义] × [FE角色定义] → LLM涌现 → 语料回校 → 采纳/降级`

**回校要求**：涌现结果中每个事实性断言，必须标注其语料来源片段；无法溯源的断言自动降级为 [待验证]，不作为可信输出。

### 5.9 框架间关系（FrameNet 标准全集，依据手册 §6.1）

输出**仅允许**以下 9 种标准关系标签，禁止自定义：

| 关系标签 | 中文名 | 定义 | 判定要点 |
|---|---|---|---|
| `Inheritance` | 继承 | 子框架 IS-A 父框架；父框架每个 FE 绑定到子框架对应 FE，子框架可新增扩展语义 | 源是目标的本体论子类型，且父 FE 可全部对应（显式对应或经继承链隐式对应） |
| `Perspective on` | 视角化 | 子框架对未视角化的父框架提供特定参与方视角 | 目标为未视角化背景场景，源凸显某一方视角 |
| `Using` | 使用 | 子框架预设父框架为语义背景；父 FE 无需全部绑定 | 源语义成立必须以目标为前提，但源**不是**目标的子类型；**释义必须点名预设的具体前提** |
| `Subframe` | 子框架 | 子框架是父框架所表复杂事件的一个子事件/阶段 | 目标为分阶段复杂事件，源为其一阶段 |
| `Precedes` | 先行 | 源框架事件在目标框架事件之前发生 | 源与目标通常为同一复杂事件的子框架，源先于目标 |
| `Causative of` | 致使 | 子框架是父框架的致使对应框架 | 源 = 目标场景 + 外部致事 |
| `Inchoative of` | 起始 | 子框架是父框架（状态）的起始对应框架 | 源刻画进入目标状态的起始变化，不词汇化致事 |
| `Metaphor` | 隐喻 | 子框架是父框架（具体源域）的隐喻映射 | 跨域映射 |
| `See also` | 参见 | 弱关联链接，无形式化语义 | 不满足以上任何强判定，仅存在领域相关性；兜底慎用 |

**方向约定**：源框架为子/依赖方，目标框架为父/背景方；`Precedes` 为时序方向（源先于目标）。

**标签选择级联**（按序检验，首个命中即用）：
1. 子类型 + 父 FE 可全部对应 → `Inheritance`
2. 不满足子类型，但源语义成立必须以目标为前提 → `Using`
3. 源是目标复杂事件的阶段 → `Subframe`；同父先后阶段 → `Precedes`
4. 状态-变化对：源 = 目标 + 致事 → `Causative of`；源 = 目标状态之起始 → `Inchoative of`
5. 目标未视角化、源凸显一方视角 → `Perspective on`
6. 跨域映射 → `Metaphor`
7. 仅领域相关 → `See also`

**质量红线**：每条关系须通过对应判定要点检验；无合格框架对的关系类型**宁缺毋滥**。

**范围界定**：本节仅规定框架间关系；FE 间关系（`CoreSet`、`Excludes`、`Requires`、相互依存等）属于框架内部标注，不进入框架关系表，单独汇入 §8.4 FE 间关系汇总表。

**旧标签迁移**（v1 → v2+）：`Is a Punctualization of` → 逐条复检为 `Inheritance` 或 `Using`；`Parallels` → `See also`。

### 5.10 主题入口框架（v4 新增，v5 重编号）

**定位**：主题的**根锚点 / 背景场景框架**——对"该主题由哪些维度构成"的元级刻画。对应 FrameNet 中背景场景帧之于子帧的角色（如 Commercial_transaction 之于 Commerce_buy / Commerce_sell）。职能：聚合、导航、**完整性校验**。

**命名**：`{主题核心词}入口框架`（如"异常体系入口框架"、"闭包入口框架"）。

**FE 设计**：
- `主题对象`（核心）：主题本体，填充为主题指称；
- 每个构成维度一个**维度槽**（通常核心；边界标记类维度可标外围），填充 = **维度摘要（须可回溯事实清单）+ 对应子框架名**。

**填充特例（对"填充必须为事实"的唯一显式例外）**：入口框架维度槽的填充值允许包含子框架名引用（导航指针）。理由：入口框架是网络根节点，其职能是聚合导航；维度摘要部分仍须来自事实清单。

**完整性校验（质量门）**：
- 每个子框架**必须**填充入口框架的至少一个维度槽；
- 出现"无槽可填的子框架" → 或者入口框架缺维度，或者该框架不属于本主题——二者必居其一，必须修正；
- 反向：入口框架的每个维度槽必须有子框架填充（空维度槽 = 虚设维度，删除或补框架）。

**表格位置**：框架表**第一行**，固定。

**关系约定**：关系表**第一组** = 各子框架 → 入口框架，每行释义注明填充的维度槽；标签按 5.9 级联判定（静态主题多为 `Using`；过程型主题可为 `Subframe`，阶段间用 `Precedes`）。

## 6. 三类中间产物判定标准

| 概念 | 定义 | 判定问题 |
|---|---|---|
| **事实** | 原文直接陈述的客观信息 | "原文是否直接说了？" |
| **缺口** | 语料本身缺少、未说明的知识 | "原文是否没交代/定义缺失/边界模糊？" |
| **误解** | 学习者由文本诱导产生的错误理解 | "读者会不会由这段话推出错误结论？" |

**红线**：三者不可混写；每条误解须注明诱导它的原文表述；缺口不得用外部知识脑补填补（启用可选项①时通过独立文件补全，见 7.1）。

### 7.1 缺口补全规范（产出：`{主题}-gapfill.md`）
- **来源白名单**（按优先级）：官方文档 > 官方 PEP/RFC/W3C 规范 > 官方语言参考/库参考 > 官方教程 > 领域权威标准（如 MDN）。**禁止**博客、论坛、问答站、第三方教程；
- 每条补全记录四要素：**缺口编号、补全资料、权威来源名称与具体定位（章节/条目/PEP 编号）、补全状态**；
- 补全状态三档：✅已补全 / ◐部分补全 / ❌未找到权威资料；
- **红线1**：补全资料不修改主文档事实清单、不进入框架表 FE 填充——v4 起物理隔离（独立文件），隔离更强；
- **红线2**：未找到权威资料如实标 ❌，禁止推测或非权威源填充；
- **红线3**：补全资料与原文冲突时单独标注"⚠️冲突提示"，不擅自改写原文事实；
- **文件结构**：标题 → 被引用说明（回链主文档）→ 来源与红线声明 → 补全表（四列：缺口编号｜补全资料｜权威来源与定位｜补全状态）→ 冲突提示区（如有）。

### 7.2 HTML 统一视图规范（产出：`{主题}-framenet.html`）
- **定位**：主文档 + gapfill 的**合并渲染视图**（md 文件族是模块化的，html 是统一视图；自包含单文件约束不变）；
- **自包含单文件**：CSS 全部内联，无外部依赖、无外链脚本，离线双击可开；
- **结构**：页头（标题 + 版本徽章 + 启用选项徽章 + 文件族说明）→ 粘性目录导航（章节锚点）→ 各章节卡片；
- **入口框架**：框架表第一行以高亮样式（如 `.entry`）区分，导航中标注；
- **表格**：框架表、FE 间关系汇总表、关系表（分两组呈现）、补全表完整渲染，外层横向滚动容器；
- **关系标签**渲染为彩色徽章，9 种标准关系各一色，附完整图例；
- **清单配色**：事实（绿）/ 缺口（橙）/ 误解（红）左侧色条；补全状态徽章复用 7.1 三档标记；
- 原文片段用 `<details open>` 折叠组件承载；响应式窄屏自适应。

## 9. 硬性约束（违反即返工）
1. FE 必须是抽象语义角色，禁止直接把事实文本当作 FE；

3. 事实、缺口、误解是分析中间产物，必须完整记录，不能丢弃；
4. 严格区分三个概念：事实 = 原文直接陈述；缺口 = 语料本身缺少；误解 = 文本诱导的错误理解；
5. 原始语料定位需记录片段编号、来源链接；
6. 主文档输出标准 Markdown（8 节固定），不依赖附属文件即完整成立；
7. 框架表不含 Gap 列；第一行固定为入口框架；
8. 原文与翻译一一对应，原文后紧跟翻译；

11. 每个 FE 必须标注核心度（核心/外围），判定依据 5.3；
12. FE 间关系标注须使用 5.4 规定的四种标准类型（CoreSet / Excludes / Requires / 相互依存）及视角化标记，禁止自定义类型；同一语义槽因本体类型不同拆分为两个 FE 时必须用 Excludes 关联（5.3 接续规则）；
13. 入口框架完整性：每个子框架必须填充至少一个维度槽，每个维度槽必须有子框架填充（5.10 质量门）；
14. 引用行仅在实际生成对应文件时出现，使用同级相对路径；
15. HTML 为统一视图（主文档 + gapfill 合并渲染），自包含单文件，内容与 md 文件族一致；
16. FE 语义角色定义须体现"功能位"本质——名称为抽象语义角色，非事实文本直写；FE 的填充对象自带语义与 FE 角色定义在框架表中分开呈现（5.5）；
17. LLM 参与的涌现结果（5.8.4）必须回校语料，无法溯源的断言降级为 [待验证]，不作为可信输出。
