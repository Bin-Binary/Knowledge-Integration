| 28 | **HBM** | <span id="jump-HBM"> High Bandwidth Memory </span> | 高带宽内存（显存），算力芯片上的极速存储介质 | UCM体系中的“热数据”实时记忆区 |
| 29 | **DRAM** | <span id="jump-DRAM"> Dynamic Random Access Memory </span>| 动态随机存取内存（系统内存），服务器的主内存 | 可降低首Token时延90% |
| 30 | **SRAM** | <span id="jump-SRAM">Static Random-Access Memory </span> | 静态随机存取内存，直接集成在 AI芯片（如昇腾/NVIDIA）内部的片上高速缓存（Cache/Shared Memory）| 可降低首Token时延90% |
| 31 | **SSD** | <span id="jump-SSD"> Solid State Drive </span> | 固态硬盘（闪存），服务器的本地高速度硬件存储 | UCM 体系中的“冷数据”长期记忆区 |
| 32 | **NFS** | <span id="jump-NFS"> Network File System </span> | 用于大模型集群跨节点同步持久化缓存 | 用于大模型集群跨节点同步持久化缓存 |
| 33 | **FP** | <span id="jump-FP"> Forward Propagation </span> | 前向传播，数据从输入层穿过各个隐藏层，最终在输出层得到预测结果的单向计算过程 | 推理和训练阶段都必须执行的基本步骤 |
| 34 | BP | <span id="jump-BP"> Backpropagation </span> | 反向传播，根据输出误差从后往前计算梯度并更新权重参数的过程 | 仅在训练（模型学习）阶段需要执行 |
| 35 | TOP-P | <span id="jump-TOP-P"> Top-p Sampling </span> | 按照概率从大到小对词表中的候选词进行排序，然后从前往后累加概率，直到累加值达到或超过设定的阈值 \(p\) 为止。最后，只在这个由高概率词组成的“核心集合（Nucleus）”中重新归一化并进行随机抽签 | 核心思想是动态筛选。候选词的候选池大小（数量）是根据概率分布的陡峭程度动态变化的 |
| 36 | Top-k | <span id="jump-Top-k"> Top-k Sampling </span> | 无论概率分布如何，死板地只保留概率最高的前 \(k\) 个词作为候选池，其余的词全部丢弃，然后再从这 \(k\) 个词里按比例抽签 | 属于静态筛选。容易在概率分布很平缓时漏掉好词，或者在分布很陡峭时引入不相关的废词 |
| 37 | Greedy | <span id="jump-Greedy"> Greedy Search </span> | 贪婪搜索。每次雷打不动地只选择概率最高的那一个词（相当于 Top-p 中 \(p \rightarrow 0\) 且 Top-k 中 \(k=1\) 的极端情况） | 没有任何随机性。会导致生成内容陷入死循环、极其枯燥，通常仅用于代码生成或数学计算等确定性场景 |
| 38 |  | TempTemperature | 温度系数。用来调整模型输出的概率分布形状。温度越高，分布越平缓（AI 越有创意/胡言乱语）；温度越低，分布越陡峭（AI 越保守/死板）| 一般先通过 Temperature 改变概率分布，再用 Top-p 划定切分线 |

## 核心概念拆解
| 序号 | 缩写 | 全称 | 含义 |
| :---- | :---- | :---- | :---- |
| 01 | W | <span id="jump-Weights"> 权重（Weights）</span> | 大模型经训练后冻结在网络中的静态参数矩阵，包含模型对知识的全部记忆与语义法则。推理时属于静态只读常量，是隐藏状态（激活值）进行矩阵乘法变换的映射底座 |
| 01-Ⅰ | | 动态全量读取（Full-Weight Loading）| 在Decode阶段，由于自回归无法并行，每生成一个新Token，隐藏状态都必须完整流经所有网络层。由于GPU计算核心（SRAM）存不下数十GB的权重，硬件每蹦一个字，都必须把全量静态权重从显存（HBM）中重新拉取、搬运进核心一次 |
| 02 | A | <span id="jump-Activations"> 激活值（Activations）</span> | 激活值是 AI 在思考、计算时的临时数据，相当于模型大脑正在“实时运算的思维草稿”。 |
| 03 |  | 分块预填充（Chunked Prefill）| 推理优化中一项关键技术。核心思想：将超长的新用户输入（Prompt）切分成多个较小的“数据块”（Chunks），分批次送入 GPU 进行计算 |
| 04 | APC | 自动前缀缓存（Automatic Prefix Cache）| 自动识别并缓存不同用户请求中“完全相同”的前缀文本（如系统提示词、RAG 检索文档），复用这部分已计算好的KV Cache |
| 05 |  | 分页注意力（PagedAttention）| 像操作系统管理内存一样，把大模型的注意力缓存切成固定大小的页（Pages/Blocks）来管理”的技术 |
| 06 | 猜测解码 | Speculative Decoding | 用于大模型推理加速，让一个体积小、速度极快的“小模型”先在前面盲猜答案。得益于 Transformer 的并行计算能力，大模型在做**唯一一次前向传播（FP）**时，其输出层（LM Head）会同时输出 $N$ 个位置的全量词表概率分布，从而实现批量审稿与对错批改。**大模型单次循环永远只做 1 次并行 FP**：<br>① 最坏情况（全错）：1 次 FP 仅产出 1 个被大模型当场修正的 Token，生成效率等于普通自回归。<br>② 最好情况（全对）：1 次 FP 连续验证通过 $N$ 个 Token 并顺带产出第 $N+1$ 个 Token，生成效率提升 $N+1$ 倍。|
| 07 |  | 异步调度（Async Scheduling）| HTTP/RPC请求处理（网络 I/O）”与“GPU 显卡的大模型矩阵计算（核心算力）”彻底解耦，让它们在两条不同的车道上并行跑，从而消灭 GPU 的“空转等数据”现象 |
| 08 | TP | <span id="jump-Tensor-Parallel">张量并行（Tensor Parallel）</span>| **拆分的是数学公式本身**，单个大模型太大，一张显卡的显存装不下，于是把大模型最核心的“矩阵（Tensor）”切成几份，分给多张显卡同时计算; 是并行计算领域中颗粒度最细的一种切片方式（直接对单层网络的矩阵乘法动刀，将参与矩阵乘法运算的数据矩阵（Tensor）拆分到不同的显卡上进行并行计算） |
| 09 | PP | <span id="jump-Pipeline-Parallel">张量并行（Pipeline Parallel）</span>| **拆分的是执行步骤的先后顺序**，将大模型由数百个顺序连接的网络层（Layers）组成的整条计算链条，按区间斩断，分段部署在不同的显卡上 |
| 10 | EP | <span id="jump-Expert-Parallel">专家并行（Expert Parallel）</span>| 在MoE架构中，大模型内部有许多个专攻不同领域的“专家矩阵”，专家并行就是把这些不同的“专家”分别安置在不同的显卡上 |
| 11 | MoE | <span id="jump-MoE">混合专家模型（Mixture of Experts）</span>| 解码时，只计算稀疏激活的专家网络（Sparse Active Experts），而不触发全量参数的计算（Dense Computation） |
| 12 | DP | <span id="jump-Data-Parallel">数据并行（Data Parallel）</span>| 由于训练数据（如千亿字语料）太多，一台服务器吞不下，于是把大模型复制多份（分身），让每个分身同时喂不同的数据进行训练。它是并行计算领域中数据层面的横向扩展，与前面的切分模型的 TP/PP/EP 处于不同的维度 |
| 13 |  | 预填充-解码解耦/计算-访存解耦部署（Prefill-decode Disaggregation）| 分布式集群架构技术, 它将大模型推理的两个阶段（Prefill 和 Decoding）彻底“分家”，分别部署在不同的物理服务器集群上，通过高速网络跨机传输数据 |
| 14 |  | 分段昇腾计算图（Piecewise AclGraph）| vLLM-Ascend适配框架中一项非常底层的图模式（Graph Mode）性能优化技术, 是华为昇腾（Ascend）硬件上的“分段图捕获与重放”机制 |
| 15 |  | 全图昇腾计算图（Fullgraph AclGraph）| 拒绝任何切分，将大模型从输入到输出的所有算子（包括最复杂的 Attention 算子），整体打包编译成一张 100% 完整的静态计算图（AclGraph），一次性整体下发给昇腾 NPU 运行 |
| 16 |  | 最大模型长度（max-model-len）| 它指定了该推理服务允许处理的“用户输入 Prompt + AI 输出回答”的最大 Token（字符）总长度上限, **这个参数会直接决定服务器能不能开机，以及开机后并发量（QPS）的高低**|
| 17 |  | 权重预取（MLP Weight Prefetch）| 在GPU/NPU 还在计算当前这一层的 Attention（注意力）时，系统就已经提前把下一层 MLP（多层感知机）层的权重参数，从 HBM（显存）搬运到计算核心内部的 Cache（缓存）里了, 利用了计算与访存的异步并行（Overlap，重叠），实现了大模型推理的进一步提速|
| 18 | FFN | <span id="jump-FFN"> 前馈网络（Feed-Forward Network）</span> | 大模型中的“知识存储与加工厂”。在 自注意力 提取出词与词之间的关联特征后，FFN 通过两层线性映射和激活函数，对这些特征进行深度加工，相当于模型脑中用来存储和提取具体概念、常识的神经元密集区 |
| 19 | SA | <span id="jump-SA"> 自注意力（Self-Attention）</span> | 大模型中的“上下文关联线索器”。当模型读到一句话时，它通过计算两两词语之间的“注意力权重”，来决定当前词应该关注哪些前文。例如读到“苹果公司推出了新手机”，SA 能让“苹果”这个词死死绑定后面的“公司”和“手机”，而不是水果 |
| 20 | AR | <span id="jump-AR"> 自回归生成（Autoregressive Generation）</span> | AI吐字时“左脚踩右脚上天”的复读机机制。大模型无法一次性生成整段话，而是根据前文预测下一个词（Token），然后把这个新词加入前文，再预测下下个词。这种“自身输出变成自身输入”的循环过程，构成了大模型的动态生成行为 |
| 21 | P | <span id="jump-Prefill"> 预填充（Prefill）</span>| 推理的第一阶段，负责一次性读取用户输入的全部提示词（Prompt）并计算生成 KV缓存，属于计算密集型（Compute-Bound）任务 |
| 22 | D | <span id="jump-Decode"> 解码（Decode）</span>| 推理的第二阶段，负责基于已有上下文逐个词（Token）向外生成文本，每次生成都需要将模型权重完整读取一遍，属于访存密集型（Memory-Bound）任务 |
| 23 |  | 索引复用技术（IndexShare Techniques）| GLM-5.2的重大工程升级方案，每4层Transformer共享同一个索引器，算力节省2.9倍 |
| 24 |  | 三层异构内存分级（3-Tier Heterogeneous Tiering）| 改变以往只靠显存存储记忆的传统模式，**将KV Cache动态分流**（按照热度）在[HBM（热）](#jump-HBM)\(\leftrightarrow \) [DRAM（温）](#jump-DRAM) \(\leftrightarrow \) [SSD（冷）](#jump-SSD)之间做无感换入换出，彻底解决OOM问题 |
| 25 |  | 跨请求前缀缓存复用（Cross-Request Prefix Caching）| 允许多个不同的推理请求共同读取同一份历史长文本缓存（如同一份财报）。[UCM](#jump-UCM)将该公共前缀锁定在[HBM](#jump-HBM)中、计算时直接按需高效换入[SRAM](#jump-SRAM)，后续并发请求无需重新计算，在超长文本多并发场景下成倍节省算力 |
| 26 |  | 持久化高速存储恢复（Persistence Pipeline Store）| 引入特殊的PipelineStore架构。[UCM](#jump-UCM)会异步将缓存数据从内存持续写入本地[SSD](#jump-SSD)或网络[NFS](#jump-NFS)。当大模型服务遭遇崩溃重启时，能“秒级”从硬件中恢复记忆，无需重新做Prefill预热 |
| 27 |  | 跨节点分布式共享（Cross-Node Cache Sharing）| 在多机多卡的分布式推理集群中，打通网络存储边界。[UCM](#jump-UCM)通过挂载共享的(NFS)(#jump-NFS)，让A服务器计算并存储的KV缓存，能够被B服务器直接远程读取，极大提升了整个算力集群的吞吐量 |
| 28 |  | 逐层换入换出控制（Layer-wise Swap Execution）| 采用一种类似于流水线（Pipeline）的控制策略。在大模型前向传播计算时，UCM配合推理引擎，一边利用[SRAM](#jump-SRAM)/[HBM](#jump-HBM)计算当前层的Attention，一边提前将下一层所需的缓存数据从[DRAM](#jump-DRAM)读入HBM，利用时间差抹平I/O延迟 |
| 29 |  | 片上算子加速（芯片级） | 在执行计算（如 Attention 算子）时，数据必须从 HBM加载到芯片内部的SRAM中才能被Core（计算核心）处理。SRAM的大小决定了单次能吞吐的 张量（Tensor）块大小 |
| 30 |  | 特征矩阵乘法 | 在FP穿过每一层时，从HBM读取该层的权重矩阵（Weights）和上一层的输入(Hidden States（隐状态矩阵）/初始语义向量（如果是第1层）)，加载进SRAM，执行海量的矩阵乘法与加法，更新当前层的Hidden States，并将其写回HBM，作为下一层的输入 |
| 31 |  | 激活值增量存储 | FP计算过程中每一层产生的中间结果被称为“激活值（Activations）”。在训练时，这些激活值必须全部缓存在HBM中，因为后面的BP计算梯度时必须用到它们 |
| 32 |  | 流水线气泡停顿 | 在超大模型多卡横向切分（流水线并行）时，由于后一张卡必须等待前一张卡的FP输出结果，如果数据传输不够快，就会在计算节点间产生“气泡”（算力闲置）。UCM就是为了在FP流动时提前换入缓存，消灭气泡 |
| 33 |  | 概率输出 | 大模型通过一次次 FP 计算概率，输出一个针对全量词表（Vocabulary）的概率分布,再交由解码策略一个字一个字把文章‘蹦’出来的 |
| 34 |  | 解码（Decoding）| 从模型输出的概率分布（连续的数值）中，推导出最终文本（离散的词元）的过程。有**搜索**和**采样**两个分支 |
| 34-Ⅰ |  | 搜索（Search）| 旨在寻找数学上整体概率最高、最绝对理性的生成路径，如贪婪搜索（[Greedy Search](#jump-Greedy)）、束搜索（Beam Search）  |
| 34-Ⅱ |  | 采样（Sampling）| 引入了随机性，旨在寻找具备创造性、多样性的生成路径，如: [Top-p](#jump-TOP-P)、Top-k、Temperature |
| 35-Ⅰ | 模型权重 | Weights/Parameters | 大模型经训练后冻结在网络中的静态参数矩阵，包含模型对知识的全部记忆与语义法则。推理时属于静态只读常量，是隐藏状态（激活值）进行矩阵乘法变换的映射底座。|
| 35-Ⅱ | 动态全量读取 | Full-Weight Loading | 在Decode阶段，由于自回归无法并行，每生成一个新Token，隐藏状态都必须完整流经所有网络层。由于GPU计算核心（SRAM）存不下数十GB的权重，硬件每蹦一个字，都必须把全量静态权重从显存（HBM）中重新拉取、搬运进核心一次，导致算力被极度白嫖。|

## 总结
为了实现极高的智商 ➔ 科学家设计了万亿参数的 MoE 模型 ➔ 因为太庞大 ➔ 工程师用 TP+PP+EP+DP 把它拆分并克隆到全球的数据中心进行训练与部署 ➔ 为了在线上迎接高并发（QPS） ➔ 推理引擎开启 异步调度 与 连续批处理，用 PagedAttention 将显存切成固定页并消灭碎片 ➔ 为了应对企业级 RAG 和长提示词 ➔ 框架利用 Automatic Prefix Cache 跨用户共享显存块，配合 解耦部署 和 Chunked Prefill 彻底消灭长文本带来的卡顿 ➔ 最后，在芯片微观层面 ➔ 通过 Fullgraph 静态图 抹平 CPU 驱动开销，利用 MLP 权重预取 隐藏硬件搬运延迟，再套上 投机采样 让小模型盲猜，最终将大模型的蹦字速度拉到了物理极限

## 🛠️ 大模型底层特性与 vLLM 部署实战的映射指南

### 1. 核心特性与 vLLM 的底层纽带（系统关系）
vLLM 的本质是一个**高性能大模型推理引擎**。它的核心使命是在不改变模型原有参数（智商）的前提下，通过对硬件、显存和计算流的极致压榨，将系统的吞吐量（QPS）和运行成本降到最低。

我们之前探索的硬核特性，在 vLLM 中扮演着不同的系统角色：
*   **vLLM 的原生核心架构**：`PagedAttention`、`Continuous Batching`、`Automatic Prefix Cache (APC)`、`Chunked Prefill`。这些是 vLLM 发明并赖以成名的独门秘籍，属于框架的底层核心代码。
*   **分布式协同机制**：`Tensor Parallel (TP)`、`Pipeline Parallel (PP)`、`Expert Parallel (EP)`、`Data Parallel (DP)`。这些是 vLLM 调用底层分布式通信库（如 Ray、NCCL、HCCL）的手段，用于多芯片联合服务。
*   **硬件生态的深度定制**：`Piecewise/Fullgraph AclGraph`、`MLP Weight Prefetch`。这些是 vLLM 与特定硬件芯片（如华为昇腾、NVIDIA）进行算子级图化对齐的厂商特异性加速特性。

---

### 2. 特性知识对模型部署目标的影响（物理表现）
对于模型部署工程师而言，这些底层特性的掌握直接决定了线上服务的生死，并在以下三个维度产生绝对的物理影响：

*   **影响算力选型与预算（省钱）**：
    *   *示例*：部署一个 72B 稠密模型，在 FP16 精度下模型重达 145GB。
    *   *影响*：掌握 `Tensor Parallel (TP)` 就能精准算出必须配置至少 4 张 40GB 显存或 2 张 80GB 显存的芯片，并明确卡间必须通过高速总线（NVLink/HCCS）互联，从根本上杜绝盲目采购或因显存不足（OOM）无法开机。
*   **影响线上服务稳定性（体验）**：
    *   *示例*：系统遭遇长文本（文档分析）与短文本（日常对话）高并发混合输入。
    *   *影响*：掌握 `Chunked Prefill` 和 `解耦部署（Disaggregation）` 可以从集群架构上做好物理隔离，确保长文本的大算力计算绝对不会卡死短文本的普通用户，保证系统可用率（SLA）。
*   **影响核心调优参数的控盘能力（性能）**：
    *   *影响*：vLLM 拥有上百个复杂的命令行参数。掌握这些知识，意味着你可以彻底告别“盲目套用默认参数”的撞运气部署阶段，能够根据业务形态针对性地压榨 QPS。

---

### 3. 生产实战：如何做到“学用结合”？
大模型部署切忌纸上谈兵，最有效的学习方式是**“将理论映射为启动参数，通过监控观察物理现象，带着痛点针对性调优”**。

#### 📌 步骤一：将硬核技术对号入座（启动参数映射）
在编写 vLLM 的 Shell 启动脚本时，直接将我们讨论的特性转化为具体的命令行参数：

```bash
# 实战：结合全链路加速特性的 vLLM 生产启动脚本示例
vllm serve /path/to/model \
  --tensor-parallel-size 2 \            # 【张量并行】单机内使用 2 张卡拆分矩阵，并发开工
  --max-model-len 8192 \               # 【最大模型长度】平衡大智商（上下文）与最大并发吞吐量
  --gpu-memory-utilization 0.90 \      # 【显存利用率】强行格式化并锁死 90% 显存供 PagedAttention 虚拟页池使用
  --enable-prefix-caching \            # 【前缀缓存】一键开启 RAG 和系统提示词的跨用户零拷贝复用，首字延迟归零
  --enable-chunked-prefill \          # 【分块预填充】长短文本混跑优化，消除大文本引起的线上蹦字卡顿
  --speculative-model /path/to/draft \ # 【投机采样】挂载同系列小模型极速盲猜，大模型单次并行批改，速度翻倍
  --block-size 16                      # 【分页机制】设置每个物理块容纳 16 Token，对齐底层硬件计算流
```

#### 📌 步骤二：利用监控工具验证物理现象
服务启动后，通过监控肉眼观测这些特性的物理表现，印证理论：
1.  **观察显存（使用 `nvidia-smi` 或 `npu-smi`）**：
    *   *物理现象*：在没有用户提问的空载状态下，显存直接被强行吃掉了 90%。
    *   *理论印证*：这是 `gpu-memory-utilization` 起作用了，vLLM 正在用 `PagedAttention` 把所有物理显存圈起来格式化为“动态虚拟页池”，确保在高并发大 Batch 进来时有充足的格子使用，防止动态申请引发 OOM。
2.  **观察标准输出日志（vLLM Engine Logs）**：
    *   *物理现象*：当拥有相同系统提示词（System Prompt）的用户并发提问时，日志中的 `Avg prompt throughput` 瞬间飙升到上万 tokens/s。
    *   *理论印证*：说明 `--enable-prefix-caching` 完美生效，系统直接在基数树（Radix Tree）上命中了缓存，免去了 GPU 重复进行 Prefill 计算的开销。

#### 📌 步骤三：带着生产痛点进行防御性调优
在真实业务演进中，根据暴露的瓶颈精准利用底层特性反哺业务：
*   **若面临高频变动的自定义模型且 CPU 驱动开销极高** ➔ 调整并开启昇腾环境下的 `Piecewise AclGraph（分段图）`。
*   **若进入极致压榨吞吐量的最终生产形态且 Stream 资源充裕** ➔ 开启编译成本极高但运行时性能拉满的 `Fullgraph AclGraph（全图）`。
*   **若遭遇 128k 超长文本集群崩溃** ➔ 放弃单机混跑，着手搭建 `Prefill-decode Disaggregation（预填充-解码解耦）` 物理隔离集群。
