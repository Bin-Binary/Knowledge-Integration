## 目标
通过该工程规范定义的工作流程控制AI生成产物(PRD、系统设计、数据库设计、代码...)的质量、可定位、可回退、可修复

## 核心原则
1. **严格串行**：上一步的产出物是下一步唯一的合法输入，禁止跨步执行或凭空产生结果
2. **状态驱动**: 用户输入 → MODULE_LIST_GENERATED → DEMO_CONFIRMED → REQUIREMENTS_CLARIFIED → PRD_GENERATED → DESIGN_APPROVED → CODE_REVIEWED → ACCEPTANCE_PASSED
3. **用户交互超时**：用户确认等待超过30分钟，流程自动暂停并保存当前状态；用户可随时恢复继续
4. **自检终止条件**：自检循环最多3轮；超过3轮仍未通过时，必须人工签署override声明（记录冲突项+接受风险）后方可继续

## 角色定义
从多角色视角进行议题(用户需求、业务规则、边界...等)发散，目的是进行设计时覆盖尽可能多的场景；"决策人"的职责是收敛当前议题，由[附录][议题收敛策略]决定; 每个角色都可以拥有决策人身份，但每个阶段只能有一个"决策人"(如明确指出需要多角色)；"决策人"由[决策人选举规则]决定。

### 角色注册表
内置角色(默认常驻)：架构师、产品经理、测试经理、评审专家
扩展方式：议题发起时，当前主调角色可声明引入临时角色
临时角色声明格式：
- 角色: {领域专家名}
- 视角骨架: {2-3个必检问题}
- 生命周期: 本议题结束后自动注销
示例：数据库设计议题 → 架构师引入"DBA"临时角色，视角骨架=[索引策略|分区策略|慢查询风险]

### 议题分级触发
按议题复杂度分级激活角色视角，避免简单议题过度发散、复杂议题发散不足：

**分级判定机制**：
- **判定输入**：用户原始需求描述 + AI预分析（AI基于需求描述快速识别涉及模块数、是否存在跨模块数据流、是否包含L3关键词）
- **判定执行者**：当前阶段主调角色
- **判定时机**：Step1.1执行时，AI先产出预分析结果（涉及模块数预估+关键特征识别），再对照下表判定等级
- **等级异议处理**：用户可在确认时调整等级，调整需记录理由

| 等级 | 触发条件 | 激活范围 | 收敛流程 | 典型示例 |
|------|---------|---------|---------|---------|
| L0-简单变更 | 影响模块数=1 且 无跨模块数据流变更 | 仅主调角色骨架维度 | 主调角色自行收敛，无需冲突识别 | 加字段、改文案、调参数 |
| L1-单域功能 | 影响模块数=1 且 涉及单模块行为重构（行为重构=修改现有功能逻辑而非新增独立功能） | 主调角色骨架维度全量 + 辅调角色仅关注点 | 五阶段收敛 | 新增功能模块、修改单模块行为 |
| L2-跨域设计 | 影响模块数>1 或 涉及多模块交互 | 四角色骨架维度全量 + 场景视角模板生成 | 五阶段收敛 + 可引入临时角色 | 导入重试机制、新增异步处理 |
| L3-架构级变更 | 含"重构/迁移/切换"关键词 或 影响数据存储层 | 四角色骨架维度 + 场景视角 + 临时角色 + 评审专家一票否决权 | 五阶段收敛 + 影响半径加成 + 争议升级预案 | MySQL→PG迁移、核心流程重构 |

**L0场景退化**：当议题被判定为L0时，自动退化为典型vibe coding流程（AI发散→人抉择→AI拆清单），仅补充主调角色骨架维度作为保底检查项。

### 阶段-角色配置
每个阶段所有角色在场，但主调角色(收敛决策人)不同、辅调角色聚焦点不同：

**需求澄清**:
- 主调: 产品经理(收敛决策人)
- 辅调关注点:
  - 架构师: "该需求是否隐含技术约束(如实时性、数据量级)？"
  - 测试经理: "该需求是否包含可测试的验收标准？"
  - 评审专家: "该需求与已有需求是否存在语义冲突？"
- 收敛标志: REQUIREMENTS_CLARIFIED

**系统设计**:
- 主调: 架构师(收敛决策人)
- 辅调关注点:
  - 产品经理: "设计方案是否覆盖了所有用户场景路径？"
  - 测试经理: "设计方案是否给出了可测试的状态定义？"
  - 评审专家: "设计中是否存在与已有模块的规则冲突？"
- 收敛标志: DESIGN_APPROVED

**代码生成**:
- 主调: 架构师(代码结构) + 测试经理(代码质量)
- 辅调关注点:
  - 产品经理: "实现是否偏离了需求意图？"
  - 评审专家: "代码是否引入了新的隐式耦合？"
- 收敛标志: CODE_REVIEWED

**验收确认**:
- 主调: 测试经理(收敛决策人)
- 辅调关注点:
  - 产品经理: "验收结果是否满足用户预期？"
  - 架构师: "是否有性能/稳定性隐患未在测试中暴露？"
  - 评审专家: "验收标准是否有遗漏项？"
- 收敛标志: ACCEPTANCE_PASSED

 多角色并行触发条件：议题同时涉及多个专业域时，由当前主调角色声明该议题为**跨域议题**，触发多角色并行评议——每个角色独立产出观点，再进入收敛流程。

**多角色并行评议规则**：
1. **评议时序**：各角色同时启动（并发），限时5分钟内产出观点；超时未产出的角色视为无补充观点
2. **评议方式**：盲评——各角色在产出观点时不可见其他角色的产出，避免观点趋同
3. **产出格式对齐**：每个角色的观点必须严格按观点矩阵格式产出（立场+依据+风险三要素），格式不符需重写
4. **合并规则**：
   - 收齐所有角色产出后，由主调角色执行冲突识别
   - 无冲突：直接生成候选方案
   - 有冲突：进入五阶段收敛流程（冲突识别→候选方案→人工抉择→可达性验证）
5. **轮次上限**：同一议题并行评议最多2轮；第2轮仅聚焦第1轮未解决的冲突项

## 核心工作流
严格按照以下步骤执行

### Step 1: 需求澄清
**目标**：根据用户的需求描述进行需求澄清、生成需求功能表
**输入**：用户需求描述
**执行**：按以下顺序执行

**1.生成模块清单**：
```
目标：多角色视角尽可能发散议题(用户需求)、根据用户选择的方案进行需求拆分
入参: {用户需求描述}

执行：
  1.1 议题分级判定：
      - AI预分析：基于用户需求描述识别涉及模块数预估、是否存在跨模块数据流、是否包含L3关键词
      - 展示预分析结果，按[议题分级触发]规则判定议题等级(L0/L1/L2/L3)
      - 用户可调整等级，调整需记录理由
  
  1.2 根据议题等级执行收敛：
      L0: 
        - AI按主调角色骨架维度直接生成模块清单初稿
        - 用户确认后进入步骤2
      L1+: 
        - 按[议题收敛策略]五阶段执行：观点收集→冲突识别→候选方案生成→人工抉择→可达性验证
        - 收敛完成后按选定方案拆分为模块清单

  1.3 自检：生成模块清单后，执行[模块清单自检]

期望输出: /references/模块清单.md
状态标志: MODULE_LIST_GENERATED
```

**2.进一步收敛需求**
```
目标：根据五要素进一步收敛需求，展示给用户并等待用户交互
入参: {模块清单.md}

执行：
  2.1 demo模块选取（选取规则见下文）
  
  2.2 对demo模块按五要素进一步收敛；五要素定义见[附录][五要素定义]
  
  2.3 用户确认：展示收敛后的demo模块
      - 用户确认 → 输出收敛demo
      - 用户提出调整 → 重新收敛该模块
      - 用户否决整个方向 → 回到步骤1.2重新选方案

期望输出: /references/模块清单_收敛demo.md
状态标志: DEMO_CONFIRMED

demo模块选取规则：
1. 优先选取复杂度最高的模块（覆盖最全，简单模块是其子集）
2. 若模块复杂度相当，优先选取包含跨模块交互的模块
3. demo确认后，后续模块按demo格式批量收敛，仅对差异点逐个交互确认
```

**3.生成完整模块需求表**
```
目标: 生成模块需求表
入参: {模块清单.md} + {模块清单_收敛demo.md}

执行：
  3.1 参照已确认的收敛demo格式，将模块清单中的所有模块按五要素进一步收敛
  
  3.2 自检：每个模块执行[模块五要素自检]，生成自检报告附录于产物

  3.3 自检不通过处理：
      - 标记不通过的模块及不通过项
      - 与用户交互修正
      - 修正后重新自检，直至全部通过
      - 自检循环最多3轮；超过3轮仍有不通过项，用户需签署override声明（记录冲突项+接受风险）后方可继续

期望输出: /references/模块需求表.md
状态标志: REQUIREMENTS_CLARIFIED
```

**输出**：REQUIREMENTS_CLARIFIED

### Step 2: 生成PRD(产品需求清单)
**目标**：根据模块需求表、生成业务、设计、开发、测试围绕展开的PRD
**输入**：{/references/模块需求表.md}

**执行**：
```
1.提取章节素材：将模块需求表中的信息按PRD章节映射
   - 项目概述：从用户需求描述+模块需求表摘要提取
   - 功能清单：从各模块的"角色+场景"提取
   - 业务规则：从各模块的"约束+输入校验"提取
   - 验收标准：从各模块的"输出+约束"转化为可执行验收点
   - 非功能性需求：需额外生成，由当前阶段架构师辅调角色补充（关注点：性能基线、安全边界、可观测性）

2.跨模块一致性校验：
  - 同一字段在不同模块中的规则是否一致
  - 模块间的数据流依赖是否完整
  - 删除操作的关联限制是否补充

3.自检：按[PRD自检清单]逐项检查，生成自检报告

4.人工确认：展示PRD，用户确认或提出修改
   - 用户确认 → 输出PRD
   - 用户提出修改 → 修改后重新自检→重新确认
   - 自检循环最多3轮；超过3轮仍有不通过项，用户需签署override声明后方可继续
```

**输出**：PRD_GENERATED
**产物**：/references/PRD.md

### Step 3: 系统设计
**目标**：确定系统骨架（分层+模块+扩展点），为后续数据设计/API设计/项目结构提供架构约束
**核心原则**：
- 设计先于实现：本阶段产出约束骨架，具体实现在Step 4填充
- 分层决策上→下约束：架构决策 → 数据决策 → 接口决策 → 项目结构，每层为下层提供约束
- 可回流修正：开发中发现新边界时先回流更新设计，再调整代码
**回流修正操作规范**：
| 触发场景 | 触发者 | 操作步骤 | 状态变更 |
|---------|-------|---------|---------|
| 发现设计遗漏 | 开发人员/架构师 | ① 识别遗漏项归属哪个独立产物 → ② 更新对应独立产物 → ③ 重新执行聚合 → ④ 记录到迭代纪要 | DESIGN_APPROVED → DESIGN_UPDATED |
| 发现规则冲突 | 测试人员/评审专家 | ① 记录冲突详情 → ② 收敛冲突（可能触发议题收敛流程） → ③ 更新受影响的独立产物 → ④ 重新聚合 | DESIGN_APPROVED → DESIGN_UPDATED |
| 技术栈调整 | 架构师 | ① 更新Architecture-Solution.md中的技术选型 → ② 检查是否影响下游产物 → ③ 如有影响则级联更新 → ④ 重新聚合 | DESIGN_APPROVED → DESIGN_UPDATED |
**回流修正强制约束**：
- 每次回流必须记录到`/references/设计迭代纪要.md`
- 更新独立产物后必须重新执行自检
- 回流超过3次需复盘：首次设计方案是否存在重大缺陷
**议题分级**：
  - L0：使用项目脚手架默认架构，跳过架构设计
  - L1：基于模板微调（如新增一个模块）
  - L2：完整执行（新系统/重大重构）
  - L3：完整执行 + 架构评审（引入外部评审专家）
**输入**：{/references/PRD.md}
**执行顺序声明**：以下5个子步骤**严格串行**执行，每个子步骤的输入依赖上一步的产出，不可跳步或并行：架构设计(Step3.1) → 数据库设计(Step3.2) → API设计(Step3.3) → 项目结构(Step3.4) → 聚合文档(Step3.5)
**执行**：按以下顺序执行

**1.生成架构设计**：
```
  目标：明确系统骨架；确定责任边界；确定模块间的调用关系
  核心原则: 目标驱动，避免设计盲区——引入角色视角的目的是覆盖设计盲区而非追求完整性
  输入：PRD
  执行：prompt驱动，以下为示例：
    背景&角色：已完成需求澄清、有一份xxx系统的PRD
    任务：基于以上信息输出完整的系统架构方案
    输出：
      1.明确分层架构(每层名称、职责、技术选型)
      2.说明模块划分及模块间的关系
      3.指出潜在扩展点(如后续加权限、日志等)
      4.划分安全边界(哪层负责鉴权、模块间是否需要内部鉴权)
    约束：
      - 不输出具体代码实现
      - 技术栈让用户确定：后端{}、前端{}（执行前由用户指定，作为prompt输入参数）
      - 输出需要加上角色视角（至少架构师+测试经理参与评审）
  输出: /references/Architecture-Solution.md
  验收标准：角色视角 + 自定义验收标准
  自定义验收标准：
    - 分层是否明确？每层的责任边界是否清晰？
    - 模块间是否解耦？是否有明确的调用关系？
    - 是否覆盖PRD中的所有功能模块？
    - 是否引入了PRD未提及的模块？（过度设计检查）
    - 是否预留扩展点？
    - 技术栈是否与项目约束一致？
    - 安全边界是否清晰？（鉴权层、内部鉴权需求是否明确）
    - 依赖不可用时是否存在降级路径？（骨架维度架构师#4映射）

```

**2.生成数据库设计**：
```
  目标：确定实体关系；字段定义；索引策略
  核心原则：数据模型服务于业务本质；结构独立于访问方式；为未来扩展留有余地
  输入：{/references/PRD.md} + 架构技术决策摘要（从Architecture-Solution.md提取：技术选型+模块关系+安全边界）
  执行：prompt驱动，以下为示例：
    背景：已有PRD+架构技术决策
    任务：输出完整的数据库设计方案
    输出：
      1.ER图（实体、关系、基数）
      2.字段清单（表名.字段名、类型、约束、默认值、备注）
      3.索引设计（索引名、字段组合、类型、适用场景）
      4.关联关系与外键规则(如 NO DELETE)
    约束：
      - 不输出DDL脚本
      - 字段命名遵循项目约定：{命名规范}
      - 敏感字段必须加密存储
      - 软删除字段统一为 is_deleted + deleted_at
  输出: /references/Database-Design.md
  验收标准：角色视角 + 自定义验收标准
  自定义验收标准：
    - ER图是否覆盖PRD所有业务实体？
    - 关系是否缺少或多余？（检查冗余关联、遗漏关联）
    - 索引是否覆盖高频查询场景？
    - 是否存在N+1查询隐患？（检查外键设计）
    - 字段类型是否匹配业务场景？（如金额用decimal而非float）
    - 主键、外键、唯一约束是否完整
    - 是否包含时间戳字段（creat_at/updated_at）

```

**3.生成API设计**：
```
  目标：确定接口清单；请求/响应结构；错误码体系；幂等设计
  核心原则：前后端解耦；接口稳定性优于实现灵活性；异常路径与正常路径同等重要
  输入：{/references/PRD.md} + {/references/Database-Design.md} + 架构技术决策摘要（从Architecture-Solution.md提取：技术选型+模块关系+安全边界）
  执行：prompt驱动，以下为示例：
```

#### 骨架维度
每个角色在任何场景下必须回答的问题，不做就不放行：

**架构师**:
| # | 必检问题 | 不覆盖的后果 |
|---|---------|------------|
| 1 | 该设计是否引入了隐式耦合？变更传播路径是否可控？ | 局部变更引发全局级联故障 |
| 2 | 写入路径是否存在部分成功/部分失败的窗口？ | 数据静默不一致，排查困难 |
| 3 | 新增同类需求时改动范围是否局限在单模块内？ | 每次新需求都是大改造，维护成本线性增长 |
| 4 | 依赖不可用时是否存在降级而非崩溃的路径？ | 下游抖动导致上游全链路雪崩 |

**产品经理**:
| # | 必检问题 | 不覆盖的后果 |
|---|---------|------------|
| 1 | 用户从意图到达成是否存在未设计的断点？ | 用户卡在某步无法继续，不知原因 |
| 2 | 非正常路径下用户是否能理解发生了什么并采取行动？ | 用户反复重试/投诉，无自助解决能力 |
| 3 | 运营是否能在用户投诉前发现数据异常？ | 口碑损失后才被动响应 |

**测试经理**:
| # | 必检问题 | 不覆盖的后果 |
|---|---------|------------|
| 1 | 合法输入、等价类、边界值是否完整？ | 边界场景线上爆雷 |
| 2 | 状态机是否有不可达/不可退的状态？ | 数据进入死锁态，只能人工介入 |
| 3 | 重试/并发是否导致数据漂移？ | 幂等失效，数据重复或丢失 |

**评审专家**:
| # | 必检问题 | 不覆盖的后果 |
|---|---------|------------|
| 1 | 本设计中的规则是否与其他已存在规则存在时钟/语义冲突？ | 交叉场景下行为不可预测 |
| 2 | 是否存在上下文中已有但本设计未继承的约束？ | 新设计与老规则矛盾，运行时异常 |

### 决策人选举规则

**规则1 — 议题域归属（首选）**：
议题的主要影响域决定主调角色为决策人：
- 影响用户行为/业务流程 → 产品经理
- 影响模块结构/数据流/技术约束 → 架构师
- 影响质量标准/测试范围 → 测试经理
- 影响已有设计的一致性/合规性 → 评审专家
- 多域冲突优先级: 数据流安全 > 合规 > 用户影响 > 其他

**规则2 — 阶段默认（兜底）**：
规则1无法判定时，取当前阶段的默认主调角色：
- 需求澄清 → 产品经理
- 系统设计 → 架构师
- 代码生成 → 架构师
- 验收确认 → 测试经理

**规则3 — 影响半径加成**：
当议题影响半径超出当前阶段或当前模块时，评审专家获得一票否决权。
触发条件：议题变更将影响≥2个其他模块，或议题变更将导致下游阶段设计调整。

**规则4 — 争议升级**：
两个角色对收敛方向存在不可调和分歧时：
1. 生成分歧摘要（各方观点 + 依据 + 风险）
2. 由评审专家做终裁（评审专家无立场偏向，适合仲裁）
3. 终裁必须附带风险声明（选A的风险是什么，选B的风险是什么）

### 议题收敛策略

**阶段1 — 观点收集**：
- 动作：各角色按视角清单独立产出观点
- 约束：每个观点必须包含 [立场] [依据] [不采纳的风险] 三要素
- 输出：观点矩阵

**阶段2 — 冲突识别**：
- 动作：按以下维度识别观点间冲突
  - 目标冲突：A要求性能，B要求一致性 → 本质取舍
  - 规则冲突：A的规则与B的规则在边界条件产生矛盾 → 需明确优先级
  - 范围冲突：A认为属于本议题，B认为不属于 → 需划定边界
- 输出：冲突清单（A观点 vs B观点, 冲突类型, 冲突根因）

**阶段3 — 候选方案生成**：
决策人职责：基于观点矩阵和冲突清单，生成**2-3个候选方案**供人类选择，方案需覆盖不同复杂度/权衡方向。

**候选方案强制格式**：
```markdown
## 方案{N}：{方案名称}（复杂度：低/中/高 | 预估新增模块数：{N} | 预估新增接口数：{N}）

**核心取舍**：
- 优先满足：______
- 牺牲/简化：______

**方案要点**：
1. ______
2. ______

**被舍弃视角的风险**：
| 视角来源 | 被忽略的问题 | 残余风险 | 缓解措施 |
|---------|------------|---------|---------|
| 架构师-2 | 写入窗口一致性 | P1：小概率数据不一致 | 增加对账任务兜底 |

**适用场景**：______
```
**方案差异要求**：
- 至少有一个**低复杂度方案**（快速实现、最小覆盖、后续可迭代）
- 至少有一个**高完整度方案**（覆盖所有视角、代价较高）
- 可选一个**折中方案**
- 方案间差异必须体现在取舍不同，而非实现细节不同

**阶段4 — 人工抉择**：
- 人类阅读候选方案后做出最终选择
- 选择方式：直接指定方案编号，或提出调整要求
- 若提出调整要求：回到阶段3，基于调整要求重新生成候选方案

**阶段5 — 可达性验证**：
对选定方案进行验证：
- 骨架维度再检：收敛是否导致任何骨架维度被牺牲？
- 依赖链验证：收敛结论是否在上下游模块间可传递？
- 退化验证：收敛结论在任何依赖不可用时是否有退化路径？
不通过则回到阶段3重新生成候选方案。

**收敛完成标志**：人工已选择 + 可达性验证通过 + 残余风险均已记录

**纪要保留策略**：
按议题等级分级保留，避免过度膨胀同时保障关键决策可追溯：

| 议题等级 | 保留范围 | 保留内容 |
|---------|---------|---------|
| L0 | 不保留 | 无收敛流程，无纪要 |
| L1 | 仅决策摘要 | 最终选择方案 + 核心理由 + 被舍弃视角的残余风险声明 |
| L2 | 精简纪要 | 各角色核心立场(1-2句/角色) + 冲突清单 + 最终决策详情 + 残余风险声明 |
| L3 | 完整纪要 | 观点矩阵全量 + 冲突清单全量 + 候选方案全量 + 最终决策详情(含风险声明) |

**必须保留的核心要素（L1及以上）**：
1. 最终选择了哪个方案
2. 核心取舍理由（为什么选A不选B）
3. 被舍弃视角的残余风险声明（已接受的P0/P1风险）

**可裁剪的非核心要素**：
- 观点矩阵：保留立场+依据，裁剪论述过程
- 冲突识别：保留冲突清单结果，裁剪推理过程
- 候选方案：保留选定方案完整描述，其他方案仅保留要点

**纪要存放**：/references/议题纪要_{阶段简称}_{模块名}_{YYYYMMDD}.md，按产物-阶段映射表随阶段产物归档
  - 阶段简称规则：需求澄清=RC, PRD生成=PRD, 系统设计=SD, 代码生成=CG, 验收确认=AC
  - 示例：/references/议题纪要_RC_用户认证_20260623.md

### 五要素定义

五要素（收敛维度 + 自检维度合一）：

| 要素 | 定义 | 量化标准 |
|-----|------|---------|
| 角色 | 谁在用 | 具体角色名（非泛指"用户"），≥1个 |
| 场景 | 什么时候触发 | 前置条件 + 触发动作，缺一不可 |
| 输入 | 接收什么 | 每个输入字段含校验规则（即使"无限制"也需显式声明） |
| 输出 | 返回什么 | 正常路径 + ≥1条异常路径 + 边界场景（数字/日期类必填） |
| 约束 | 遵循什么业务规则 | 可量化，禁含"适当/合理/看情况"等不可测词汇 |

### 质量保障分层模型

**第一层（发散时）**：角色骨架维度 + 场景视角 → 确保设计时不遗漏关键维度
**第二层（产出后）**：产物自检清单 → 确保产物形态符合规范且有可量化完成标准

**两者关系**：
- 骨架维度检查"设计是否覆盖了该考虑的维度"（发散完整性）
- 自检清单检查"产物是否符合形态规范"（产出规范性）
- 关系：互补而非替代，自检清单不重复骨架维度的检查项
