# 从模型设计到复盘

在[垂直领域 Agent 门禁配置模型设计](./gate_event.md)落地过程中，总结出以下经验。

## 认知起点：四层皆是知识表示，不是能力

entity/config-unit/physical-file与frame_net都是"知识表示"，但表达两种不同性质的知识：

- 层1-3：陈述性知识（静态"是什么"），用formal/constitutive/telic/agentive 四性结构描述领域事实，靠跨层链接表达关系，通过作为frame的FE填充项与"意图"建立关系。
- frame_net：意向性/事件知识（"发生了什么、为什么"），用frame语义（agent/action/purpose/means/result/manner）把动作结构化为可检索的记录。

四层共同点：只描述世界，无一层执行。entity/config-unit回答"有什么"，physical-file 回答"最终在哪"，frame_net回答"谁因何意图把它们落地"。它们都是知识的载体，不是能力的载体。

## 描述与执行分离，Frame是知识系统的边界

原策略层（路径模板/组织偏好/渲染器/补丁生成器）是执行能力而不是知识，需拆分：路径规则与组织偏好是知识，可回填进 schema；渲染器和补丁生成器才是真正的执行。

边界划定：表示层负责"意图流出"（可观测、可审计的意图 + 领域事实），执行层负责"结果流回"。执行层 = 父图（编排器）+ 子图集合：子图内的执行单元是确定性纯函数（输入意图帧+事实 → 输出文件操作 → 回写结果帧）；父图负责编排（选子图、管依赖、兜底），可替换、可测试、可审计。

## Frame的双时态——intent态与record 态

同一件事（如"为新版本C50搭门禁"）有两个时间点，由result这一FE的状态区分：

| 时态 | 含义 | result 状态 |
|---|---|---|
| intent 态（执行前） | 生成事件计划，尚未执行 | 空 |
| record 态（执行后） | 文件已生成，事件已发生 | 已填充 |

因此**不需要独立的"意图实体"**：intent态下patient（版本实体）关联的代码仓列表已承载操作范围（对哪些仓操作），means承载"用什么配置单元构成"，result为空即intent、填充即record——同一frame、同一schema，状态由FE填充度而非新增字段区分。

反之若设计成result必填，想记录"打算做 X"（intent）会被拒绝，只能伪造占位或拖延补帧，意图知识永远进不了系统，导致：失败无法回滚、审计丢失"计划 vs 结果"偏差、跨版本传承只剩结果态。

## Frame不只是边界，更是事件快照

认知跃迁：frame不只是领域内的知识表示，也是当次执行的实例快照。流程为：用户输入 → 意图识别 → 依frame_schema生成部分填充的快照实例（agent/action/patient/purpose/means 已填、result 待定）→ 执行层执行 → 回写result -> 生成快照。

形态：[快照1、快照2、快照3、...]

快照的使用方式：
- 校验：快照中的result与版本实体数据对比，不通过则进入下一轮执行（新一轮 = 新快照实例）；
- 结束：达到最大重试次数或校验通过，指定末端快照为最终frame实例（快照不可变，不做原位修改，故"指定"而非"转换"）；
- 回滚：经 prev_round 链回退到快照序列中的任意一个记录。

价值：数据与计算分离在此闭环——frame快照是数据（记录"做了什么、因何而做"），执行层是计算（纯函数），快照序列是可重放、可审计、可回滚的事实链路。

## 升级四：快照的归档与角色

快照是 frame 实例，不是实体：有 id、可寻址、可被实体的 agentive 引用（实体形态），但只追加、无生命周期（实体实质）。判据：实体可被修改，快照只产生新快照。故归档于 frame_net 而非 entity。

物理树（类型与实例分离，树即链）：

```
frame_net/
├── *_schema.json            # 类型：帧长什么样
└── records/
    ├── <frame_instance_id>/ # 实例：一个意图 = 一个目录
    │   ├── 01_intent.json   #   第1轮：意图固化（result 空）
    │   ├── 02_failed.json   #   第2轮：执行终止-失败
    │   └── 03_recorded.json #   第3轮：校验通过-record态
    └── _index.json          # 按产品/版本/时间的检索索引
```

实例文件除FE外带：round（轮次）、phase（intent/recorded/failed/review/degraded）、prev_round（回滚指针）、created_at。缃记承载于独立信封 schema（`records/_snapshot_envelope_schema.json`），FE语义整体委托给 frame_id 指向的 frame schema——信封与帧语义分离。

并非每次状态变化都归档，只在语义节点实体化：
- 意图固化：intent态第1个快照（计划诞生）；
- 执行终止：校验通过=recorded，或失败终止=failed；
- 人工干预：review态顶层评审闸（人工放行后继续）；
- 降级：degraded态（更换子图或需过，链不中断）。

中间计算态（渲染中间产物、diff中间结果）是执行层临时状态而非知识，不归档。

同一实例三重角色，不拆对象：
| 角色 | 形态 | 功能 |
|---|---|---|
| 意图源 | intent态（result空） | 执行层的输入契约 |
| 事实汇 | record态（result已回填） | 回流，供result vs 版本实体校验 |
| 审计档 | 快照链即整体 | 回滚、重放、"计划 vs 结果"偏差证据 |

价值：帧类型与实例分离、事件目录即历史链、变更只增不改，回滚以 prev_round 寻址；快照归frame_net内，不跨越知识边界。

## 升级五：编排模型——父图（Supervisor）选子图 + 子图内（Plan-and-Execute）计划-执行-校验

针对意图多样性、子图依赖复杂、执行须可靠三大目标，执行层定形为两层正交编排：

| 层 | 模式 | 职责 |
|---|---|---|
| 父图 | supervisor | 按意图识别结果选择调用哪个子图（handoff 回传即控制依赖）、管理子图间的数据依赖与前序输出传递、顶层做人工介入闸与降级兜底 |
| 子图 | plan-and-execute | LU→frame 唤起→Planner 生成部分填充 intent 快照→执行→result 校验→replan 循环（重试/回滚靠快照链 prev_round） |

- 控制依赖（条件满足才执行某些子图）落在父图的条件边 + frame.condition；数据依赖（前序输出作后续输入）落在父图的输出输配 + frame 的 patient/source/required_deps 引用。父图必须显式声明两类依赖，禁止隐式耦合。
- 降级 = 满足约束不变时更换子图或跳过（记录为 degraded 态快照，链不中断）；人工介入 = 顶层评审闸，产生 review 态快照后再放行。二者都不是"静默失败"：每个终止节点都留有快照，可重放、可审计、可回滚。
- frame=事件快照不变：子图是计算，快照是数据，父图是计算的组织者；“数据与计算分离”纹丝不动。

## 小结

- 四层 = 知识表示（陈述性 + 意向性），不是能力。
- 知识与能力分离：表示层出意图，执行层回流结果。
- 意图/记录由 result 的填充度区分，无需意图实体。
- frame = 事件快照：校验、重试、回滚都建立在快照链上。
- 快照 = frame 实例（非实体），类型与实例分离归档，树即链，只增不改。
- 编排 = 父图（supervisor）选子图 + 子图内（plan-and-execute）计划-执行-校验；依赖显式声明于 condition/required_deps，降级与人工介入以 degraded/review 态快照归档，杜绝静默失败。
