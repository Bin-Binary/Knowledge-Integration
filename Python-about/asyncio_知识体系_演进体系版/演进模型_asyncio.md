# asyncio 演进模型

## 元信息
- 业务目标(G): 在单线程内实现I/O并发等待，且提供结构化的结果获取和简洁的编程模型
- 0号约束集: {A1(时序), A2(时序+结构), A3(边界), A4(边界)}

## 演进图谱

### 节点 N0: 核心冲突 (时序维度碰撞)
- **张力构成**: G(时序:需要I/O并发重叠等待) + A1(时序:CPU与I/O速度鸿沟，串行等待必致CPU空转)
- **冲突表现**: 串行执行流遇到慢I/O时停滞，时间轴上的并发断裂——CPU在等待I/O期间空转，无法利用这段时间执行其他就绪任务
- **设计选择(D1)**: EventLoop接管控制权——引入事件循环，主动轮询I/O就绪事件，在时间轴上实现"遇到I/O就跳过，转而执行其他就绪任务"
- **副作用传导**: D1解决了时序上的空转问题，但要求任务主动让出控制权 → 触发N1(结构维度断裂)

### 节点 N1: 协作式调度 (时序突破 → 结构缺失)
- **张力构成**: D1(时序:EventLoop需要任务主动让出) + A2(结构:函数调用栈连续压栈不可中断)
- **冲突表现**: EventLoop能监听I/O就绪事件，但调度的"任务"仍是传统函数，函数一旦开始执行就占满调用栈直到返回，无法在I/O等待点暂停
- **设计选择(D2)**: 协程(yield/await切断栈帧) + Task(保存断点状态并将协程包装为可调度单元)
- **必然性推导**: 只有打破传统函数的连续栈帧结构，才能在I/O等待点切出执行流，交还控制权给EventLoop
- **副作用传导**: 协程切断了结构，挂起了执行，但脱离了当前执行流，缺乏感知外部I/O事件何时完成的边界接口 → 触发N2(边界维度缺失)
- **▶ 挂载执行实体**:
    - [Task](./执行实体/实体_asyncio.md) (主导维度: 结构★★★, 时序★★★)
    - [Handle+TimerHandle](./执行实体/实体_asyncio.md) (主导维度: 时序★★★)

### 节点 N2: Future状态机 (边界与实体突破 → 边界更深缺失)
- **张力构成**: D2(结构:协程已切断，需要信号告知何时恢复) + A4(边界:应用无法感知内核I/O事件何时完成)
- **冲突表现**: 协程await一个I/O操作后挂起，但需要一个"未来的结果"作为锚点，以及跨边界唤醒通道
- **设计选择(D3)**: Future(实体:状态容器PENDING→FINISHED) + 回调(边界:跨任务唤醒接口)——协程await Future后将Task.__wakeup注册为回调，Future完成时通过set_result() → __schedule_callbacks() → loop.call_soon(Task.__wakeup) → Task.__step()恢复协程
- **必然性推导**: 需要一个实体在协程挂起期间锚定结果(PENDING→FINISHED)，并通过回调跨越任务边界实现唤醒
- **副作用传导**: Future只是用户态容器，不知道内核何时产生数据，与内核I/O事件之间存在边界鸿沟 → 触发N3(边界维度更深缺失)
- **▶ 挂载执行实体**:
    - [Future](./执行实体/实体_asyncio.md) (主导维度: 实体★★★, 边界★★★)

### 节点 N3: Protocol-Transport层 (边界闭合 → 时序补充需求)
- **张力构成**: D3(边界:Future需要外部触发set_result()) + A4(边界:内核I/O事件→用户态的通道) + C_Arch_5(时序:OS提供select/epoll/IOCP可监听多I/O)
- **冲突表现**: 需要组件下探到内核I/O边界，将selector/IOCP通知转化为Future.set_result()调用
- **设计选择(D4)**: Transport封装底层非阻塞I/O(边界下探)，Protocol处理业务逻辑(边界上交)——Transport._read_ready()读取数据 → Protocol.data_received() → 业务处理 → Future.set_result()
- **必然性推导**: 只有Transport下探内核边界读取数据，通过Protocol向上递交，才能完成从内核I/O事件到用户态Future状态的完整链路
- **副作用传导**: I/O边界桥接完成，但多协程并发访问共享资源需要时序协调机制 → 触发N4(时序维度补充)
- **▶ 挂载执行实体**:
    - [Protocol+Transport](./执行实体/实体_asyncio.md) (主导维度: 边界★★★)
    - [Selector+Proactor](./执行实体/实体_asyncio.md) (主导维度: 边界★★★)
    - [StreamReader+StreamWriter](./执行实体/实体_asyncio.md) (主导维度: 边界★★★)
    - [SSLProtocol](./执行实体/实体_asyncio.md) (主导维度: 边界★★★)

### 节点 N4: 同步原语 (时序补充 → 结构补充需求)
- **张力构成**: D4(业务:多协程需要协调访问顺序) + 单线程无抢占(需要主动等待点)
- **冲突表现**: 协程间的"同步"本质是时序协调——一个协程需要等待另一个协程完成操作后才能继续，缺乏标准语义
- **设计选择(D5)**: 基于Future的同步原语族(Lock/Event/Condition/Semaphore/Barrier/Queue)——将线程同步语义适配到单线程协程世界
- **必然性推导**: 协程切换是协作式的，需要显式等待点; Future作为等待器可以精确实现让出-唤醒时序
- **副作用传导**: 同步原语解决了时序协调，但复杂并发场景缺乏结构化管理(裸create_task的Task散养) → 触发N5(结构维度补充)
- **▶ 挂载执行实体**:
    - [同步原语族](./执行实体/实体_asyncio.md) (主导维度: 时序★★★)
    - [Queue](./执行实体/实体_asyncio.md) (主导维度: 时序★★★)

### 节点 N5: 结构化并发与超时 (结构补充 → 闭环)
- **张力构成**: D5(时序:多Task需要结构管理) + C_Biz_2(结果正确获取) + C_Biz_3(编程模型简洁)
- **冲突表现**: 裸create_task()无作用域约束; 超时需将时间限制转化为协程可感知的取消; 异常需跨Task传播
- **设计选择(D6)**: TaskGroup(结构化并发) + Timeout(超时→异常转化) + Runner(生命周期管理)
- **必然性推导**: 只有结构化约束(async with作用域)才能保证Task在退出时全部完成; 只有TimerHandle→Task.cancel→uncancel链路才能将时间边界转化为编程边界
- **副作用传导**: 无!闭环完成。
- **▶ 挂载执行实体**:
    - [TaskGroup](./执行实体/实体_asyncio.md) (主导维度: 结构★★★)
    - [Timeout](./执行实体/实体_asyncio.md) (主导维度: 边界★★★)
    - [Runner+asyncio.run()](./执行实体/实体_asyncio.md) (主导维度: 结构★★★)

## 闭环验证

### S1: 目标达成验证
目标G: 在单线程内实现I/O并发等待+结构化结果获取+简洁编程模型
- 时序: EventLoop+协程实现了I/O并发重叠 ✓
- 结构: 协程+Task实现了栈帧切断与恢复 ✓
- 边界: Transport+Protocol桥接了内核/用户态 ✓
- 实体: Future状态机锚定了结果 ✓
- 编程模型: async/await + TaskGroup提供了简洁的同步式编写 ✓

### S2: 约束守恒验证
- A1(时序): EventLoop重叠等待解决了CPU空转 ✓ 未破坏
- A2(结构): 协程yield切断栈帧，但栈帧仍存在于coroutine对象中 ✓ 未破坏
- A3(边界): 未引入多线程，避免GIL问题 ✓ 未破坏
- A4(边界): 通过selector/IOCP+Transport+Protocol桥接内核边界 ✓ 未破坏
