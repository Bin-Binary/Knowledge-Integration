# Asyncio，并发困境下的野望 

## 并发的困境真相，与Asyncio的抉择

程序要运行离不开CPU的计算操作, 那它用于的计算数据哪来？ 靠I/O来搬运数据，两者紧密合作成就了计算机领域的百花齐放。
但是，CPU与I/O在执行速度上存在着超级夸张的鸿沟，有多夸张？ CPU一级缓存访问约1纳秒，磁盘I/O约10毫秒，网络I/O可达百毫秒甚至秒级——纳秒 vs 毫秒~秒，约10^6倍速度差
下面通过一个演示动画来感受一下慢IO： 

(./问题演示_GIF/N0_timing_conflict.gif)

演示中的工作方式，即step-by-step,严格按顺序执行的方式，就是同步执行。而同步执行遇到慢I/O时, CPU在等待I/O期间算力浪费，无法利用这段时间执行其他任务。这种现象就是"并发的困境"

"CPU极快，I/O极慢"这个物理事实导致的并发问题，是所有想实现高并发方案都得面对的共同困境。这不单单是Python的问题, nginx、Node.js、Go scheduler都在自己的具体场景下给出了答卷。

Python实现高并发是演进式的，Asyncio之前是多线程方案。但是由于其本身架构约束叠加物理约束，就衍生出了以下具体场景：
1. 语言架构带来的窘境：多线程受GIL限制(8MB栈/线程、上下文切换开销、竞态条件)
2. C10K问题的本质：不是连接数大，而是10K个连接中大多数的时间在等I/O, 物理约束还在发力。
这里不展开，感兴趣可移步[附录](#多线程的弊端简述)。

为了实现高并发，同时为规避多线程的弊端(调度权需要从内核态转移给用户态)。Asyncio采用了异步模型，一句话概括核心思想: "在单线程内重叠I/O等待——遇到I/O就跳过，去执行其他就绪任务"。
当任务A发起I/O操作并等待结果时，让它先去执行任务B。等任务A的I/O完成了，再让控制流回来继续执行任务 A 剩下的部分。在时间轴上这样安排: 任务A的I/O等待时间就被任务B的计算“填充”。这样的工作方式就是异步。

## 非阻塞模型与多路复用，异步的前提条件
知易行难，想要实现从同步到异步的范式转变有两个前提条件：
1. I/O模型转换: 阻塞I/O → 非阻塞I/O
2. 就绪检测: 单一等待 → I/O多路复用

[全文重点1]，为什么是必须要有这两个前提条件？一句话概况：非阻塞"守权"，多路复用"提效"。

在阻塞模型下，如果遇到阻塞式系统调用，线程会被挂起，然后等待I/O完成，直到阻塞结束才能重新排队获取。阻塞的本质是当前线程向操作系统交出了CPU控制权, 简单概述就是"冻结",具体表现为当前对象(线程 进程)在等待某个操作(网络I/O、磁盘I/O、用户输入)期间，自身无法进行操作。而失去控制权意味着当前线程的代码执行彻底停滞。阻塞模型连'跳过I/O去执行其他任务'的资格都没有。
[阻塞演示](./问题演示_GIF/阻塞模型演示.png)

图中代码演示了一个极端场景，连接了一个不存在的端口。在I/O(这里是网络响应)没有返回时，一定执行不了后面的“简单计算”部分。直到超时，线程还处于挂起状态。所以，如果是阻塞模型, 无法实现从同步到异步。

聪明的朋友可能会说了：不让当前线程被挂起不就行了。是的，这就是非阻塞模型。**非阻塞的核心作用就是"守权",守住CPU控制权**。要想实现非阻塞也有个前提条件: OS需要支持非阻塞模式。好消息是它支持 --> 'O_NONBLOCK'。I/O操作不阻塞线程，立即返回EAGAIN。

## EventLoop

I/O状态的变化(阻塞->就绪)被多路复用封装为'就绪事件', 这其实是属于事件机制中,机制的一部分。那什么是[事件机制]呢? [事件]指的是系统中发生的某个动作或状态变化，例如：用户点击按钮、网络请求到达、定时器到期、文件读写完成等。[机制]的意思是一套管理和响应这些事件的框架或处理流程，一个完整的生命周期通常包括以下步骤：事件注册监听(哪些事件是需要关注的，比如本文的I/O就绪事件) --> 事件触发(事件到来了，通知可以处理了) --> 事件处理(具体的业务逻辑，通常通过[回调]处理)。
[回调]
```
维基百科(wiki)：
原文："In computer programming, a callack is any executable code that is passed as an argument to other code, which is expected to call back (execute) the argument at a given time."
翻译：回调是一段可执行的代码，通过参数传递给别一段代码，以期望在一个合适的时间调用这个参数（可执行的代码）。
白话：完整的短句，"妈，我是BIN, 我又饿又困。我睡先，等饭做好通知我，我要干三大碗"。回调就是BIN的妈妈在饭做好后通知BIN，BIN收到通知后，执行"我要干三大碗"
在异步的语境下，回调的本质是为了对抗非阻塞带来的'执行错位(谁，接下来要执行什么操作)'，为了在前置条件就绪后预留下的'执行占位符'。因为没有它，未来的I/O结果到达时，就如同快递送到了无主之地"
```

Asyncio的[事件机制]需要在用户态和内核态之间相互切换：当单线程遇到I/O操作时，封装回调(生成一个`Handle(callback, args)`)接着注册映射(在EventLoop内部的字典 `_fd_to_handle`中建立fd到Handle的映射) -- `selector.select()` 交出控制权给操作系统内核等待 I/O 事件 (会阻塞)--> 操作系统监听I/O状态变化 --通知就绪，内核态切换到用户态 --> 回调处理。

这是一个预期(非阻塞,遇到I/O事件先跳过)和工作流程(遇到I/O事件先阻塞)很矛盾和很反直觉的现象：我们费尽心思用非阻塞保住了控制权，转头却在`selector.select()`里把线程阻塞了。这不是又回到同步阻塞的老路了吗？[事件机制]的好处是什么呢?

首先我们要严格区分"什么被阻塞了"和"为什么被阻塞"。这就涉及到了网络I/O本质的"两步走"。一次完整的网络读取在物理上被拆分为两个完全不同的阶段：
1.等待阶段（等数据就绪）：网卡接收数据，内核把数据写入Socket的接收缓冲区。
2.操作阶段（搬数据）：调用recv()，把数据从内核缓冲区拷贝到用户态内存。
我们说的"阻塞"和"非阻塞"，到底是在阻塞哪个阶段？

我们从三个维度看：
维度一：单点等待 vs. 多路复用（被绑架 vs. 开盲盒）
同步阻塞：调用`sock_A.recv()`（recv()是网络编程中用于接收数据的系统调用函数），线程被挂起(阻塞调用会将线程从CPU调度中移除，直到数据到达)、必须按顺序处理IO事件，无法检查或处理其他IO事件。此时线程和sock_A死死绑定。如果A的数据10个小时后才来，线程就挂起10个小时。哪怕sock_B、sock_C的数据早就准备好了，这叫被单点绑架。
多路复用：调用 `select()`(系统调用，允许单个线程同时监控多个文件描述符的状态。)，线程挂起。但此时，线程是在同时等待10000个socket。只要这10000个里有任何一个数据准备好了，内核就会立刻唤醒你，此时的`recv()`是非阻塞的，可以处理已经就绪的数据。这叫开盲盒，谁先来处理谁，绝不死等某一个。
核心区别：同步阻塞下的`recv()`调用在两个阶段都被阻塞，无法操作其他IO事件，。多路复用是撒下一张网，网上任何一处震动都能破局，因为只有在等待期间阻塞，而操作阶段的`recv()`是非阻塞的，可以处理已经就绪的数据。

维度二：被迫交出 vs. 主动让出（被动 vs. 主动）
同步阻塞（被迫交出）：在同步代码里，在执行业务逻辑的中途，被操作系统强行夺走控制权，上下文直接断绝。
多路复用（主动让出）：在EventLoop里，是把所有就绪的回调都处理完了，事件就绪队列空了，发现当前无事可做，才主动调用`select()` 进入休眠。
休眠前给操作系统定了规矩：如果有I/O来了就唤醒（事件触发），或者到了 0.5 秒无论如何都唤醒（定时器触发）。
如果timeout=0，`select()` 甚至连觉都不睡，立刻返回，这就是非阻塞轮询的微操。
核心区别：前者是失控，后者是调度。

维度三：CPU视角的零浪费
我们回到最初的目标：解决CPU浪费。
非阻塞轮询：线程不交出CPU控制权，CPU满载跑 while True，发热巨大但没干正事。
多路复用的阻塞：线程阻塞，CPU被彻底释放去执行别的进程了。当网卡中断传来，内核唤醒线程，CPU才开始执行回调。此时CPU执行的每一行代码，都是在处理确实已经就绪的数据，没有任何浪费。
核心区别：多路复用的阻塞，是对CPU资源的尊重——没有活儿的时候，绝不占用CPU哪怕一个周期。这就是为上面"为什么被阻塞"的原因

要厘清上面几个问题，核心就在于理解[I/O事件的时间不确定性]这个物理事实，以及不同阶段阻塞会带来什么影响。等待期间的阻塞（通过多路复用）是可以被接受的，我们真正希望的是操作期间的非阻塞。等待时主动休眠，操作时绝不阻塞——两者结合，才真正实现了单线程内重叠I/O等待的高并发。

"纸上学来终归浅，当知此事须躬行"，Asyncio的事件机制具体怎么落地呢? 我们从结构、时序、实体、边界四个维度展开，其中时序和边界是主维度，我们重点关心、其余为辅助维度，简单理解即可。
### 结构
这个维度主要描调度容器长什么样，核心问题为：需要考虑哪些约束？ 容器如何设计？ 这里我们将事件源简单归为两类, I/O事件、定时器事件。两类事件各自携带一个关键属性，而属性的差异直接决定了容器的形态。
I/O事件到达时间不可预知, 这是I/O事件的物理特性，意味着数据到达就是就绪态，排队等着被执行; 而定时器事件的到达时间预先指定，没到指定时间就是等待态, 需要按时间排序等待。由此我们可以得出以下两条约束：
约束一：排序规则互斥
I/O就绪事件遵循FIFO——谁先就绪谁先执行，只关心先后顺序；定时器事件按时间戳排序——1秒后到期的事件必须排在5秒后的前面。一条队列无法同时满足两种排序规则。

约束二：状态隔离
I/O事件只有一种状态：就绪，直接入队即可。定时器事件有两种状态：等待和就绪。等待时它不能被执行，必须等到指定时间；到期后它和I/O事件没有区别，都是"现在该执行了"。

但是如果发生这样的场景: 其中一个容器中先出现就绪事件, 并且期间源源不断有就绪事件到来，另一个容器中的事件不断累积不能被消费。饥饿问题出现。所以我们还必须引入第三条约束：
约束三：防止饥饿
设计一个就绪回调队列，只调度就绪队列的回调。两个事件源的就绪事件统一入队，新到的就绪事件先到各种事件源的容器等待，等待下一轮进入就绪队列

这三条约束共同导致事件循环必须采用分容器 + 就绪回调队列的设计。
[eventloop结构]
简单拓扑：
- `_ready: deque[Handle]` — 就绪回调队列，FIFO 顺序消费
- `_scheduled: list[TimerHandle]` — 定时回调堆，按 `_when` 排序
- `_selector: selectors.BaseSelector` — I/O 多路复用器，注册文件描述符到回调的映射

### 时序
这个维度主要描述控制流程，核心问题为：公平调度
“批次边界” --> ，将“执行已就绪任务”和“收集新的就绪事件”分成了两个清晰的步骤，通过“快照”长度来隔离。这种设计还简化了逻辑，不需要复杂的递归或中断处理。它利用了事件循环本身的循环结构来自然地处理并发执行流。

**理解问题比闷头看别人的设计更有价值**，开始这节前，补充一个前置知识。`_ready`就绪队列有[重入]的特性，消费即生产。回调本身如果产生新回调，会立即将新回调加入就绪队列。举个一个最简单的例子，比如有个TCP Echo服务器(从客户端读取数据后立马返回)，事件正处于 `_run_once`(简单理解为一个执行即可)：
1. 消费阶段开始：_ready队列里当前只有一个回调，它是一个读取客户端数据的读回调:sock_read_callback。
2. 执行消费：取出并执行这个sock_read_callback。
3. 生产发生：sock_read_callback内部逻辑可能是这样：
step1：从socket读到了数据。--> step2：想立刻把同样的数据写回给客户端。
但由于socket的写缓冲区可能满了，它不能直接写，而是会调用 `loop.call_soon(sock_write_cb, data)`（回调注册函数）将一个"sock_write_callback"注册到事件。
4. 生产的结果：`call_soon()` 的内部实现，正是把sock_write_callback直接追加到_ready队列的末尾。

于是, 就在消费 `_ready` 队列的过程中, 新的待消费项(sock_write_callback)又被生产回了同一个`_ready` 队列。
想象一种极端情况，消费同时源源不断的生产，就出现了"无限消费"的现象。永远回不到`select()`，I/O检查饿死(永远不会执行)。

既然会饿死I/O检查，为什么还要这样设计？
答案是：**效率与止损**。效率: 为了满足上层应用对操作顺序和低延迟的预期。止损: 避免更严重的"回调饥饿"。这是单线程协作式调度非常反直觉也是最精妙的设计。下面分别展开解释：

效率: 在上面的例子中，服务器接收并立刻回复，这在逻辑上是“处理一个请求”的原子操作。如果sock_write_callback不被放入`_ready ` 队列立即执行，而是被放入另一个"低优先级"队列，或者等到下一轮事件才执行，那么这次"请求-响应"的生命周期就被强行延后了。这会打破上层应用预期。将新回调重入`_ready` 队列，保证了在同一次事件迭代中，逻辑上连续的操作可以尽可能连续执行。

止损: 消费读回调同时产生写回调，姑且粗暴的归为"嵌套回调"一列。设想一下，如果`call_soon()` 添加的回调必须等到下一次`_run_once()` 才能执行。那么：
1. 当前 `_ready` 队列只有sock_read_callback。
2. 执行完它之后，`_ready` 队列就空了。
本轮 `_run_once()` 会因为"无事可做"而退出处理回调阶段，进入`select()` 等待 I/O 事件。此时，sock_write_callback虽然早已就绪，但必须强制等待，直到`select()` 可能因为超时返回，或者被新 I/O 事件唤醒。
这等于让一个完全可以立即执行的、CPU密集度极低的任务，去等待相对慢得多的I/O。这本身就是一种调度上的巨大不公平，会造成响应延迟的急剧增加。

ready有任务时阻塞=回调饿死，不阻塞=CPU空转[边界条件]怎么理解：
场景分析：
1. _ready 队列中有就绪任务
2. select() 调用时设置 timeout
两种策略的矛盾：
策略A：_ready非空时仍然阻塞
- 如果 _ready 里已经有任务，但 select() 仍然 block 等待新事件
- 那么已经就绪的任务（回调）得不到执行 → "回调饿死"
- 因为 select 阻塞等待新事件，而不去处理已有的就绪任务
策略B：_ready非空时不阻塞（timeout=0）
- 如果 _ready 里已经有任务，select() 立即返回（timeout=0）
- 表面看没问题，但问题是：即使 timeout=0，select() 系统调用仍然需要 用户态→内核态→用户态 的切换
- 如果没有新事件，这就是纯粹的空转开销
- 高频调用 → CPU空转
这是一个经典的"两难"问题：
- 阻塞→有可能饿死已就绪的回调
- 不阻塞→CPU在内核态切换上空转
timeout 的三种策略：
- _ready 非空时设为 0：立即返回处理现有任务
- 依据堆顶定时器设差值：平衡等待与及时性
- 都为空时设无限：彻底阻塞等待新事件

## 是解药也是毒药，异步的代价

怎么在线程内实现"遇到I/O就跳过"? 这里有个架构约束：Python调用栈机制不允许frame(栈帧)对象序列化, 传统函数调用栈是连续压栈的，栈帧结构固化，无法在中途切断并恢复执行。意味着无法通过以下方式实现"跳出"：
一切早已标好价码，做出选择的那一刻就注定失去某些东西。同样，系统的复杂度和局限性绝不会凭空消失。
我们先看单线程同步模型的天然特性：(1)函数执行期间栈帧连续(2)返回值直接可达(3)执行顺序可预测(4)资源有天然作用域。这是同步模型的数学性质——只要是串行的，它们自动成立。Asyncio选择异步这条路时，"同步特性"就同时被"毒杀"。

Asyncio缺失了"同步特性"的具体表现为:
1. 上下文悬空: EventLoop回调执行时，前一个回调的局部变量、指令位置已经消失了
2. 结果不可达: I/O操作的结果在未来某个时刻到达，但调用者的栈帧已经不存在了
3. 时序失控: 成百上千个切分后的控制流碎片——谁先谁后？谁能取消？谁依赖谁？
4. 逃逸的代码块: 满天飞的任务——谁管生命周期？父级退出后子任务还在跑？异常被谁吃掉了？

## 附录

### 多线程的弊端简述 
一句话概述多线程的调度机制：**操作系统抢占式调度线程**。
"抢占式" + "线程" 叠加GIL会导致以下问题：

1. 抢占式带来的问题
os调度属于内核态，这种切断是隐式的，在哪被切断，接下来执行哪个线程，对用户透明的。
这意味着：相同的代码、相同的输入，因为系统负载不同、时钟中断的微小偏移，每次运行抢占的“断点”不同。出现不可复现的"幽灵BUG"

2. 线程引发防守成本，抢占式加剧锁问题：
当多个线程共享同一片内存时，所有共享的临界区都需要小心加锁。
持锁的线程可能还没释放锁就被切断，若多个线程各自持有对方所需的锁，循环等待一旦形成，死锁便不可逆转。

3. GIL拖累性能
在CPython里，多线程无法真正并行执行CPU密集任务，GIL还会导致线程频繁切换，I/O密集场景下也因争抢GIL而性能下降。

工程角度看一下，多线程带来的时/空成本 以及不可忽视的维护成本。
时间成本：调度权属于OS，内核态 <--> 用户态线之间的切换需要时间，线程之间的切换、叠加GIL反而可能拖累性能。
空间成本：线程是内核资源，创建和切换成本高（系统调用），每个线程还默认分配几8MB栈内存。想顶住 10k 并发，机器先被内存压垮
维护成本：
1. 极高的锁防守成本。
2. 可能因锁竞争和上下文切换导致性能退化——收益与成本倒挂。
3. "幽灵BUG"，导致人工成本叠加时间成本，直接经济损失，甚至更严重的"客户信任"成本。

### Asyncio解决了多线程的哪些痛?
1. 竞态条件与数据竞争
同一时刻只有一个协程在运行。只要不在await点，代码就是“原子”的，完全不用担心另一个协程突然插入修改你的变量。大多数场景下你甚至不需要锁。

2. 死锁风险
asyncio.Lock用错也可能死锁，但因为在单线程里执行，死锁更容易诊断。而且核心业务逻辑通常可以通过结构化并发避免深层锁依赖。

3. GIL的拖累
整个事件循环跑在一个线程里，GIL不再是需要争抢的资源，也就没有了线程切换时的GIL竞争开销，I/O 处理更高效。

4. 线程调度开销与内存占用
协程是用户态对象，创建成本极低，切换只是函数调用级的操作。轻松运行数万个协程，内存和 CPU 开销都很小。这也是“高并发”优势的根源。

5. 隐式的上下文切换
协程只在await时显式让出控制权。两个await之间的代码完全连续，切换点是透明的、可控的，大大简化了并发逻辑的思维模型。

6. 复杂的线程安全结构
asyncio可以直接使用 Python 的内置类型（如 list, dict），因为运行环境本身是单线程的。只有在你主动用 asyncio 的跨协程同步原语时，才需要关心协作式的调度安全，但复杂度远低于多线程。

# 演示 非阻塞 and 轮询
import socket
def step2_nonblocking_and_busy_wait():
    """非阻塞：O_NONBLOCK 解放线程"""
    sock = socket.socket()
    sock.setblocking(False) # <--- 核心前提1：OS 支持 O_NONBLOCK
    print("[非阻塞模型] 尝试连接...")
    try:
        sock.connect(("1.1.1.1", 9999))
    except BlockingIOError:
        # 连接尚未建立，OS立刻交还控制权，线程没被挂起！
        print("[非阻塞模型] 连接进行中，线程没卡死，可以干别的！")
    print("[非阻塞模型] 但怎么知道连接成功了？只能死循环问 OS...")
    import time
    start = time.perf_counter()
    loops = 0
    
    # 模拟轮询等待（这就是 CPU 空转的元凶）
    while time.perf_counter() - start < 0.01: # 0.01 跑 10 毫秒
        try:
            # 不断尝试发送数据探测连接是否完成
            sock.send(b"") 
            break # 没抛异常，说明连接成功了
        except (BlockingIOError, OSError):
            loops += 1 # 没好，继续死循环问
            
    print(f"[非阻塞模型] 10ms 内循环问了 OS {loops} 次！")

step2_nonblocking_and_busy_wait()

### 多路复用
"""
多路复用提效证明：N个连接仅2个就绪，轮询vs多路复用
"""
import socket, select, time, threading

N = 60  # Windows FD_SETSIZE=64

server = socket.socket()
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind(("127.0.0.1", 0))
port = server.getsockname()[1]
server.listen(N)

server_conns = []
def accept_all():
    for _ in range(N):
        conn, _ = server.accept()
        server_conns.append(conn)
    server_conns[10].send(b"Hi")
    server_conns[50].send(b"Yo")

threading.Thread(target=accept_all, daemon=True).start()

client_conns = []
for _ in range(N):
    s = socket.socket()
    s.connect(("127.0.0.1", port))
    s.setblocking(False)
    client_conns.append(s)

time.sleep(0.3)

# ===== 多路复用先测（否则轮询会先消费数据） =====
mux_calls, mux_reads, mux_hits = 0, 0, 0
for _ in range(5):
    r_list, _, _ = select.select(client_conns, [], [], 0.1)
    mux_calls += 1
    for s in r_list:
        try:
            data = s.recv(64)
            mux_reads += 1
            if data: mux_hits += 1
        except OSError:
            pass

# 重新发送数据给轮询测试
server_conns[10].send(b"Hi")
server_conns[50].send(b"Yo")
time.sleep(0.1)

# ===== 轮询：逐个read() =====
poll_reads, poll_hits = 0, 0
for _ in range(5):
    for s in client_conns:
        try:
            data = s.recv(64)
            poll_reads += 1
            if data: poll_hits += 1
        except BlockingIOError:
            poll_reads += 1
        except OSError:
            pass

total_mux = mux_calls + mux_reads
print(f"connections={N}, ready=2, rounds=5\n")
print(f"polling:  {poll_reads} read() calls, {poll_hits} hits, waste={poll_reads-poll_hits} ({(poll_reads-poll_hits)/poll_reads*100:.0f}%)")
print(f"mux:      {mux_calls} select + {mux_reads} read = {total_mux} calls, {mux_hits} hits")
print(f"\n=> {N} connections only 2 ready: polling={poll_reads} vs mux={total_mux}")
print(f"=> 10000 connections 5 rounds: polling=50000, mux~15")
print(f"=> poll is O(N), mux is O(ready)")

for s in client_conns: s.close()
for s in server_conns: s.close()
server.close()
