# S3: 冲突推导链——代价集群重建与副作用传导

## 推导方法

从0号约束出发，按两阶段动力学推进：

> **外生驱动（N0）**：目标G × 约束A → D1 → 代价集群{C1,C2,...}
> **内生驱动（N1+）**：代价集群C{N} × 约束A → 重建C{N}（主导）；D{X-1}副作用 × 约束A → 解决子问题（辅助）

范式转换型演进中，D1打破旧范式的同时**同时丧失多项原有保证**，构成代价集群。后续节点逐项重建这些保证，节点间顺序由**构建依赖**决定（必须先修地基再盖楼），而非由问题逐个发现决定。仅实现过程中暴露的更深层子问题才属副作用传导。

---

## N0: 核心冲突 (时序维度碰撞) [外生冲突]

- **通用困境**: 高速处理单元与低速I/O设备存在速度鸿沟——串行等待模型下处理单元被迫空转。这是所有I/O密集型系统(nginx、Node.js、Go scheduler、Java NIO、Rust tokio)面对的同一类根本问题
- **转换前提**: T1(非阻塞I/O) + T2(I/O多路复用)[详见S0_范式转换链]
- **继承影响**: I3(时序:需要调度中枢) + I4(边界:需绑定完成动作)[详见S0_范式转换链]
- **张力构成**: G(时序:需要I/O并发重叠等待) + A1(时序:CPU与I/O速度鸿沟，串行等待必致CPU空转)
- **冲突表现(时序)**: 串行执行流遇到慢I/O时停滞，时间轴上的并发断裂——CPU在等待I/O期间空转，无法利用这段时间执行其他任务
- **设计选择(D1)**: EventLoop接管控制权(I3驱动) + 回调绑定完成动作(I4驱动)——引入事件循环作为调度中枢，通过主动轮询I/O就绪事件实现"遇到I/O就跳过"；通过回调将就绪事件绑定到具体处理逻辑
- **代价集群**(自身代价): D1打破同步模型的四项保证:
  - C1(结构): 执行上下文悬空——任务让出控制权后，局部变量、指令位置无处安放
  - C2(边界+实体): 控制流断层——I/O结果无法传回给退场的协程，唤醒缺乏信号，函数返回值变成跨越时间的幽灵
  - C3(时序): 时序失控——成百上千个切分后的控制流碎片缺乏协调机制，谁先谁后？谁能取消？谁依赖谁？
  - C4(结构): 宏观秩序崩塌——满天飞的任务谁来管生命周期？
- **完整代价 = 继承影响{I3,I4} + 自身代价集群{C1,C2,C3,C4}**

## N1: 上下文保存 (重建C1) [内生冲突: 代价集群C1 × A2]

- **通用困境**: 异步系统中任务让出控制权后，执行上下文(局部变量、指令位置)无处安放——回调驱动的系统中控制流被切碎，每个碎片丢失了"我从哪里来"的信息。Node.js的闭包嵌套(callback hell)、Java的CompletionStage链式调用、C的显式状态机都是同一困境的不同应对
- **动力来源**: D1代价集群C1(结构:执行上下文悬空)
- **张力构成**: C1(结构:上下文悬空) + A2(结构:函数调用栈连续压栈不可中断)
- **构建依赖**: 无(D1已就位即可)
- **冲突表现(结构)**: EventLoop能监听I/O就绪事件，但它调度的"任务"仍然是传统函数，传统函数一旦开始执行就占满调用栈直到返回，无法在I/O等待点暂停执行交出控制权
- **设计选择(D2)**: 协程(Generator/yield切断栈帧) + Task(保存断点状态)——用协程的yield/await在I/O等待点切断连续栈帧，将执行状态(局部变量、指令位置)封装在generator/coroutine对象中; 用Task将协程包装为可调度单元，与EventLoop的_ready队列对接

## N2: 结果传回与唤醒 (重建C2) [内生冲突: 代价集群C2 × A4]

- **通用困境**: 异步系统中调用者让出控制权后，I/O操作的结果无法传回给已退场的调用者——这是所有异步系统的根本问题：结果在未来某个时刻到达，但调用者的栈帧已经不存在了。JavaScript的Promise、Java的CompletableFuture、C++的std::future都是同一困境的不同应对
- **动力来源**: D1代价集群C2(边界+实体:控制流断层，结果无法传回，唤醒缺乏信号)
- **张力构成**: C2(边界+实体:结果不可达，唤醒无信号) + A4(边界:应用无法感知内核I/O事件何时完成)
- **构建依赖**: D2已就位(需要协程的挂起点作为结果交付目标)
- **冲突表现(边界+实体)**: 协程await一个I/O操作后挂起自身，但它需要一个"未来的结果"作为锚点——一个在时序上尚未到来但在逻辑上已经确定的实体。I/O完成事件从内核到用户态的通知需要一个跨边界的通道
- **设计选择(D3)**: Future(实体:状态容器PENDING→FINISHED) + 回调(边界:跨任务唤醒接口)——Future用实体状态(PENDING→FINISHED)锚定了未来的结果，协程await Future后，Task将自己注册为Future的done_callback; Future完成时通过set_result()/set_exception() → __schedule_callbacks() → loop.call_soon(Task.__wakeup) → Task.__step()恢复协程执行
- **副作用(实现中发现)**: Future只是用户态的状态容器，它不知道底层操作系统何时产生数据。用户态Future与内核态I/O事件之间存在**边界鸿沟**——此为实现D3时发现的更深层子问题，属副作用传导，传导至N3

## N3: 内核边界桥接 [内生冲突: D3副作用 × A4]

- **通用困境**: 用户态异步框架必须跨越内核/用户态边界获取I/O完成通知——任何基于操作系统I/O的异步系统(无论语言)都必须解决"用户态如何感知内核I/O事件"的问题。libuv的uv__io_poll、Java NIO的Selector、Go的netpoller都是对同一问题的不同实现
- **动力来源**: D3实现副作用(边界:Future不知道内核何时产生数据)
- **张力构成**: D3副作用(边界:用户态/内核态鸿沟) + A4(边界:内核I/O事件→用户态的通道) + C_Arch_5(时序:OS提供select/epoll/IOCP可监听多I/O)
- **构建依赖**: D3已就位(需要Future作为数据注入目标)
- **冲突表现(边界)**: Future提供了状态容器和回调通道，但谁来调用Future.set_result()?需要一个组件下探到内核I/O边界，将selector/IOCP的通知转化为Future的状态变迁
- **设计选择(D4)**: Transport封装底层非阻塞I/O + Protocol处理业务逻辑——Transport监听内核I/O事件(selector报告fd可读)，跨越内核/用户态边界，读取数据并调用Protocol.data_received(); Protocol处理数据后(如解析完整帧)，调用Future.set_result()完成状态锚定

## N4: 时序协调 (重建C3) [内生冲突: 代价集群C3 × 单线程协作约束]

- **通用困境**: 并发系统中协作任务需要时序协调——无协调则数据竞争(多线程)或逻辑互斥违反(单线程协程)，这是所有并发编程的共性问题。Go的sync.Mutex/channel、Java的synchronized/CountDownLatch、Rust的Mutex/mpsc::channel都是同一困境的不同应对
- **动力来源**: D1代价集群C3(时序:多控制流碎片缺乏协调机制)
- **张力构成**: C3(时序:协程间让出-唤醒顺序需显式控制) + 单线程无抢占(协程切换是协作式的，需要主动等待点)
- **构建依赖**: D3已就位(同步原语内部使用Future作为等待器)
- **冲突表现(时序)**: 在单线程中，协程之间的"同步"本质上是时序协调——一个协程需要等待另一个协程完成某操作后才能继续。裸Future可以实现等待，但缺乏标准语义(Lock/Event/Queue等)
- **设计选择(D5)**: 基于Future的同步原语族(Lock/Event/Condition/Semaphore/Barrier/Queue)——这些原语内部全部使用Future作为等待器，在Lock.acquire()中await一个Future，在Lock.release()中对Future.set_result()唤起; 将线程同步语义适配到单线程协程世界

## N5: 生命周期管理 (重建C4) [内生冲突: 代价集群C4 × 业务约束]

- **通用困境**: 并发任务逃逸——无作用域约束的任务可在父级退出后继续运行，异常静默丢失，取消信号无法级联传播。结构化并发是近年来Go(errgroup)、Rust(tokio::task::JoinSet)、Swift(TaskGroup)等系统共同趋近的解法方向
- **动力来源**: D1代价集群C4(结构:满天飞的任务缺乏生命周期管理)
- **张力构成**: C4(结构:裸create_task无作用域约束) + C_Biz_2(实体:结果必须正确获取) + C_Biz_3(结构:编程模型需简洁)
- **构建依赖**: D5已就位(结构化并发建立在协调原语之上)
- **冲突表现(结构)**: 裸create_task()没有作用域约束，Task可能在父协程结束后仍在运行(结构失控); 超时场景需要将"时间限制"转化为协程可感知的取消信号; 异常需要在Task组间正确传播
- **设计选择(D6)**: TaskGroup(结构化并发) + Timeout(超时控制) + Runner(生命周期管理)——TaskGroup确保async with块内的所有Task在退出前完成或取消，异常收集为ExceptionGroup; Timeout通过TimerHandle→Task.cancel→uncancel实现将时间边界转化为异常边界; Runner管理EventLoop从创建到关闭的完整生命周期
- **闭环**: 代价集群{C1,C2,C3,C4}全部重建完成。时序上的I/O并发重叠(EventLoop); 结构上的上下文保存与恢复(协程+Task); 边界上的结果传回与内核桥接(Future+Transport+Protocol); 时序上的协调(同步原语); 结构上的生命周期管理(TaskGroup+Timeout+Runner)。目标G被满足，0号约束全部守恒。

---

## 闭环验证

### S1: 目标达成验证
目标G: 在单线程内实现I/O并发等待+结构化结果获取+简洁编程模型
- 时序: EventLoop+协程实现了I/O并发重叠 ✓
- 结构: 协程+Task实现了栈帧切断与恢复 ✓
- 边界: Transport+Protocol桥接了内核/用户态 ✓
- 实体: Future状态机锚定了结果 ✓
- 编程模型: async/await + TaskGroup提供了简洁的同步式编写 ✓

### S2: 约束守恒验证
- A1(时序): EventLoop重叠等待解决了CPU空转 ✓ 未破坏
- A2(结构): 协程yield切断栈帧，但栈帧仍存在于coroutine对象中 ✓ 未破坏
- A3(边界): 未引入多线程，避免GIL问题 ✓ 未破坏
- A4(边界): 通过selector/IOCP+Transport+Protocol桥接内核边界 ✓ 未破坏

## 演进结构图

```
D1 EventLoop ─── 代价集群 {C1, C2, C3, C4}
                  │     │      │      │
                  ▼     ▼      │      │
    N1→D2 协程+Task  N2→D3 Future+回调  │      │
    [重建C1]        [重建C2]     │      │
                  │     │      │      │
                  │     ▼      │      │
                  │   N3→D4 Transport+Protocol  │
                  │   [D3副作用传导]     │
                  │                  │      │
                  └──────────────────┼──────┘
                                     ▼      ▼
                           N4→D5 同步原语   N5→D6 TaskGroup+Timeout+Runner
                           [重建C3]        [重建C4]
                                     │
                                     ▼
                                    闭环
```

**演进规律**: 范式转换型演进的驱动力不是因果发现链，而是"代价集群→构建依赖序重建链"。D1打破的保证同时可见，节点间顺序由"必须先修地基再盖楼"的构建依赖决定，而非"走一步发现一步"的副作用传导。
