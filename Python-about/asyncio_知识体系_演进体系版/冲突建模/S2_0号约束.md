# S2: 0号约束——递归Why的公理提取

## 递归Why算法

对S1中的每条约束，反复追问"为什么这是一个不可回避的约束？"，直到到达**不可再分的事实**——即该事实由物理定律或体系结构决定，无法通过任何设计选择消除。这些不可再分的事实即为0号约束(公理)。

| 0号约束编号 | 源自S1约束 | 递归终点描述 (不可再分事实) | 归属维度 |
| :--- | :--- | :--- | :--- |
| A1 | C_Phys_1+C_Biz_1 | CPU与I/O速度鸿沟(CPU纳秒级 vs I/O毫秒级)导致串行等待必致CPU空转，必须在时间轴上重叠多个I/O等待 | 时序 |
| A2 | C_Arch_1+C_Arch_2 | 单线程串行控制流 + 传统函数调用栈连续压栈不可中断，导致遇到I/O等待时无法保存断点切换执行其他任务 | 时序+结构 |
| A3 | C_Arch_3 | GIL限制 + 跨线程上下文切换开销大，导致多线程方案在Python中不是高并发I/O的高效解法 | 边界 |
| A4 | C_Arch_4 | I/O操作跨越内核/用户态边界，应用无法感知内核I/O事件何时完成，必须依赖OS通知机制 | 边界 |
| G | C_Biz_1+C_Biz_2+C_Biz_3 | 必须在单线程内实现I/O并发等待，且提供结构化的结果获取和简洁的编程模型 | 时序+实体+结构 |

## 递归Why过程记录

### A1的推导链

```
C_Phys_1: CPU纳秒级 vs I/O毫秒级，10^6倍速度鸿沟
  → Why这不可回避？因为CPU和I/O的物理速度差异由半导体工艺和光速/机械延迟决定
  → Why需要重叠I/O？C_Biz_1要求高并发(数千连接同时等待)
  → 归并：串行等待必致CPU空转(物理事实) + 必须支持高并发等待(业务事实)
  → 不可再分终点：必须在时间轴上重叠多个I/O等待
```

### A2的推导链

```
C_Arch_1: Python单线程串行执行字节码
  → Why不可回避？CPython解释器主循环逐条执行字节码是架构事实
C_Arch_2: 传统函数调用栈连续压栈不可中断
  → Why不可回避？x86/ARM的栈帧结构是硬件事实，Python frame对象在此基础上构建
  → 归并：串行控制流遇到I/O等待时，既不能跳过(串行)，也不能保存断点(栈连续)
  → 不可再分终点：无法保存断点切换执行其他任务
```

### A3的推导链

```
C_Arch_3: GIL阻止多线程真正并行 + 上下文切换开销大(微秒级)
  → Why不可回避？GIL是CPython内存管理的架构选择(引用计数非线程安全)
  → 不可再分终点：多线程方案在Python中不是高并发I/O的高效解法
  → 注：A3排除了多线程路径，将解空间限定在单线程内
```

### A4的推导链

```
C_Arch_4: I/O操作跨越内核/用户态边界，系统调用阻塞
  → Why不可回避？保护模式/分页机制是x86/ARM的硬件事实，用户态无法直接访问设备
  → 不可再分终点：应用无法感知内核I/O事件何时完成，必须依赖OS通知机制
```

### G的推导链

```
C_Biz_1: 高并发I/O等待 → 时序维度：必须在单线程内重叠I/O等待(结合A3排除多线程)
C_Biz_2: 结果必须正确获取 → 实体维度：异步操作结果必须可锚定
C_Biz_3: 简洁编程模型 → 结构维度：避免回调地狱，需要同步式写法
  → 归并：综合目标是"单线程I/O并发 + 结果可达 + 简洁模型"
  → 不可再分终点：G是设计目标公理，满足G即asyncio成立
```

## 守恒验证

> 对每个0号约束，证明：**如果移除这个公理，asyncio的设计基础是否崩塌？**

### 移除A1的后果

如果CPU与I/O没有速度鸿沟(I/O也纳米级完成)，则串行执行遇到I/O时不会产生可感知的等待，CPU不会空转，完全没有必要在时间轴上重叠多个I/O等待。EventLoop、协程、Task等全部机制失去存在意义。**设计基础崩塌。**

### 移除A2的后果

如果传统函数栈帧可以中途切断并恢复(如硬件级continuation)，则遇到I/O等待时可以直接保存整个栈帧状态并切换到另一个函数，不需要yield/await语法，不需要generator/coroutine对象封装断点。协程、Task的整个设计都不需要。**设计基础崩塌。**

### 移除A3的后果

如果GIL不存在且线程切换开销可忽略(如Go的goroutine)，则可以用OS线程实现高并发I/O，每个线程同步地做I/O等待，由OS调度器负责切换。asyncio的单线程事件循环方案失去相对优势。**设计基础崩塌(至少失去必要性)。**

### 移除A4的后果

如果应用可以直接感知内核I/O事件完成(如统一地址空间、无内核/用户态边界)，则不需要selector/epoll/IOCP等通知机制，不需要Transport层去跨越边界读取数据。Future可以被I/O操作本身直接触发set_result()。**Transport/Protocol层的设计基础崩塌。**

### 移除G的后果

G是目标公理——如果不需要"单线程I/O并发+结果可达+简洁模型"，则asyncio这个项目根本没有目标。**整个设计基础崩塌。**

## 公理独立性检查

| 检查项 | 结论 |
| :--- | :--- |
| A1能否从其他公理推导？ | 不能。A1是物理层事实，A2/A3/A4是架构层事实，G是业务层目标，均不蕴含"CPU与I/O速度鸿沟" |
| A2能否从其他公理推导？ | 不能。A1只说"需要重叠I/O"，不蕴含"栈帧不可中断"这一结构事实 |
| A3能否从其他公理推导？ | 不能。GIL是CPython特定选择，不是通用架构事实 |
| A4能否从其他公理推导？ | 不能。内核/用户态边界是OS架构事实，A1-A3均不蕴含此边界 |
| G能否从其他公理推导？ | 不能。G是价值判断(业务需求)，不能从物理/架构事实中推导"应该"做什么 |

五个公理相互独立，且移除任一个均导致设计基础崩塌。**公理集最小且完备。**
