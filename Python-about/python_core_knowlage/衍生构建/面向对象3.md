## 六、自测题目

### 题目1：MRO预测

给定以下类层次结构：

```python
class X: pass
class Y: pass
class Z: pass
class A(X, Y): pass
class B(Y, Z): pass
class C(A, B): pass
```

问题：
1. 手动计算C3线性化，写出`C.__mro__`
2. 如果将`A`改为`class A(Y, X):`会发生什么？
3. 解释为什么C3算法拒绝第二种情况

<details>
<summary>参考答案</summary>

1. `C.__mro__ = (C, A, X, B, Y, Z, object)`

   推导过程：
   ```
   L[X] = [X, object]
   L[Y] = [Y, object]
   L[Z] = [Z, object]
   L[A] = A + merge([X, object], [Y, object], [X, Y])
        = [A, X, Y, object]
   L[B] = B + merge([Y, object], [Z, object], [Y, Z])
        = [B, Y, Z, object]
   L[C] = C + merge([A, X, Y, object], [B, Y, Z, object], [A, B])
        = C + A + merge([X, Y, object], [B, Y, Z, object], [B])
        = C + A + X + merge([Y, object], [B, Y, Z, object], [B])
        = C + A + X + B + merge([Y, object], [Y, Z, object], [])
        = C + A + X + B + Y + merge([object], [Z, object], [])
        = C + A + X + B + Y + Z + merge([object], [object], [])
        = [C, A, X, B, Y, Z, object]
   ```

2. 改为`class A(Y, X):`后，`class C(A, B):`会抛出TypeError。

3. 因为`A(Y, X)`承诺Y在X前面，而`B(Y, Z)`的MRO中Y在Z前面。当C继承A和B时，merge会尝试将X放在某个位置，但X与Y的相对顺序在A和B的MRO中矛盾。具体来说：
   ```
   L[A'] = [A, Y, X, object]  (Y在X前)
   L[B]  = [B, Y, Z, object]
   
   L[C'] = C + merge([A, Y, X, object], [B, Y, Z, object], [A, B])
         = C + A + merge([Y, X, object], [B, Y, Z, object], [B])
         = C + A + B + merge([Y, X, object], [Y, Z, object], [])
   
   下一个候选: Y头部 → 在第二列表尾部[Z, object]中？不在 → 选Y
   = C + A + B + Y + merge([X, object], [Z, object], [])
   下一个候选: X → 在第二列表尾部[object]中？不在 → 选X
   = C + A + B + Y + X + merge([object], [Z, object], [])
   下一个候选: object → 在第二列表尾部中 → 坏
   Z → 在第一列表尾部中 → 坏
   ```
   
   其实这个情况是能通过的... 让我重新考虑。实际上`class A(Y, X)`与`class B(Y, Z)`的组合不会导致C3失败——因为Y在两个MRO中都排在前面，没有矛盾。
   
   真正的C3失败需要两个基类对同一对类的顺序做出**矛盾承诺**。回到前面的经典例子：
   ```python
   class A(X, Y): pass  # 承诺 X > Y
   class B(Y, X): pass  # 承诺 Y > X
   class C(A, B): pass  # TypeError! X>Y 和 Y>X 矛盾
   ```
   
   回到本题第二种情况`class A(Y, X)`：L[A'] = [A, Y, X, object]，L[B] = [B, Y, Z, object]。合并：
   ```
   C + A + B + Y + merge([X, object], [Z, object], [])
   X不在Z的尾部 → 选X
   C + A + B + Y + X + Z + object
   ```
   所以MRO = (C, A, B, Y, X, Z, object)，这是合法的！
   
   要制造失败，需要比如 `class A(X, Y)` 与 `class B(Y, X)` 的组合。
</details>

### 题目2：描述符优先级陷阱

```python
class Desc:
    def __get__(self, obj, objtype=None):
        return f"Desc.__get__, obj={type(obj).__name__ if obj else 'None'}"

class Foo:
    desc = Desc()

    def __init__(self):
        self.desc = "instance value"  # 这行会怎样？
```

问题：
1. `Foo().__init__`中`self.desc = "instance value"`会做什么？会改实例`__dict__`吗？
2. 如果`Desc`只定义`__get__`不定义`__set__`呢？
3. 解释背后的描述符优先级规则

<details>
<summary>参考答案</summary>

1. `Desc`定义了`__get__`和`__set__`（这里虽然没展示`__set__`，但`Desc`需要定义`__set__`才是数据描述符）。假设`Desc`只定义了`__get__`：
   - `self.desc = "instance value"`会在实例`__dict__`中创建`'desc'`键
   - 之后`obj.desc`返回`"instance value"`（实例`__dict__`优先于非数据描述符）

2. 如果`Desc`同时定义了`__get__`和`__set__`（数据描述符）：
   - `self.desc = "instance value"`会调用`Desc.__set__(self, "instance value")`
   - 之后`obj.desc`调用`Desc.__get__`，而非返回实例`__dict__`中的值
   - 数据描述符优先级高于实例`__dict__`

3. 属性查找优先级：数据描述符 > 实例`__dict__` > 非数据描述符 > 类`__dict__`普通属性。这确保了`property`（数据描述符）总是能拦截访问/修改，而方法（非数据描述符）可以被实例属性覆盖。
</details>

### 题目3：__new__与单例

```python
class Singleton:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

class MySingleton(Singleton):
    value = 0
```

问题：
1. 调用`MySingleton()`两次，得到的是同一个对象吗？
2. 每次调用`MySingleton()`时，`__init__`会被调用几次？（假设MySingleton定义了`__init__`）
3. 如果`MySingleton`的子类也想要单例行为，`_instance`变量会不会冲突？

<details>
<summary>参考答案</summary>

1. 是同一个对象——`__new__`返回缓存的`cls._instance`。

2. `__init__`**每次调用都会执行**！`type.__call__`中，`__new__`返回后如果`Py_TYPE(obj) == type`就调用`__init__`。单例模式中返回的是同类型实例，所以条件满足。必须在`__init__`中手动检测是否已初始化。

3. **会冲突**！`_instance`存储在`Singleton.__dict__`中，所有子类共享。`MySingleton()`和`AnotherSubSingleton()`都会检查同一个`Singleton._instance`，导致第一个创建的子类的实例被所有子类共享。解决方案：让`_instance`为`None`时检查`cls is Singleton`，或使用`cls._instance = ...`而非`Singleton._instance = ...`，这样`cls._instance`会在子类的`__dict__`中创建：
   ```python
   def __new__(cls):
       if not hasattr(cls, '_instance') or cls._instance is None:
             cls._instance = super().__new__(cls)
       return cls._instance
   ```
</details>

## 附录C：C3算法的Python实现

```python
def c3_linearize(cls, *, _cache=None):
    """C3线性化算法的Python实现，用于理解和验证MRO"""
    if _cache is None:
        _cache = {}

    if cls in _cache:
        return _cache[cls]

    if cls is object:
        _cache[cls] = [object]
        return [object]

    bases = cls.__bases__
    if not bases:
        # 没有显式基类 → 默认继承 object
        result = [cls, object]
        _cache[cls] = result
        return result

    # 递归计算每个基类的线性化
    base_linearizations = [c3_linearize(b, _cache=_cache) for b in bases]

    # merge 操作
    result = [cls]
    lists_to_merge = [list(lin) for lin in base_linearizations] + [list(bases)]

    while any(lists_to_merge):
        # 找一个好的头部
        good_head = None
        for lst in lists_to_merge:
            if not lst:
                continue
            candidate = lst[0]
            # 检查 candidate 是否在任何其他列表的尾部
            is_in_tail = any(candidate in other[1:] for other in lists_to_merge if other)
            if not is_in_tail:
                good_head = candidate
                break

        if good_head is None:
            raise TypeError(
                f"Cannot create a consistent method resolution order (MRO) "
                f"for {cls.__name__} with bases {[b.__name__ for b in bases]}"
            )

        result.append(good_head)
        # 从所有列表中删除 good_head
        for lst in lists_to_merge:
            if lst and lst[0] == good_head:
                lst.pop(0)

        # 清理空列表
        lists_to_merge = [lst for lst in lists_to_merge if lst]

    _cache[cls] = result
    return result


# 验证
class A: pass
class B(A): pass
class C(A): pass
class D(B, C): pass

computed = c3_linearize(D)
actual = list(D.__mro__)
print(f"计算: {computed}")
print(f"实际: {actual}")
print(f"一致: {computed == actual}")  # True

# 验证C3失败
try:
    class X: pass
    class Y: pass
    class P(X, Y): pass
    class Q(Y, X): pass
    class R(P, Q): pass
except TypeError as e:
    print(f"C3失败（预期）: {e}")

# 手动验证失败
try:
    c3_linearize(R)
except TypeError as e:
    print(f"手动C3也失败: {e}")
```

## 附录D：完整的属性查找流程字节码追踪

```python
import dis

class VerboseGetAttr:
    def __getattribute__(self, name):
        print(f"  __getattribute__ called for '{name}'")
        # 调用默认实现（object.__getattribute__）
        return object.__getattribute__(self, name)

    def __getattr__(self, name):
        print(f"  __getattr__ called for '{name}' (fallback)")
        raise AttributeError(f"{type(self).__name__} has no attribute '{name}'")

v = VerboseGetAttr()
v.x = 42

print("=== 访问存在的属性 ===")
print(v.x)
#   __getattribute__ called for 'x'
#   42

print("\n=== 访问不存在的属性 ===")
try:
    print(v.missing)
except AttributeError as e:
    print(f"  → {e}")
#   __getattribute__ called for 'missing'
#   __getattr__ called for 'missing' (fallback)
#   → VerboseGetAttr has no attribute 'missing'

# 字节码分析
print("\n=== 字节码 ===")
dis.dis(compile("v.x", '<test>', 'eval'))
# 1           0 LOAD_NAME                0 (v)
#             2 LOAD_ATTR                1 (x)  ← 触发 __getattribute__
#             4 RETURN_VALUE

# LOAD_ATTR 在 CPython 3.12+ 中做了重大优化:
# - 使用 inline cache 缓存属性查找结果
# - 对常见模式（类属性查找 + 描述符绑定）做了特化
# - 但语义不变：仍走 __getattribute__ → 描述符 → __dict__ → __getattr__ 的完整流程
```

**全文总结**：

Python的面向对象系统由三个核心支柱构成：
1. **类型对象（type/metaclass）**：class是可调用对象，`type.__call__`统一了类调用和实例创建，元类提供了拦截类创建的入口
2. **MRO与super()**：C3线性化算法将多重继承菱形图压为线性链，`super()`沿MRO进行协作式委托，而非简单地调用"父类"
3. **描述符协议**：属性访问的真正引擎，5层优先级（数据描述符→实例`__dict__`→非数据描述符→类`__dict__`→`__getattr__`）统一解释了方法绑定、property封装、slot优化等行为

这三者在CPython层面对应`PyTypeObject`的`tp_new`/`tp_init`、`tp_mro`、`tp_descr_get`/`tp_descr_set`等类型槽，是Python"一切皆协议"设计哲学的终极体现。
