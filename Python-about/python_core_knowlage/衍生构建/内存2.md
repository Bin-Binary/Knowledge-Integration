#### 2.2.3 收集触发条件与过程

```python
import gc

# 查看当前各代状态
print("各代对象数量:", gc.get_count())  # (gen0_count, gen1_count, gen2_count)
```

**触发条件**（gcmodule.c中的`collect_generations`函数逻辑）：

```python
# 伪代码描述GC触发逻辑
def maybe_collect():
    gen0_count, gen1_count, gen2_count = gc.get_count()
    gen0_thresh, gen1_thresh, gen2_thresh = gc.get_threshold()
    
    # 从最高代开始检查
    for gen in range(2, -1, -1):
        if gen == 2 and gen2_count >= gen2_thresh:
            collect_generation(2)  # 全量收集
            break
        elif gen == 1 and gen1_count >= gen1_thresh:
            collect_generation(1)  # 收集gen1 + gen0
            break
        elif gen == 0 and gen0_count >= gen0_thresh:
            collect_generation(0)  # 仅收集gen0
            break
```

**收集过程（标记-清除算法详细步骤）**：

1. **更新引用计数（可选）**：Merge暂时的DECREF（某些边缘情况）
2. **标记阶段**：
   - 从根集合出发（全局变量、栈帧中的局部变量、永久对象）
   - 递归遍历所有可达对象，标记为存活（`_gc_prev`最低位设置）
3. **清除阶段**：
   - 遍历该代链表
   - 未标记的对象即为垃圾 → 回收
   - 标记的对象取消标记，并**晋升到下一代**
4. **处理不可达但有`__del__`的对象**（Python < 3.4放到gc.garbage）

```python
# 手动触发指定代的收集
collected = gc.collect(0)  # 仅收集gen0
collected = gc.collect(1)  # 收集gen0 + gen1
collected = gc.collect(2)  # 收集所有代（full collection）
collected = gc.collect()   # 默认full collection（同collect(2)）
```

#### 2.3.3 `__del__`与GC的复杂互动

**Python < 3.4**：如果循环引用中**有对象定义了`__del__`**，GC**无法回收**该循环，对象会被放入`gc.garbage`列表。

原因：CPython不知道应该先调用哪个对象的`__del__`——两个对象互相引用，调用A的`__del__`时可能访问B，但B也可能在`__del__`中访问A，顺序不确定。

```python
import gc

class Problematic:
    def __init__(self, name):
        self.name = name
        self.link = None
    
    def __del__(self):
        # __del__中可能访问self.link，但如果link已被回收呢？
        print(f"{self.name}清理，link={self.link}")

gc.disable()
a = Problematic('A')
b = Problematic('B')
a.link = b
b.link = a

del a, b
gc.enable()

# 旧版Python中，这两个对象进入gc.garbage，无法回收
gc.collect()
print(f"gc.garbage: {len(gc.garbage)} 个对象")  # 旧版: 2
```

**Python 3.4+ (PEP 442)**：CPython实现了**安全终端`__del__`**，循环引用可以正常回收：

```python
# Python 3.4+ 的表现
import gc

class Safe:
    def __init__(self, n):
        self.n = n
        self.link = None
    def __del__(self):
        print(f"对象{self.n}析构，link={self.link}")

a = Safe(1)
b = Safe(2)
a.link = b
b.link = a

del a, b
collected = gc.collect()
print(f"回收: {collected} 个（gc.garbage应为空）")
# 输出:
# 对象1析构，link=<Safe object at 0x...>
# 对象2析构，link=<Safe object at 0x...>
# 回收: 2 个
```

PEP 442的关键改进：在清理循环引用时，先将对象的引用断开（解除循环），再调用`__del__`。这样`__del__`中仍可安全访问被引用的对象（因为它们还没被释放），但循环已被打破。

## 三、GIL——全局解释器锁的真相

### 3.1 GIL是什么

#### 3.1.1 定义与位置

**GIL（Global Interpreter Lock）**是一把**进程级别的互斥锁**，保护CPython解释器的内部状态。

CPython源码中的GIL定义（Python 3.12+）：

```c
// CPython Python/ceval_gil.c (简化版)

struct _gil_runtime_state {
    _Py_atomic_int _gil_locked;     // GIL状态：0=未锁，1=已锁
    _Py_atomic_int _gil_drop_request; // 请求释放GIL的标志
    // 条件变量、互斥量等
};

// 获取GIL（阻塞直到获得）
static void take_gil(PyThreadState *tstate) {
    // ...
    while (_Py_atomic_load_int(&gil->_gil_locked)) {
        // GIL被其他线程持有，等待
        PyCOND_WAIT(gil->cond, gil->mutex);
    }
    _Py_atomic_store_int(&gil->_gil_locked, 1);
    tstate->owns_gil = 1;
}

// 释放GIL
static void drop_gil(PyThreadState *tstate) {
    _Py_atomic_store_int(&gil->_gil_locked, 0);
    PyCOND_SIGNAL(gil->cond);  // 唤醒等待的线程
}
```

#### 3.1.2 为什么必须有GIL

**核心原因**：CPython的引用计数（`ob_refcnt`）**不是线程安全的**。

设想的竞态条件（**无GIL**）：

```
线程1                               线程2
obj.ob_refcnt = 1                   
读 ob_refcnt → 1                    
     INCREF: 读1，计算2              
                                        读 ob_refcnt → 1
                                        DECREF: 读1，计算0
                                        写 ob_refcnt = 0
                                        调用 tp_dealloc → 释放内存！
    写 ob_refcnt = 2 → 写入已释放的内存！ → 💥崩溃
```

没有GIL，两个线程同时INCREF/DECREF会导致竞态条件。

**更根本的原因**：不只是引用计数，CPython内部大量全局状态都非线程安全：
- 小整数缓存池（`small_ints`）
- 字符串驻留表（`interned strings`）
- 类型对象的缓存字段（`tp_mro`、`tp_subclasses`）
- 模块导入缓存（`sys.modules`）
- GC的分代链表

GIL用一把大锁串行化所有这些状态的访问，是**最简单粗暴但有效**的方案。

#### 3.1.3 其他Python实现的对比

| 实现 | 有GIL？ | 内存管理 | 并行执行 |
|------|---------|---------|---------|
| **CPython** | ✅ 有 | 引用计数+分代GC | 不支持Python代码并行 |
| **PyPy** | ❌ 无（有GIL但可释放） | 增量式标记-清除GC | 部分支持 |
| **Jython** | ❌ 无 | JVM GC | 完全支持多线程并行 |
| **IronPython** | ❌ 无 | .NET GC | 完全支持多线程并行 |
| **GraalPy** | ❌ 无 | GraalVM GC | 完全支持多线程并行 |

Jython没有GIL是因为它运行在JVM上，用Java的GC而非引用计数，天然线程安全。但Jython性能慢、生态不完整，所以绝大多数人仍在用CPython。

### 3.2 GIL的调度

#### 3.2.1 切换间隔

```python
import sys

# Python 3.2+: 使用时间间隔（秒）
interval = sys.getswitchinterval()
print(f"GIL切换间隔: {interval}秒")  # 默认0.005 (5ms)

# 修改间隔
sys.setswitchinterval(0.01)  # 设为10ms
```

**Python 3.2前**：使用tick计数，默认每1000条字节码指令检查一次是否释放GIL。这导致简单指令（如`LOAD_FAST`）和复杂指令（如`CALL_FUNCTION`）占据相同的"时间片"，不公平。

**Python 3.2+ (PEP 3145)**：改用**时间间隔**（默认5ms），更公平。Antoine Pitrou实现的"new GIL"使用条件变量而非轮询，降低了CPU浪费。

#### 3.2.2 GIL的释放与获取时机

**自动释放GIL的场景**：

1. **I/O操作**：`time.sleep()`, `file.read/write`, `socket.send/recv`, `select.select()`
2. **部分C扩展**：`numpy`矩阵运算, `PIL`图像处理, `zlib`压缩, `_hashlib`哈希
3. **显式释放**：C扩展中使用`Py_BEGIN_ALLOW_THREADS`/`Py_END_ALLOW_THREADS`宏

C扩展释放GIL的模式：

```c
// C扩展中释放GIL的标准写法
static PyObject *
my_cpu_intensive_function(PyObject *self, PyObject *args) {
    double result;
    
    Py_BEGIN_ALLOW_THREADS  // 释放GIL
    
    // 此区域可以并行执行
    // 但不能访问任何Python对象！
    result = heavy_c_computation();
    
    Py_END_ALLOW_THREADS    // 重新获取GIL
    
    return PyFloat_FromDouble(result);  // 创建Python对象需要GIL
}
```

#### 3.2.3 GIL工作流图示

```
时间 → ──────────────────────────────────────────────→

线程1:  [持有GIL执行字节码]──5ms──→释放→[等待GIL][持有GIL]──→
线程2:  [等待GIL]→[持有GIL执行字节码]──5ms──→释放→[等待GIL]→

I/O场景:
线程1:  [持有GIL]→[I/O调用,释放GIL]→[I/O等待中...]→[I/O完成,获取GIL]→
线程2:  [等待GIL]→[持有GIL执行字节码]→[时间片到,释放GIL]→
```

### 3.3 GIL的影响与应对

#### 3.3.1 CPU密集型——GIL扼杀并行

#### 3.3.5 应对方案3：asyncio——单线程高并发

```python
import asyncio
import time

async def fetch(session, url):
    async with session.get(url) as response:
        return await response.text()

start = time.perf_counter()
asyncio.run(main())

```

```python
# numpy在执行C级数组运算时释放GIL
def numpy_parallel():
    a = np.random.rand(10000, 10000)
    b = np.random.rand(10000, 10000)
    
    import threading
    start = time.perf_counter()
    
    # numpy.dot释放GIL，多线程可真并行
    t1 = threading.Thread(target=np.dot, args=(a, b))
    t2 = threading.Thread(target=np.dot, args=(a, b))
    t1.start()
    t2.start()
    t1.join()
    t2.join()
    
    print(f"numpy并行dot: {time.perf_counter()-start:.2f}s")

numpy_parallel()
```

### 3.4 GIL的争议与未来

#### 3.4.1 为什么移除GIL如此困难

**问题1：现有C扩展不兼容**

数以万计的C扩展模块依赖GIL的存在——它们可以放心操作Python对象，因为GIL保证没有其他线程同时访问。移除GIL意味着：

```c
// 之前（有GIL）: 安全，无需加锁
PyList_Append(list, item);  // GIL保证线程安全

// 之后（无GIL）: 不安全，需要显式加锁
Py_CRITICAL_SECTION(list);
PyList_Append(list, item);
Py_CRITICAL_SECTION_END();
```

**问题2：引用计数需要原子操作**

```c
// 有GIL时: 普通加法（1条CPU指令）
#define Py_INCREF(op) ((op)->ob_refcnt++)

// 无GIL时: 原子加法（10-100条CPU指令，含memory barrier）
#define Py_INCREF(op) \
    _Py_atomic_add_ssize_t(&((op)->ob_refcnt), 1)
```

原子操作比普通加法慢10-100倍，会拖慢**所有**Python代码——哪怕单线程。

#### 3.4.2 PEP 703——让GIL可选

**PEP 703（Python 3.13+）**提出了"free-threaded CPython"：

```bash
# 编译无GIL版本
./configure --disable-gil
make
# 或
./configure --disable-gil --with-experimental-is-gil-mode
```

关键技术：

1. **有偏引用计数（Biased Reference Counting）**：
   - 对象的"所有者线程"用普通非原子操作INCREF/DECREF
   - 其他线程用原子操作修改`ob_refcnt`的后半部分
   - 只有当所有者释放对象时，才合并两个计数

2. **临界区API**：
   ```c
   // 替代GIL的细粒度锁
   Py_BEGIN_CRITICAL_SECTION(object);
   // 操作object
   Py_END_CRITICAL_SECTION();
   ```

3. **逐个扩展迁移**：
   - 支持`Py_mod_gil`模块标记，声明是否支持无GIL
   - 导入时检查兼容性

#### 3.4.3 Python 3.13+ free-threaded实验

```python
import sys

# 检测是否为free-threaded构建
print(f"GIL启用: {sys._is_gil_enabled()}")

# 检测是否支持free-threaded
print(f"Python版本: {sys.version}")
if hasattr(sys, '_is_gil_enabled'):
    if not sys._is_gil_enabled():
        print("当前为无GIL模式！多线程可以真并行")
    else:
        print("当前为标准GIL模式")
else:
    print("当前Python版本不支持_is_gil_enabled")
```

## 四、编译与执行——从源码到PVM

### 4.1 执行管线

#### 4.1.1 完整执行流程

```
.py源码文件
    ↓ (Tokenizer/Lexer)
Tokens词法单元序列
    ↓ (Parser/CFG Parser)
AST抽象语法树
    ↓ (Compiler/Ast_Optimize → Bytecode)
Code Object代码对象
    ↓ (写入.pyc缓存 或 直接执行)
PyCodeObject + PyFrameObject
    ↓ (PVM: Python Virtual Machine)
执行结果
```

每一步的输入输出：

| 阶段 | 输入 | 输出 | 工具/函数 |
|------|------|------|----------|
| 词法分析 | 源码字符串 | Token序列 | `tokenize.generate_tokens()` |
| 语法分析 | Token序列 | AST | `ast.parse()` |
| 编译 | AST | Code Object | `compile()`/`PyAST_Compile()` |
| 执行 | Code Object | 执行结果 | `exec()`/`PyEval_EvalFrame()` |

#### 4.1.2 词法分析——Tokenizer

```python
import tokenize
import io

source = """
def f(x):

for tok in tokens[:10]:
    print(f"{tok.type:2d} {tokenize.tok_name[tok.type]:10s} {tok.string!r:15s} L{tok.start[0]}")
```

输出：


CPython的词法分析器是用C手写的（`Parser/tokenizer.c`），而非lex/yacc生成。

### 4.2 字节码——PVM的指令集

#### 4.2.1 PyCodeObject结构

```c
// CPython Include/code.h (简化版)
typedef struct {
    PyObject_HEAD
    
    int co_argcount;           // 位置参数数量
    int co_posonlyargcount;    // 仅位置参数数量 (3.8+)
    int co_kwonlyargcount;     // 仅关键字参数数量
    int co_nlocals;            // 局部变量数量
    int co_stacksize;          // 值栈大小
    int co_flags;              // 标志位（生成器、协程等）
    
    PyObject *co_code;         // 字节码指令序列 (bytes)
    PyObject *co_consts;       // 常量元组
    PyObject *co_names;        // 名称元组（全局变量名、属性名）
    PyObject *co_varnames;     // 局部变量名元组
    PyObject *co_freevars;     // 自由变量名元组（闭包捕获）
    PyObject *co_cellvars;     // cell变量名元组（被闭包捕获的变量）
    
    PyObject *co_filename;     // 源文件名
    PyObject *co_name;         // 函数/模块名
    int co_firstlineno;        // 首行行号
    
    PyObject *co_lnotab;       // 行号映射表（Python 3.10-）
    // Python 3.11+: co_linetable, co_endlinetable 等
    
    void *co_extra;            // 扩展空间（特化解释器用）
} PyCodeObject;
```
