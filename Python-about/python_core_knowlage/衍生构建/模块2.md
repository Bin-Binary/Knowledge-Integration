## 三、`__name__` 的双重身份

### 3.1 模块名与脚本的分野

每个 Python 模块都有一个 `__name__` 属性，它有一个双重身份：

1. **被导入时**：`__name__` = 模块的全限定名（如 `'myproject.core.engine'`）
2. **被直接运行时**：`__name__` = `'__main__'`

这个设计解决了一个核心问题：**同一份 `.py` 文件既可以作为模块被导入，也可以作为脚本直接运行**——两种用途需要对模块级初始化代码有不同的行为。

```python
# mymodule.py
def main():
    print("执行主逻辑")

if __name__ == '__main__':
    main()  # 直接运行时执行，被导入时不执行
```

当 `python mymodule.py` 时，CPython 设置 `__name__ = '__main__'`，条件为真，`main()` 执行。当 `import mymodule` 时，`__name__ = 'mymodule'`，条件为假，`main()` 不执行。这是 Python 最基本的**可复用模块**与**可执行脚本**的统一机制。

### 3.2 `__main__` 守卫的必要性

没有 `__main__` 守卫的模块会在被导入时执行所有模块级代码：

```python
# bad_module.py（没有 __main__ 守卫）
print("开始处理数据...")
data = expensive_computation()  # 导入时就执行！
save_results(data)

# 任何其他模块只需 import bad_module，就会触发上面的全部代码
import bad_module  # 副作用：打印信息、执行耗时计算、写入文件
```

```python
# good_module.py（有 __main__ 守卫）
def main():
    print("开始处理数据...")
    data = expensive_computation()
    save_results(data)

if __name__ == '__main__':
    main()  # 只有直接运行时才执行

# 其他模块导入时，只获得函数定义，不触发任何执行
import good_module  # 无副作用
good_module.main()  # 需要显式调用
```

**`__main__` 守卫的本质**：它利用 `__name__` 的双重身份，将"模块级副作用"与"模块定义"区分开来。导入模块时只需要定义（函数、类、常量），不需要执行。直接运行时才需要触发入口逻辑。这是 Python 中**模块作为库**和**模块作为脚本**两种角色的分界线。

### 3.3 `-m` 标志——带包上下文运行模块

`python -m package.module` 与 `python package/module.py` 有本质区别：

```python
# 项目结构:
# myapp/
#   __init__.py
#   runner.py → from . import config; print("running")
#   config.py

# 方式1: 直接运行文件
python myapp/runner.py
# __name__ = '__main__', __package__ = None 或 ''
# from . import config → ImportError（无法解析相对导入）

# 方式2: 模块方式运行
python -m myapp.runner
# __name__ = '__main__', __package__ = 'myapp'
# from . import config → 成功（__package__ 提供了相对导入的基点）
```

| 运行方式 | `__name__` | `__package__` | 相对导入 | `sys.path[0]` |
|:---|:---|:---|:---|:---|
| `python file.py` | `'__main__'` | `None` | 失败 | 文件所在目录 |
| `python -m pkg.mod` | `'__main__'` | `'pkg'` | 成功 | 当前工作目录 |
| `import pkg.mod` | `'pkg.mod'` | `'pkg'` | 成功 | 取决于 `sys.path` |

**实验：`__name__` 在不同执行上下文中的值**

```python
# name_test.py
import sys

print(f"__name__ = {__name__!r}")
print(f"__package__ = {__package__!r}")
print(f"__file__ = {__file__!r}")
print(f"sys.path[0] = {sys.path[0]!r}")

# 场景1: 直接运行
# python name_test.py
# __name__ = '__main__'
# __package__ = None
# __file__ = '/path/name_test.py'
# sys.path[0] = '/path' (文件所在目录)

# 场景2: 作为模块运行
# python -m name_test (假设 name_test.py 在当前目录)
# __name__ = '__main__'
# __package__ = ''
# __file__ = '/cwd/name_test.py'
# sys.path[0] = '' (当前工作目录)

# 场景3: 被导入
# import name_test (在其他模块中)
# __name__ = 'name_test'
# __package__ = ''
# __file__ = '/path/name_test.py'
# sys.path[0] = (取决于主脚本)
```

### 3.4 `__main__` 模块也是 `sys.modules` 中的一员

直接运行脚本时，CPython 也会将脚本注册到 `sys.modules['__main__']`：

```python
# 在任何脚本中直接运行
import sys
print(__name__)                    # '__main__'
print(sys.modules['__main__'])     # <module '__main__' from '...'>
print(sys.modules['__main__'] is sys.modules['__name__'])  # True — 它们是同一个对象

# 可以通过 sys.modules['__main__'] 访问脚本的全局命名空间
print(sys.modules['__main__'].__dict__ is globals())  # True
```

`__main__` 也是一个正规的 `PyModuleObject`，只是它的 `__name__` 被特殊设置为 `'__main__'`。它同样有 `__dict__`，同样受 `sys.modules` 缓存管理。这个细节解释了为什么 `python -c` 和交互式解释器也有 `__name__ == '__main__'`——它们各自创建了 `__main__` 模块对象。

## 四、`sys.path` 与搜索机制

### 4.1 `sys.path` 的组成

`sys.path` 是一个字符串列表，决定了 Python 在哪些目录中搜索模块。当 PathFinder 执行 `find_spec` 时，它遍历 `sys.path` 中的每一条路径，依次查找模块文件。

`sys.path` 的组成按初始化顺序：

```
sys.path 组成（按优先级）

1. 脚本目录（或 '' 表示交互模式下的当前目录）
   python script.py → sys.path[0] = 脚本所在目录
   python -m pkg.mod → sys.path[0] = 当前工作目录('' 或 cwd)
   交互模式 → sys.path[0] = ''

2. PYTHONPATH 环境变量
   export PYTHONPATH=/my/libs:/opt/python
   → sys.path 在位置2处插入这些路径

3. 安装依赖的默认路径
   - 标准库目录: /usr/lib/python3.11 (Linux), C:\Python311\Lib (Windows)
   - site-packages: /usr/lib/python3.11/site-packages
   - 第三方库安装位置 (pip install 的目标目录)

4. .pth 文件
   site-packages/*.pth 文件中每行一个路径，追加到 sys.path
   用途: 不修改 PYTHONPATH 也能添加搜索路径

5. 运行时修改
   sys.path.append('/new/path')
   sys.path.insert(0, '/priority/path')  # 插入到最前面，最高优先级
```

```python
import sys

for i, p in enumerate(sys.path):
    label = ""
    if i == 0:
        label = " ← 脚本目录/当前目录"
    elif 'site-packages' in p:
        label = " ← 第三方库 (pip install)"
    elif 'python3' in p.lower() and 'lib' in p.lower() and 'site' not in p:
        label = " ← 标准库"
    print(f"  [{i}] {p}{label}")
```

**搜索优先级的陷阱**

由于 `sys.path` 是有序列表，**同名的模块按照列表中路径的先后顺序被找到**。如果 `sys.path[0]`（脚本目录）下有一个与标准库同名的 `.py` 文件，它会屏蔽标准库模块：

```python
# 在当前目录下创建一个 email.py
# email.py
print("这不是标准库的 email！")

# 在另一个脚本中
import email  # 导入的是当前目录的 email.py，不是标准库的 email！
```

这是 `sys.path[0]` 设计的直接后果——脚本目录的优先级最高，方便开发但不方便隔离。避免方式：不要用标准库模块名命名自己的文件。

### 4.2 路径钩子与元路径

`sys.path` 的搜索不是简单的"遍历目录"，而是通过 `sys.path_hooks` 这一可扩展机制来实现的。

**`sys.path_hooks`——路径条目钩子**

`sys.path_hooks` 是一个可调用对象列表，每个对象接受一个路径字符串，返回一个路径导入器（`PathEntryFinder`）或抛出 `ImportError`。PathFinder 遍历 `sys.path` 时，对每条路径调用 `sys.path_hooks` 中的钩子，直到找到能处理该路径的钩子。

```python
import sys

for hook in sys.path_hooks:
    print(hook)
# 典型输出:
# <class 'zipimport.zipimporter'>              ← 处理 .zip 文件路径
# <class '_frozen_importlib_external.WindowsPathFinder'>  ← 处理 Windows 目录路径
```

```python
# PathFinder 的搜索逻辑（简化）
class PathFinder:
    @classmethod
    def _get_spec(cls, fullname, path, target=None):
        for path_entry in path:  # path = sys.path (或包的 __path__)
            # 先查缓存
            importer = sys.path_importer_cache.get(path_entry)
            if importer is None:
                # 遍历 path_hooks，找到一个能处理此路径的
                for hook in sys.path_hooks:
                    try:
                        importer = hook(path_entry)
                        sys.path_importer_cache[path_entry] = importer
                        break
                    except ImportError:
                        continue
                else:
                    # 没有钩子能处理，PathFinder 设置为 None（表示跳过）
                    sys.path_importer_cache[path_entry] = None
                    continue

            if importer is not None:
                spec = importer.find_spec(fullname, target)
                if spec is not None:
                    return spec
        return None
```

**`sys.path_importer_cache`——路径导入器缓存**

为了避免每次导入都遍历 `sys.path_hooks`，PathFinder 维护了一个缓存 `sys.path_importer_cache`：

```python
import sys

# 查看路径条目与导入器的映射
for path, importer in list(sys.path_importer_cache.items())[:5]:
    if importer is not None:
        print(f"  {path} → {type(importer).__name__}")
    else:
        print(f"  {path} → None (无法处理)")
```

**zipimport——从 ZIP 文件导入模块**

Python 可以直接从 `.zip` 文件中导入模块，这是 `zipimport.zipimporter` 提供的能力：

```python
import zipfile
import tempfile, os

# 创建一个包含模块的 zip 文件
demo_dir = tempfile.mkdtemp()
zip_path = os.path.join(demo_dir, 'mymodules.zip')

with zipfile.ZipFile(zip_path, 'w') as zf:
    zf.writestr('zipmod.py', 'ZIP_MESSAGE = "Hello from ZIP!"\nprint("zipmod imported from ZIP")')

# 将 zip 文件路径加入 sys.path
import sys
sys.path.insert(0, zip_path)

import zipmod
# 输出: zipmod imported from ZIP
print(zipmod.ZIP_MESSAGE)  # "Hello from ZIP!"

# 验证 zipimporter 被使用
print(type(sys.path_importer_cache[zip_path]))
# <class 'zipimport.zipimporter'>

# 查看模块的 __file__（指向 zip 内的路径）
print(zipmod.__file__)  # '...mymodules.zip/zipmod.py'
```

这就是 Python egg 格式和 wheel 格式的基础——它们本质上是 `.zip` 文件（或 `.egg`/`.whl` 本身就是 zip 格式），Python 可以直接从中导入模块而无需解压。

### 4.3 自定义元路径查找器

Python 的导入机制最强大的扩展点是 `sys.meta_path`——你可以注册自定义的元路径查找器，完全接管特定模块的查找和加载：

```python
import sys
import importlib.abc
import importlib.machinery
import types

class VirtualModuleFinder(importlib.abc.MetaPathFinder):
    """虚拟模块查找器：在内存中创建模块，无需真实文件"""

    def __init__(self, registry):
        self.registry = registry  # {name: source_code}

    def find_spec(self, fullname, path, target=None):
        if fullname in self.registry:
            loader = VirtualModuleLoader(self.registry[fullname])
            return importlib.machinery.ModuleSpec(
                fullname, loader,
                origin=f'<virtual:{fullname}>'
            )
        return None

class VirtualModuleLoader(importlib.abc.Loader):
    def __init__(self, source):
        self.source = source

    def create_module(self, spec):
        return None  # 使用默认创建逻辑

    def exec_module(self, module):
        code = compile(self.source, module.__spec__.origin, 'exec')
        exec(code, module.__dict__)

# 注册
registry = {
    'math_plus': 'import math\nPI = math.pi\ndef circle_area(r): return PI * r * r\n',
    'greet': 'def hello(name): return f"Hello, {name}!"\n',
}
finder = VirtualModuleFinder(registry)
sys.meta_path.insert(0, finder)

# 现在可以正常导入虚拟模块
import math_plus
print(math_plus.circle_area(5))  # 78.53981633974483

import greet
print(greet.hello("World"))      # "Hello, World!"

# 清理
sys.meta_path.remove(finder)
del sys.modules['math_plus']
del sys.modules['greet']
```

**Django/Flask 中 `settings` 模块的自定义导入**

许多 Python Web 框架利用 `sys.meta_path` 实现配置模块的灵活导入。例如 Django 的 `DJANGO_SETTINGS_MODULE` 环境变量——它指定一个 Python 模块路径（如 `myproject.settings`），Django 在启动时通过 `importlib.import_module` 动态导入该模块，从中读取配置。这本质上是 `import_module` 对字符串模块名的动态加载能力。

### 4.4 `__pycache__` 与字节码缓存

当 Python 首次导入一个 `.py` 文件时，SourceFileLoader 会编译源码为字节码并缓存到 `__pycache__/` 目录：

```
myproject/
├── __pycache__/
│   ├── __init__.cpython-311.pyc    ← 编译后的字节码
│   ├── utils.cpython-311.pyc
│   └── core/
│       └── __pycache__/
│           ├── __init__.cpython-311.pyc
│           └── engine.cpython-311.pyc
├── __init__.py
├── utils.py
└── core/
    ├── __init__.py
    └── engine.py
```

`.pyc` 文件的命名规则：`{module_name}.cpython-{version}.pyc`，包含版本号以避免不同 Python 版本间的 `.pyc` 冲突。

```python
# 查看字节码缓存行为
import importlib

# __pycache__ 启用/禁用
import sys
print(sys.pycache_prefix)  # None = 默认位置（源文件旁的 __pycache__/）

# 优化级别: -O (移除 assert) → .opt-1.pyc, -OO (移除 assert + docstring) → .opt-2.pyc
# 编译时检查源码修改时间（mtime），如果 .py 比 .pyc 新则重新编译
```

## 五、`import` 的高级模式

### 5.1 `__all__`——控制 `from mod import *` 的导出

`__all__` 是一个字符串列表，定义了 `from module import *` 时应该导出哪些名字：

```python
# mymodule.py
__all__ = ['public_func', 'PUBLIC_CONST']

def public_func():
    """公开 API"""
    pass

def _private_helper():
    """内部辅助函数"""
    pass

PUBLIC_CONST = 42
_INTERNAL_CONST = "should not be exported"
```

```python
# 使用者
from mymodule import *

print(public_func)     # 可用
print(PUBLIC_CONST)    # 可用
print(_private_helper) # NameError: 未定义
print(_INTERNAL_CONST) # NameError: 未定义
```

没有 `__all__` 时，`from mod import *` 导入所有不以 `_` 开头的名字（约定优于配置）。有了 `__all__`，只导入列表中的名字（显式优于隐式）。

**注意**：`__all__` 只影响 `import *`，不影响显式的 `from mod import name`：

```python
from mymodule import _private_helper  # 正常工作，不受 __all__ 影响
```

`__all__` 的最佳实践：始终在公开 API 的模块中定义 `__all__`，明确导出接口，防止内部符号泄漏。

### 5.2 动态导入——`importlib.import_module`

`import` 语句要求模块名是一个标识符，不能是变量或字符串拼接。但许多场景需要根据字符串动态导入：

```python
import importlib

# 基本用法
mod = importlib.import_module('json')
print(mod.dumps({"key": "value"}))  # '{"key": "value"}'

# 导入子模块
decoder = importlib.import_module('json.decoder')
print(decoder.JSONDecoder)  # <class 'json.decoder.JSONDecoder'>

# 动态模块名（import 语句做不到的）
module_names = ['os', 'sys', 'json']
for name in module_names:
    mod = importlib.import_module(name)
    print(f"{name}: {mod}")

# 根据配置动态加载
import os
db_driver_name = os.getenv('DB_DRIVER', 'sqlite3')
db_driver = importlib.import_module(db_driver_name)
```

`import_module` 的行为与 `import` 语句完全等价——它走同样的 `sys.modules` 缓存、同样的元路径搜索、同样的加载流程。唯一的区别是模块名可以是运行时确定的字符串。

### 5.3 懒导入——延迟到使用时

将 `import` 语句放在函数内部而非模块顶层，使得模块只在函数被调用时才加载：

```python
# 懒导入: 避免启动时加载所有依赖
def process_image(path):
    import PIL.Image          # 只在需要图像处理时才加载 PIL
    img = PIL.Image.open(path)
    return img.resize((100, 100))

def analyze_text(text):
    import nltk               # 只在需要 NLP 时才加载 nltk
    return nltk.word_tokenize(text)
```

懒导入的优势：

1. **减少启动时间**：仅在需要时才加载大型库
2. **可选依赖**：某些依赖可能不存在，懒导入允许优雅降级
3. **避免循环导入**：如前所述，函数内导入是解决循环依赖的常用手段

Python 3.7+ 的 `importlib.util.LazyLoader` 提供了模块级的懒导入支持：

```python
import importlib.util

def lazy_import(name):
    spec = importlib.util.find_spec(name)
    if spec is None:
        raise ModuleNotFoundError(name)
    loader = importlib.util.LazyLoader(spec.loader)
    spec.loader = loader
    module = importlib.util.module_from_spec(spec)
    sys.modules[name] = module
    loader.exec_module(module)
    return module

# 模块对象创建后，实际加载延迟到首次属性访问
csv_mod = lazy_import('csv')  # 此时 csv 模块尚未真正执行
print(csv_mod.reader)         # 首次访问属性时才真正加载
```

### 5.4 条件导入——平台兼容性

```python
# 平台特定的模块
import sys

if sys.platform == 'win32':
    import winreg as registry
elif sys.platform == 'darwin':
    import plistlib as registry
else:
    import registry  # 自定义回退

# 可选依赖的优雅降级
try:
    import rapidjson as json
except ImportError:
    import json  # 回退到标准库

# Python 版本兼容
try:
    from asyncio import to_thread  # Python 3.9+
except ImportError:
    async def to_thread(func, *args):
        loop = asyncio.get_event_loop()
        return await loop.run_in_executor(None, func, *args)
```

条件导入的关键：**`except ImportError` 是处理可选依赖的正确方式**，而不是 `except Exception`（后者会掩盖真正的错误）。

### 5.5 导入副作用——模块级代码的执行

Python 的设计选择——`import = execute module code`——意味着模块级代码在导入时无条件执行。这既是强大的能力也是潜在的问题：

```python
# 模块级代码作为初始化
# config.py
import os
SETTINGS = {
    'DEBUG': os.getenv('DEBUG', 'false').lower() == 'true',
    'PORT': int(os.getenv('PORT', '8000')),
}
# import config 时，SETTINGS 立即可用

# 模块级代码作为注册
# plugins/auth.py
from framework import register_plugin
register_plugin('auth', AuthPlugin)  # 导入即注册
# 使用者只需 import plugins.auth，注册自动完成

# 模块级代码的危险
# dangerous.py
import shutil
shutil.rmtree('/tmp/old_cache')  # 导入就删文件！
# 任何 import dangerous 都会触发副作用
```

**设计原则**：

- 模块级代码只应做**无副作用的初始化**（定义常量、创建函数/类对象）
- 有副作用的操作（文件 I/O、网络请求、修改全局状态）应放在函数中，由调用者显式触发
- `if __name__ == '__main__'` 守卫是隔离脚本行为与模块行为的标准手段

## 六、常见陷阱

### 陷阱 1：循环导入——最隐蔽的运行时炸弹

```python
# models/user.py
from models.order import Order

class User:
    def get_orders(self):
        return Order.query.filter_by(user_id=self.id)

# models/order.py
from models.user import User

class Order:
    def get_user(self):
        return User.query.get(self.user_id)

# 错误:
# ImportError: cannot import name 'Order' from partially initialized module 'models.order'
# (most likely due to a circular import)
```

**原因**：`import models.user` → 执行到 `from models.order import Order` → `import models.order` → 执行到 `from models.user import User` → `sys.modules['models.user']` 存在但未完全初始化（`User` 类尚未定义）→ `ImportError`。

**修复**：延迟导入或提取公共依赖：

```python
# 修复方案: 延迟导入
# models/order.py
class Order:
    def get_user(self):
        from models.user import User  # 延迟到方法调用时
        return User.query.get(self.user_id)
```

### 陷阱 2：`from mod import *` 污染命名空间

```python
from os import *
from os.path import *

# os 模块中有 open()，它覆盖了内置的 open()！
f = open("file.txt")  # 调用的是 os.open()，不是内置 open()
# TypeError: open() takes at least 2 arguments — os.open 需要 flags 参数

# 另一个常见案例:
from numpy import *
from math import *
# numpy.sin 和 math.sin 行为不同，谁覆盖了谁取决于导入顺序
```

**原因**：`from mod import *` 将模块的所有公开名字（或 `__all__` 中的名字）倒入当前命名空间，可能与已有名字冲突。Python 的名字空间是平坦字典，同键覆盖不报警。

**避免**：永远不要使用 `import *`。用 `import mod` 或 `from mod import specific_name`。

### 陷阱 3：`reload` 不更新已持有的引用

```python
import importlib

# mod.py → X = [1, 2, 3]
import mod

original_list = mod.X  # 引用旧列表

# 修改 mod.py → X = [4, 5, 6]
importlib.reload(mod)

print(mod.X)           # [4, 5, 6] — 模块命名空间已更新
print(original_list)   # [1, 2, 3] — 旧引用仍然指向旧列表！

# 因为 reload 更新 __dict__，但 original_list 绑定的是旧列表对象
# 旧列表对象仍然存在（被 original_list 引用），不会被回收
```

**原因**：`reload()` 用新代码重新执行模块，更新 `module.__dict__`。但其他模块中通过 `from mod import X` 或 `original = mod.X` 获取的引用是**独立的绑定**，指向旧对象。`reload` 不遍历进程中的所有命名空间去更新绑定。

**避免**：

- 使用 `mod.X` 而非 `from mod import X`（前者总是查 `mod.__dict__`，后者是独立绑定）
- 在生产环境中不使用 `reload`，重启进程是最可靠的方式
- 开发时使用自动重载工具（如 `uvicorn --reload`、Django 的 `runserver`）

### 陷阱 4：脚本直接运行时相对导入失效

```python
# myproject/utils/helpers.py
from .. import config  # 相对导入

# 直接运行:
python myproject/utils/helpers.py
# ImportError: attempted relative import with no known parent package

# 原因: 直接运行时 __package__ 为 None，无基准包
```

**修复**：始终用 `python -m` 运行带相对导入的模块：

```bash
python -m myproject.utils.helpers  # 正确
```

或在项目根目录设置入口脚本：

```python
# run.py（项目根目录）
from myproject.utils.helpers import main
main()
```

### 陷阱 5：同名模块遮蔽标准库

```python
# 在当前目录下创建了 random.py（或者有同名文件）
# random.py → print("This is my random!")

import random  # 导入的是当前目录的 random.py，不是标准库
# 输出: This is my random!

# 因为此 random.py 没有 randint 等函数
random.randint(1, 10)  # AttributeError
```

**原因**：`sys.path[0]`（脚本目录）优先级最高，同名文件先于标准库被发现。

**避免**：

- 永远不要用标准库模块名命名自己的文件
- 使用 `python -m` 运行而非直接 `python file.py`（当前工作目录可能不同）
- 使用 IDE 的模块名冲突检测

```python
if 'demo' in sys.modules:
```

```python
# pkg/__init__.py (空)
# pkg/a.py
from . import b
A_VALUE = 100

from . import a
B_VALUE = 200
```

运行: `python -c "from pkg import a"`

**题目 3**：解释以下三种导入方式的运行时行为差异，以及它们在 `sys.modules` 中产生的影响。

```python
import os.path
from os import path
import os; path = os.path
```

<summary>参考答案</summary>

**题目 1**：

1. `import demo` → 首次导入：查找 demo.py → 编译 → 执行 → 打印 `"demo loaded"` → `sys.modules['demo'] = <module>` → 当前命名空间绑定 `demo`
2. `import demo` → 二次导入：`sys.modules` 已有 → 直接返回缓存 → **不打印**"demo loaded"
3. `from demo import X` → `sys.modules` 已有 → 从 `demo.__dict__['X']` 取值 → 当前命名空间绑定 `X = 10` → **不打印**
4. `print(X)` → `10`
5. `del sys.modules['demo']` → 清除缓存
6. `import demo` → 首次导入（缓存已清除）→ 查找 → 编译 → 执行 → 打印 `"demo loaded"` → 重新缓存 → 绑定 `demo`
7. `print(demo.X)` → `10`

**题目 2**：

错误: `ImportError: cannot import name 'a' from partially initialized module 'pkg.b'`

分析: `from pkg import a` → 导入 `pkg`（成功）→ 导入 `pkg.a` → 执行 `pkg/a.py` → `from . import b` → 导入 `pkg.b` → 执行 `pkg/b.py` → `from . import a` → `sys.modules` 中已有 `pkg.a`（部分初始化，`A_VALUE` 尚未定义）→ 尝试从 `pkg.a` 导入 `a` 失败（属性不存在）。

修复方式1：延迟导入：

```python
# pkg/a.py
A_VALUE = 100
def get_b_value():
    from . import b
    return b.B_VALUE
```

修复方式2：将共享数据提取到独立模块：

```python
# pkg/constants.py
A_VALUE = 100
B_VALUE = 200

# pkg/a.py
from . import constants
# pkg/b.py
from . import constants
```

**题目 3**：

1. `import os.path`：导入 `os`（加载并缓存到 `sys.modules['os']`），再导入 `os.path`（加载并缓存到 `sys.modules['os.path']`）。当前命名空间绑定 `os`（顶层模块），`os.path` 通过 `os.__dict__['path']` 访问。

2. `from os import path`：导入 `os`（同上），从 `os.__dict__['path']` 取出 `path` 对象，绑定到当前命名空间的 `path`。不绑定 `os`。`sys.modules` 中有 `os` 和 `os.path`。

3. `import os; path = os.path`：导入 `os`，从 `os.path` 取属性赋值给 `path`。等价于方式2，但显式分两步。`sys.modules` 中有 `os`（和 `os.path`，如果 `os.__init__` 自动加载了 `path`）。

三者差异：方式1绑定 `os`（通过 `os.path` 访问），方式2和3绑定 `path`（直接访问，不带模块前缀）。`sys.modules` 影响相同——`os` 和 `os.path` 都会被缓存。

## 八、导入系统的解释力——N个疑惑的统一回溯

理解 Python 导入系统的最大收益，不是记住 `import` 的几种语法，而是获得一个**统一的解释框架**：表面上五花八门的 Python 导入行为，回溯到 `PyModuleObject` 的命名空间、`sys.modules` 的缓存语义、`sys.meta_path` 的搜索管线和 `importlib._bootstrap` 的加载流程，就不再是散落的知识点，而是**同一套机制的不同运行路径**。

下表汇总了常见疑惑，统一标注其导入系统根因：

| # | 表象疑惑 | 导入系统根因 | 本文章节 |
|:--|:---|:---|:---|
| 1 | 为什么第二次 `import` 不执行模块代码？ | `sys.modules` 缓存：首次导入加载+执行+缓存，后续直接返回缓存对象 | §1.3 |
| 2 | 为什么 `from mod import name` 仍加载整个模块？ | `from ... import` 分两步：先完整导入模块（与 `import mod` 等价），再从 `__dict__` 取属性 | §1.3 |
| 3 | 为什么循环导入会报 `ImportError`？ | `_load_unlocked` 在 `exec_module` 之前就注册到 `sys.modules`，后续导入得到部分初始化对象 | §2.4 |
| 4 | 为什么 `reload` 不更新其他模块的引用？ | `reload` 只更新 `module.__dict__`，`from mod import X` 创建的独立绑定不受影响 | §1.3 |
| 5 | 为什么直接运行脚本时相对导入失败？ | 直接运行 `__name__='__main__'`, `__package__=None`，相对导入无基准包可解析 | §2.3 |
| 6 | 为什么 `python -m` 能修复相对导入问题？ | `-m` 走导入流程，`__package__` 正确设置为模块所属包，提供相对导入基准 | §2.3 |
| 7 | 为什么目录加 `__init__.py` 就变成包？ | PathFinder 遇到含 `__init__.py` 的目录会创建 `ModuleSpec` 并设置 `__path__`，使其成为可搜索的命名空间 | §2.1 |
| 8 | 为什么没有 `__init__.py` 的目录也能当包？ | PEP 420 命名空间包：PathFinder 遍历 `sys.path` 收集同名目录，合并为 `__path__` 列表 | §2.2 |
| 9 | 为什么同名模块会遮蔽标准库？ | `sys.path[0]`（脚本目录）优先级最高，同名列在前面的路径先被找到 | §4.1 |
| 10 | 为什么 `import os.path` 绑定的是 `os` 而非 `os.path`？ | `IMPORT_NAME` 字节码返回顶层模块，`from ... import` 才通过 `IMPORT_FROM` 取子属性 | §1.2 |
| 11 | 为什么 `__pycache__` 存在？ | SourceFileLoader 将编译后的字节码缓存为 `.pyc`，避免重复编译，mtime 变化时自动更新 | §4.4 |
| 12 | 为什么修改 `.py` 后不用手动删除 `.pyc`？ | SourceFileLoader 比较源文件和 `.pyc` 的 mtime，源文件更新时自动重编译 | §4.4 |
| 13 | 为什么 `import *` 只导入不以 `_` 开头的名字？ | 默认行为：`dir(mod)` 过滤 `_` 前缀；有 `__all__` 时按列表导出 | §5.1 |
| 14 | 为什么可以用 `importlib.import_module('mod')` 代替 `import mod`？ | 两者走相同的 `_find_and_load` 管线，`import_module` 只是允许运行时确定模块名 | §5.2 |
| 15 | 为什么导入 `.zip` 文件中的模块可行？ | `zipimport.zipimporter` 是 `sys.path_hooks` 中注册的钩子，处理 `.zip` 路径条目 | §4.2 |
| 16 | 为什么自定义 finder/loader 能让虚拟模块可用？ | `sys.meta_path` 上的 finder 在 PathFinder 之前被查询，返回有效 `ModuleSpec` 就能接管加载 | §4.3 |
| 17 | 为什么 `__main__` 守卫能防止导入时执行代码？ | 直接运行 `__name__='__main__'`→守卫为真→执行；导入时 `__name__='模块名'`→守卫为假→跳过 | §3.1 |
| 18 | 为什么 `__name__` 有双重身份？ | CPython 在直接运行时将 `__name__` 设为 `'__main__'`，导入时设为全限定名——同一文件两种角色需要区分 | §3.1 |
| 19 | 为什么 `sys.modules` 是进程级全局缓存？ | 同一进程中所有模块共享 `sys.modules`，这是单进程内模块唯一性的保证 | §1.3 |
| 20 | 为什么 `from . import` 必须在包内使用？ | 相对导入用 `__package__` 计算 `from` 的起始包，非包模块 `__package__` 为空，无法定位 | §2.3 |

每一个疑惑都不是独立的知识点——它们的答案都回溯到 `PyModuleObject`（模块是对象、`__dict__` 是命名空间、`__name__`/`__package__`/`__path__` 是元数据）、`sys.modules`（导入缓存、重入语义、循环依赖的根因）、`sys.meta_path`/`sys.path_hooks`（搜索管线的可扩展架构）和 importlib._bootstrap 的加载流程（创建→注册→执行的顺序决定了循环导入的行为）这四根支柱。导入系统就是 Python 从"脚本"到"项目"的元语言：**理解它，模块、包、命名空间、搜索路径、缓存、循环依赖这些概念就不再是需要分别记忆的规则，而是同一套机制在不同条件下的自然推论**。
