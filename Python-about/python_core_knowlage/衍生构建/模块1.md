# Python核心基础（八）：从脚本到项目——模块/包/导入系统

## 引言

C 用 `#include` 做代码组织——它是预处理器的文本替换，把一个文件的源码机械地插入另一个文件，没有命名空间，没有隔离，多次 include 同一头文件需要 `#ifndef` 守卫来防止重复。Java 用 classpath + 包做组织——一个类一个文件，目录结构强制等于包名，classpath 是一个扁平的 URL 列表，类加载器在运行时按需搜索。Go 用 `go.mod` 做组织——模块有显式的版本声明，依赖是严格的有向无环图，编译器在构建时解析一切，不存在运行时的导入机制。Rust 用 crate 和 `mod` 做组织——crate 是编译单元，`mod` 声明模块树，`use` 引入路径，所有权与借用检查器让跨模块的共享有严格的编译期规则。

Python 做了一个足够激进的决定：**`import` = 执行模块代码 + 创建模块对象 + 缓存到 `sys.modules`**。

这不是文本替换——模块代码在独立的命名空间执行，`import` 的副作用严格隔离。这不是编译期解析——Python 的 `import` 在运行时发生，可以用字符串拼接动态构造模块名，可以在条件分支中按需导入，甚至可以自定义 finder/loader 完全接管导入流程。这不是刚性约束——`__init__.py` 可以只留空也可定义整个包的公开 API，命名空间包允许跨目录拼合同一包，`sys.path` 可以在运行时任意修改。但极致的灵活有代价：模块级代码在 `import` 时执行意味着**导入即产生副作用**，`sys.modules` 的进程级缓存让**同一进程中不同代码无法看到同一模块的不同版本**，而自由的双向导入让**循环依赖**成为一个比其他语言更容易陷入的陷阱。

理解 Python 的模块/包/导入系统，不只是知道 `import` 语句的几种写法。它是读懂 Python 从"脚本"走向"项目"的关键：为什么一个 `.py` 文件就是一个模块？为什么目录加 `__init__.py` 就变成了包？`from foo import bar` 时到底发生了什么？为什么第二次 `import` 不再执行模块代码？`__name__ == "__main__"` 这个守卫到底在守什么？为什么循环导入会报错，又该怎么解？这些问题的答案都回溯到同一个机制——**CPython 的 import machinery**：`PyModuleObject` 承载命名空间，`sys.modules` 做进程级缓存，`sys.meta_path` 上的 finder 和 loader 构成搜索与加载管线，而字节码层面的 `IMPORT_NAME` 指令是这一切的入口点。

本文将追踪一次 `import` 从**触发字节码**到**返回模块对象**的完整管线，用可运行的代码逐步揭开 `PyModuleObject` 的内部结构、`importlib._bootstrap` 的核心流程、`sys.path` 与元路径的搜索机制，以及包/命名空间包/相对导入的设计闭环——你将亲眼看到模块对象如何桥接文件与命名空间，导入缓存如何决定重入行为，以及"从脚本到项目"在运行时究竟意味着什么。

### 四种语言的模块机制对比

| 维度 | C `#include` | Java classpath+包 | Go modules | Python import |
|:---|:---|:---|:---|:---|
| **本质** | 预处理器文本替换 | 类加载器运行时查找 | 编译期依赖图解析 | 运行时执行+对象创建+缓存 |
| **隔离性** | 无隔离，共享全局名字空间 | 包级隔离，`package`声明 | 包级隔离，大写导出 | 模块级隔离，每个模块独立 `__dict__` |
| **命名空间** | 手动前缀/`static` | 目录=包名，强制对应 | `module.function` | 模块 `__dict__` 即命名空间 |
| **重入保护** | `#ifndef` 守卫 | 类加载器双重检查 | 编译器保证唯一 | `sys.modules` 缓存，自动退避 |
| **动态性** | 无（编译前文本替换） | 反射 `Class.forName()` | 无 | `importlib.import_module()`，自定义 finder/loader |
| **副作用** | 无（纯文本） | 类初始化 `<clinit>` | `init()` 函数显式调用 | 模块级代码全部执行 |
| **循环依赖** | 不存在（文本展开无方向） | 编译期可检测，运行时抛 `LinkageError` | 编译期禁止 | 运行时可能部分初始化，`ImportError` |

Python 的设计权衡清晰可见：**极致灵活**（动态导入、运行时修改搜索路径、自定义导入钩子、命名空间包）的代价是**导入副作用不可控**和**循环依赖更隐蔽**。但正是这种灵活性，让 Python 的插件系统、测试框架、动态配置这些在其他语言中需要复杂框架支持的能力，在 Python 中只是 `import` 机制的自然推论。

## 一、模块——一个文件就是一个对象

### 1.1 PyModuleObject——模块的 CPython 内部结构

在 CPython 中，模块不是文件、不是命名空间的抽象概念——它是一个**对象**，一个 `PyObject` 的实例，类型为 `PyModule_Type`。当你写 `import os`，CPython 最终在堆上创建了一个 `PyModuleObject`，其结构如下：

```
PyModuleObject                          ← 继承 PyObject
├── [PyObject 头部, 16B]
│   ├── ob_refcnt  (Py_ssize_t, 8B)
│   └── ob_type    (PyTypeObject*) → &PyModule_Type
├── md_dict      (PyObject*, 8B)        ← 模块的 __dict__，命名空间字典
├── md_name      (PyObject*, 8B)        ← 模块的 __name__
├── md_doc       (PyObject*, 8B)        ← 模块的 __doc__
├── md_state     (PyObject*, 8B)        ← 模块的 __state__（每模块子解释器状态）
└── md_weaklist  (PyObject*, 8B)        ← 弱引用链表
```

核心字段是 `md_dict`——它指向一个普通的 Python `dict` 对象，里面存放着模块命名空间的所有绑定。当你在模块顶层写 `x = 42`、`def foo(): ...`、`class Bar: ...`，这些名字统统写入这个 `dict`。`md_dict` 就是模块的 `__dict__`，也就是模块全局代码执行时的 `f_globals`。

```python
import os

# PyModuleObject 本质上就是一个带名字的 dict 容器
print(type(os))                    # <class 'module'>
print(type(os.__dict__))           # <class 'dict'>
print(os.__name__)                 # 'os'
print(os.__doc__[:50])             # 'OS routines for NT or Posix depending...'

# 模块的 __dict__ 就是模块的全部命名空间
print('path' in os.__dict__)       # True
print(os.__dict__['path'] is os.path)  # True — 直接访问内部 dict
```

模块对象与字典之间的等价关系是理解一切导入行为的基石：**模块 = 一个名字（`__name__`）+ 一个字典（`__dict__`）+ 生命周期管理（`sys.modules` 缓存）**。文件只是模块对象的数据来源，`import` 的真正产物不是文件被"加载"，而是一个 `PyModuleObject` 被创建并注册到 `sys.modules`。

可以用 `ctypes` 直接窥视 `PyModuleObject` 的内存布局，验证 `md_dict` 确实指向 `__dict__`：

```python
import ctypes
import sys

PyModuleObject = None  # CPython 内部结构体大小可测
import os

# 获取模块对象的内存地址
addr = id(os)

# PyObject 头部: ob_refcnt(8B) + ob_type(8B) = 16B
# md_dict 在偏移 16 字节处
dict_ptr = ctypes.c_ssize_t.from_address(addr + 16).value
print(f"md_dict 指针值: {hex(dict_ptr)}")
print(f"os.__dict__ 的 id: {hex(id(os.__dict__))}")
print(f"两者相同: {dict_ptr == id(os.__dict__)}")  # True

# md_name 在偏移 24 字节处
name_ptr = ctypes.c_ssize_t.from_address(addr + 24).value
print(f"md_name 指针与 os.__name__ 的 id 相同: {name_ptr == id(os.__name__)}")
```

> 注意：`ctypes` 直接读取 CPython 堆内存的结果依赖具体的 CPython 版本和编译配置（调试版 CPython 的 `PyModuleObject` 有额外字段）。上面代码在 CPython 3.8-3.12 的标准 64-bit 发布版上验证通过。核心结论不因版本变化：**`md_dict` 就是 `__dict__`**。

再做一个更根本的验证——模块全局代码执行时的 `f_globals` 与模块 `__dict__` 是否真为同一字典：

```python
# module_globals_test.py
x = 42

def show_globals_id():
    return id(globals())

# 在另一个模块中导入
import module_globals_test
print(id(module_globals_test.__dict__) == module_globals_test.show_globals_id())
# True — 模块的 __dict__ IS 它的全局命名空间
```

这不是巧合，而是设计：当 CPython 创建一个模块对象时，先创建一个空 `dict` 赋给 `md_dict`，然后以这个 `dict` 作为 `f_globals` 执行模块的编译后代码对象（`PyCodeObject`）。所有顶层赋值、函数定义、类定义都写入同一个 `dict`——也就是说，模块代码执行完毕后，`__dict__` 里就有了所有名字，而 `import` 返回的对象就是持有这个 `__dict__` 的 `PyModuleObject`。

### 1.2 import 的完整流程——从字节码到模块对象

当你在 Python 中写下 `import foo`，CPython 执行的完整流程比表面看到的复杂得多。它不是简单的"读文件-执行-返回"，而是一个多阶段的管线，涉及缓存查询、元路径搜索、规格构建、模块创建、代码执行和缓存注册。先用一个总览图建立全局视图：

```
import foo 的完整管线

1. 字节码层
   IMPORT_NAME 'foo'  →  调用内置 __import__('foo', globals, locals, [], 0)
       │
2. 缓存查询
   sys.modules['foo'] 存在？  ──→ YES → 直接返回缓存模块对象
       │ NO
3. 元路径搜索 (sys.meta_path)
   ──→ BuiltinImporter.find_spec('foo')     → 无 → 继续
   ──→ FrozenImporter.find_spec('foo')      → 无 → 继续
   ──→ PathFinder.find_spec('foo')          → 发现在 sys.path 中
       │                                       │
       │ PathFinder 遍历 sys.path_hooks       │
       │ 每个 hook 尝试处理 sys.path 条目      │
       │ → 返回 PathEntryFinder               │
       │ → finder.find_spec('foo') → 找到      │
       ↓                                       ↓
4. 构建 ModuleSpec
   spec = ModuleSpec(name='foo', loader=SourceFileLoader, origin='.../foo.py')
       │
5. 创建模块对象
   loader.create_module(spec)  →  通常返回 None (让 importlib 用默认逻辑)
   → importlib._bootstrap._new_module(spec) → 创建空 PyModuleObject
       │
6. 执行模块代码
   loader.exec_module(module)
   → 读取 foo.py → 编译为 PyCodeObject → exec(code, module.__dict__)
   → 所有顶层代码执行，名字写入 module.__dict__
       │
7. 缓存注册
   sys.modules['foo'] = module
       │
8. 返回
   import 语句将模块对象绑定到当前命名空间的名字 'foo'
```

**第一步：字节码层面的入口**

CPython 编译器将 `import foo` 编译为 `IMPORT_NAME` 字节码指令。可以用 `dis` 模块验证：

```python
import dis

def test_import():
    import os

dis.dis(test_import)
#   2           0 LOAD_CONST               0 (0)
#               2 LOAD_CONST               1 (('os',))
#               4 IMPORT_NAME              0 (os)
#               6 STORE_FAST               0 (os)
#               8 LOAD_CONST               2 (None)
#              10 RETURN_VALUE
```

`IMPORT_NAME` 的执行逻辑（CPython `ceval.c` 中的实现）：

1. 从操作数栈获取模块名（`os`）和 `fromlist`（空列表，因为这不是 `from ... import` 语句）
2. 调用内置的 `__import__` 函数：`__import__('os', f_globals, f_locals, [], 0)`
3. 将返回值压入操作数栈
4. `STORE_FAST` 将栈顶的模块对象绑定到局部变量 `os`

对于 `from os import path` 这样的语句，字节码有所不同：

```python
def test_from_import():
    from os import path

dis.dis(test_from_import)
#   2           0 LOAD_CONST               0 (0)
#               2 LOAD_CONST               1 (('path',))
#               4 IMPORT_NAME              0 (os)
#               6 IMPORT_FROM              1 (path)
#               8 STORE_FAST               0 (path)
#              10 POP_TOP
#              12 LOAD_CONST               2 (None)
#              14 RETURN_VALUE
```

关键差异：`fromlist` 不是空列表而是 `('path',)`，多了 `IMPORT_FROM` 指令。`IMPORT_NAME` 返回的是 **顶级模块** `os`（不是 `os.path`），而 `IMPORT_FROM` 从该模块的 `__dict__` 中取出 `path` 属性。这解释了一个重要事实：**`from os import path` 实际上加载了整个 `os` 模块**——`os` 模块全部代码已被执行，`sys.modules['os']` 已存在——只是在当前命名空间只绑定了 `path` 这个名字。

**第二步：`__import__` 的核心——`importlib._bootstrap._find_and_load`**

`__import__` 的实际执行逻辑位于 `importlib._bootstrap` 模块（这是 Python 的启动代码，在 C 层面内嵌在 CPython 解释器中，不对应任何 `.py` 文件）。核心函数是 `_find_and_load`，其简化逻辑如下：

```python
# importlib._bootstrap._find_and_load 的简化逻辑（伪代码）
def _find_and_load(name, import_):
    module = sys.modules.get(name, _NEEDS_LOADING)
    if module is _NEEDS_LOADING:
        # 加锁
        with _ModuleLock(name):
            # 双重检查（类比 Java 的双重检查锁定）
            module = sys.modules.get(name, _NEEDS_LOADING)
            if module is _NEEDS_LOADING:
                # 查找模块规格
                spec = _find_spec(name, ...)
                if spec is None:
                    raise ModuleNotFoundError(name)
                # 创建并加载模块
                module = _load_unlocked(spec)
            # 不完全初始化的模块在此处等待（处理循环导入的等待态）
        # 模块后处理（执行 __spec__._set_fileattr 等）
    if hasattr(module, '__path__'):
        # 包模块：处理子模块导入
        parent = name.rpartition('.')[0]
        ...
    return module
```

```python
def _find_spec(name, path=None, target=None):
    # 遍历 sys.meta_path 上的所有元路径查找器
    for finder in sys.meta_path:
        spec = finder.find_spec(name, path, target)
        if spec is not None:
            return spec
    return None  # 没有找到 → ModuleNotFoundError

def _load_unlocked(spec):
    module = module_from_spec(spec)
    # 先注册到 sys.modules（关键！此时模块可能未完全初始化）
    sys.modules[spec.name] = module
    try:
        spec.loader.exec_module(module)
    except:
        # 加载失败，从缓存中移除（除非已在异常处理中改为占位符）
        if spec.name in sys.modules:
            del sys.modules[spec.name]
        raise
    return module
```

一个至关重要的细节：**模块在 `exec_module` 执行之前就已注册到 `sys.modules`**。这意味着如果模块 A 导入模块 B，而模块 B 又导入模块 A，当 B 执行 `import A` 时，`sys.modules` 中已经有一个 A 的条目（虽然 A 还没执行完）——B 能拿到一个**部分初始化的 A**。这就是循环依赖失效的根因：模块还没完全初始化就被其他模块使用了。

**第三步：元路径查找器（`sys.meta_path`）**

CPython 默认注册三个元路径查找器：

```python
import sys
for finder in sys.meta_path:
    print(finder)
# <class '_frozen_importlib.BuiltinImporter'>      ← 内置模块(如 sys, _io)
# <class '_frozen_importlib.FrozenImporter'>       ← 冻结模块(编译为 C 代码的模块)
# <class '_frozen_importlib_external.PathFinder'>  ← 文件系统路径查找
```

- **BuiltinImporter**：查找 CPython 解释器内嵌的 C 扩展模块（如 `sys`、`_io`、`marshal`）。这些模块不是 `.py` 文件，而是编译进 `python.exe`/`libpython.so` 的 C 代码。
- **FrozenImporter**：查找冻结模块——Python 字节码被编译为 C 数组嵌入二进制中，如 `_frozen_importlib` 本身（bootstrap 必须是冻结模块，因为 `importlib` 需要 `importlib` 来加载自身——鸡生蛋问题的解决方案）。
- **PathFinder**：最常用的查找器，负责在文件系统中搜索 `.py`、`.pyc`、`.pyd`/`.so` 文件。它遍历 `sys.path`，对每条路径调用 `sys.path_hooks` 中的钩子来获取路径导入器（`PathEntryFinder`），再由路径导入器执行实际的文件系统查找。

```python
# PathFinder 的工作流程
import sys

# sys.path_hooks: 路径条目钩子列表
for hook in sys.path_hooks:
    print(hook)
# <class 'zipimport.zipimporter'>             ← 从 .zip 文件导入
# <class '_frozen_importlib_external.WindowsPathFinder'>  ← Windows 文件系统
# <class '_frozen_importlib_external.PathInitializer'>    ← 路径初始化

# sys.path_importer_cache: 已解析的路径条目 → 导入器缓存
for path, importer in list(sys.path_importer_cache.items())[:3]:
    print(f"{path} → {type(importer).__name__}")
```

**第四步：ModuleSpec——模块规格对象**

`ModuleSpec` 是 PEP 451 引入的统一规格对象，封装了模块加载所需的全部信息：

```python
import importlib.util

spec = importlib.util.find_spec('os')
print(spec)
# ModuleSpec(name='os', loader=<class '_frozen_importlib.BuiltinImporter'>, origin='built-in')

spec = importlib.util.find_spec('json')
print(spec)
# ModuleSpec(name='json', loader=<_frozen_importlib_external.SourceFileLoader ...>,
#            origin='.../json/__init__.py', submodule_search_locations=['.../json'])

print(spec.name)          # 'json' — 模块的全限定名
print(spec.loader)        # SourceFileLoader 对象 — 负责创建和执行模块
print(spec.origin)        # '/.../json/__init__.py' — 模块的来源文件
print(spec.submodule_search_locations)  # ['/.../json'] — 包的搜索路径(仅包有此属性)
```

**第五步：Loader——模块加载器**

加载器只需要实现两个方法：

- `create_module(spec)`：创建模块对象。可以返回 `None` 让 importlib 使用默认逻辑（调用 `types.ModuleType` 构造函数）。自定义加载器可以在这里返回预先构造的模块对象。
- `exec_module(module)`：执行模块代码，填充模块的 `__dict__`。对于 `.py` 文件，这是"读取源码→编译→exec"三部曲。

```python
# 自定义加载器的最小实现
import importlib.abc
import types

class StringLoader(importlib.abc.Loader):
    def __init__(self, source_code):
        self.source = source_code

    def create_module(self, spec):
        return None  # 使用默认模块创建逻辑

    def exec_module(self, module):
        code = compile(self.source, module.__spec__.origin, 'exec')
        exec(code, module.__dict__)
```

**实验：完整跟踪一次 `import` 的每个阶段**

```python
import sys
import importlib
import importlib.abc
import importlib.machinery
import types

class TracingFinder(importlib.abc.MetaPathFinder):
    """自定义元路径查找器，打印查找过程的每一步"""

    def find_spec(self, fullname, path, target=None):
        print(f"  [TracingFinder] find_spec('{fullname}', path={path})")
        return None  # 不处理，让后续 finder 继续查找

class TracingLoader(importlib.abc.Loader):
    """自定义加载器，跟踪模块创建和执行"""

    def __init__(self, source):
        self.source = source

    def create_module(self, spec):
        print(f"  [TracingLoader] create_module('{spec.name}')")
        return None

    def exec_module(self, module):
        print(f"  [TracingLoader] exec_module('{module.__name__}')")
        print(f"    模块 __dict__ 的键（执行前）: {list(module.__dict__.keys())[:5]}...")
        code = compile(self.source, f'<{module.__name__}>', 'exec')
        exec(code, module.__dict__)
        print(f"    模块 __dict__ 的键（执行后）: {list(module.__dict__.keys())}")

# 注册自定义查找器
sys.meta_path.insert(0, TracingFinder())

# 用自定义加载器创建并导入模块
spec = importlib.machinery.ModuleSpec(
    name='hello_dynamic',
    loader=TracingLoader('x = 42\ndef greet(): return "hello"'),
    origin='<hello_dynamic>'
)
module = importlib._bootstrap._load_unlocked(spec)

print(f"sys.modules['hello_dynamic'] 存在: {'hello_dynamic' in sys.modules}")
print(f"module.x = {module.x}")
print(f"module.greet() = {module.greet()}")

# 清理
del sys.meta_path[0]
if 'hello_dynamic' in sys.modules:
    del sys.modules['hello_dynamic']
```

输出：

```
  [TracingFinder] find_spec('hello_dynamic', path=None)
  [TracingLoader] create_module('hello_dynamic')
  [TracingLoader] exec_module('hello_dynamic')
    模块 __dict__ 的键（执行前）: ['__name__', '__doc__', '__package__', '__loader__', '__spec__']...
    模块 __dict__ 的键（执行后）: ['__name__', '__doc__', '__package__', '__loader__', '__spec__', ... 'x', 'greet']
sys.modules['hello_dynamic'] 存在: True
module.x = 42
module.greet() = hello
```

可以看到，`exec_module` 执行前模块 `__dict__` 中只有 `importlib` 自动注入的元数据属性（`__name__`, `__doc__`, `__package__`, `__loader__`, `__spec__`），执行后才加入用户定义的 `x` 和 `greet`。这正是"模块级代码在 `import` 时执行"的字面含义。

**实验：测量 `import` 的执行时间**

```python
import importlib
import time

# 首次导入（如果模块尚未被导入）
# 注意：标准库模块可能在解释器启动时已被导入，用一个小模块测试
def measure_import(module_name):
    if module_name in sys.modules:
        # 模块已缓存，重新导入只需查 sys.modules
        start = time.perf_counter()
        importlib.import_module(module_name)
        cached_time = time.perf_counter() - start
        # 清除缓存，测试冷导入
        del sys.modules[module_name]
        start = time.perf_counter()
        importlib.import_module(module_name)
        cold_time = time.perf_counter() - start
        print(f"  缓存导入: {cached_time*1e6:.1f}μs")
        print(f"  冷导入:   {cold_time*1e6:.1f}μs")
        print(f"  差异倍数: {cold_time/max(cached_time, 1e-9):.0f}x")
    else:
        start = time.perf_counter()
        importlib.import_module(module_name)
        cold_time = time.perf_counter() - start
        print(f"  冷导入: {cold_time*1e6:.1f}μs")

measure_import('csv')
# 典型输出:
#   缓存导入: 0.3μs
#   冷导入:   150.0μs
#   差异倍数: 500x

measure_import('collections')
# 典型输出:
#   缓存导入: 0.3μs
#   冷导入:   500.0μs
#   差异倍数: 1666x
```

缓存导入和冷导入的性能差异可达**数百倍到数千倍**——这就是 `sys.modules` 缓存的存在理由。

### 1.3 sys.modules——导入缓存机制

`sys.modules` 是一个 `dict`，键是模块的全限定名（`str`），值是模块对象（`PyModuleObject*`）。它是 Python 导入系统的**全局状态缓存**，决定了导入行为的重入语义。

```python
import sys

# 查看当前已加载的模块数量
print(f"已加载模块数: {len(sys.modules)}")
# 典型值: 100-200（取决于标准库和第三方库的使用情况）

# 查看部分模块
for name in sorted(sys.modules)[:10]:
    print(f"  {name}: {type(sys.modules[name])}")
#  __abc__: <class 'module'>
#  _abc: <class 'module'>
#  _collections: <class 'module'>
#  _collections_abc: <class 'module'>
#  _frozen_importlib: <class 'module'>
#  ...
```

**关键语义：首次导入 vs 后续导入**

```python
import sys

# 创建一个临时模块来演示
module_source = '''
count = 0
print(f"模块代码被执行！count = {count}")
count += 1
'''

import importlib.util
spec = importlib.util.spec_from_loader('demo_cache', loader=None)
demo = importlib.util.module_from_spec(spec)
exec(compile(module_source, 'demo_cache.py', 'exec'), demo.__dict__)
sys.modules['demo_cache'] = demo

# 第一次 import——不会执行模块代码，直接返回缓存
import demo_cache  # 无输出！模块代码不重新执行

# 第二次 import——仍然不会执行
import demo_cache  # 无输出！

# 验证是同一个对象
print(demo_cache is sys.modules['demo_cache'])  # True
```

**importlib.reload()——强制重新执行模块代码**

当确实需要重新加载模块（例如开发中的热更新场景），`importlib.reload()` 可以强制重新执行模块代码：

```python
import importlib
import sys

# 先创建一个文件来演示
import tempfile, os
demo_dir = tempfile.mkdtemp()
demo_path = os.path.join(demo_dir, 'reload_demo.py')
with open(demo_path, 'w') as f:
    f.write('version = 1\nprint(f"reload_demo 被执行, version={version}")\n')
sys.path.insert(0, demo_dir)

import reload_demo
# 输出: reload_demo 被执行, version=1

# 修改模块文件
with open(demo_path, 'w') as f:
    f.write('version = 2\nprint(f"reload_demo 被执行, version={version}")\n')

# 普通 import 无效
import reload_demo  # 无输出！version 仍然是 1
print(reload_demo.version)  # 1

# reload 有效
importlib.reload(reload_demo)
# 输出: reload_demo 被执行, version=2
print(reload_demo.version)  # 2
```

但 `reload` 有一个重要的语义细节：**它更新模块的 `__dict__`，但不更新其他模块中已持有的旧引用**：

```python
# other_module.py（假设已导入）
from reload_demo import version

# 即使 reload 了 reload_demo，other_module.version 仍然是旧值
importlib.reload(reload_demo)
# other_module 的 version 变量是一个独立的绑定，不随 reload 更新
```

这是 `reload` 的根本限制：`from mod import name` 在当前模块的命名空间创建了一个**新的绑定**，这个绑定指向的是导入时刻 `mod.name` 的值。`reload` 只更新 `mod.__dict__`，不会遍历所有导入了 `mod` 的模块去更新它们的绑定。

```python
# reload 的语义：原地更新 __dict__
import importlib

# 场景演示
import tempfile, os
demo_dir = tempfile.mkdtemp()
demo_path = os.path.join(demo_dir, 'reload_ref.py')
with open(demo_path, 'w') as f:
    f.write('value = "original"\ndef get_value(): return value\n')
sys.path.insert(0, demo_dir)

import reload_ref

# 方式1: module.name 引用——reload 后能看到新值
print(reload_ref.value)                     # original
print(reload_ref.get_value())               # original

# 修改文件
with open(demo_path, 'w') as f:
    f.write('value = "updated"\ndef get_value(): return value\n')

importlib.reload(reload_ref)

print(reload_ref.value)                     # updated
print(reload_ref.get_value())               # updated — 函数内部通过 globals()['value'] 访问

# 方式2: from mod import name — reload 后看不到新值
from reload_ref import value
print(value)  # original！不是 "updated"
# value 是当前模块命名空间中的独立绑定，reload 不触及它
```

**部分导入的完整加载语义**

`from foo import bar` 看似只导入 `bar`，但实际行为是：

1. 执行完整的 `import foo`（查找、加载、执行 `foo` 模块的全部代码）
2. 从 `foo.__dict__['bar']` 取出 `bar` 的值
3. 在当前命名空间创建名字 `bar`，绑定到该值
4. `foo` 模块对象本身**不在**当前命名空间中（除非显式 `import foo`）

```python
import sys

# 确认 from ... import 仍然加载了整个模块
if 'pprint' in sys.modules:
    del sys.modules['pprint']

from pprint import pprint  # 整个 pprint 模块被加载和执行

print('pprint' in sys.modules)  # True — 模块已在缓存中
print('pprint' in dir())        # False — 当前命名空间中只有 pprint 函数，没有 pprint 模块
print('pprint' in globals())    # True — 但这个 pprint 是函数对象，不是模块对象
print(type(globals()['pprint']))  # <class 'function'>

print(sys.modules['pprint'] is not globals()['pprint'])  # True
```

### 1.4 模块的其他内部属性

除了 `__dict__`、`__name__`、`__doc__`，每个模块还有几个由 import machinery 自动注入的属性：

```python
import json

print(json.__name__)       # 'json' — 模块全限定名
print(json.__doc__[:30])   # 模块文档字符串
print(json.__package__)    # 'json' — 所属包（顶层模块的 __package__ 为自身名或 None）
print(json.__loader__)     # <_frozen_importlib_external.SourceFileLoader object>
print(json.__spec__)       # ModuleSpec(name='json', ...)
print(json.__file__)       # '/.../json/__init__.py' — 源文件路径
print(json.__path__)       # ['/.../json'] — 包的搜索路径（仅包有此属性）
```

| 属性 | 来源 | 含义 |
|:---|:---|:---|
| `__name__` | importlib 注入 | 模块的全限定名 |
| `__doc__` | 模块顶层 docstring | 模块文档 |
| `__package__` | importlib 注入 | 所属包名，用于相对导入解析 |
| `__loader__` | ModuleSpec | 创建此模块的加载器 |
| `__spec__` | importlib 注入 | 模块规格对象 |
| `__file__` | SourceFileLoader | 源文件路径（内置模块无此属性） |
| `__path__` | 包的 `__init__.py` 执行后设置 | 包的子模块搜索路径（仅包有此属性） |
| `__dict__` | PyModuleObject.md_dict | 模块命名空间字典 |

这些属性不是"附加信息"——它们是 import machinery 的**运行时数据**。`__package__` 决定相对导入的基点，`__spec__` 让加载器可追溯模块的来源，`__path__` 让 PathFinder 知道在哪些目录中搜索子模块。理解这些属性，就理解了包和相对导入的底层机制。

## 二、包——模块的命名空间层级

### 2.1 `__init__.py`——包的入口与命名空间

Python 的包机制是模块机制的自然延伸：**目录 + `__init__.py` = 常规包**。`__init__.py` 是包的入口文件，当包被导入时，Python 执行 `__init__.py`，创建一个模块对象，该对象的 `__name__` 是包名，`__dict__` 是包的命名空间，`__path__` 是包的搜索路径列表。

```
myproject/
├── __init__.py          ← 包入口，导入 myproject 时执行
├── utils.py             ← 子模块 myproject.utils
├── core/
│   ├── __init__.py      ← 子包入口，导入 myproject.core 时执行
│   ├── engine.py        ← 子模块 myproject.core.engine
│   └── config.py        ← 子模块 myproject.core.config
└── api/
    ├── __init__.py
    └── handlers.py
```

```python
# myproject/__init__.py
"""MyProject 包的入口"""
from .utils import helper        # 包级 API 导出
from .core.engine import Engine  # 包级 API 导出

__version__ = "1.0.0"
__all__ = ['helper', 'Engine']

# 导入包时的行为
import myproject
# 等价于: 执行 myproject/__init__.py → 创建模块对象 → 绑定到名字 'myproject'
# 由于 __init__.py 中 from .utils import helper，所以:
print(myproject.helper)          # <function helper at 0x...>
print(myproject.__version__)     # '1.0.0'
```

`__init__.py` 的三种典型用法：

| 用法 | 示例 | 效果 |
|:---|:---|:---|
| 空文件 | `__init__.py`（0字节） | 仅标记目录为包，不定义任何包级 API |
| 包级 API | `from .sub import func; __all__ = ['func']` | 使用者只需 `import pkg; pkg.func()` 即可 |
| 包级初始化 | 在 `__init__.py` 中配置日志、注册插件 | 导入包时自动执行初始化逻辑 |

**`__init__.py` 何时执行？**

```python
# 实验：跟踪 __init__.py 的执行时机
# 文件结构:
# test_pkg/
#   __init__.py   → print("__init__.py of test_pkg executed")
#   mod.py        → print("mod.py executed")

import sys
# 确保未缓存
if 'test_pkg' in sys.modules:
    del sys.modules['test_pkg']
if 'test_pkg.mod' in sys.modules:
    del sys.modules['test_pkg.mod']

import test_pkg
# 输出: __init__.py of test_pkg executed
# 此时 test_pkg.mod 还未被导入

import test_pkg.mod
# 输出: mod.py executed
# 注意: __init__.py 不会再次执行（已在 sys.modules 缓存中）

# 但如果 from test_pkg import mod:
# 这种情况下，会先确保 test_pkg 已导入（执行 __init__.py），然后导入 mod
```

**包的 `__path__` 属性**

包模块与普通模块的关键区别是 `__path__`。普通模块没有 `__path__`，而包模块的 `__path__` 是一个列表，包含其子模块的搜索目录：

```python
import json
print(json.__path__)  # ['/usr/lib/python3.11/json'] (Linux) 或 ['C:\\Python311\\Lib\\json'] (Windows)

# 当导入 json.decoder 时，PathFinder 会在 json.__path__ 列表中搜索
# 这就是为什么包的子模块不需要在 sys.path 中——包的 __path__ 已提供了搜索路径
```

### 2.2 命名空间包（PEP 420）

Python 3.3 引入了**命名空间包**（PEP 420）——目录下没有 `__init__.py` 也能成为包。与常规包的关键差异：

| 维度 | 常规包 | 命名空间包 |
|:---|:---|:---|
| 标记 | 目录下有 `__init__.py` | 目录下无 `__init__.py` |
| `__file__` | `__init__.py` 的路径 | `None` |
| `__path__` | 单个目录的列表 | 多个目录的列表 |
| 初始化代码 | `__init__.py` 中的代码 | 无 |
| `__package__` | 包名 | 包名 |
| 用途 | 常规项目组织 | 跨目录合并且无需公共 `__init__.py` 的插件系统 |

命名空间包的核心能力：**多个不同目录可以贡献同一个包的子模块**，只要这些目录下都没有 `__init__.py`：

```python
# 目录结构:
# /path_a/
#   mynamespace/
#     module_a.py   →  CONTENT_A = "from path_a"
# /path_b/
#   mynamespace/
#     module_b.py   →  CONTENT_B = "from path_b"

# 两个目录下都没有 __init__.py，所以 mynamespace 是命名空间包
import sys
sys.path.extend(['/path_a', '/path_b'])

import mynamespace
print(mynamespace.__path__)  # ['/path_a/mynamespace', '/path_b/mynamespace']
print(mynamespace.__file__)  # None — 命名空间包没有 __init__.py

from mynamespace import module_a, module_b
print(module_a.CONTENT_A)    # "from path_a"
print(module_b.CONTENT_B)    # "from path_b"
```

**命名空间包的查找机制**

当 PathFinder 在 `sys.path` 的多个目录中发现同名目录且都没有 `__init__.py` 时，不会报错，而是创建一个命名空间包，其 `__path__` 是所有这些目录的列表。当导入该包的子模块时，PathFinder 会遍历 `__path__` 中**所有**目录来查找。

```python
# 真实案例: setuptools 的命名空间包机制
# 许多大型项目使用命名空间包来拆分单体仓库:
# google-cloud-ndb 包提供 google.cloud.ndb
# google-cloud-storage 包提供 google.cloud.storage
# 这两个包安装到不同的 site-packages 目录，但共享 google 和 google.cloud 命名空间

import google.cloud
print(google.cloud.__path__)
# ['/.../site-packages/google/cloud']  — 可能只有一个，由已安装的 google-cloud 包贡献
# 如果同时安装了多个包，__path__ 会合并多个贡献目录
```

命名空间包特别适合插件系统：核心框架定义一个命名空间（如 `plugins/`），第三方插件各自安装到不同的 `site-packages` 子目录，但都贡献到 `plugins` 命名空间下。框架只需遍历 `plugins.__path__` 即可发现所有插件——零配置、零注册代码。

### 2.3 相对导入 vs 绝对导入

Python 有两种导入子包/子模块的方式：

**绝对导入**——从顶层包名开始的完整路径：

```python
# 在 myproject/core/engine.py 中
from myproject.utils import helper     # 绝对导入：从顶层包开始
from myproject.core.config import load # 绝对导入
```

**相对导入**——相对于当前模块的位置：

```python
# 在 myproject/core/engine.py 中
from . import config                   # 同级模块: myproject.core.config
from .config import load               # 同级模块的属性
from .. import utils                   # 上级包的同级模块: myproject.utils
from ..utils import helper             # 上级包的同级模块的属性
```

相对导入的语法：`.` 表示当前包，`..` 表示上一级包，`...` 表示上两级包，以此类推。

**Python 3 的绝对导入默认（PEP 328）**

Python 2 中，`import foo` 是模糊的——可能导入当前包的 `foo`，也可能导入顶层 `foo`。Python 3 强制 `import foo` 始终为绝对导入，相对导入必须用显式的 `from .` 语法。

```python
# Python 2 (已弃用的旧行为)
# 在 myproject/core/engine.py 中
import config  # 模糊！可能指 myproject.core.config，也可能指顶层 config

# Python 3 (当前行为)
import config                    # 绝对导入：只查找顶级 config
from . import config             # 相对导入：明确指 myproject.core.config
```

**相对导入的解析机制**

相对导入依赖模块的 `__package__` 属性来确定基准包：

```python
# myproject/core/engine.py
# __name__ = 'myproject.core.engine'
# __package__ = 'myproject.core'

# from . import config
# 解析: __package__ + '.' + 'config' = 'myproject.core.config'

# from .. import utils
# 解析: __package__ 上移一级 = 'myproject'
# 然后找 'myproject.utils'
```

```python
# 相对导入的内部解析逻辑（简化版）
def _resolve_name(name, package, level):
    """解析相对导入名"""
    # level = 1 → 一个点 (当前包)
    # level = 2 → 两个点 (上一级包)
    bits = package.rsplit('.', level - 1)
    if len(bits) < level:
        raise ImportError("attempted relative import beyond top-level package")
    base = bits[0]
    return f"{base}.{name}" if name else base

# 示例:
# name='config', package='myproject.core', level=1
# bits = ['myproject', 'core']
# base = 'myproject'
# 但 level=1 意味着在同一级，所以:
# base = 'myproject.core', return 'myproject.core.config'
```

**相对导入的限制——脚本直接运行时 `__package__` 为 `None`**

这是 Python 初学者最常踩的坑之一：

```python
# myproject/core/engine.py
from . import config  # 相对导入

# 如果直接运行: python myproject/core/engine.py
# 报错: ImportError: attempted relative import with no known parent package
# 原因: 直接运行的脚本 __name__ = '__main__', __package__ = None（或 ''）
# 相对导入无法解析基准包
```

当脚本被直接运行时（`python file.py`），CPython 设置 `__name__ = '__main__'`，`__package__ = None`。相对导入需要 `__package__` 来确定基准，`None` 意味着没有基准——报错。

解决方案：用 `python -m` 方式运行模块，而非直接运行文件：

```bash
# 错误: 直接运行文件，相对导入失效
python myproject/core/engine.py  # ImportError

# 正确: 以模块方式运行，包上下文完整
python -m myproject.core.engine  # 正常工作
```

`-m` 标志让 Python 执行模块导入流程（而非简单的文件运行），保留完整的包上下文：`__name__ = '__main__'`，但 `__package__ = 'myproject.core'`——相对导入有了基准。

### 2.4 循环导入——原因与解决方案

循环导入是 Python 中最臭名昭著的问题之一。当模块 A 导入模块 B，而模块 B 又导入模块 A 时，就可能触发 `ImportError` 或导致部分初始化的模块被使用。

**循环导入如何发生**

```python
# module_a.py
import module_b

class A:
    def use_b(self):
        return module_b.B()

# module_b.py
import module_a

class B:
    def use_a(self):
        return module_a.A()
```

执行 `import module_a` 时的流程：

1. `import module_a` → `sys.modules` 中无 `module_a` → 创建并注册（部分初始化）
2. 执行 `module_a.py` 的代码 → 遇到 `import module_b`
3. `import module_b` → `sys.modules` 中无 `module_b` → 创建并注册（部分初始化）
4. 执行 `module_b.py` 的代码 → 遇到 `import module_a`
5. `import module_a` → `sys.modules` 中已有 `module_a`（步骤1注册的） → 返回**部分初始化的 `module_a`**
6. `module_a.A` 尚不存在（步骤2还停在 `import module_b` 那行）→ `AttributeError`

```python
# 实际错误:
# AttributeError: partially initialized module 'module_a' has no attribute 'A'
# (most likely due to a circular import)
```

**解决方案 1：延迟导入（函数内导入）**

```python
# module_a.py（修改后）
class A:
    def use_b(self):
        from module_b import B  # 延迟到函数调用时才导入
        return B()
```

函数内的 `import` 直到函数被调用时才会执行。此时两个模块都已完成初始化，`sys.modules` 中都有完整的模块对象，因此不会出现部分初始化的问题。

**解决方案 2：重构模块结构**

将两个模块共用的代码提取到第三个模块中：

```
# 重构前:
# module_a ←→ module_b (循环)

# 重构后:
# module_common (共用部分)
#    ↑           ↑
# module_a    module_b (各自独立导入 module_common，不循环)
```

**解决方案 3：TYPE_CHECKING 守卫**

如果循环导入仅用于类型提示，可以用 `TYPE_CHECKING` 守卫：

```python
# module_a.py
from __future__ import annotations  # Python 3.7+
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from module_b import B

class A:
    def use_b(self) -> B:  # 类型检查器可见，运行时不导入
        from module_b import B  # 运行时延迟导入
        return B()
```

`TYPE_CHECKING` 是一个在运行时为 `False` 但类型检查器（mypy、pyright）视为 `True` 的常量。类型提示只在 `TYPE_CHECKING` 块中导入，运行时不执行。

**实验：复现循环导入并逐步修复**

```python
# 实验1: 复现循环导入
import tempfile, os, sys

demo_dir = tempfile.mkdtemp()

# 创建循环导入的模块
with open(os.path.join(demo_dir, 'circ_a.py'), 'w') as f:
    f.write('import circ_b\nA_VALUE = "from A"\n')

with open(os.path.join(demo_dir, 'circ_b.py'), 'w') as f:
    f.write('import circ_a\nB_VALUE = "from B"\nprint(f"circ_b: circ_a.A_VALUE = {circ_a.A_VALUE}")\n')

sys.path.insert(0, demo_dir)

try:
    import circ_a
except AttributeError as e:
    print(f"循环导入错误: {e}")
# 输出: 循环导入错误: partially initialized module 'circ_a' has no attribute 'A_VALUE'

# 实验2: 用延迟导入修复
os.remove(os.path.join(demo_dir, 'circ_b.py'))
with open(os.path.join(demo_dir, 'circ_b.py'), 'w') as f:
    f.write('B_VALUE = "from B"\ndef get_a_value():\n    import circ_a\n    return circ_a.A_VALUE\n')

# 清除缓存
for key in list(sys.modules):
    if key.startswith('circ_'):
        del sys.modules[key]

import circ_a
import circ_b
print(circ_b.get_a_value())  # "from A" — 延迟导入成功
```
