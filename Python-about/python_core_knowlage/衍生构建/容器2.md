#### 跨语言比较：映射容器

| 特性 | Python dict | C++ std::unordered_map | Java HashMap | Go map |
|:---|:---|:---|:---|:---|
| 冲突解决 | 开放寻址 | 链式寻址 | 链式+红黑树 | 开放寻址 |
| 插入序 | 保证 | 不保证 | 不保证 | 不保证 |
| 负载因子 | 2/3 | 可配(max_load_factor) | 0.75 | 视实现 |
| 键类型约束 | 不可变(hashable) | hash<> + eq<> 特化 | hashCode+equals | comparable |
| 视图 | dict_keys/values/items | 无 (返迭代器) | keySet/values/entrySet | 无 |
| 并发安全 | 否 | 否 | 否(ConcurrentHashMap) | 否(需 sync.Mutex) |

Python dict 用开放寻址而非链式寻址的原因：缓存局部性。开放寻址的所有数据在连续内存中，CPU 缓存命中率高；链式寻址的链表节点散布在堆上，缓存命中率低。在 Python 的典型工作负载（小 dict、频繁查找）下，开放寻址的缓存优势压倒了最坏情况 O(n) 的风险。

## 三、集合兄弟——set与frozenset

set 和 frozenset 的关系如同 list 和 tuple——一个可变，一个不可变，共享同一套哈希表算法。set 是"dict 去掉 value"，frozenset 是"set 加上不可变和可哈希"。

### 3.1 set：可变哈希集合

#### PySetObject 的 C 结构

```c
// CPython/Include/cpython/setobject.h
typedef struct {
    PyObject_HEAD                          // ob_refcnt(8B) + ob_type(8B) = 16B
    Py_ssize_t fill;                       // 已用槽位数 (含 DUMMY) (8B)
    Py_ssize_t used;                       // 有效元素数 (8B)
    Py_ssize_t mask;                       // dk_size - 1 (8B)
    PyObject **table;                      // 指向哈希表 (8B)
    Py_hash_t hash;                        // hash 缓存 (仅 frozenset 使用) (8B)
    Py_ssize_t finger;                     // 搜索起点的"手指" (8B)
    SetEntry *smalltable[PySet_MINSIZE];   // 内联小表 (8个entry) (8*24=192B)
    // ...
} PySetObject;

typedef struct {
    Py_hash_t hash;                        // 元素的哈希值
    PyObject *key;                         // 元素指针 (无 value!)
} SetEntry;
```

内存布局图：

```
PySetObject 实例 (集合 {42, "hi", 99}):
┌──────────────────────────────────────┐
│ ob_refcnt  = 1              (8B)     │
│ ob_type    → <class 'set'>  (8B)     │
│ fill       = 3              (8B)     │ ← 填充(含 DUMMY)
│ used       = 3              (8B)     │ ← 有效元素数 = len(set)
│ mask       = 7              (8B)     │ ← table_size - 1
│ table      ──────────────────────╂──→ SetEntry 数组
│ hash       = -1             (8B)     │     │
│ finger     = 0              (8B)     │     ↓  ┌─────────────────────────┐
│ smalltable[8] (内联小表)  (192B)    │        │ [0] hash=..., key=NULL  │ (空)
│ ...                                  │        │ [1] hash=..., key→42    │ (42)
└──────────────────────────────────────┘        │ [2] hash=..., key→"hi"  │ ("hi")
                                                │ [3] hash=..., key→99    │ (99)
                                                │ ...                     │
                                                └─────────────────────────┘

对比 PyDictKeyEntry:
  dict entry: hash + key + value = 24B
  set  entry: hash + key         = 16B (无 value, 省 8B)
```

set 与 dict 的核心差异：

1. **无 value 字段**：`SetEntry` 只有 `hash` 和 `key`，没有 `me_value`
2. **不在 split/share 模式**：set 没有 PEP 412 键共享优化（因为 set 不像实例 `__dict__` 那样有大量同结构实例）
3. **不保证插入序**：set 的实现不是 Python 3.7+ 的紧凑 dict 方案——set 仍然是旧式的哈希表，迭代顺序取决于哈希值分布

#### set 操作与时间复杂度

| 操作 | 时间复杂度 | 等价 C 层 | 说明 |
|:---|:---|:---|:---|
| `x in s` | O(1) 平均 | `set_contains` | 哈希查找 |
| `s.add(x)` | O(1) 平均 | `set_add` | 查找 + 插入/更新 |
| `s.discard(x)` | O(1) 平均 | `set_discard` | 找到则删除标 DUMMY，未找到不做任何事 |
| `s.remove(x)` | O(1) 平均 | `set_remove` | 找到则删除，未找到 → KeyError |
| `s.pop()` | O(1) 平均 | `set_pop` | 弹出任意一个元素（非"最后一个"） |
| `s & t` | O(min(len(s),len(t))) | `set_intersection` | 遍历小集合, 在大集合中查找 |
| `s \| t` | O(len(s)+len(t)) | `set_union` | 合并两个集合 |
| `s - t` | O(len(s)) | `set_difference` | 遍历 s, 排除 t 中的元素 |
| `s ^ t` | O(len(s)+len(t)) | `set_symmetric_difference` | 双方遍历 |
| `len(s)` | O(1) | `sq_length` | 直接返回 `used` |

**实验 17：add/discard/remove 的区别**

```python
s = {1, 2, 3}

s.discard(99)        # 99 不存在, 安静跳过
print(s)             # {1, 2, 3}

try:
    s.remove(99)     # 99 不存在, KeyError
except KeyError as e:
    print(f"remove(99) → {e}")

s.discard(2)         # 2 存在, 删除
print(s)             # {1, 3}

s.add(1)             # 1 已存在, 静默(不做任何事)
print(s)             # {1, 3}
```

#### set 为什么无序——哈希函数决定位置

set 的元素存储位置由 `hash(element) & mask` 决定，迭代时按哈希表物理顺序扫过——这完全取决于哈希值的分布，与插入顺序无关。

```python

s.add("a")
s.add("b")
print(s)    # 可能 {'a', 'b', 'c'} 也可能 {'c', 'a', 'b'} —— 不确定

# 对比 dict 保证插入序:
d = {}
d["c"] = 1
d["a"] = 2
d["b"] = 3
print(list(d.keys()))   # ['c', 'a', 'b']  — 保证!
```

### 3.2 frozenset：不可变集合

frozenset 与 set 的关系如同 tuple 与 list——相同的哈希表算法，但冻结为不可变：

- **不可变** → `tp_hash` 实现了 → 可做 dict key / set 元素
- **`hash` 字段缓存**：`PySetObject.hash` 在首次 `hash()` 调用后缓存，后续直接返回（与 str 的 hash 缓存类似）

**实验 19：frozenset 可做 dict key**

```python

# frozenset 可哈希

# frozenset 做 dict key
d = {fs: "hello"}
print(d[frozenset([1, 2, 3])])  # "hello" — 值相等即同一 key

# set 不可哈希
try:
    hash({1, 2, 3})
except TypeError as e:
    print(f"hash(set) → {e}")   # unhashable type: 'set'
```

**实验 20：frozenset 的哈希缓存**

```python
import ctypes

class PySetObject(ctypes.Structure):
    _fields_ = [
        ("ob_refcnt", ctypes.c_ssize_t),
        ("ob_type", ctypes.c_void_p),
        ("fill", ctypes.c_ssize_t),
        ("used", ctypes.c_ssize_t),
        ("mask", ctypes.c_ssize_t),
        ("table", ctypes.c_void_p),
        ("hash_field", ctypes.c_ssize_t),  # hash 字段 (叫 hash_field 避免与内置冲突)
    ]

fs = frozenset([1, 2, 3])
addr = id(fs)
py_set = PySetObject.from_address(addr)

print(f"哈希前: hash_field = {py_set.hash_field}")  # -1 (未缓存)
h = hash(fs)
# 重新读取 (注意: from_address 是实时引用)

```

### 3.3 集合与字典的血缘关系

set 和 dict 的历史和实现高度耦合：

```
血缘关系:
  早期 CPython: set 直接用 dict 实现 — {key: True} 中的 True 是占位符
  Python 2.4+:  set 获得独立的 PySetObject, 但哈希算法与 dict 相同
  Python 3.x:   set 和 dict 的实现趋同(open addressing, perturbation probe)

共同点:
  - 开放寻址 + perturbation 探测
  - 负载因子 2/3 触发 resize
  - 墓碑(DKIX_DUMMY)机制
  - 要求元素可哈希 (tp_hash 非 NULL)
  - 哈希随机化 (PYTHONHASHSEED)

差异点:
  - dict 保证插入序 (Python 3.7+), set 不保证
  - dict 有 PEP 412 键共享, set 无
  - dict 有紧凑 dict (dk_indices + dk_entries), set 用 SetEntry 数组
  - dict entry 24B (hash+key+value), set entry 16B (hash+key)
```

## 四、哈希——容器世界的通行证

dict 的 key 和 set 的 element 共同要求一个属性：**可哈希性**。这不是任意的限制，而是哈希表数据结构的基本前提——如果对象的哈希值不确定（因其内容可变），在哈希表中的位置就无法保持一致，查找将失败。

### 4.1 hash() 与 __hash__

`hash(obj)` 在 C 层面调用的路径：

```
Python: hash(obj)
  ↓
C层: PyObject_Hash(obj)
  ↓
1. 检查 obj.ob_type->tp_hash:
   - 非 NULL → 调用 tp_hash(obj) → 返回 Py_hash_t
   - 等于 _PyObject_HashNotImplemented → TypeError("unhashable type")
  ↓
2. 返回值截断为 Py_hash_t (通常 64 位有符号整数)
  ↓
3. 如果返回 -1 (错误标记) → 重新设为 -2 (因为 -1 有特殊含义)
```

**实验 22：内置类型的 tp_hash 映射**

```python
# 不可变类型: tp_hash 实现了
print(hash(42))          # 42 — int 的 hash 就是自身(小区间)
print(hash("hello"))     # 大整数 — str 的 hash 基于 xxHash
print(hash((1, 2)))      # 大整数 — tuple 递归混合各元素 hash
print(hash(frozenset([1])))  # 大整数 — frozenset 的 hash 混合各元素
print(hash(True))        # 1 — bool 继承 int

# 可变类型: tp_hash = _PyObject_HashNotImplemented
try:
    hash([1, 2])
except TypeError as e:
    print(f"hash(list) → {e}")

try:
    hash({1: 2})
except TypeError as e:
    print(f"hash(dict) → {e}")

try:
    hash({1, 2})
except TypeError as e:
    print(f"hash(set) → {e}")
```

### 4.2 为什么可变对象不可哈希

这是一个设计公理，不是实现限制：

```
可变对象不可哈希的闭环:
  可变 → 内容可变 → hash 值应随内容变 → 但 hash 值决定对象在哈希表中的位置
  → 内容变后位置改变, 但哈希表中旧位置仍存着条目
  → 查找时用新 hash 值找新位置 → 找不到 → 数据"丢失"

  所以: tp_hash = _PyObject_HashNotImplemented → TypeError
  这不是"Python 做不到", 而是"做了就是 bug"——语义上不可能
```

**假设实验：如果 mutable 对象可以哈希会发生什么**

```python
# 假设 list 可以哈希 (以下代码实际会 TypeError)
# L = [1, 2]
# s = {L}             # 把 list 放进 set
# L.append(3)         # 修改 list → hash 改变
# "L" in s            # False? 数据"丢失"了！
# 但 L 仍在 set 的内存中, 只是找不到它 → 内存泄漏 + 语义错误

# 这正是 Python 禁止可哈希化可变类型的原因
```

### 4.3 哈希随机化——PYTHONHASHSEED

Python 3.3+ 默认启用哈希随机化——每次 Python 解释器启动时，str/bytes/datetime 的哈希函数注入一个随机种子，使同一字符串在不同进程中的 hash 值不同。这是对**哈希碰撞 DoS 攻击**的防御：

```
攻击原理:
  攻击者构造大量 hash 相同的 key → 所有 key 探测链极长 → dict 操作 O(n) → 服务器瘫痪
  2011 年 multipart POST 攻击让大量 Web 框架(基于 dict 解析)瘫痪

防御:
  PYTHONHASHSEED=random (默认) → 启动时随机化 hash 函数
  → 攻击者无法预测 hash 值 → 无法构造大规模碰撞
```

```python
import os
import subprocess

# 固定 seed → hash 确定性
result1 = subprocess.run(
    ["python", "-c", "print(hash('hello'))"],
    env={**os.environ, "PYTHONHASHSEED": "0"},
    capture_output=True, text=True
)

result2 = subprocess.run(
    ["python", "-c", "print(hash('hello'))"],
    env={**os.environ, "PYTHONHASHSEED": "0"},
    capture_output=True, text=True
)

print(f"seed=0, 两次 hash: {result1.stdout.strip()}, {result2.stdout.strip()}")
# 两次相同 — seed 固定 → hash 确定性

# 注意: int 的 hash 不受 PYTHONHASHSEED 影响
# hash(42) 在所有 seed 下都是 42
```

### 4.4 __eq__ 与 __hash__ 的契约

Python 的数据模型定义了一条铁律：

> **如果 `a == b` 为 `True`，则 `hash(a) == hash(b)` 必须为 `True`**

反之不要求：`hash(a) == hash(b)` 不能推出 `a == b`（这就是哈希冲突）。

违背这条契约的后果：该类的实例用作 dict key 或 set 元素时，行为将不可预测——即使 `a == b`，它们可能被存到不同哈希槽位，变成"两个不同的 key"。

**实验 23：违背 __eq__/__hash__ 契约的后果**

```python
class BadKey:
    """故意违背契约: __eq__ 基于 val, __hash__ 基于随机值"""
    def __init__(self, val):
        self.val = val
    
    def __eq__(self, other):
        return isinstance(other, BadKey) and self.val == other.val
    
    def __hash__(self):
        return id(self) % (2**31)   # 基于 id(), 每个实例 hash 不同!

k1 = BadKey("x")
k2 = BadKey("x")

print(k1 == k2)          # True — __eq__ 说它们相等
print(hash(k1) == hash(k2))  # False — __hash__ 说它们不等!

d = {k1: "value1"}
d[k2] = "value2"

print(d)   # {<BadKey at 0x...>: 'value1', <BadKey at 0x...>: 'value2'}
# 两个"相等"的 key 居然同时存在! → 契约破坏 → dict 语义崩溃
```

**实验 24：自定义可哈希不可变类型**

```python
class ImmutablePoint:
    __slots__ = ('_x', '_y', '_hash')
    
    def __init__(self, x, y):
        object.__setattr__(self, '_x', x)
        object.__setattr__(self, '_y', y)
        object.__setattr__(self, '_hash', hash((x, y)))
    
    @property
    def x(self):
        return self._x
    
    @property
    def y(self):
        return self._y
    
    def __setattr__(self, name, value):
        raise AttributeError("ImmutablePoint is immutable")
    
    def __eq__(self, other):
        return isinstance(other, ImmutablePoint) and self._x == other._x and self._y == other._y
    
    def __hash__(self):
        return self._hash   # 缓存哈希值, 创建后不变

p1 = ImmutablePoint(1, 2)
p2 = ImmutablePoint(1, 2)

print(p1 == p2)           # True
print(hash(p1) == hash(p2))  # True — 契约满足
d = {p1: "A"}
print(d[p2])              # "A" — 值相等即可查找
```

### 4.5 哈希碰撞——生日悖论与 CPython 的处理

哈希碰撞（collision）是指两个不同对象的 `hash()` 返回值相同。碰撞不是 bug，而是哈希函数的数学极限——将无限空间映射到有限的 `Py_hash_t`（通常 64 位），必然存在碰撞。

**生日悖论**：在哈希表大小为 N 的情况下，只需要 √N 次插入，碰撞概率就达到 50%。这也是为什么 CPython 的负载因子阈值设为 2/3——超过此阈值，碰撞概率急剧上升。

CPython 处理碰撞的方式是探测序列（perturbation probe）——当 hash 相同时，向后探测寻找空位。探测链的平均长度与负载因子直接相关：

```
负载因子 α → 期望探测次数 (查找成功) ≈ -ln(1-α)/α
  α=0.25 → 1.3 次
  α=0.50 → 1.9 次
  α=0.67 → 2.9 次   ← CPython 阈值
  α=0.75 → 3.8 次
  α=0.90 → 8.5 次   ← 灾难
```

**实验 25：碰撞率随负载因子变化**

```python
class FixedHash:
    def __init__(self, n, bucket_size):
        self.n = n
        self.bucket_size = bucket_size
    def __hash__(self):
        return self.n % self.bucket_size
    def __eq__(self, other):
        return isinstance(other, FixedHash) and self.n == other.n

# 模拟不同负载因子下的查找性能
for load in [0.25, 0.50, 0.67, 0.90]:
    n = int(10000 * load)
    d = {FixedHash(i, 10000): i for i in range(n)}
    
    start = __import__('time').perff_counter() if hasattr(__import__('time'), 'perff_counter') else __import__('time').perf_counter()
    for i in range(n):
        _ = FixedHash(i, 10000) in d
    elapsed = __import__('time').perf_counter() - start
    
    print(f"负载因子 {load:.2f} ({n:5d}条目): 查找{elapsed:.4f}s")
# 负载因子越高, 查找越慢 (碰撞更多)
```

## 五、容器协议与鸭子类型

Python 的容器类型通过**协议**（protocol）而非继承体系实现多态。协议是 `PyTypeObject` 槽位在 Python 层面的映射——当 `ob_type` 的某个槽位非 NULL，该对象就"满足"对应的协议。`collections.abc` 模块将这些协议形式化为抽象基类（ABC），但 Python 运行时**不查 isinstance**——它直接查 C 层槽位。

### 5.1 核心协议与槽位映射

| Python 层协议 | 双下方法 | C 层槽位 | 典型操作 | 满足的类型 |
|:---|:---|:---|:---|:---|
| **Container** | `__contains__` | `sq_contains` | `x in obj` | list, tuple, dict, set, str |
| **Sized** | `__len__` | `sq_length` / `mp_length` | `len(obj)` | list, tuple, dict, set, str |
| **Iterable** | `__iter__` | `tp_iter` | `for x in obj` | list, tuple, dict, set, str, 文件 |
| **Sequence** | `__getitem__` + `__len__` | `sq_item` + `sq_length` | `obj[i]`, `obj[i:j]` | list, tuple, str |
| **Mapping** | `__getitem__` + `__len__` + `__iter__` | `mp_subscript` + `mp_length` | `obj[key]` | dict |
| **Reversible** | `__reversed__` | (Python 层) | `reversed(obj)` | list, tuple, str |

### 5.2 len()/iter()/in 的分派机制

**`len(obj)` 的分派路径**：

```
Python: len(d)
  ↓
C层: builtin_len_impl(module, obj)
  ↓
1. 读 obj.ob_type->tp_as_sequence->sq_length (序列类型)
   或 obj.ob_type->tp_as_mapping->mp_length (映射类型)
  ↓
2. 调用对应槽位函数 → 返回 Py_ssize_t
  ↓
3. 如果返回值 < 0 → 槽位函数设置了异常 → 传播
  ↓
4. 返回 Python int
```

**实验 26：len() 的统一分派——不同容器走同一入口**

```python
class FakeContainer:
    """自定义容器, 只实现 __len__"""
    def __len__(self):
        return 42

fc = FakeContainer()
print(len(fc))    # 42 — len() 不关心类型, 只找 __len__

# collections.abc.Sized 自动识别
from collections.abc import Sized
print(isinstance(fc, Sized))  # True — ABC 通过 __subclasshook__ 检测方法存在
print(isinstance([], Sized))  # True
print(isinstance({}, Sized))  # True
print(isinstance(42, Sized))  # False — int 没有 __len__
```

**`x in obj` 的分派路径**：

```
Python: x in obj
  ↓
C层: PySequence_Contains(obj, x)
  ↓
1. 检查 obj.ob_type->tp_as_sequence->sq_contains
   - 存在 → 调用 → 返回 1(真)/0(假)/-1(异常)
   - 不存在 → 回退: 用 tp_iter 迭代遍历, 逐个 __eq__
```

这就是为什么 `in` 对 dict/set 是 O(1)，对 list/tuple 是 O(n)——dict/set 的 `sq_contains` 槽位实现了哈希查找，而 list/tuple 的 `sq_contains` 实现了线性扫描。**同一个 `in` 运算符，两种完全不同的算法——分派由 `ob_type` 决定**。

**实验 27：自定义容器协议——鸭子类型验证**

```python
from collections.abc import Container, Iterable, Sized, Sequence

class MySeq:
    """自定义序列, 只实现必要协议"""
    def __init__(self, data):
        self._data = list(data)
    
    def __getitem__(self, index):
        return self._data[index]
    
    def __len__(self):
        return len(self._data)
    
    # 没有 __contains__ — Container 的 mixin 实现会遍历
    # 没有 __iter__ — Sequence 的 mixin 会用 __getitem__ 迭代
    # 没有 __reversed__ — Sequence 的 mixin 会用 __len__ + __getitem__

ms = MySeq([10, 20, 30])

print(isinstance(ms, Container))  # True — 有 __contains__ mixin
print(isinstance(ms, Iterable))   # True — 有 __iter__ mixin
print(isinstance(ms, Sized))      # True — 有 __len__
print(isinstance(ms, Sequence))   # True — 有 __getitem__ + __len__

print(20 in ms)                   # True — 走 __contains__ (O(n) 线性扫描)
print(len(ms))                    # 3
print(ms[1])                      # 20
print(list(reversed(ms)))         # [30, 20, 10]
for x in ms:                      # 走 __getitem__ 迭代
    print(x, end=" ")             # 10 20 30
```

### 5.3 collections.abc 的层次结构

```
Container ──── __contains__
    │
Sized ────────── __len__
    │
Iterable ────── __iter__
    │
    ├── Iterator ──── __next__ + __iter__ (自反)
    │
    ├── Reversible ── __reversed__ (Python 3.5+)
    │       │
    │       └── Sequence ──── __getitem__ + __len__
    │               │
    │               ├── list, tuple, str, bytes, range
    │               │
    │               └── MutableSequence ──── __setitem__, __delitem__, insert, append...
    │                       │
    │                       └── list, bytearray, deque
    │
    ├── Mapping ────── __getitem__ + __len__ + __iter__
    │       │
    │       └── MutableMapping ──── __setitem__, __delitem__, pop, update...
    │               │
    │               └── dict, OrderedDict, defaultdict
    │
    └── Set ─────────── __contains__ + __len__ + __iter__ + __eq__
            │
            └── MutableSet ──── add, discard, pop, remove...
                    │
                    └── set
                    (frozenset 只实现 Set, 不实现 MutableSet)
```

关键设计：Python 的 ABC 使用 `__subclasshook__` 实现**结构性子类型**（structural subtyping）——不要求显式继承，只要实现了对应的方法就 `isinstance` 返回 True。这比 Java 的显式 `implements` 和 C++ 的模板 duck typing 在运行时更灵活。

## 六、常见陷阱

### 陷阱 1：迭代中修改 dict → RuntimeError

```python
d = {"a": 1, "b": 2, "c": 3}
for k in d:
    if k == "b":
        del d[k]        # RuntimeError: dictionary changed size during iteration
```

**原因**：dict 迭代器在每次 `__next__` 时检查 `ma_version_tag`——如果与创建迭代器时不同（说明 dict 被修改了），立即抛出 `RuntimeError`。这是保护措施——否则 `dk_entries` 的变动可能导致跳过元素或重复访问。

**避免**：收集待删除的 key，迭代结束后批量删除：

```python
d = {"a": 1, "b": 2, "c": 3}
to_delete = [k for k in d if k == "b"]
for k in to_delete:
    del d[k]
print(d)  # {'a': 1, 'c': 3}
```

或使用 `dict comprehension` 一步构建新 dict：

```python
d = {"a": 1, "b": 2, "c": 3}
d = {k: v for k, v in d.items() if k != "b"}
```

### 陷阱 2：set/dict 中使用不可哈希元素

```python
s = set()
s.add([1, 2])        # TypeError: unhashable type: 'list'
d = {}
d[[1, 2]] = "v"      # TypeError: unhashable type: 'list'
```

**原因**：list 的 `tp_hash = _PyObject_HashNotImplemented`，哈希表无法确定其位置。

**避免**：将 list 转为 tuple（不可变且可哈希）：

```python
s.add((1, 2))            # OK — tuple 可哈希
d[(1, 2)] = "v"          # OK
```

### 陷阱 3：函数默认可变参数——共享陷阱

```python
def append_to(item, target=[]):   # 危险! 默认值是同一 list 对象
    target.append(item)
    return target

print(append_to(1))    # [1]
print(append_to(2))    # [1, 2] — 上次调用的影响!

# 验证: 默认参数是函数对象的属性, 只创建一次
print(append_to.__defaults__)   # ([1, 2],) — 同一 list
```

**原因**：默认参数在函数**定义时**求值——`[]` 创建一个 list `PyObject`，绑定到 `append_to.__defaults__[0]`。每次调用不创建新 list，直接复用同一对象。这与 §2.2 "赋值不是拷贝"是同一个根因——函数定义时的 `[]` 是一次对象创建 + 一次名字绑定。

**避免**：

```python
def append_to(item, target=None):
    if target is None:
        target = []        # 每次调用创建新 list
    target.append(item)
    return target
```

### 陷阱 4：包含可变对象的 tuple 是可哈希的但危险

```python
t = (1, [2, 3])
# tuple 本身 tp_hash 存在 → 调用 tuplehash()
try:
    hash(t)
except TypeError as e:
    print(f"hash((1,[2,3])) → {e}")   # unhashable type: 'list'
    # tuplehash() 递归调用 hash() 时发现 list 不可哈希 → TypeError
```

但如果 tuple 内含的元素可哈希但"逻辑上可变"（如自定义类实现了 `__hash__` 但留了修改后门），就会产生更隐蔽的 bug：

```python
class Sneaky:
    def __init__(self, val):
        self.val = val
    def __hash__(self):
        return hash(self.val)
    def __eq__(self, other):
        return isinstance(other, Sneaky) and self.val == other.val

s = Sneaky(1)
d = {s: "found"}
s.val = 2                    # 修改内部状态 → hash 值改变!
try:
    print(d[s])              # KeyError — hash 值变了, 在旧位置找不到
except KeyError:
    print("KeyError: 因为 hash 值改变, dict 查找失败")

# 旧条目仍在 dict 内存中, 但已无法通过正常方式访问 → 内存泄漏
```

**原因**：tuple 的 `tp_hash` 在创建时**不缓存**——每次 `hash(t)` 都递归计算元素的哈希。但 dict 在**插入时**计算一次 hash 并存入 `dk_entries[].me_hash`，之后查找也用这个缓存的 hash。如果元素内部状态改变了，tuple 的 hash 不会变（因为每次重新算），但如果 tuple 被放入 dict/set 后，其元素的内部状态变了，那么：

1. 如果元素本身可哈希（如 Sneaky），dict 用的是**插入时**的 hash → 元素修改后查找失败
2. 如果元素不可哈希（如 list），tuplehash 在计算时就失败

**规则**：永远不要将"逻辑上可变"的对象放入 dict/set——即使 Python 的类型系统允许（自定义 `__hash__`），语义上它仍然是 bug。

L = list(range(100000))

d1 = {"a": 1, "b": 2}

<summary>参考答案</summary>

**题目 1**：

list 的 `+=` 等价于 `extend()`（调用 `list.__iadd__` → 原地修改 → 返回 self），所以 `b += [4]` 原地修改了 `b` 指向的 list。`a` 和 `b` 绑定同一对象，所以 `print(a)` 输出 `[1, 2, 3, 4]`，`a is b` 为 `True`。

tuple 的 `+=` 等价于 `t = t + other`（调用 `tuple.__add__` → 创建新 tuple），所以 `d += (4,)` 创建了新 tuple `(1, 2, 3, 4)`，`d` 重新绑定到新对象。`c` 仍指向旧 tuple `(1, 2, 3)`，所以 `print(c)` 输出 `(1, 2, 3)`，`c is d` 为 `False`。

这体现了可变对象与不可变对象的根本区别——list 的 `sq_ass_item` 开放，`+=` 原地修改（`ob_size`/`ob_item` 改变）；tuple 的 `sq_ass_item` 为 NULL，`+=` 只能创建新对象。

**题目 2**：

- `50000 in L`：**O(n)**。list 的 `sq_contains` 是线性扫描，逐个 `__eq__` 比较，最坏扫描 n 个元素。
- `50000 in T`：**O(n)**。tuple 的 `sq_contains` 也是线性扫描——与 list 相同的序列协议。
- `50000 in S`：**O(1) 平均**。set 的 `sq_contains` 走哈希查找——`hash(50000) & mask` 直接定位槽位。
- `50000 in D`：**O(1) 平均**。dict 的 `sq_contains`（实际上是 `mp_contains`）走哈希查找——与 set 相同的哈希算法。

同一个 `in` 运算符，list/tuple 和 set/dict 走了完全不同的 C 层路径。这是通过 `ob_type → PyTypeObject` 槽位分派实现的——序列类型实现线性扫描，哈希类型实现 O(1) 查找。

**题目 3**：

`d2["a"]` 输出 **1**。`dict(d1)` 是浅拷贝——创建新 dict，但 key/value 是原对象的引用。`d1["a"] = 100` 修改的是 `d1` 的 `ma_keys/ma_values` 中的条目，不影响 `d2`。因为 int 是不可变的，`d1["a"] = 100` 是 `d1` 中的 key "a" 重新绑定到新 int 100，`d2` 中的 key "a" 仍指向旧 int 1。

`d4["x"]` 输出 **[1, 2, 3]**。浅拷贝只复制容器骨架——`d3` 和 `d4` 是不同的 `PyDictObject`，但 `"x"` 对应的 value 是**同一个 list 对象**。`d3["x"].append(3)` 原地修改了那个 list，`d4["x"]` 指向同一个 list，所以也看到了 `[1, 2, 3]`。

```
d3 ──→ {"x": ──→ [1, 2, 3]}   ← list 被 d3["x"] 和 d4["x"] 共享
              ↗
d4 ──→ {"x": ─┘}
```

## 八、容器类型的解释力——N个表象疑惑统一回溯

理解容器四剑客的最大收益，不是记住几个 `sys.getsizeof` 的值，而是获得一个**统一的解释框架**：表面上千差万别的 Python 容器行为，回溯到 C 结构体的数据布局、`PyTypeObject` 的槽位矩阵和哈希表的物理约束，就不再是散落的知识点，而是同一个根上长出的枝叶。

| # | 表象疑惑 | 根因回溯 | 本文章节 |
|:--|:---|:---|:---|

## 设计闭环——从对象模型到容器的完整链条

将全文的知识串联，Python 容器的设计遵循一条清晰的闭环逻辑：

```
PyObject 统一契约 (ob_refcnt + ob_type)
    │
    ├── 数据布局决定可变性
    │   ├── 内联存储 (tuple/str/bytes/int) → 不可 realloc → sq_ass_item = NULL → 不可变
    │   └── 间接存储 (list/bytearray) → 可 realloc → sq_ass_item 开放 → 可变
    │   └── 独立哈希表 (dict/set) → 可重组 → 可变
    │
    ├── 可变性决定哈希性
    │   ├── 不可变 → tp_hash 可实现 → 可做 dict key / set 元素
    │   └── 可变 → tp_hash = NULL → TypeError("unhashable")
    │   └── 根因: 可变对象的 hash 值不确定 → 哈希表位置不稳定 → 查找失败
    │
    ├── 哈希性决定容器能力
    │   ├── hashable → 可做 dict key, 可做 set 元素, 可做 frozenset 元素
    │   └── unhashable → 只能做 list/tuple 元素, 不能做 dict key/set 元素
    │
    ├── 协议决定接口统一
    │   ├── len() → sq_length/mp_length → 所有容器共享
    │   ├── in  → sq_contains → 序列:O(n), 哈希:O(1)
    │   ├── for → tp_iter → 所有可迭代对象共享
    │   └── []  → sq_item/mp_subscript → 序列 vs 映射
    │
    └── 槽位决定行为差异
        ├── list.sq_ass_item → 可原地修改 → += 原地 extend
        ├── tuple.sq_ass_item = NULL → 不可修改 → += 创建新 tuple
        ├── dict.mp_ass_subscript → key 赋值 → 增/改条目
        └── set.__ior__ → |= 合并操作 → 原地修改
```

这个闭环的意义在于：你不需要分别记忆"为什么 list 可变""为什么 dict key 不能是 list""为什么 tuple 可做 key"——它们是**同一个因果链上的三个环节**。理解了数据布局→可变性→哈希性这条链，所有表象疑惑都是定理而非公理。

### 容器选型的工程决策树

```
需要容器?
  │
  ├── 需要键值对?
  │   └── dict (O(1) 查找, 插入序保证, key 须 hashable)
  │
  ├── 需要去重?
  │   ├── 需要可变?
  │   │   └── set (O(1) 查找, 可增删)
  │   └── 需要不可变? (做 key / 做元素)
  │       └── frozenset (O(1) 查找, hashable)
  │
  ├── 需要序列?
  │   ├── 需要可变?
  │   │   └── list (动态指针数组, 摊还 O(1) append)
  │   └── 需要不可变? (做 key / 安全共享)
  │       └── tuple (内联定长数组, hashable, 省内存)
  │
  └── 需要频繁 in 查找?
      └── set/dict (O(1)), 不要用 list/tuple (O(n))
```

每个选择都有根因——list vs tuple 由可变性需求决定（而可变性由数据布局决定），list vs set 由查找模式决定（序列协议 vs 哈希协议），dict vs set 由是否需要 value 决定（映射协议 vs 集合协议）。**选择容器不是口味问题，而是数据结构和算法的选择**——理解 C 层的实现，你才能做出正确的选择。
