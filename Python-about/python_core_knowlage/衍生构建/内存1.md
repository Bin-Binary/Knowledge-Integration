# Python核心基础（十二）：Python的内存真相——引用计数/GC/GIL/字节码

> **一句话总结**：Python选择了引用计数作为**主**回收机制（即时、确定性强、零停顿），分代GC作为**兜底**（仅处理循环引用），GIL保证单线程字节码安全，字节码则是CPython虚拟机的执行载体——四者环环相扣，共同构成Python的内存与执行全貌。

---

## 引言：五门语言的内存哲学

| 语言 | 内存管理策略 | 核心机制 | 优势 | 劣势 |
|------|-------------|---------|------|------|
| **C** | 手动管理 | `malloc`/`free`，程序员掌控一切 | 零开销、极致控制 | 内存泄漏/野指针常发，正确性完全依赖人 |
| **Java** | 分代GC | 新生代(Eden+Survivor)+老年代，stop-the-world | 安全、自动化 | GC停顿(STW)可达数百ms，`finalize`时机不确定 |
| **Go** | 并发三色标记GC | 三色标记+混合写屏障，与用户协程并发 | 低停顿(<1ms)，为goroutine设计 | 仍需STW(极短)，有写屏障开销 |
| **Rust** | 所有权+借用检查 | 编译期确定生命周期，零成本抽象 | 零运行时开销，编译期保证内存安全 | 学习曲线陡峭，编译器"啰嗦" |
| **Python** | **引用计数(主)+分代GC(辅)+GIL** | `ob_refcnt`主导即时回收，GC处理循环引用，GIL串行化字节码 | 确定性回收、零停顿、实现简单 | 每对象8B开销，GIL扼杀真并行，循环引用需GC |

**Python的激进选择**：让引用计数担任主角——每次绑定+1、解绑-1，归零立即释放，`__del__`时机可预测，无需stop-the-world；代价是每对象多8字节`ob_refcnt`字段，且无法处理循环引用。GC作为补丁仅在循环引用时介入。GIL则是因为引用计数本身非线程安全，必须用一把大锁串行化所有字节码执行。

这三者的耦合关系：

```
引用计数 ──(非线程安全)──→ 必须有GIL ──(串行化字节码)──→ 无真并行
    │
    └──(无法处理循环引用)──→ 必须有分代GC ──(mark-and-sweep)──→ 可回收循环引用
```

**C的哲学**：程序员是神。`malloc`给你一块内存，`free`还回去，一切靠人。忘记`free`？泄漏。`free`两次？崩溃。`free`后继续用？未定义行为。C给予绝对自由，也给予绝对责任。

**Java的哲学**：机器来管。JVM运行分代GC：新对象放Eden，存活够久进老年代，GC时stop-the-world暂停所有线程，然后标记-清除/标记-整理。好处是安全（不可能野指针），坏处是停顿不可控（老年代Full GC可暂停数百ms），`finalize`调用时机不确定。

**Go的哲学**：低停顿折中。三色标记+混合写屏障，GC与goroutine并发执行，暂停时间通常<1ms。代价是写屏障的运行时开销和稍高的内存占用（存活率需要额外空间）。

**Rust的哲学**：编译期解决。所有权规则（每个值有且仅有一个所有者）、借用检查器（编译期验证引用合法性），零运行时开销。代价是编译器"啰嗦"（lifetime标注）、学习曲线陡峭。

**Python的哲学**：确定性与简单的极致追求。引用计数让`__del__`时机可控、零停顿，但引入8B/对象开销和循环引用漏洞。GIL让CPython实现极简（不需考虑线程安全的INCREF/DECREF），但牺牲了真并行。这是权衡——Guido van Rossum多次表态GIL是为简单性做的选择。

本文将从**CPython源码层**逐一拆解这四大基石，配合`ctypes`实验、跨语言对比，让你从"知其然"到"知其所以然"。

## 一、引用计数——`ob_refcnt`主导一切

### 1.1 引用计数的工作机制

#### 1.1.1 PyObject与ob_refcnt

CPython中**一切皆对象**，所有对象的首部都是`PyObject`结构体（Python 3.12+为`PyObject`，更早版本为`PyObject_HEAD`宏展开）：

```c
// CPython Include/object.h (简化版)
typedef struct _object {
    Py_ssize_t ob_refcnt;   // 引用计数 —— 8字节 (64位系统)
    PyTypeObject *ob_type;  // 类型指针   —— 8字节
} PyObject;
```

每个Python对象，无论是`int`、`str`、`list`还是自定义类的实例，内存布局的最前面都有这16字节（`ob_refcnt` + `ob_type`）。引用计数字段`ob_refcnt`占8字节，这意味着**每个Python对象仅为了引用计数就多消耗8字节内存**。

以一个空列表为例的实际内存布局：

```
┌─────────────────────────────────────────────────────────────┐
│ PyListObject 内存布局 (64位系统)                              │
├──────────┬──────────┬──────────┬──────────┬──────────┬──────┤
│ ob_refcnt│ ob_type  │ ob_size  │ ob_item  │ allocated│      │
│ (8B)     │ (8B)     │ (8B)     │ (8B)     │ (8B)     │      │
│ = 1      │ &list    │ = 0      │ NULL     │ = 0      │      │
├──────────┴──────────┴──────────┴──────────┴──────────┴──────┤
│                      共 56 字节                              │
└─────────────────────────────────────────────────────────────┘
```

对于一个小整数对象（缓存的-5到256）：

```
┌──────────────────────────────────────────┐
│ PyLongObject 内存布局                      │
├──────────┬──────────┬──────────┬─────────┤
│ ob_refcnt│ ob_type  │ ob_size  │ ob_digit│
│ (8B)     │ (8B)     │ (8B)     │ (4B)    │
│ 常被共享  │ &int     │ = 1(正数)│ 数值    │
├──────────┴──────────┴──────────┴─────────┤
│             共 28 字节                     │
└──────────────────────────────────────────┘
```

#### 1.1.2 INCREF与DECREF宏

CPython通过两个核心宏操作引用计数：

```c
// CPython Include/object.h
#define Py_INCREF(op) ( \
    _Py_INCREF((PyObject *)(op)))   // ob_refcnt++

#define Py_DECREF(op)  do { \
    PyObject *_py_decref_tmp = (PyObject *)(op); \
    if (--(_py_decref_tmp)->ob_refcnt == 0) { \
        _Py_Dealloc(_py_decref_tmp); \
    } \
} while (0)
```

**Py_INCREF**简单地增加`ob_refcnt`。**Py_DECREF**则复杂得多：减少引用计数后判断是否归零，归零则调用`_Py_Dealloc`触发`tp_dealloc`（类型的释放函数），真正回收内存。

**关键**：DECREF是**inline操作**，无函数调用开销，且在归零时**立即**调用`tp_dealloc`——这就是Python引用计数"即时回收"的源码根源。

INCREF/DECREF的调用频率极高——每一个Python操作背后都隐含了多次引用计数操作。以简单的`a = b`为例：

```c
// 简化的STORE_NAME字节码处理
case TARGET(STORE_NAME): {
    v = POP();                  // 从值栈弹出
    SETLOCAL(lnames[i], v);    // 设置局部变量
    // SETLOCAL内部:
    //   old = locals[i];       // 取旧值
    //   locals[i] = v;        // 赋新值
    //   Py_XDECREF(old);      // DECREF旧值
    //   (v已INCREF在栈上，无需再INCREF)
    break;
}
```

每次赋值至少涉及一次DECREF（旧值）和一次"保引用"（新值已在栈上INCREF过）。

#### 1.1.3 tp_dealloc——类型特定的释放函数

每个类型对象（`PyTypeObject`）都有一个`tp_dealloc`函数指针，负责该类型对象的销毁逻辑：

```c
// CPython Objects/listobject.c (list的dealloc)
static void
list_dealloc(PyListObject *op)
{
    Py_ssize_t i;
    PyObject_GC_UnTrack(op);  // 从GC追踪中移除
    Py_TRASHCAN_BEGIN(op, list_dealloc)
    i = Py_SIZE(op);
    while (--i >= 0) {
        Py_XDECREF(op->ob_item[i]);  // DECREF每个子元素
    }
    if (op->ob_item != NULL) {
        PyMem_Free(op->ob_item);     // 释放元素数组
    }
    Py_TYPE(op)->tp_free((PyObject *)op);  // 释放对象自身
    Py_TRASHCAN_END
}
```

`list_dealloc`展示了容器类释放的标准模式：先DECREF所有子元素（可能触发连锁DECREF），再释放自身内存。这决定了Python的内存回收是**递归的、连锁的**——一个容器归零会传播到所有子对象，形成"DECREF风暴"。

再来看`dict`的dealloc：

```c
// CPython Objects/dictobject.c (dict的dealloc)
static void
dict_dealloc(PyDictObject *mp)
{
    PyDictValues *values = mp->ma_values;
    Py_ssize_t i, n;
    
    PyObject_GC_UnTrack(mp);
    Py_TRASHCAN_BEGIN(mp, dict_dealloc)
    
    // 遍历键值对，DECREF每个key和value
    n = mp->ma_keys->dk_nentries;
    for (i = 0; i < n; i++) {
        Py_XDECREF(keys->dk_entries[i].me_key);
        Py_XDECREF(values[i]);  // 如果是split dict
    }
    
    // 释放哈希表结构
    // ...
    
    Py_TYPE(mp)->tp_free((PyObject *)mp);
    Py_TRASHCAN_END
}
```

`Py_TRASHCAN_BEGIN/END`是一个重要的安全机制：当DECREF链太深（递归释放大嵌套结构），可能导致C栈溢出。trashcan机制将嵌套释放延迟，避免栈溢出崩溃。

#### 1.1.4 演示：用ctypes直接读取ob_refcnt

我们可以用`ctypes`绕过Python API，直接读取对象的`ob_refcnt`字段：

```python
import ctypes
import sys

class PyObject(ctypes.Structure):
    """模拟CPython的PyObject结构体"""
    _fields_ = [
        ("ob_refcnt", ctypes.c_ssize_t),  # 8字节，引用计数
        ("ob_type", ctypes.c_void_p),     # 8字节，类型指针
    ]

def get_real_refcount(obj):
    """绕过sys.getrefcount的临时引用，直接读取ob_refcnt"""
    py_obj = ctypes.py_object(obj)
    addr = ctypes.addressof(py_obj)
    obj_struct = PyObject.from_address(addr)
    return obj_struct.ob_refcnt

# 实验：观察引用计数的精确变化
x = []
print(f"创建空列表: ob_refcnt = {get_real_refcount(x)}")  # 期望: 1

y = x  # 新增一个引用
print(f"y=x后: ob_refcnt = {get_real_refcount(x)}")      # 期望: 2

z = [x]  # 作为列表元素
print(f"放入列表后: ob_refcnt = {get_real_refcount(x)}") # 期望: 3

del y
print(f"del y后: ob_refcnt = {get_real_refcount(x)}")    # 期望: 2

del z
print(f"del z后: ob_refcnt = {get_real_refcount(x)}")    # 期望: 1

# 对比sys.getrefcount
print(f"\nsys.getrefcount(x) = {sys.getrefcount(x)}")    # 比1多1(临时引用)
print(f"get_real_refcount(x) = {get_real_refcount(x)}")  # 精确值

del x
# 此时ob_refcnt应归零，列表被回收
```

输出：

```
创建空列表: ob_refcnt = 1
y=x后: ob_refcnt = 2
放入列表后: ob_refcnt = 3
del y后: ob_refcnt = 2
del z后: ob_refcnt = 1

sys.getrefcount(x) = 2
get_real_refcount(x) = 1
```

**注意**：`sys.getrefcount()`比直接读取多1，因为它在调用时创建了临时引用（参数传递INCREF）。

深入一步：我们可以读取`ob_type`指针并验证它指向正确的类型对象：

```python
import ctypes

class PyObject(ctypes.Structure):
    _fields_ = [
        ("ob_refcnt", ctypes.c_ssize_t),
        ("ob_type", ctypes.c_void_p),
    ]

def inspect_object_header(obj):
    py_obj = ctypes.py_object(obj)
    addr = ctypes.addressof(py_obj)
    header = PyObject.from_address(addr)
    
    type_ptr = header.ob_type
    # 将类型指针转回PyObject来读取类型名
    type_obj = ctypes.py_object(obj.__class__)
    type_addr = ctypes.addressof(type_obj)
    
    print(f"对象地址: 0x{addr:x}")
    print(f"ob_refcnt: {header.ob_refcnt}")
    print(f"ob_type: 0x{type_ptr:x}")
    print(f"类型: {type(obj).__name__}")

inspect_object_header(42)
inspect_object_header("hello")
inspect_object_header([1, 2, 3])
```

#### 1.1.5 引用计数的关键特性

| 特性 | 说明 | 对比分代GC |
|------|------|-----------|
| **即时性** | 归零立即释放，无延迟 | GC有收集周期，对象死后可能存活到下次收集 |
| **确定性** | `__del__`调用时机完全可预测（最后一个引用消失时） | `finalize`/`__del__`时机不确定，可能在下次GC |
| **零停顿** | 无stop-the-world，不影响其他线程 | GC需要STW暂停所有线程（Java可达数百ms） |
| **增量式** | 每次操作的开销均摊到每次引用变化 | GC批量处理，瞬间可能有大开销 |
| **循环引用失效** | a→b→a时两者refcnt永不为0 | 专门设计来处理循环引用 |
| **内存开销** | 每对象8字节`ob_refcnt` | 需要标记位、card table等额外结构 |
| **缓存不友好** | 频繁INCREF/DECREF修改对象头 | GC周期运行，日常无修改开销 |
| **连锁释放** | 容器归零递归DECREF子对象 | 批量标记清除，无递归风险 |

### 1.2 引用计数的所有触发场景

引用计数的变化发生在**每一次对象绑定的建立与解除**。以下逐一枚举所有场景：

#### 1.2.1 赋值语句

```python
# 赋值 = 绑定名字到对象 → INCREF
a = obj        # obj.ob_refcnt += 1

# 重新赋值 = 解绑旧对象 + 绑定新对象
a = new_obj    # old_obj.ob_refcnt -= 1; new_obj.ob_refcnt += 1

# 多重赋值
a = b = c = obj  # obj.ob_refcnt += 3（三个名字绑定）

# 增量赋值（注意：创建新对象）
x = 1
x += 1  # 等价于 x = x + 1，创建新int对象，旧int的refcnt -= 1
```

**CPython字节码解析**：

```python
import dis
dis.dis("a = b = c = obj")
```

```
  1           0 LOAD_NAME                0 (obj)
              2 DUP_TOP
              4 STORE_NAME               1 (a)
              6 DUP_TOP
              8 STORE_NAME               2 (b)
             10 STORE_NAME               3 (c)
```

`DUP_TOP`复制栈顶引用（隐含INCREF），每次`STORE_NAME`都建立一个新的名字绑定。

```python
dis.dis("x = 1; x += 1")
```

```
  1           0 LOAD_CONST               0 (1)
              2 STORE_NAME               0 (x)

  2           4 LOAD_NAME                0 (x)
              6 LOAD_CONST               1 (1)
              8 INPLACE_ADD             # x + 1，创建新对象
             10 STORE_NAME               0 (x)  # x绑定新对象，旧int(1)的refcnt -= 1
```

#### 1.2.2 del语句

```python
a = obj
del a  # a绑定解除 → obj.ob_refcnt -= 1
```

**del不删除对象，只删除名字绑定**。对象是否被回收取决于是否还有其他引用。

```python
a = [1, 2, 3]
b = a
del a  # 列表.refcnt从2降到1，列表仍然存活（b引用它）
print(b)  # [1, 2, 3]
del b  # 列表.refcnt从1降到0，列表被回收！
```

#### 1.2.3 函数调用——参数绑定

```python
import sys

def func(param):
    # param绑定到传入对象 → 对象.ob_refcnt += 1（在调用时）
    print(f"函数内refcnt: {sys.getrefcount(param)}")
    # 函数返回时 → 对象.ob_refcnt -= 1（param解除绑定）

x = []
print(f"函数调用前: {sys.getrefcount(x)}")  # 某个值
func(x)
print(f"函数调用后: {sys.getrefcount(x)}")  # 应该与调用前相同
```

输出：

```
函数调用前: 2  # 变量x + getrefcount的临时引用
函数内refcnt: 4  # x + param + getrefcount临时 + 栈帧中的副本
函数调用后: 2  # 调用结束，param绑定解除
```

#### 1.2.4 函数返回——返回值引用

```python
def create_list():
    result = []
    # result绑定 → [].ob_refcnt = 1
    return result
    # 增加一个"返回值引用" → [].ob_refcnt = 2
    # 然后result离开作用域 → [].ob_refcnt = 1
    # 最终函数返回一个refcnt=1的对象

x = create_list()
# x绑定 → [].ob_refcnt = 2
```

Python函数返回时，会先INCREF返回对象（确保调用者拿到有效对象），然后局部变量DECREF，最终返回的对象`refcnt`恰好是1（如果调用者立即绑定）。

**CPython源码中的返回值处理**：

```c
// CPython Python/ceval.c
case TARGET(RETURN_VALUE): {
    retval = POP();  // 弹出返回值（已是INCREF过的状态）
    goto fast_block_end;  // 跳转到frame清理
    // frame清理时会DECREF所有局部变量
}
```

#### 1.2.5 容器操作——增删元素

```python
lst = []
dct = {}

# append/setitem → INCREF
lst.append(obj)     # obj.ob_refcnt += 1
dct['key'] = obj    # obj.ob_refcnt += 1
st = {obj}          # obj.ob_refcnt += 1

# pop/del → DECREF
lst.pop()           # obj.ob_refcnt -= 1
del dct['key']      # obj.ob_refcnt -= 1
st.remove(obj)      # obj.ob_refcnt -= 1

# 替换
lst[0] = new_obj    # old_obj.ob_refcnt -= 1; new_obj.ob_refcnt += 1

# 删除容器 → 所有元素DECREF
del lst  # 每个元素的ob_refcnt -= 1
```

**实验**：观察容器操作的引用计数变化：

```python
import sys

obj = object()  # 创建一个普通对象
print(f"初始: {sys.getrefcount(obj)}")  # 约2（obj变量 + 临时）

lst = [obj]
print(f"放入列表: {sys.getrefcount(obj)}")  # +1

dct = {'k': obj}
print(f"放入字典: {sys.getrefcount(obj)}")  # +1

tup = (obj,)
print(f"放入元组: {sys.getrefcount(obj)}")  # +1

st = {obj}
print(f"放入集合: {sys.getrefcount(obj)}")  # +1

del lst
print(f"删除列表: {sys.getrefcount(obj)}")  # -1

del dct, tup, st
print(f"全部删除: {sys.getrefcount(obj)}")  # 回到初始
```

#### 1.2.6 属性绑定

```python
class A:
    pass

a = A()
obj = []

a.attr = obj  # obj.ob_refcnt += 1（实例字典__dict__存储）
del a.attr    # obj.ob_refcnt -= 1
del a         # 实例DECREF，如果a还有其他属性则DECREF它们
```

属性赋值的字节码：

```python
import dis
dis.dis("a.attr = obj")
```

```
  1           0 LOAD_NAME                1 (obj)
              2 LOAD_NAME                0 (a)
              4 STORE_ATTR               2 (attr)
```

`STORE_ATTR`在CPython内部调用`PyObject_SetAttr`，该函数会INCREF新值、DECREF旧的属性值。

#### 1.2.7 with语句——上下文管理

```python
with open('test.txt') as f:
    # f绑定到文件对象 → refcnt += 1
    pass
# with块结束 → f.__exit__调用，然后DECREF f
```

#### 1.2.8 for循环——迭代器协议

```python
for item in iterable:
    # item绑定到iterable.__next__()的返回值 → INCREF
    # 循环体结束 → item解绑，DECREF（进入下一次迭代前）
    pass
# 循环结束，迭代器DECREF
```

字节码：

```python
import dis
dis.dis("for x in it: pass")
```

```
              2 GET_ITER                 # 获取迭代器
        >>    4 FOR_ITER                 6 (to 18)
              6 STORE_NAME               1 (x)

        >>   10 END_FOR
             12 LOAD_CONST               0 (None)
             14 RETURN_VALUE
```

`FOR_ITER`每次取下一个元素时INCREF返回值，循环变量`x`绑定时也是INCREF。迭代结束时DECREF迭代器和最后一个元素。

#### 1.2.9 异常处理——异常对象

```python
try:
    raise ValueError("error")
except ValueError as e:
    # e绑定到异常对象 → INCREF
    pass
# except块结束 → e解绑，DECREF异常对象
# 注意：在Python 3中，异常对象在except块结束时自动DECREF
```

#### 1.2.10 闭包捕获

```python
def outer():
    x = [1, 2, 3]  # x绑定的列表refcnt = 1
    
    def inner():
        print(x)   # 闭包捕获x → x的refcnt += 1
        return x   # 返回x → x的refcnt += 1（返回值）
    
    return inner   # 返回inner函数对象

f = outer()
# outer退出后，x的局部变量绑定解除
# 但闭包函数inner.__closure__持有x的引用
# 所以x的refcnt仍 > 0，不会被回收

del f
# inner函数被DECREF，如果inner归零
# 则inner.__closure__中的cell变量也被DECREF
# 级联导致x的refcnt -= 1
```

### 1.3 引用计数的性能影响

#### 1.3.1 内存开销分析

对于大量小对象，8字节/对象的引用计数开销不可忽视：

```python
import sys

# 大量自定义对象
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

# 单个Point实例的内存分析（64位系统）:
# - PyObject头部:  ob_refcnt(8B) + ob_type(8B) = 16B
# - __dict__指针:  8B
# - __weakref__指针: 8B（如果有弱引用支持）
# - __dict__本身: 约72B（空dict的初始大小）
# - 属性x的int对象: 28B（共享小整数时为0）
# - 属性y的int对象: 28B（共享小整数时为0）
# 合计约 132B+，其中ob_refcnt占8B ≈ 6%

# 更极端的情况：大量小int
# 每个PyLongObject: 28B，其中ob_refcnt占8B ≈ 29%
# 但CPython对小整数-5~256有缓存，实际不创建新对象

# 对比Java的Integer对象布局:
# - 对象头(Mark Word + Klass Pointer): 12-16B
# - int值: 4B
# - 对齐填充: 0-4B
# 合计: 16-24B，无refcnt字段但需要GC的card table等
```

100万个对象仅`ob_refcnt`就额外消耗：

```
1,000,000 × 8B = 8MB
```

对于一个内存敏感的应用，这不是小数目。

#### 1.3.2 CPU开销分析

每一次赋值、传参、返回、容器操作都触发INCREF/DECREF（虽然inline但仍是CPU指令）：

```python
import dis

def simple_add(a, b):
    c = a + b
    return c

dis.dis(simple_add)
```

```
  2           0 LOAD_FAST                0 (a)  # INCREF a
              2 LOAD_FAST                1 (b)  # INCREF b
              4 BINARY_ADD                      # DECREF a, DECREF b, INCREF result
              6 STORE_FAST               2 (c)  # INCREF result (for c)

  3           8 LOAD_FAST                2 (c)  # INCREF c (for return)
             10 RETURN_VALUE                     # return c (DECREF locals on frame exit)
```

一条`a + b`的背后是5次引用计数操作（2次LOAD_INCREF + 2次DECREF操作数 + 1次INCREF结果）。对于一个执行百万次的循环，这就是500万次引用计数操作。

**与C的对比**：

```c
// C等价代码
int simple_add(int a, int b) {
    int c = a + b;
    return c;
}
// 无任何引用计数操作，就是一个CPU的ADD指令
```

#### 1.3.3 Cache不友好

引用计数频繁修改对象头部的`ob_refcnt`字段，而这些修改会导致CPU缓存行失效：

```
线程1修改obj1.ob_refcnt → cache line dirty → 其他核心需要重新加载
线程2修改obj2.ob_refcnt → 如果obj2和obj1在同一cache line → false sharing
```

这在多线程环境下（即使有GIL）也是性能杀手——GIL保证正确性但不保证缓存友好性。

## 二、分代GC——循环引用的终结者

### 2.1 循环引用——引用计数的失效区

#### 2.1.1 什么是循环引用

当对象A引用B，B又引用A（或更长的环A→B→C→A）时，形成循环引用：

```python
class Node:
    def __init__(self, value):
        self.value = value
        self.next = None

# 创建循环引用
a = Node('A')
b = Node('B')
a.next = b  # a → b (b的refcnt +1)
b.next = a  # b → a (a的refcnt +1)

# 此时: a.refcnt = 2 (变量a + b.next)
#      b.refcnt = 2 (变量b + a.next)

del a  # a.refcnt = 1 (b.next仍引用它)
del b  # b.refcnt = 1 (a.next仍引用它)

# 两者refcnt都不为0，无法被引用计数回收
# 但实际上它们已不可达，形成内存泄漏！
```

**只有容器对象**（可以引用其他对象的对象）才能形成循环：

| 对象类型 | 能否形成循环 | 原因 |
|---------|------------|------|
| `list` | ✅ 能 | 可包含任意对象引用 |
| `dict` | ✅ 能 | 值可以是任意对象 |
| `set` | ✅ 能 | set本身可被引用（虽然元素需可哈希） |
| 自定义类实例 | ✅ 能 | 属性可以是任意对象 |
| `tuple` | ❌ 不能（通常） | 不可变，创建后无法添加引用；除非包含可变对象 |
| `int` | ❌ 不能 | 不可变，不引用其他对象 |
| `str` | ❌ 不能 | 不可变，不引用其他对象 |
| `float` | ❌ 不能 | 不可变，不引用其他对象 |

**特殊情况——包含可变对象的tuple可以被GC追踪**：

```python
import gc

t = ([],)  # 包含list的tuple
print(gc.is_tracked(t))  # True！因为它的元素可能形成循环

t2 = (1, 2, 3)  # 纯不可变tuple
print(gc.is_tracked(t2))  # False
```

#### 2.1.2 常见循环引用模式

```python
# 模式1：双向链表
class Node:
    def __init__(self):
        self.next = None
        self.prev = None

# 模式2：父子关系
class Parent:
    def __init__(self):
        self.children = []

class Child:
    def __init__(self, parent):
        self.parent = parent
        parent.children.append(self)

# 模式3：观察者模式
class Subject:
    def __init__(self):
        self.observers = []

class Observer:
    def __init__(self, subject):
        self.subject = subject
        subject.observers.append(self)

# 模式4：缓存自引用
_cache = {}

class Cached:
    def __init__(self, key):
        self.key = key
        _cache[key] = self  # 全局缓存引用，永不释放
```

### 2.2 分代GC算法

#### 2.2.1 三代假说

Python的GC基于"**分代假说**"（Generational Hypothesis）：
1. **大多数对象朝生夕死**（弱分代假说）——大部分对象在创建后很快变成垃圾
2. **越老的对象越不容易死**（强分代假说）——存活越久的对象越可能继续存活

据此，Python将可追踪对象分为**三代**：

```python
import gc

# 默认阈值
thresholds = gc.get_threshold()
print(f"GC阈值: gen0={thresholds[0]}, gen1={thresholds[1]}, gen2={thresholds[2]}")
# 输出: GC阈值: gen0=700, gen1=10, gen2=10
```

- **第0代（年轻代）**：新创建的可追踪对象。阈值700——当对象数≥700时触发收集
- **第1代（中年代）**：在第0代收集中存活的对象。每10次gen0收集，连带收集gen1
- **第2代（老年代）**：在第1代收集中存活的对象。每10次gen1收集，连带收集gen2

**与Java分代GC的对比**：

| 对比项 | Python GC | Java GC |
|--------|-----------|---------|
| 分代数 | 3代 | 理论上3代（新生代/老年代/永生代），实际更灵活 |
| 收集算法 | 标记-清除 | 新生代：复制算法；老年代：标记-整理 |
| 收集频率 | gen0频繁，gen2罕见 | Minor GC频繁，Full GC罕见 |
| 停顿 | 极短（Python对象数有限） | 可达数百ms（堆可能几十GB） |
| 空间划分 | 无独立空间，所有代共享堆 | Eden/Survivor/Old有独立空间 |
| 对象移动 | **不移动**（标记-清除） | **移动**（复制/整理，解决碎片） |

#### 2.2.2 GC内部数据结构

CPython源码中的分代结构：

```c
// CPython Modules/gcmodule.c (简化版)

struct gc_generation {
    PyGC_Head head;         // 链表头：该代所有对象的双向链表
    int threshold;          // 触发阈值
    int count;              // 当前对象计数（或收集计数）
};

// 全局分代数组
static struct gc_generation generations[NUM_GENERATIONS];  // NUM_GENERATIONS = 3
```

**PyGC_Head结构**——每个可追踪对象前置的GC头部：

```c
// CPython Include/objimpl.h
typedef struct {
    uintptr_t _gc_next;    // 下一个对象指针 (链表)，使用tagged pointer
    uintptr_t _gc_prev;    // 上一个对象指针
} PyGC_Head;

// 实际内存布局（对于被GC追踪的对象）：
// [PyGC_Head (16字节)] [PyObject (16字节)] [对象的实际数据...]
```

内存中一个被GC追踪的list对象：

```
┌─────────────┬─────────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│ _gc_next    │ _gc_prev    │ ob_refcnt│ ob_type  │ ob_size  │ ob_item  │ allocated│
│ (8B)        │ (8B)        │ (8B)     │ (8B)     │ (8B)     │ (8B)     │ (8B)     │
│ GC链表指针  │ GC链表指针  │ 引用计数 │ &list    │ 元素数   │ 元素数组 │ 已分配  │
├─────────────┴─────────────┼──────────┴──────────┴──────────┴──────────┴──────────┤
│  PyGC_Head (16B)         │             PyListObject 数据 (40B)                    │
└───────────────────────────┴──────────────────────────────────────────────────────┘
```

被GC追踪的对象额外消耗**16字节**（PyGC_Head）+ **16字节**（PyObject头部）= 32字节最小开销。

GC链表将同一代的所有对象串在一起，方便mark-and-sweep时遍历：

```
gen0.head ⇄ objA ⇄ objB ⇄ objC ⇄ ... ⇄ gen0.head
gen1.head ⇄ objX ⇄ objY ⇄ ... ⇄ gen1.head
gen2.head ⇄ objP ⇄ objQ ⇄ ... ⇄ gen2.head
```
