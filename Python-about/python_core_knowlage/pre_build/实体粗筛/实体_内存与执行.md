║  【运行时】引用计数与垃圾收集                              ║
║  编号: E033 | 来源: 提取清单C120+C121+C122               ║
╚═══════════════════════════════════════════════════════════╝

【定义】 CPython内存管理采用引用计数(reference counting)为主、分代垃圾收集(generational GC)为辅的双轨机制: 引用计数回收无引用对象, GC回收循环引用对象。

【结构】"它长什么样？"
- 引用计数: ob_refcnt(Py_ssize_t), 在PyObject基类中
  - INCREF: ob_refcnt++
  - DECREF: ob_refcnt--, 归零时调用tp_dealloc释放
  - 引用传递: 函数传参、赋值、列表添加、dict插入都INCREF
  - 引用释放: 变量离开作用域、del obj、容器清空都DECREF
- 分代GC (gc module):
  - 三代: generation 0(新对象), generation 1, generation 2(长期存活)
  - 阈值: 每代有分配阈值, gen0超过阈值触发GC
  - 代升级: 在GC中存活的对象提升到下一代
  - 循环引用检测: 遍历对象图查找不可达环
- 引用复制:
  - 直接赋值 a = b: a和b指向同一对象 (引用复制)
  - 浅拷贝 copy.copy(x): 新容器对象, 元素引用原对象 (仅顶层复制)
  - 深拷贝 copy.deepcopy(x): 递归复制所有嵌套对象 (完全独立副本)

【时序】"它按什么顺序动？"
- 引用计数变化:
  - a = 1: INCREF(1) → ob_refcnt=2 (含小整数池)
  - b = a: INCREF(1) → ob_refcnt=3
  - del a: DECREF(1) → ob_refcnt=2
  - b = None: DECREF(1) → ob_refcnt=1
  - 函数返回: 局部变量全部DECREF

- GC触发:
  1. 分配新对象 → gen0计数增加
  2. gen0计数达到阈值(默认700) → 暂停分配→遍历gen0对象→标记不可达→回收
  3. 清理后存活对象→提升到gen1, gen0清零
  4. gen1达到阈值(默认10)→同时回收gen0和gen1→存活提升到gen2
  5. gen2达到阈值(默认10)→回收所有代(full GC)

- 浅拷贝 vs 深拷贝:
  - copy.copy(lst):
    1. 创建新list对象
    2. 遍历lst → INCREF每个元素 → 放入新list
    3. 返回新list (元素与lst共享)
  - copy.deepcopy(lst):
    1. 创建memo dict (防止循环引用无限递归)
    2. 递归拷贝每个元素:
       - 不可变对象 → 直接返回引用
       - 可变对象 → 创建新对象 → 递归拷贝子元素
    3. 返回完全独立副本

【实体】"它的最小数据单元？"
- ob_refcnt: Py_ssize_t (CPython用ssize_t, 有符号, 支持负数检测)
- GC头: PyGC_Head {gc_refs, gc_prev, gc_next} (参与GC的对象链表节点)
- 小型对象分配器: obmalloc (256KB arenas → 4KB pools → 固定size blocks)

【边界】"它在哪里交出控制权？"
- 引用计数: 确定性析构(引用归零立即释放), 但无法处理循环引用
- GC: 非确定性, 由阈值触发, 可通过gc.disable()关闭
- __del__: 析构函数执行时机不确定(GC顺序), 可能有复活现象
- 循环引用检测代价: O(N)扫描, full GC可能显著暂停
- 深拷贝: 无限递归时RecursionError
- GIL保护: ob_refcnt操作不是原子的(C扩展中GIL保护)

【内部关联】
- INCREF --[触发(引用→计数+1)]--> ob_refcnt
- DECREF --[触发(引用释放→归零析构)]--> tp_dealloc
- GC --[触发(循环检测→回收环)]--> 遍历对象图
- copy.copy --[使用(浅层→INCREF)]--> 元素引用

【薄概念合并】 C120+C121+C122 同属内存管理三层面。

【示例】
```python
import gc, copy

# GC
gc.set_debug(gc.DEBUG_STATS)
lst = []
lst.append(lst)  # 循环引用
del lst
gc.collect()     # 手动触发GC回收

# 浅拷贝 vs 深拷贝
original = [[1, 2], [3, 4]]
shallow = copy.copy(original)
deep = copy.deepcopy(original)
original[0][0] = 99
print(shallow)   # [[99, 2], [3, 4]]  跟着变了
print(deep)      # [[1, 2], [3, 4]]   独立

# 引用计数观察
import sys
a = []
print(sys.getrefcount(a))  # 2 (a本身 + getrefcount形参)
```

╔═══════════════════════════════════════════════════════════╗
║  【运行时】编译与执行模型                                  ║
║  编号: E034 | 来源: 提取清单C124+C125                     ║
╚═══════════════════════════════════════════════════════════╝

【定义】 Python执行流程: 源码→词法分析(Token)→语法分析(AST)→语义分析(符号表)→编译(字节码)→PVM(Python Virtual Machine)执行; GIL(Global Interpreter Lock)确保CPython解释器同一时刻仅一个线程执行字节码。

【结构】"它长什么样？"
- 编译阶段(前端):
  1. Tokenizer: 源码 → Token流 (Parser/tokenize.c)
  2. Parser: Token → CST → AST (Parser/parser.c, PEG解析器, Python 3.9+)
  3. Symbol Table: AST → 作用域分析 → 名字分类(局部/全局/自由变量)
  4. Compiler: AST → CFG → 字节码 (Python/compile.c)
  5. 输出: PyCodeObject (字节码 + 元数据)

- 执行阶段(后端):
  - PVM: ceval.c中的 _PyEval_EvalFrameDefault 主循环
  - 每条字节码: switch(opcode) → case 对应操作 → eval breaker周期性检查
  - 栈帧: PyFrameObject {上一帧, 指令指针, 栈, locals, globals}

- GIL:
  - 一个互斥锁(PyThread_type_lock)
  - 获取GIL → 执行字节码 → 每100条指令(or I/O时)释放GIL → 重新获取
  - 作用: 保护CPython解释器状态(引用计数/内存分配)的一致性
  - 影响: CPU密集型多线程无加速(单核跑), I/O密集型多线程有效(I/O时释放GIL)

- 编译产物缓存: .pyc文件 (__pycache__/module.cpython-314.pyc)
  - 包含magic number(版本标识), 源码size, 修改时间戳, 字节码

【时序】"它按什么顺序动？"
- import时的完整流程:
  1. 查找.py文件 → 检查.pyc是否最新
  2. 若过期: 读取.py → 完整的编译流水线 → 写入.pyc
  3. 加载: 从.pyc读PyCodeObject → 创建模块 → exec(code, module.__dict__)

- GIL释放/获取:
  1. 线程启动: 尝试获取GIL(阻塞直到排队获取)
  2. 执行: 执行 ~100字节码 或 until I/O → 释放GIL
  3. 信号处理: eval breaker检查(pending calls/异步事件)
  4. 线程切换: 内核调度, 获GIL者执行

- Python 3.12+: PEP 684 (per-interpreter GIL) 允许多解释器各自持有独立GIL

【实体】"它的最小数据单元？"
- PyCodeObject: co_code(字节码bytes), co_consts, co_names, co_varnames, co_stacksize
- PyFrameObject: f_code, f_lasti(指令索引), f_localsplus(局部变量+值栈)
- GIL: 一个pthread_mutex(or Windows CRITICAL_SECTION)

【边界】"它在哪里交出控制权？"
- 字节码边界: 每条字节码执行完检查eval breaker → 可能处理信号/异步事件/释放GIL
- GIL: 阻止真正的CPU并行(多核场景)
- .pyc: 跨版本不兼容(magic number不同)
- compile/exec/eval: 动态执行代码的安全风险
- PyFrameObject: 栈帧在堆上(非C栈) → 可序列化(生成器/协程依赖此)

【内部关联】
- 源码 --[触发(编译→字节码)]--> PyCodeObject
- PVM --[触发(执行→帧)]--> PyFrameObject
- GIL --[触发(锁→串行)]--> 单线程执行字节码

【薄概念合并】 C124+C125

【示例】
```python
import dis

def greet(name):
    return f"Hello {name}"

dis.dis(greet)  # 查看字节码

# GIL演示 (多线程CPU密集无加速)
import threading, time

def count(n):
    while n > 0:
        n -= 1

# 单线程
start = time.time()
count(50_000_000)
print(f"Single: {time.time()-start:.2f}s")

# 多线程 (GIL限制, 可能更慢)
t1 = threading.Thread(target=count, args=(25_000_000,))
t2 = threading.Thread(target=count, args=(25_000_000,))
start = time.time()
t1.start(); t2.start()
t1.join(); t2.join()
print(f"Threaded: {time.time()-start:.2f}s")
```
