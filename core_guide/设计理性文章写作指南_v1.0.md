## 核心定位

本系列文章不是教程、不是源码导读、不是API参考。它占领的生态位是**设计理性推导**——回答"为什么必须是这样，不这样行不行"。

读者读完后获得的不是"我会用了"，而是"我知道为什么必须这样设计，换一个技术栈我能判断哪些设计保留、哪些必须换"。

---

## 护城河原则

**本系列文章绝不暴露建模方法论本身**。方法论是底层引擎，文章是面向读者的产出。引擎不可见，但驱动力在每篇文章的逻辑线中体现。

具体禁令：
- 不得出现任何方法论术语：0号约束、代价集群、冲突挤压、设计内因、SC编号、四维锚点、S1/S2/S3、V系列验证、构建依赖等
- 不得出现类似的框架性描述，如"根据XX模型推导"、"按照XX步骤分析"
- 不得在文章中暴露推导公式或结构化步骤

读者感受到的应该是"自然推导"——困境→被迫选择→代价→下一个困境，而非"套用框架"。

## 文章结构规范

### 章节过渡公式

"已闭合的环 + 新裂开的口"

- 上一章结尾 = 本章解决了什么（闭合感）+ 但这个方案本身又撕开了什么（缺口感）
- 下一章开头 = 捡起这个缺口，展开为新的困境

闭合感给读者成就感，缺口感给读者方向感。两者缺一不可：
- 只有闭合没有缺口 → 读者觉得"已经完了"而懈怠
- 只有缺口没有闭合 → 读者觉得"什么都没解决"而疲惫

### 单篇结构

每篇文章遵循四段式结构：

```
1. 通用困境 → "这类系统都会面对什么问题"（读者代入："这不是Python的事，是我的事"）
2. 具体困境实例化 → "在我们的系统中这个问题如何触发、违反后会怎样"
3. 被迫的设计选择 → "你试试不用这个机制"（用失败路径证明必然性）
4. 代价 + 悬念 → "这个选择丧失了什么"+"还缺什么"（指向下一篇）
```

### 叙事规则

1. **困境先行，不先给答案**。任何组件引入前，读者必须先感到"确实没有别的出路了"。
2. **用失败路径证明必然性**。"你试试不用三队列"比"三队列的好处是"有力100倍。写代码展示崩溃，而非描述正确用法。
3. **代价诚实标注**。每个设计选择说完优势后，必须紧接着说代价。不允许只写好处。但不用"代价："这样的标签——自然融入叙事即可。
4. **通用困境跨系统引用**。在合适的地方自然提到"Node.js的setImmediate就是同类解法"、"Go的errgroup解决的是同样的问题"——这使读者感到"哇，真的是同一类问题"，而非刻意对比。
5. **代码示例写崩溃路径**。展示"问题暴露"的代码，而非"正确用法"的代码。正确用法读者能在官方文档找到，崩溃路径只有我们写。

## 禁止事项

1. 禁止方法论术语（见护城河原则）
2. 禁止"让我们来看看asyncio是怎么做的"这类导游式开头
3. 禁止堆API参数列表——那是官方文档的事
4. 禁止"总结一下"式结尾——必须以代价+悬念结尾
5. 禁止纯描述性段落——每段必须有信息增量

## 素材来源映射

文章内容来源于建模产物，但**经过叙事转换**，读者不应感知到后面的结构。

| 文章中的要素 | 来源产物 | 叙事转换 |
|---|---|---|
| 通用困境 | S3节点通用困境 + 实体设计内因通用困境 | 直接使用，但去掉维度标签和编号 |
| 具体困境实例 | S3冲突表现 + 实体设计内因场景段 | 改写成叙事：先描述问题场景，再写代码展示崩溃 |
| 被迫选择 | S3设计选择 + 实体设计内因选择段 | 用"你试试不用"的反证模式引入，而非"它使用了XX" |
| 代价 | S3代价集群 + 实体设计内因代价段 | 自然融入叙事，不说"代价是"，而说"但这个选择意味着..." |
| 设计细节 | 实体四维描述(结构/时序/实体/边界) | 只在需要解释"为什么这样实现"时才展开，不做全面描述 |
| 角色交互 | 实体内部关联(角色标注) | 用叙事描述"谁在什么身份下和谁交互"，不出现箭头标注格式 |
| 跨系统对比 | 通用困境本身的外延 | 自然提及，不做独立章节（下一篇系列或衍生篇才展开） |
