# 《三源约束提取协议》

核心原则：**源码/文档提供一手信息，LLM 提供逻辑验证，体系结构提供物理铁律。**

#### 信息源 1：源码与官方文档 —— 【表层摩擦提取】
**作用**：发现系统在防御什么、妥协什么。
**提取目标**：显性约束、副作用、异常报错。

**提取手法**：
1.  **找“不要”和“必须”**：文档中所有出现 "must not", "avoid", "never", "ensure" 的地方，背后都是硬性约束。
    *   *示例*：asyncio 文档说 "Never call blocking I/O from the event loop"。 -> **提取表层约束：EventLoop 怕阻塞。**
2.  **找异常与边界守卫**：源码中的 `raise InvalidStateError` 或 `if not ... raise` 是约束的强制执行点。
    *   *示例*：`futures.py` 中 `if self._state != _PENDING: raise InvalidStateError`。 -> **提取表层约束：Future 状态不可逆。**
3.  **找逃生舱**：系统提供的妥协方案，往往指向了无法绕过的底层限制。
    *   *示例*：asyncio 提供了 `run_in_executor`。 -> **反推约束：单线程内必然存在无法协程化的阻塞操作，必须借用多进程/线程。**

#### 信息源 2：体系结构与物理常识 —— 【隐性约束注入】
**作用**：提供第一性原理的物理/架构约束，解答“为什么会有表层摩擦”。
**提取目标**：物理极限、平台硬性限制。

**提取手法**：依靠工程师的先验知识，或通过 LLM 联网检索体系结构常识。
*   *推演*：为什么 EventLoop 怕阻塞（信息源1）？因为单线程串行执行时，一个卡住，全盘皆输。为什么单线程要并发？因为 CPU 比磁盘/网络快千万倍。 -> **注入约束：CPU/I/O 速度鸿沟（物理），单线程串行指针（架构）。**

#### 信息源 3：LLM 大模型 —— 【深度追问与跨界推演】
**作用**：当你从源码提取了表象，但缺乏体系结构知识来解释时，用 LLM 作为“约束挖掘机”。
**提取目标**：填补 1（表象）和 2（约束）之间的逻辑黑洞。

**LLM 专属 Prompt 模板（约束追问法）**：
当你从文档/源码发现一个设计特征（D）或限制（L）时，向 LLM 提问：

> "在 {技术领域} 中，我观察到存在这样的设计/限制：{填入信息源1的发现，如：asyncio采用单线程协作式调度，遇到阻塞会卡死}。
> 请帮我进行约束逆向推导：
> 1. 这种设计是为了规避什么更严重的副作用？（逼出架构约束）
> 2. 这种设计妥协了什么能力？为了弥补这个妥协，系统必须引入什么新机制？（逼出内部冲突）
> 3. 支撑这一切的底层物理规律或计算机体系结构常识是什么？（逼出物理约束）
> 请用工程化的语言分点回答。"

### 执行闭环：三源融合验证

提取出约束后，不能直接信任，必须通过源码进行**闭环验证**。因为 LLM 可能会幻觉出看似合理但该系统并未采纳的约束。

**验证算法**：
**推导出的底层约束 => 必须在源码中找到对抗该约束的“防御性设计”**

**实操案例**：

1.  **假设推导**：通过 LLM 追问，得出底层约束为“**多线程上下文切换开销大且存在 GIL 竞争**”。
2.  **源码寻宝**：如果这个约束是真的，asyncio 的源码里必然有机制在对抗它。
3.  **验证命中**：我们在 `base_events.py` 中找到了 `run_in_executor`，它小心翼翼地将阻塞操作外包，并使用 `call_soon_threadsafe` 跨线程通信，极力避免直接创建多个线程来跑协程。源码证实了该约束的存在。
4.  **确认入库**：该约束通过验证，写入 `S1_维度约束矩阵`。
