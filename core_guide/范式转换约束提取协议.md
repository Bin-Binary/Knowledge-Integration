# 《范式转换约束提取协议》

## 定位

与《三源约束提取协议》互补，同属冲突建模的分析协议层：

| 协议 | 提取对象 | 性质 | 回答的问题 |
|------|---------|------|-----------|
| 三源约束提取协议 | 静态事实(物理定律、架构硬性、业务诉求) | 静态约束 | "当前状态受什么约束？" |
| 范式转换约束提取协议 | 动态转换(范式转变的前提条件与影响传导) | 动态转换约束 | "范式转变过程中必须满足什么前提、产生什么影响？" |

两者共同构成冲突建模的完整输入：三源协议提供约束底座，本协议提供转换层的必然性推导。

---

## 核心论题

**现有框架的缺口**

冲突推导链(S3)采用"G x A -> D1 -> 代价集群{C1,...Cn}"的推导结构。但在范式转换型系统中，D1的形态无法仅从代价集群推导——因为D1的部分组成响应的是**上游范式转换的继承影响**，而非本源转换的自身代价。

asyncio案例：EventLoop无法从C1-C4推导。EventLoop响应的是"控制权真空需要一个调度中枢"这一继承影响，它来自上游转换(阻塞->非阻塞 + 单一等待->多路复用)，而非本源转换(同步->异步)丧失的同步特性。

**本协议的核心主张**

> 核心范式转换时，会继承上游范式转换的影响。**完整代价 = 继承影响集 + 自身代价集群**。

- 继承影响解释"为什么必须存在X"（EventLoop、回调）
- 自身代价解释"为什么必须修复Y"（上下文悬空、结果不可达）
- 二者共同构成设计推导的完整动力来源

## 关键定义

| 术语 | 定义 | asyncio示例 |
|------|------|------------|
| **范式转换** | 系统运行模型发生根本性转变，旧范式的特性不再自动成立 | 同步->异步 |
| **上游范式转换** | 本源转换的前提转换，必须先完成才能发生本源转换 | 阻塞->非阻塞 |
| **本源范式转换** | 当前分析的核心转换，是框架存在的根本理由 | 同步->异步 |
| **转换前提条件** | 使范式转换得以发生的必要条件，通常是上游转换的产出 | "I/O必须非阻塞" |
| **继承影响** | 上游转换传导至本源转换的设计驱动力，要求本源转换必须安排特定机制来承接 | "需要调度中枢"驱动EventLoop |
| **自身代价集群** | 本源转换自身丧失的原有保证(与S3代价集群一致) | C1-C4 |
| **完整代价** | 继承影响集 + 自身代价集群 | {I3,I4} + {C1,C2,C3,C4} |
| **条件** | 使转换可能存在，不直接驱使设计响应 | I/O非阻塞是条件 |
| **影响** | 驱使系统必须设计特定机制来承接的需求 | 需要调度中枢是影响 |

**条件 vs 影响的判定方法**：追问"如果去掉这个项，系统是需要一种新的机制(影响)，还是转换根本不可能发生(条件)？"

**溯源法**（判定影响归属）：追问"这个影响最初是在哪个转换中产生的？"追溯至上游则为继承影响，追溯至本源则为自身代价。

## 协议步骤

### Step 1: 识别范式转换链

**目标**：识别知识框架涉及的所有范式转换，按依赖关系排序。

**执行**：

1. 确定本源范式转换：该框架存在是为了完成什么根本性的模型转变？
2. 追溯上游转换：本源转换要求什么前提？这个前提本身是否也是一个范式转换？
3. 递归追溯直到遇到非范式转换型前提（属于静态约束，停在这里，那是三源协议的职责）
4. 将所有转换按依赖序排列：T1 -> T2 -> ... -> Tn(本源)

**前置判断——是否适用本协议**：
- 若框架不涉及范式转换（渐进增强型、聚合型框架），标注"不适用"并说明理由，跳过本协议
- 若存在范式转换，继续

**输出**：范式转换链（有序列表，每项标注：转换编号、转换名称、从->到、是否本源）

---

### Step 2: 分解转换层（前提条件 -> 继承影响）

**目标**：对每个转换，识别其前提条件和产生的影响，区分条件与影响，标注维度。

**执行**：对范式转换链中的每个转换Ti：

1. **识别前提条件**：Ti发生之前必须满足什么？(来自上游转换的产出或三源协议的静态约束)
2. **识别影响集**：Ti发生后，产生了什么新的设计驱动力？（"Ti完成后，系统必须安排什么机制来承接？"）
3. **区分条件与影响**：用判定方法(见定义部分)逐项判定
4. **标注主辅**：
   - 主影响：直接驱动核心设计决策
   - 辅影响：驱动辅助/支持性机制
   - **若无法清晰判定，标注"待定"，不强分**
5. **标注维度**：每项影响必须打上维度标签(时序/结构/实体/边界)

**汇总**：本源转换Tn的完整代价 = 来自所有上游转换的继承影响集 + Tn自身代价集群

**输出**：每个转换Ti的影响清单（维度标签、主辅/待定、条件/影响分类）；本源转换的完整代价

---

### Step 3: 完整代价 -> 推导设计

**目标**：从完整代价推导通用设计与体系设计。

**3a. 通用设计（从继承影响推导）**

所有经历相同范式转换链的系统都必须安排的机制：

- 继承影响Ii -> 通用设计组件Di(what: 必须解决什么问题)
- 通用设计预告**结构性必然**，不预告**具体解法**(how)

示例："需要调度中枢"(I3) -> 通用设计：所有异步系统必须有调度中枢。具体为EventLoop/libuv主循环/Go scheduler是how的选择。

**3b. 体系设计（通用设计 + 具体约束）**

通用设计Di + 0号约束Ai(来自S2) + 0号约束以外的架构/业务约束 -> 本系统的具体设计选择

**推导能力声明**：

| 可推导层级 | 含义 | 示例 |
|-----------|------|------|
| 结构性必然 | 必须有什么 | 必须有调度中枢 |
| 受约束倾向 | 在特定约束下倾向于怎么做 | Python+单线程 -> 用户态EventLoop |
| 工程偶然 | 不可推导 | ensure_future vs create_task的反复 |

动态约束(向后兼容、社区反馈、已有生态)可能影响设计但未纳入推导，应在附录注明。

---

### Step 4: 不确定部分标记

对以下情况写入附录，标注"待定"或"边界待厘清"：

1. 转换分组粒度不确定（两个转换是否应合并？）
2. 主辅分类无法清晰判定
3. 条件与影响的边界模糊
4. 继承影响与三源协议静态约束的重叠关系待厘清
5. 本协议对新框架类型的适用性待验证

不强行给出确定结论。后续集成时可升级"待定"为"确定"，或降级为"不适用"。

## 与现有框架的集成关系

```
三源约束提取协议 ---> S1_维度约束矩阵 ---> S2_0号约束
                                              |
范式转换约束提取协议 ---> S0_范式转换链 --------+
                                              |
                                              v
                                       S3_冲突推导链
                                  (增强：N0节点引用S0的完整代价)
```

**集成方式**：

1. 本协议产出`S0_范式转换链.md`，存放于冲突建模目录
2. S3的N0节点模板增强：
   - 新增"转换前提"字段：引用S0的前提条件
   - 新增"继承影响"字段：引用S0的继承影响集
   - "代价集群"字段微调：仅包含自身代价(完整代价 = 继承影响 + 代价集群)
3. S3推导链中，D1的形态解释从S0的继承影响获取
4. 冲突模型构建指南新增"Step 0: 范式转换链识别"，引用本协议

## 示例：asyncio范式转换链

### Step 1 产出

| 编号 | 转换名称 | 从 -> 到 | 类型 |
|------|---------|---------|------|
| T1 | I/O模型转换 | 阻塞I/O -> 非阻塞I/O | 上游 |
| T2 | 就绪检测转换 | 单一等待 -> I/O多路复用 | 上游 |
| T3 | 执行模型转换 | 同步执行 -> 异步执行 | 本源 |

### Step 2 产出

**T1: 阻塞I/O -> 非阻塞I/O**
- 前提条件：OS支持非阻塞模式(O_NONBLOCK / WSA)
- 产出：
  - I1(边界·条件)：I/O操作不阻塞线程，立即返回EAGAIN -> 使"遇到IO就跳过"物理可能
  - I2(边界·影响·辅)：需要就绪检测机制知道哪个I/O准备好了 -> 驱动T2

**T2: 单一等待 -> I/O多路复用**
- 前提条件：OS提供select/poll/epoll/IOCP
- 产出：
  - I3(时序·影响·主)：控制权真空 -> 需要调度中枢决定"接下来执行谁" -> 驱动EventLoop
  - I4(边界·影响·主)：就绪事件需绑定处理逻辑 -> 驱动回调机制

**T3: 同步执行 -> 异步执行 [本源]**
- 前提条件：T1(非阻塞I/O) + T2(I/O多路复用)
- 继承影响集：{I3(时序:需要调度中枢), I4(边界:需绑定完成动作)}
- 自身代价集群：{C1(结构:上下文悬空), C2(边界+实体:结果不可达), C3(时序:时序失控), C4(结构:逃逸代码块)}
- **完整代价 = {I3, I4} + {C1, C2, C3, C4}**

### Step 3 产出

| 完整代价项 | 通用设计(what) | +具体约束 -> asyncio设计(how) |
|-----------|--------------|--------------------------|
| I3(时序:需要调度中枢) | 所有异步系统必须有调度中枢 | Python+单线程+GIL -> 用户态EventLoop |
| I4(边界:需绑定完成动作) | 所有异步系统必须有完成通知机制 | 单线程协程 -> 回调(Handle+done_callback) |
| C1(结构:上下文悬空) | 必须有机制保存执行断点 | CPython有generator -> 协程+Task |
| C2(边界+实体:结果不可达) | 必须有实体锚定未来结果 | Future状态机(PENDING->FINISHED) |
| C3(时序:时序失控) | 必须有协程间时序协调机制 | 单线程协作式 -> Future-based同步原语 |
| C4(结构:逃逸代码块) | 必须有任务生命周期管理 | TaskGroup+Timeout+Runner |

**推导能力边界**：
- 可推导：必须有调度中枢、必须有完成通知、必须有断点保存、必须有结果锚定
- 可推导(受约束倾向)：Python下调度中枢为用户态EventLoop、协程基于generator实现
- 不可推导：create_task vs ensure_future的历史反复、gather的API设计

### Step 4 产出（附录-不确定部分）

1. **转换粒度**：T1和T2是否应合并为"阻塞->非阻塞+多路复用"？当前拆分基于"I/O模型"和"就绪检测"是两个不同的OS能力层。但若有人认为它们不可分割(因为非阻塞必然需要某种就绪检测才实用)，也合理。当前标注"当前最佳拆分，待迭代修订"。

2. **I2归属**：I2(需要就绪检测)是T1的影响还是T2的条件？当前标注为T1的影响(辅)，因为它从T1的"非阻塞"直接衍生。但也可理解为T2的前提条件。边界待厘清。

3. **继承影响与0号约束的关系**：A4(应用无法感知内核I/O完成)与I4(需绑定完成动作)描述同一现象的不同层面——A4是什么(约束)，I4是必须做什么(影响响应)。不视为重叠，但精确关系待厘清。

4. **适用范围**：本协议在范式转换型框架(asyncio/tokio/libuv)中验证有效，在非范式转换型框架中待验证。

## 附录：与三源协议的边界

| 维度 | 三源约束提取协议 | 范式转换约束提取协议 |
|------|----------------|-------------------|
| 提取对象 | 静态事实 | 动态转换过程 |
| 分析视角 | "系统当前受什么约束" | "范式转变过程中必须满足什么、产生什么" |
| 时间性 | 无时间性(一直成立) | 有时间性(转换前后不同) |
| 输出归属 | S1维度约束矩阵 | S0范式转换链 |
| 重叠地带 | 物理定律/架构硬性约束 | 转换前提条件(可能引用同一条约束) |

**处理原则**：当两者涉及同一事实时，三源协议描述约束本身(是什么)，本协议描述转换对该约束的响应(必须做什么)。互补而非重叠。
