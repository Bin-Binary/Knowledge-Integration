# S1: 维度约束矩阵

## 扫描过程

从三源协议(体系结构常识 / CPython源码机制 / 官方文档与业务需求)出发，按物理层→架构层→业务层逐级扫描，提取所有对asyncio设计产生刚性压迫的约束。每条约束被归入其主要的**压迫维度**：

| 维度 | 含义 | 检验标准 |
| :--- | :--- | :--- |
| **时序** | 时间轴上的顺序、并发、等待关系 | 能否在时间轴上重叠多个操作？ |
| **结构** | 代码组织形态、调用栈、作用域 | 能否中途切断并恢复执行流？ |
| **边界** | 跨域接口(内核/用户态、线程间、模块间) | 能否感知域外事件？ |
| **实体** | 数据对象的状态、生命周期、持久性 | 结果是否能被锚定和获取？ |

## 约束矩阵

| 约束编号 | 扫描层级 | 约束描述 | 压迫维度 | 来源(三源协议) |
| :--- | :--- | :--- | :--- | :--- |
| C_Phys_1 | 物理层 | CPU速度极快(纳秒级)，I/O极慢(毫秒~秒级)，存在约10^6倍速度鸿沟 | 时序 | 体系结构常识 |
| C_Phys_2 | 物理层 | 网络延迟不可预测且回路时间长(RTT毫秒~百毫秒) | 时序 | 网络物理特性 |
| C_Arch_1 | 架构层 | Python单线程控制流严格串行执行(解释器主循环逐条执行字节码) | 时序 | CPython源码机制 |
| C_Arch_2 | 架构层 | 传统函数调用栈是连续压栈的，栈帧结构固化，无法在中途切断并恢复执行 | 结构 | Python调用栈机制/源码:frame对象不可序列化 |
| C_Arch_3 | 架构层 | CPython GIL阻止多线程真正并行执行Python字节码，跨线程上下文切换开销大(微秒级) | 边界 | CPython GIL源码 |
| C_Arch_4 | 架构层 | 操作系统I/O操作(读写socket/文件)跨越内核态/用户态边界，系统调用开销且阻塞 | 边界 | OS内核机制 |
| C_Arch_5 | 架构层 | 操作系统提供I/O多路复用机制(select/poll/epoll/IOCP)可同时监听多个I/O通道的就绪状态 | 时序 | OS内核机制/源码:selector_events.py |
| C_Biz_1 | 业务层 | 必须支持高并发重叠I/O等待(数千连接同时等待不同I/O操作完成) | 时序 | 官方文档:asyncio是"使用协程编写并发代码"的库 |
| C_Biz_2 | 业务层 | 异步操作的结果必须能被正确获取或传播异常 | 实体 | 业务需求 |
| C_Biz_3 | 业务层 | 用户代码需要简洁的编程模型(避免回调地狱) | 结构 | 业务需求/社区痛点 |

## 维度分析

### 时序维度占据主导(6条约束直接涉及时序)

C_Phys_1、C_Phys_2、C_Arch_1、C_Arch_5、C_Biz_1 均直接压迫时序维度——它们共同刻画了一个核心矛盾：**时间轴上存在大量I/O等待空隙，而串行执行流无法利用这些空隙**。这是asyncio存在的根本理由。

### 结构维度是关键瓶颈(C_Arch_2 + C_Biz_3)

传统函数的连续栈帧结构是物理现实，它与时序维度的"需要中途切出"需求直接冲突。C_Biz_3进一步要求解决方案必须是**简洁的编程模型**，排除了手动状态机等丑陋方案。

### 边界维度划定了可行解空间(C_Arch_3 + C_Arch_4)

GIL(C_Arch_3)排除了"用多线程绕过串行限制"这条路径；内核/用户态边界(C_Arch_4)划定了"应用无法主动感知I/O完成"这一事实。二者共同将解空间压缩到**单线程+I/O多路复用**这一方向。

### 实体维度确保结果可达(C_Biz_2)

无论执行流如何切换、协程如何挂起/恢复，异步操作的结果必须作为一个**可锚定的实体**被后续代码获取。这是从业务需求中提取的硬约束，不允许结果"丢失在异步黑洞中"。

### 维度间交叉

约束并非孤立压迫单一维度，多条约束存在跨维度交叉：
- **C_Phys_1 × C_Arch_1 × C_Biz_1**：时序维度的三重压迫——速度鸿沟+串行执行+需要高并发，三者叠加构成了asyncio必须解决的核心矛盾
- **C_Arch_2 × C_Biz_3**：结构维度的双重压迫——栈帧不可切断+需要简洁模型，二者叠加排除了"手动状态机"等低级方案
- **C_Arch_3 × C_Arch_4**：边界维度的双重压迫——GIL封堵多线程+I/O跨越内核边界，二者叠加将解空间压缩到单线程+I/O多路复用
