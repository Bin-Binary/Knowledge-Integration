# Python核心基础（三）：容器四剑客——list/tuple/dict/set的内部世界

## 引言

在 C++ 中，STL 将容器与算法分离——`vector`/`map`/`set` 是数据结构，`sort`/`find`/`transform` 是独立算法，两者通过迭代器（iterator）这个胶水概念连接。编译器在实例化 `vector<int>` 的那一刻就固化了元素类型，运行时无法改变。在 Java 中，集合框架（Collections Framework）用接口-实现分层——`List`/`Map`/`Set` 是接口，`ArrayList`/`HashMap`/`HashSet` 是实现，泛型在编译期擦除，运行时一切仍是 `Object`。在 Go 中，`slice` 和 `map` 是语言内建的泛型容器，编译器直接支持，但没有继承体系，也不存在 `Iterable` 这样的统一协议——`range` 关键字是唯一的遍历原语，自建容器必须自己实现 `Len`/`Less`/`Swap` 才能配合 `sort`。

Python 做了一个不同方向上的激进选择：**容器就是 `PyObject`，通过协议（protocol）实现鸭子类型的多态**。

没有迭代器类型体系（C++），没有接口-实现分层（Java），没有编译器内建魔法（Go）。Python 的容器只管实现 `__len__`、`__iter__`、`__contains__`、`__getitem__` 这些双下方法，内置函数 `len()`/`for`/`in` 自动通过 `ob_type → PyTypeObject` 的槽位分派——所有容器共享同一套调用入口，而各容器在 C 层面自行实现槽位对应的逻辑。这是第一节"对象模型"的直接推论：**统一入口在 `PyTypeObject` 的槽位矩阵，差异化行为在各自 C 结构体的数据布局**。

这种设计的收益是**接口的统一性**：`len(list)`、`len(dict)`、`len(set)`、`len(str)` 走的完全是同一条 `len()` → `sq_length`/`mp_length` 槽位调用路径；`for x in container` 无需知道 container 是 list 还是 dict，只要 `tp_iter` 槽位非空即可。但代价是**没有运行时泛型类型安全**：`[1, "two", 3.0]` 合法——list 的 `ob_item` 存的是 `PyObject*` 指针，8 字节定长，不关心指向的对象类型。你无法在编译期或运行时限定"这个 list 只能存 int"，因为 Python 的对象模型从根基上就没有这个机制——类型信息随对象走，不随容器走。

但统一接口之下，四种容器的内部世界截然不同。list 是动态指针数组，靠 `realloc` 伸缩；tuple 是定长内联数组，创建即固化；dict 是开放寻址哈希表，用探测序列化解冲突；set 本质上是"只有 key 没有 value 的 dict"。它们在 C 层面各有独立的 `PyListObject`/`PyTupleObject`/`PyDictObject`/`PySetObject` 结构体，各有独立的增长策略、内存布局和操作复杂度。理解这些差异不是"底层知识储备"，而是写出正确、高效 Python 代码的必要前提——当你知道 `in` 对 list 是 O(n) 线性扫描而对 set 是 O(1) 哈希查找时，选择哪个容器就不再是口味问题。

本文将逐一拆开四种容器的 C 结构体，用 `ctypes` 和 `sys.getsizeof` 直接观测内存布局，追踪每一个操作在 C 层面的执行路径，最后回到协议层解释为什么 `len()`/`in`/`for` 对所有容器"看起来一样，跑起来不一样"。这是从对象模型向下深入数据结构、向上统合协议范式的完整旅程。

### 容器四剑客的语言定位——根植于对象模型

| 语言定位 | 对象模型根因 | 体现 |
|:---|:---|:---|
| **容器是对象** | 一切皆 `PyObject`，容器自身也有 `ob_refcnt`/`ob_type` | `id([])`、`type({})`、`isinstance([], object)` 全部合法 |
| **统一协议入口** | `len()`/`in`/`for` 通过 `ob_type` 槽位分派 | `len(list)` → `sq_length`，`len(dict)` → `mp_length`，同入口不同实现 |
| **元素无类型约束** | `ob_item`/`ob_value` 存 `PyObject*`，8B 定长指针 | `[1, "a", None]` 合法，容器不关心元素类型 |
| **可变性由结构决定** | 内联数据→不可变，间接指针→可变（§1.1 闭环） | `tuple` 内联→`sq_ass_item=NULL`，`list` 间接→`sq_ass_item` 开放 |
| **哈希性是通行证** | `tp_hash` 槽位决定能否做 dict key / set 元素 | 不可变→有 `tp_hash`→可做 key，可变→`tp_hash=NULL`→TypeError |

## 一、序列双生——list与tuple

list 和 tuple 共享序列协议（`__getitem__`、`__len__`、`__contains__`、`__iter__`、`__reversed__`），但底层 C 结构体截然不同。list 的数据存放在**独立的指针数组**中（通过 `ob_item` 间接引用），tuple 的数据**内联在结构体尾部**。这个差异是 §1.1 "内联→不可变，间接→可变" 闭环在容器世界的完整重现。

### 1.1 list：动态指针数组

#### PyListObject 的 C 结构

```c
// CPython/Include/cpython/listobject.h
typedef struct {
    PyObject_VAR_HEAD              // ob_refcnt(8B) + ob_type(8B) + ob_size(8B) = 24B
    PyObject **ob_item;            // 指向指针数组的指针 (8B)
    Py_ssize_t allocated;          // 已分配槽位数, ≥ ob_size (8B)
} PyListObject;
// 空列表: 24 + 8 + 8 = 40B? 实际 sys.getsizeof([]) = 56 (CPython 含对齐/padding)
```

内存布局图（64 位系统）：

```
PyListObject 实例 (列表 [42, "hi", None]):
┌─────────────────────────────────────────────┐
│ ob_refcnt  = 1              (8B)            │ ← PyObject_VAR_HEAD
│ ob_type    → <class 'list'> (8B)            │
│ ob_size    = 3              (8B)            │ ← 当前元素数
│ ob_item    ──────────────────────╂──→ 独立指针数组
│ allocated  = 5              (8B)            │      │
└─────────────────────────────────────────────┘      ↓
                                               ┌───────────────────┐
                                               │ ptr0 │ ptr1 │ ptr2│ ptr3 │ ptr4 │
                                               │  ↓   │  ↓   │  ↓  │ NULL │ NULL │
                                               └──┼───┴──┼───┴──┼──┴──────┴──────┘
                                                  ↓      ↓      ↓
                                             PyLong   PyUnicode  PyNone
                                             28B      50B       16B
```

关键点：

1. **`ob_item` 是二级间接**：`PyListObject` 中存的是 `PyObject**`（指向指针数组的指针），指针数组中每个元素是 `PyObject*`（指向实际对象的指针）。修改 `ob_item` 指向的数组不需移动 `PyListObject` 自身，`realloc` 发生在独立的数组上。
2. **`ob_size` vs `allocated`**：`ob_size` 是实际元素数（`len(list)` 直接返回此值），`allocated` 是已分配的指针槽位数。`allocated ≥ ob_size`，差额就是"预留空间"——避免每次 `append` 都 `realloc`。
3. **指针定长**：不管元素是 `int`(28B)、`str`(50B) 还是 `None`(16B)，`ob_item` 数组中每个槽位始终是 8 字节指针。这让 `realloc` 只需移动定长指针，不需要移动元素对象本身。

**实验 1：用 ctypes 直接观测 PyListObject 内部**

```python
import ctypes
import sys

class PyObject(ctypes.Structure):
    _fields_ = [
        ("ob_refcnt", ctypes.c_ssize_t),
        ("ob_type", ctypes.c_void_p),
    ]

class PyVarObject(PyObject):
    _fields_ = [
        ("ob_size", ctypes.c_ssize_t),
    ]

class PyListObject(PyVarObject):
    _fields_ = [
        ("ob_item", ctypes.POINTER(ctypes.c_void_p)),
        ("allocated", ctypes.c_ssize_t),
    ]

L = [42, "hi", None]
addr = id(L)
py_list = PyListObject.from_address(addr)

print(f"ob_refcnt  = {py_list.ob_refcnt}")      # 2 (L + from_address临时)
print(f"ob_size    = {py_list.ob_size}")         # 3
print(f"allocated  = {py_list.allocated}")        # 预分配槽数 ≥ 3
print(f"ob_item非空 = {py_list.ob_item is not None}")  # True

# 读 ob_item 数组中的指针
for i in range(py_list.ob_size):
    ptr = py_list.ob_item[i]
    print(f"  ob_item[{i}] = {hex(ptr)}  →  id(L[{i}]) = {hex(id(L[i]))}")
    # 两者应相等: ob_item[i] 就是 L[i] 的 PyObject 地址

print(f"len(L) = {len(L)}")                      # 3 — 直接读 ob_size
```

**实验 2：空列表与单元素列表的内存对照**

```python
import sys

print(sys.getsizeof([]))        # 56 — PyListObject 头部 (含对齐)
print(sys.getsizeof([1]))       # 64 — 56 + 8 (一个指针槽位)
print(sys.getsizeof([1, 2]))    # 72 — 56 + 8*2
print(sys.getsizeof([None]))    # 64 — 56 + 8, None 也是 8B 指针

# 验证: 每增加一个元素, 增加 8 字节 (一个 PyObject* 指针)
for n in range(0, 10):
    L = list(range(n))
    print(f"[{n}个元素] sizeof={sys.getsizeof(L)}, 8*n+56={8*n+56}")
```

注意 `sys.getsizeof([1])` = 64 中**不含** int 对象 `1` 的 28 字节——`getsizeof` 只计容器自身，不计其引用的对象。list 的"自身内存" = `PyListObject` 结构体 + `ob_item` 指向的指针数组。

#### 增长策略——近似 1.125 倍扩容

当 `append` 发现 `ob_size == allocated`（位置用完），需要 `realloc` 扩大 `ob_item` 数组。CPython 的扩容公式：

```c
// CPython/Objects/listobject.c list_resize()
// newsize 是所需的最小槽位数
size_t new_allocated = (size_t)newsize + (newsize >> 3) + (newsize < 9 ? 3 : 6);
// ≈ newsize * 1.125 + 常数
```

这意味着：

- **小列表**（newsize < 9）：额外加 3 → 一次 append 后 allocated 可能从 0 跳到 4
- **大列表**（newsize ≥ 9）：`newsize + newsize/8 + 6` ≈ 1.125 倍增长
- **摊还 O(1) 的 append**：虽然偶发 `realloc` 代价 O(n)，但几何级数增长让每个元素平摊的扩容成本为常数

**实验 3：追踪 list 的扩容过程**

```python
import sys

L = []
prev_size = sys.getsizeof(L)
prev_allocated = 0

for i in range(64):
    L.append(i)
    cur_size = sys.getsizeof(L)
    if cur_size != prev_size:
        # 指针数组扩容了
        new_allocated = (cur_size - 56) // 8   # (sizeof - 头部) / 每槽8B
        print(f"append {i}: sizeof {prev_size}→{cur_size}, "
              f"ob_size={len(L)}, allocated≈{new_allocated}")
        prev_size = cur_size

# 输出类似:
# append 0:  sizeof 56→64,  ob_size=1,  allocated≈1
# append 4:  sizeof 64→96,  ob_size=4,  allocated≈5
# append 8:  sizeof 96→128, ob_size=8,  allocated≈9
# append 17: sizeof 128→192, ob_size=17, allocated≈17
# ...
```

**实验 4：验证 1.125 倍增长公式**

```python
def list_allocated(n):
    """模拟 CPython list_resize 的 allocated 值"""
    newsize = n
    new_allocated = newsize + (newsize >> 3) + (3 if newsize < 9 else 6)
    if new_allocated > n:
        return new_allocated
    return n + 1

for n in [0, 1, 4, 8, 16, 32, 64, 128, 256]:
    alloc = list_allocated(n)
    ratio = alloc / max(n, 1)
    print(f"newsize={n:3d}  → allocated={alloc:3d}  ratio={ratio:.3f}")

# 输出:
# newsize=  0  → allocated=  3  ratio=3.000 (初始特殊)
# newsize=  1  → allocated=  4  ratio=4.000
# newsize=  4  → allocated=  7  ratio=1.750
# newsize=  8  → allocated= 14  ratio=1.750
# newsize= 16  → allocated= 24  ratio=1.500
# newsize= 32  → allocated= 42  ratio=1.312
# newsize= 64  → allocated= 78  ratio=1.219
# newsize=128  → allocated= 150 ratio=1.172
# newsize=256  → allocated= 294 ratio=1.148
# 趋近 1.125x
```

#### append/extend/insert/pop 的时间复杂度

| 操作 | 时间复杂度 | 说明 |
|:---|:---|:---|
| `L.append(x)` | 摊还 O(1) | `ob_size < allocated` 时直接放入（O(1)），满时 `realloc`（O(n)），但摊还常数 |
| `L.extend(iter)` | 摊还 O(k) | k = iter 长度，一次性算好 newsize 再 realloc，比逐个 append 少多次扩容 |
| `L.insert(i, x)` | O(n) | 需要移动 `ob_item[i:]` 之后的所有指针（memmove），最坏 i=0 |
| `L.pop()` | O(1) | `ob_size -= 1`，不缩减 allocated，只释放尾部 |
| `L.pop(i)` | O(n) | 需要移动 `ob_item[i+1:]` 之前的指针 |
| `L[i]` / `L[i] = v` | O(1) | 指针数组的随机访问，直接 `ob_item[i]` |
| `x in L` | O(n) | 线性扫描 `ob_item` 数组，逐个 `__eq__` 比较 |
| `L.sort()` | O(n log n) | TimSort，利用已有序列减少比较 |

**实验 5：append vs insert 的性能差异**

```python
import time

def bench_append(n=100000):
    L = []
    start = time.perf_counter()
    for i in range(n):
        L.append(i)
    return time.perf_counter() - start

def bench_insert_head(n=100000):
    L = []
    start = time.perf_counter()
    for i in range(n):
        L.insert(0, i)      # 每次头部插入, 需移动所有已有元素
    return time.perf_counter() - start

t_append = bench_append()
t_insert = bench_insert_head()
print(f"append:   {t_append:.3f}s")
print(f"insert(0): {t_insert:.3f}s")
print(f"insert 慢了 {t_insert/t_append:.0f} 倍")  # 通常 50-200 倍
```

#### 为什么 list 是可变的——从结构到槽位的闭环

回到 §1.1 的规律：**数据区的内存布局是否允许在不移动结构体本身的前提下改变大小**。

list 的 `ob_item` 指向一个**独立的指针数组**。`realloc` 可以将这个数组搬到新的内存位置（只需更新 `ob_item` 指针），**不影响 `PyListObject` 结构体本身的位置**——`id(L)` 不会因为 `append` 而改变。指针数组中的每个槽位定长 8 字节，不论元素类型，这就保证了 `realloc` 只需搬定长数据，无需关心元素对象的内存布局。

在 `PyTypeObject` 层面，`list` 的 `sq_ass_item` 槽位指向 `list_ass_item` 函数——支持 `L[i] = value` 的索引赋值。而 `tuple` 的 `sq_ass_item` 为 NULL，所以 `t[i] = value` 抛出 `TypeError`。

```
list 的可变闭环:
  ob_item 指向独立数组 → 可 realloc 改变大小
  指针定长 8B → realloc 只需搬指针，元素不动
  sq_ass_item 开放 → Python 层可原地修改
  ↕ 互为因果
  ob_size 可变 → append/pop 改变元素数
  allocated ≥ ob_size → 预留空间减少 realloc
```

### 1.2 tuple：定长不变数组

#### PyTupleObject 的 C 结构

```c
// CPython/Include/cpython/tupleobject.h
typedef struct {
    PyObject_VAR_HEAD              // ob_refcnt(8B) + ob_type(8B) + ob_size(8B) = 24B
    PyObject *ob_item[1];          // 变长数组, 实际长度 = ob_size (内联!)
} PyTupleObject;
// 注意: ob_item[1] 是 C 的柔性数组技巧, 实际分配时大小 = sizeof(PyTupleObject) + ob_size * 8
```

内存布局图：

```
PyTupleObject 实例 (元组 (42, "hi")):
┌──────────────────────────────────────────────┐
│ ob_refcnt  = 1                (8B)           │ ← PyObject_VAR_HEAD
│ ob_type    → <class 'tuple'>  (8B)           │
│ ob_size    = 2                (8B)           │
│ ob_item[0] → PyLongObject(42) (8B)          │ ← 数据内联在结构体内!
│ ob_item[1] → PyUnicodeObject  (8B)          │
└──────────────────────────────────────────────┘
  总大小 = 24B(头部) + 2*8B(指针) = 40B → sizeof((42,"hi")) = 56? 
  实际 sizeof(())=40, sizeof((1,))=48 — 每个元素 +8B

对比 PyListObject:
┌──────────────────────┐        ┌──────────┐
│ ob_refcnt  │ ob_type │        │ ptr0│ptr1│ ← 独立数组
│ ob_size    │         │  ob_item──→│    │    │
│ ob_item ────────╂────│        └──────────┘
│ allocated  │         │
└──────────────────────┘
```

**核心差异**：tuple 的 `ob_item` 数组是**内联**在 `PyTupleObject` 结构体中的（C 语言的柔性数组），而 list 的 `ob_item` 是一个**独立分配**的指针数组，通过 `PyObject**` 间接引用。

这个差异的后果：

1. **tuple 比 list 省 8 字节**：list 多了 `allocated` 字段（因为 tuple 不需要——大小固定）和一个间接指针（list 的 `ob_item` 是指向数组的指针，而 tuple 的数组直接跟在头部后面）。
2. **tuple 不能 realloc**：整个 `PyTupleObject` + 内联数组是一块连续内存，realloc 意味着结构体本身要搬位置——所有指向它的引用（名字、容器中的指针）都要更新，这在 Python 的对象模型中不可能实现（引用语义意味着 `id()` 必须稳定）。
3. **创建即固化**：`ob_size` 在对象创建时确定，此后的生命周期内不可改变——没有 `append`、`insert`、`pop` 方法。

**实验 6：tuple 与 list 的内存对照**

```python
import sys

# 空容器
print(f"sizeof(()) = {sys.getsizeof(())}")     # 40
print(f"sizeof([]) = {sys.getsizeof([])}")     # 56 — 多 16B (allocated + 间接指针)

# 1 元素
print(f"sizeof((1,)) = {sys.getsizeof((1,))}")  # 48
print(f"sizeof([1])  = {sys.getsizeof([1])}")   # 64 — 多 16B

# 5 元素
print(f"sizeof((1,2,3,4,5)) = {sys.getsizeof((1,2,3,4,5))}")  # 80 = 40 + 5*8
print(f"sizeof([1,2,3,4,5]) = {sys.getsizeof([1,2,3,4,5])}")  # 104 = 56 + 预分配
# tuple: 恰好 头部40 + n*8
# list:  头部56 + allocated*8 (allocated 可能 > n)
```

**实验 7：用 ctypes 读取 tuple 内联数据**

```python
import ctypes

class PyTupleObject(ctypes.Structure):
    _fields_ = [
        ("ob_refcnt", ctypes.c_ssize_t),
        ("ob_type", ctypes.c_void_p),
        ("ob_size", ctypes.c_ssize_t),
        ("ob_item", ctypes.c_void_p * 0),   # 柔性数组, 用 0 长度占位
    ]

t = (42, "hi")
addr = id(t)

# 读取头部
py_tuple = PyTupleObject.from_address(addr)
print(f"ob_refcnt = {py_tuple.ob_refcnt}")
print(f"ob_size   = {py_tuple.ob_size}")      # 2

# 读取内联指针: 在 ob_size 之后, 偏移 24 字节处
class TupleItems(ctypes.Structure):
    _fields_ = [
        ("_pad0", ctypes.c_ssize_t * 3),       # ob_refcnt + ob_type + ob_size = 24B
        ("items", ctypes.c_void_p * 2),         # 2 个元素
    ]

ti = TupleItems.from_address(addr)
for i in range(2):
    print(f"  item[{i}] = {hex(ti.items[i])}  →  id(t[{i}]) = {hex(id(t[i]))}")
```

#### 为什么 tuple 是不可变的——结构约束→槽位制度化

与 §1.1 中 `str` 不可修改的闭环完全相同：

```
tuple 不可变的闭环:
  数据内联在结构体尾部 → realloc 会移动结构体 → id() 不稳定 → 违反引用语义
  → 物理上不可能原地修改大小
  → PyTypeObject.sq_ass_item = NULL
  → Python 层 t[i] = v → TypeError
  → 不可变 → tp_hash 可实现 → 可做 dict key / set 元素
  → 不可变 → 安全共享(浅拷贝无需复制) → 小优化空间
```

**实验 8：tuple 不可变性的直接验证**

```python
t = (1, 2, 3)

# 尝试索引赋值
try:
    t[0] = 99
except TypeError as e:
    print(f"t[0]=99 → {e}")    # 'tuple' object does not support item assignment

# 尝试 append
print(dir(t))                    # 没有 append, insert, pop, remove, sort...
# 对比 list:
L = [1, 2, 3]
print(hasattr(L, 'append'))      # True
print(hasattr(t, 'append'))      # False
```

#### tuple 作为 dict key——tp_hash 与哈希缓存

tuple 是不可变的 → `PyTypeObject` 中 `tp_hash` 指向 `tuplehash` 函数 → `hash((1, 2))` 合法。但 tuple 的哈希计算需要递归计算所有元素的哈希：

```c
// CPython/Objects/tupleobject.c tuplehash()
static Py_hash_t tuplehash(PyTupleObject *v) {
    Py_uhash_t acc = _PyHASH_XXPRIME_5;
    for (i = 0; i < Py_SIZE(v); i++) {
        // 计算每个元素的 hash, 用 xxHash 算法混合
        acc += (Py_uhash_t)PyObject_Hash(item) * _PyHASH_XXPRIME_2;
        // ...
    }
    return (Py_hash_t)acc;
}
```

这解释了为什么包含可变元素的 tuple **仍然可以**做 dict key——tuple 的 `tp_hash` 不会缓存到结构体中（因为计算结果依赖元素内容），但 `tp_hash` 函数本身存在就够了。然而，如果 tuple 中嵌套了 list，`hash()` 会失败，因为 `list.__hash__ = None`：

```python
d = {}
d[(1, 2)] = "ok"              # OK, 纯不可变 tuple
try:
    d[(1, [2])] = "bad"       # TypeError: unhashable type: 'list'
except TypeError as e:
    print(e)
```

这不是 tuple 自身的 `tp_hash` 缺失，而是 `tuplehash()` 递归调用 `PyObject_Hash()` 时，发现内部 list 的 `tp_hash = _PyObject_HashNotImplemented`，抛出 `TypeError`。

#### 空元组单例——`()` is `()` 永远为 True

空 tuple 是 CPython 中的**单例对象**——全局只创建一次，所有 `()` 都指向同一个 `PyTupleObject`。这与空 list 不同（每次 `[]` 都新建对象）：

```c
// CPython/Objects/tupleobject.c
static PyTupleObject *free_list[PyTuple_MAXSAVESIZE];  // tuple 自由列表
// 空 tuple: 单例 free_list[0]
```

**实验 9：空 tuple 单例 vs 空 list 非单例**

```python
# 空 tuple: 全局单例
print(() is ())            # True — 同一对象
print(id(()) == id(()))    # True

# 空 list: 每次新建
print([] is [])            # False — 不同对象
a = []
b = []
print(id(a) == id(b))      # False

# 小 tuple 也有自由列表缓存(非单例, 但有复用)
t1 = (1, 2)
t2 = (1, 2)
print(t1 is t2)            # 可能 True (取决于自由列表是否复用), 但不保证
```

CPython 的 tuple 自由列表（free list）缓存了大小 1~19 的已释放 tuple 对象，下次创建同大小 tuple 时复用内存块，省去 malloc/free 开销。但这是实现细节，不保证 `is` 比较结果。

#### tuple 的哈希缓存机制

与 `str` 的 `hash` 字段类似，CPython 的 tuple 对象**没有**内置哈希缓存字段（因为 tuple 无专用 `hash` 槽），每次调用 `hash()` 都重新计算。但对于频繁用作 dict key 的 tuple，这是可接受的——因为哈希结果一旦在 dict 的 `dk_entries` 中落地，就不需要重复计算。

```python
t = (1, 2)
h1 = hash(t)
h2 = hash(t)
print(h1 == h2)  # True — 结果相同, 但每次都重新递归计算

# 对比: str 的哈希只在首次计算后缓存
s = "hello"
h3 = hash(s)
h4 = hash(s)
print(h3 == h4)  # True — 第二次读缓存
```

### 1.3 通用序列协议

list 和 tuple 都实现序列协议（Sequence Protocol），这是 `PyTypeObject` 槽位矩阵中一组相关槽位的统称：

| 双下方法 | 对应槽位 | 操作 | list | tuple |
|:---|:---|:---|:---|:---|
| `__len__` | `sq_length` | `len(L)` | ✅ → 返回 `ob_size` | ✅ → 返回 `ob_size` |
| `__getitem__` | `sq_item` | `L[i]` | ✅ → 读 `ob_item[i]` | ✅ → 读 `ob_item[i]` |
| `__setitem__` | `sq_ass_item` | `L[i] = v` | ✅ → 写 `ob_item[i]` | ❌ NULL → TypeError |
| `__contains__` | `sq_contains` | `x in L` | ✅ → O(n) 线性扫描 | ✅ → O(n) 线性扫描 |
| `__iter__` | `tp_iter` | `for x in L` | ✅ → listiter | ✅ → tupleiter |
| `__reversed__` | (无直接槽位) | `reversed(L)` | ✅ | ✅ |
| `__add__` | `nb_add` | `L + L2` | ✅ → 新 list | ✅ → 新 tuple |
| `__mul__` | `nb_multiply` | `L * n` | ✅ → 新 list | ✅ → 新 tuple |

**`in` 操作符的两条路径**：

当执行 `x in container` 时，CPython 先检查 `sq_contains` 槽位。如果存在，调用它（序列走线性扫描）；如果不存在，尝试用 `tp_iter` 迭代遍历。对于 `dict` 和 `set`，`in` 走的是完全不同的路径——哈希查找 O(1)，而非线性扫描。

```python
# in 对序列: O(n)
import time
L = list(range(1000000))
start = time.perf_counter()
print(999999 in L)        # True, 但需扫描到最后
print(f"list in: {time.perf_counter()-start:.4f}s")

# in 对集合: O(1)
S = set(range(1000000))
start = time.perf_counter()
print(999999 in S)        # True, 哈希查找
print(f"set  in: {time.perf_counter()-start:.6f}s")
# set 的 in 比 list 快 100-1000 倍
```

#### 切片——永远创建新对象

序列的切片操作 `L[a:b:c]` 在 Python 层面等价于 `L.__getitem__(slice(a, b, c))`，而**永远**返回一个新对象——不管是 list 还是 tuple：

```python
L = [1, 2, 3, 4, 5]
t = (1, 2, 3, 4, 5)

L2 = L[1:3]
print(L2 is L)           # False — 新 list
print(L2)                # [2, 3]

t2 = t[1:3]
print(t2 is t)           # False — 新 tuple
print(t2)                # (2, 3)

# 切片对象本身
print(type(slice(1, 3))) # <class 'slice'>
s = slice(1, 3)
print(s.start, s.stop, s.step)  # 1 3 None
```

CPython 的 `list_subscript` 和 `tuple_subscript` 在收到 `slice` 对象时，先计算切片范围，然后分配新数组复制指针——这就是切片"永远新建"的原因。

#### 跨语言比较：序列容器

| 特性 | Python list | C++ std::vector | Java ArrayList | Go slice |
|:---|:---|:---|:---|:---|
| 元素类型 | `PyObject*` (异构) | `T` (编译期固定) | `Object` (擦除) | `T` (编译期泛型) |
| 增长策略 | ≈1.125x | 2x | 1.5x | 2x (runtime) |
| 随机访问 | O(1) | O(1) | O(1) | O(1) |
| 尾部追加 | 摊还 O(1) | 摊还 O(1) | 摊还 O(1) | 摊还 O(1) |
| 头部插入 | O(n) | O(n) | O(n) | O(n) |
| 内存开销/元素 | 8B(指针) + 对象自身 | `sizeof(T)` | 4B(ref) + 对象 | `sizeof(T)` |
| 不可变对应体 | tuple | 无(靠 const) | 无(靠 final) | 无(靠 copy) |

Python list 的增长因子（≈1.125x）比 C++ vector（2x）和 Java ArrayList（1.5x）都小——意味着 Python list 的内存浪费更少，但扩容更频繁。这是 CPython 的工程选择——在内存相对宝贵的服务器场景，牺牲少量扩容次数换取更紧凑的内存占用。

## 二、映射之王——dict

dict 是 Python 中最复杂也最核心的内置容器。名字空间（`globals()`、`locals()`、`__dict__`）都用 dict 实现，对象的属性查找走 dict，模块的符号表也是 dict。Python 的运行时几乎建在 dict 之上——理解 dict 的内部机制，就是理解 Python 运行时的脊椎。

### 2.1 开放寻址哈希表

#### PyDictObject 的 C 结构（Python 3.7+）

```c
// CPython/Include/cpython/dictobject.h
typedef struct {
    PyObject_HEAD                          // ob_refcnt(8B) + ob_type(8B) = 16B
    Py_ssize_t ma_used;                    // 当前条目数 (8B)
    uint64_t ma_version_tag;               // 版本号, 每次修改递增 (8B)
    PyDictKeysObject *ma_keys;             // 指向键表 (8B) — 可能被多个 dict 共享
    PyDictValues *ma_values;               // 指向值表 (8B) — 可能为 NULL(内联模式)
} PyDictObject;
// 空字典: 16 + 8 + 8 + 8 + 8 = 48? 实际 sizeof({}) = 64 (含对齐)
```

关键结构拆解——`PyDictKeysObject`：

```c
typedef struct {
    Py_hash_t dk_hash;                     // 哈希种子 (-1 = 未种子化)
    char dk_keys;                          // 键的存储区 (变长)
    Py_ssize_t dk_nentries;                // dk_entries 中有效条目数
    uint8_t dk_log2_size;                  // dk_indices 的 size_log2
    uint8_t dk_log2_index_bytes;           // dk_indices 字节大小的 log2
    uint8_t dk_kind;                       // DK_KEYS(0)/DK_SplIt(1) (Python 3.11+)
    uint32_t dk_version;                   // 版本号
    Py_ssize_t dk_usable;                  // dk_indices 中可用槽位数
    Py_ssize_t dk_nentries;                // 有效条目数
    // 紧接着:
    // dk_indices[dk_size]   ← 紧凑索引数组, 存 entry 的 index 或 DKIX_EMPTY/DKIX_DUMMY
    // dk_entries[dk_nentries] ← PyDictKeyEntry 数组, 插入顺序存储
} PyDictKeysObject;

typedef struct {
    Py_hash_t me_hash;                     // 缓存的哈希值
    PyObject *me_key;                      // 键对象指针
    PyObject *me_value;                    // 值对象指针 (split 模式下在 ma_values 中)
} PyDictKeyEntry;
```

内存布局图（Python 3.7+ compact dict）：

```
PyDictObject 实例 (字典 {"name": "Alice", "age": 30}):
┌──────────────────────────────────────────────────┐
│ ob_refcnt       = 1               (8B)           │
│ ob_type         → <class 'dict'>  (8B)           │
│ ma_used         = 2               (8B)           │ ← 条目数
│ ma_version_tag  = 1               (8B)           │ ← 修改版本
│ ma_keys         ───────────────────────╂──────→ PyDictKeysObject
│ ma_values       = NULL             (8B)           │           │
└──────────────────────────────────────────────────┘           ↓
                                                    ┌──────────────────────┐
  PyDictKeysObject:                                 │ dk_hash = ... (8B)  │
  ┌────────────────────────────────┐                │ dk_log2_size = 3    │
  │ dk_indices[8] (索引数组):       │                │ dk_usable = 4       │
  │  [0, -1, 1, -1, -1, -1, -1, -1]│                │ dk_nentries = 2     │
  │  index 0 → entries[0]          │                ├──────────────────────┤
  │  index 2 → entries[1]          │                │ dk_entries:          │
  │  -1 = DKIX_EMPTY               │                │  [0] hash, key, value│ ← "name"→"Alice"
  │  -2 = DKIX_DUMMY (墓碑)        │                │  [1] hash, key, value│ ← "age"→30
  └────────────────────────────────┘                └──────────────────────┘
```

**紧凑字典（Compact Dict）的核心设计**：

Python 3.6 之前，dict 的内部存储是"合并表"——keys 和 values 交错存储在 `PyDictKeyEntry` 数组中，每个 entry 占 24 字节（hash + key + value），即使 dict 被删除了大量条目，数组大小不会缩容，空位只是标记为 DKIX_DUMMY（墓碑）。

Python 3.7+ 的紧凑字典将存储分为两层：

1. **`dk_indices`**：一个紧凑的索引数组，长度 = `dk_size`（哈希表大小），每个元素是一个小整数索引或 `DKIX_EMPTY`(-1)/`DKIX_DUMMY`(-2)。小字典用 1 字节/索引，中等用 2 字节，大字典用 4 或 8 字节。
2. **`dk_entries`**：一个 `PyDictKeyEntry` 数组，始终按**插入顺序**紧密排列——删除操作在 `dk_indices` 中插入墓碑（DKIX_DUMMY），但 `dk_entries` 中对应条目不清除（直到 resize 时紧凑化）。

这样，遍历 `dk_entries[0..dk_nentries)` 就是按插入顺序迭代——Python 3.7 保证的插入序就是由此而来。

**实验 10：dict 的插入序保证**

```python
d = {}
d["banana"] = 2
d["apple"] = 1
d["cherry"] = 3
print(list(d.keys()))    # ['banana', 'apple', 'cherry'] — 插入序
print(list(d.values()))  # [2, 1, 3]
print(list(d.items()))   # [('banana', 2), ('apple', 1), ('cherry', 3)]

# 删除后重新插入: 移到序尾
del d["banana"]
d["banana"] = 5
print(list(d.keys()))    # ['apple', 'cherry', 'banana'] — banana 移到末尾
```

#### 开放寻址法——探测序列

CPython dict 使用**开放寻址法**（open addressing）解决哈希冲突——不同于 Java HashMap 的链式寻址（桶 + 链表/红黑树）。冲突时通过探测序列（probe sequence）寻找下一个空槽：

```c
// CPython/Python/dictobject.c
#define PERTURB_SHIFT 5

// i = 初始位置 = hash(key) & mask, mask = dk_size - 1
// perturb = hash(key)
// while (dk_indices[i] != DKIX_EMPTY && dk_indices[i] != 匹配):
//     i = (i*5 + perturb + 1) & mask    ← 探测公式
//     perturb >>= PERTURB_SHIFT          ← 扰动值右移
// 最终: perturb → 0, 退化为线性探测 i = (i+1) & mask
```

探测序列巧妙之处：初始几步利用哈希值高位信息做"远距离跳跃"，减少聚集；后期退化为线性探测，保证**所有槽位最终都会被探测**（遍历完整性）。

```
探测序列示例 (dk_size=8, hash=0b11010110...):
  i₀ = hash & 7 = 6
  i₁ = (6*5 + hash + 1) & 7 = ...   (远跳)
  i₂ = ...
  最终退化为 iₖ = (iₖ₋₁ + 1) & 7  (线性)
```

**实验 11：观察哈希冲突与探测链**

```python
class BadHash:
    """故意制造哈希冲突"""
    def __init__(self, val):
        self.val = val
    def __hash__(self):
        return 42          # 所有实例哈希相同!
    def __eq__(self, other):
        return isinstance(other, BadHash) and self.val == other.val

d = {}
for i in range(5):
    d[BadHash(i)] = i
    print(f"inserted BadHash({i})")

# 虽然哈希全是 42, dict 通过探测序列仍然正常工作
print(f"dict size = {len(d)}")   # 5
print(d[BadHash(3)])             # 3 — O(n) 查找(退化为线性), 但结果正确
```

#### 负载因子与 resize

当 `dk_usable == 0`（可用槽位用完），dict 触发 resize。CPython 的策略：

```c
// CPython/Python/dictobject.c
// us = dk_nentries (当前有效条目数)
// 新 dk_size = 下一个 2 的幂次
if (dk_size >= 8) {
    // 小字典: 4x 扩容 (初始 dk_size=8, 4x=32)
    new_size = dk_size * 4  当 us < 50000
    // 大字典: 2x 扩容 (节省内存)
    new_size = dk_size * 2  当 us ≥ 50000
} else {
    new_size = 8  // 最小 dk_size = 8
}
// 新表 dk_usable = new_size * 2/3 - us
// 负载因子阈值: 2/3 — 即 dk_size 填满 2/3 时必须 resize
```

为什么负载因子阈值是 2/3？开放寻址法对负载因子极敏感——超过 2/3 后冲突概率急剧上升（生日悖论），查找性能从 O(1) 退化为 O(n)。低于 1/3 则浪费内存。2/3 是理论和实践的折中点。

**实验 12：追踪 dict 的 resize**

```python
import sys

d = {}
prev = sys.getsizeof(d)
sizes = []

for i in range(100):
    d[i] = i
    cur = sys.getsizeof(d)
    if cur != prev:
        print(f"insert {i}: sizeof {prev}→{cur}, len={len(d)}")

# 注意: sys.getsizeof(d) 只计 PyDictObject 本身, 不计 ma_keys/ma_values 的独立分配!
# 要真正测哈希表大小, 需要更底层的方法
```

#### 墓碑（DKIX_DUMMY）——删除不缩容

删除 dict 条目时，`dk_indices` 中对应位置被标记为 `DKIX_DUMMY`（-2），而非 `DKIX_EMPTY`（-1）。两者的区别：

- `DKIX_EMPTY`：从未使用过的槽位——**探测链在此终止**，后续哈希到此位置认为"键不存在"
- `DKIX_DUMMY`：曾经被使用但已删除——**探测链不能在此终止**，否则在其后插入的同哈希键可能"丢失"

```
插入: hash(A)=3, hash(B)=3, hash(C)=3
  dk_indices: [... A_idx ... B_idx ... C_idx ...]
  探测链: 3 → 4 → 5 (A→B→C 依次探测)

删除 B:
  dk_indices: [... A_idx ... DUMMY ... C_idx ...]
  探测链: 3 → 4(跳过DUMMY) → 5 (C 仍可被找到!)

如果用 EMPTY 替代:
  dk_indices: [... A_idx ... EMPTY ... C_idx ...]
  探测链: 3 → 4(EMPTY=终止) → C 丢失!
```

墓碑不回收的后果：频繁增删的 dict 不会自动缩容——`dk_size` 只增不减，直到 resize 时才整理墓碑。如果需要"瘦身"，必须创建新 dict。

**实验 13：删除后 dict 不缩容**

```python
import sys

# 大量插入
d = {i: i for i in range(1000)}
size_after_insert = sys.getsizeof(d)
print(f"插入1000条: sizeof={size_after_insert}, len={len(d)}")

# 大量删除
for i in range(900):
    del d[i]
size_after_delete = sys.getsizeof(d)
print(f"删除900条: sizeof={size_after_delete}, len={len(d)}")
# sizeof 不变! 墓碑占据空间

# "瘦身": 重建
d = {k: v for k, v in d.items()}
size_after_rebuild = sys.getsizeof(d)
print(f"重建dict:  sizeof={size_after_rebuild}, len={len(d)}")
# sizeof 变小了
```

### 2.2 dict 操作与性能

#### d[key] 的完整查找路径

```
Python: value = d[key]
  ↓
C层: PyObject_GetItem(d, key)
  ↓
1. hash(key) → 调用 key.ob_type->tp_hash(key)
   若 tp_hash = _PyObject_HashNotImplemented → TypeError("unhashable")
  ↓
2. 初始位置 i = hash & (dk_size - 1)
  ↓
3. 查 dk_indices[i]:
   - DKIX_EMPTY → 键不存在 → KeyError
   - DKIX_DUMMY → 继续探测
   - idx ≥ 0    → 比较 dk_entries[idx].me_key 与 key:
     - __eq__ 为 True  → 返回 me_value
     - __eq__ 为 False → 继续探测
  ↓
4. 重复步骤 3 直到找到或 DKIX_EMPTY
```

**实验 14：dict 查找的内部——用 ctypes 观察 dk_indices**

```python

import sys

        ("ma_keys", ctypes.c_void_p),

    ]

addr = id(d)
py_dict = PyDictObject.from_address(addr)

```

#### d[key] = value 的完整写入路径

```
Python: d[key] = value
  ↓
C层: PyObject_SetItem(d, key, value)
  ↓
1. hash(key)
  ↓
2. 查找 key 是否已存在 (同上查找路径)
   - 已存在 → 更新 me_value (DECREF 旧值, INCREF 新值)
   - 不存在 → 进入插入流程
  ↓
3. 插入:
   - dk_usable > 0? → 在 dk_entries 末尾追加新 entry, dk_indices 写入 index
   - dk_usable == 0? → 触发 resize → 重建更大的 dk_indices + dk_entries
  ↓
4. ma_used++, ma_version_tag++ (标记修改)
```

#### dict 迭代——按插入序遍历 dk_entries

`for k in d:` 遍历的是 `dk_entries[0..dk_nentries)`，跳过被删除的条目（`me_key == NULL` 的条目不产出键）。这就是插入序的物理实现——不是"额外维护一个链表"，而是 entries 本身就按插入顺序排列。

```python
d = {}
d["x"] = 1
d["y"] = 2
d["z"] = 3
del d["y"]

# dk_entries:
# [0] me_key="x", me_value=1  ← 有效
# [1] me_key=NULL, me_value=NULL  ← 已删除, 但位置保留
# [2] me_key="z", me_value=3  ← 有效

for k in d:
    print(k, end=" ")  # x z — 跳过 entry[1]
```

#### 时间复杂度汇总

| 操作 | 平均 | 最坏 | 说明 |
|:---|:---|:---|:---|
| `d[key]` | O(1) | O(n) | 哈希查找，最坏=所有 key 同一 hash |
| `d[key] = v` | O(1) | O(n) | 同上 |
| `del d[key]` | O(1) | O(n) | 查找 + 标墓碑 |
| `key in d` | O(1) | O(n) | 同 d[key] 但不反引用 |
| `len(d)` | O(1) | O(1) | 直接返回 ma_used |
| `for k in d` | O(n) | O(n) | 遍历 dk_entries |
| `d.keys()` | O(1) | O(1) | 返回视图对象，不拷贝 |
| `d.items()` | O(1) | O(1) | 同上 |

**实验 15：dict 的 O(1) vs 最坏 O(n)**

```python
import time

class SameHash:
    def __init__(self, n):
        self.n = n
    def __hash__(self):
        return 1               # 所有实例同一哈希
    def __eq__(self, other):
        return isinstance(other, SameHash) and self.n == other.n

# 正常 dict (哈希分散)
d1 = {i: i for i in range(10000)}
start = time.perf_counter()
_ = 9999 in d1
print(f"正常dict 查找: {time.perf_counter()-start:.6f}s")

# 全冲突 dict
d2 = {SameHash(i): i for i in range(10000)}
start = time.perf_counter()
_ = SameHash(9999) in d2
print(f"全冲突dict 查找: {time.perf_counter()-start:.6f}s")
# 全冲突可能慢 100-1000 倍 → O(n) 退化的可怕之处
```

### 2.3 dict 演进史

理解 dict 的演进能让你看清"当前实现为什么要这样设计"——每一步改进都指向具体问题。

#### Python 3.5 及之前：合并表（Combined Table）

```
dk_entries = [entry0, entry1, entry2, ..., entry_{dk_size-1}]
  每个 entry: (hash: 8B, key: 8B, value: 8B) = 24B
  dk_size 个 entry, 无论实际有多少条目
  空位: hash=-1 (empty), key=NULL, value=NULL

缺点:
  - 空位占 24B, 浪费严重
  - 大量删除后, 墓碑占据空间不释放
  - 同一类的多个实例各自持有完整 dict (key 重复存储)
```

#### Python 3.6：紧凑字典（Compact Dict）

PEP 412 + Raymond Hettinger 的紧凑 dict 实验合并，引入了 `dk_indices` + `dk_entries` 分离的两层结构：

```
dk_indices[dk_size]:  [idx, -1, idx, -2, ...]  ← 1B/2B/4B/8B 每索引
dk_entries[nentries]: [entry0, entry1, ...]     ← 紧密排列

节省:
  - 空槽位从 24B 降到 1-8B (索引大小)
  - 条目紧密排列, 删除只标墓碑在 indices 中
  - 实测节省 20-25% 内存
```

同时，因为 `dk_entries` 按插入顺序排列，`for k in d` 自然按插入序遍历——但这在 3.6 中只是**实现细节**，不是语言保证。

#### Python 3.7+：插入序成为语言保证

Python 3.7 将 3.6 的紧凑 dict 实现细节升格为**语言规范**——所有 Python 实现都必须保证 dict 的迭代顺序等于插入顺序。这是一个罕见的"实现细节驱动语言规范"的案例。

#### PEP 412 键共享字典（Key-Sharing Dict）

同一类的多个实例共享相同的 key 集合——`ma_keys` 指向同一个 `PyDictKeysObject`（包含 key 和 hash），各自的 `ma_values` 是独立的值数组。当实例首次插入新 key 时，发生"键脱离"（key split），转为独立 dict。

```python
class Point:
    __slots__ = ('x', 'y')   # 用 __slots__ 避免 dict
# 对比:
class Point2:
    pass

p1 = Point2()
p1.x = 1; p1.y = 2
p2 = Point2()
p2.x = 3; p2.y = 4

# p1.__dict__ 和 p2.__dict__ 可能共享 ma_keys (key 都是 'x','y')
# p1 的 ma_values = [1, 2], p2 的 ma_values = [3, 4]
```

**实验 16：键共享 dict 的验证**

```python
class Foo:
    pass

instances = [Foo() for _ in range(100)]
for inst in instances:
    inst.a = 1
    inst.b = 2

# 所有实例的 __dict__ 可能共享 ma_keys
d0_id = id(instances[0].__dict__)  # 每个 __dict__ 是独立 PyDictObject
# 但 ma_keys 可能指向同一 PyDictKeysObject

# 如果插入新 key → 键脱离, 转为独立 dict
instances[0].c = 3  # 新 key, 可能触发脱离
```

### 2.4 dict 视图与协议

#### dict.keys()/values()/items()——动态视图

```python
d = {"a": 1, "b": 2}
keys = d.keys()
values = d.values()
items = d.items()

print(type(keys))     # <class 'dict_keys'>
print(type(values))   # <class 'dict_values'>
print(type(items))    # <class 'dict_items'>

# 视图是动态的——dict 改变, 视图随之改变
d["c"] = 3
print(list(keys))     # ['a', 'b', 'c'] — 自动反映新增键!
print(list(values))   # [1, 2, 3]
```

视图不是拷贝——它是挂在 `PyDictObject` 上的**轻量引用**，读取时直接访问 `ma_keys`/`ma_values`/`dk_entries`。这也意味着在迭代视图期间**不能修改 dict**（否则 `ma_version_tag` 变化，运行时检测到并抛出 `RuntimeError`）。

#### Mapping 协议

dict 实现了 `collections.abc.Mapping` 协议，定义了 `__getitem__`、`__len__`、`__iter__`、`__contains__` 等方法。这意味着任何实现了这些方法的自定义类都可以"充当 dict"：

```python
from collections.abc import Mapping

class SimpleMap(Mapping):
    def __init__(self, data):
        self._data = dict(data)
    
    def __getitem__(self, key):
        return self._data[key]
    
    def __iter__(self):
        return iter(self._data)
    
    def __len__(self):
        return len(self._data)

sm = SimpleMap({"a": 1})
print(isinstance(sm, Mapping))   # True
print("a" in sm)                  # True — 走 __contains__ (Mapping 提供 mixin)
print(list(sm))                   # ['a'] — 走 __iter__
```
