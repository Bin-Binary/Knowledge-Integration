### 3.1.4 序列模式——列表/元组解构

```python
def describe_sequence(seq):
    match seq:
        case []:
            return "Empty"
        case [x]:
            return f"Singleton: {x}"
        case [x, y]:
            return f"Pair: {x}, {y}"
        case [first, *rest]:          # *rest 捕获剩余元素
            return f"Head: {first}, Tail: {rest}"
        case (x, y, z):
            return f"Triple: {x}, {y}, {z}"

print(describe_sequence([]))           # Empty
print(describe_sequence([1]))          # Singleton: 1
print(describe_sequence([1, 2]))       # Pair: 1, 2
print(describe_sequence([1, 2, 3, 4])) # Head: 1, Tail: [2, 3, 4]
print(describe_sequence((1, 2, 3)))    # Triple: 1, 2, 3
```

**序列模式匹配规则**：
- 匹配任何**序列类型**（`list`、`tuple` 等），不要求类型精确匹配
- `*rest` 最多出现一次，匹配零个或多个元素
- 不可变序列（`tuple`）和可变序列（`list`）可以交叉匹配

### 3.1.5 映射模式——字典解构

```python
def handle_command(cmd):
    match cmd:
        case {"action": "move", "x": x, "y": y}:
            return f"Moving to ({x}, {y})"
        case {"action": "quit"}:
            return "Quitting"
        case {"action": action, **rest}:
            return f"Unknown action: {action}, data: {rest}"
        case _:
            return "Not a valid command"

print(handle_command({"action": "move", "x": 10, "y": 20}))
# Moving to (10, 20)

print(handle_command({"action": "move", "x": 10, "y": 20, "z": 30}))
# Moving to (10, 20) — 映射模式允许额外键!
```

**映射模式的关键特性**：
- 只检查指定的键是否存在且值匹配，**忽略额外的键**（与序列模式不同——序列模式要求长度匹配）
- `**rest` 捕获剩余键值对

### 3.1.6 类模式——对象解构

```python
class Point:
    __match_args__ = ("x", "y")       # 定义位置参数的捕获顺序

    def __init__(self, x, y):
        self.x = x
        self.y = y

def describe_point(pt):
    match pt:
        case Point(0, 0):
            return "Origin"
        case Point(0, y):
            return f"On Y-axis, y={y}"
        case Point(x, 0):
            return f"On X-axis, x={x}"
        case Point(x, y) if x == y:   # 守卫条件
            return f"On diagonal, x=y={x}"
        case Point(x, y):
            return f"Point({x}, {y})"

print(describe_point(Point(0, 0)))    # Origin
print(describe_point(Point(3, 3)))    # On diagonal, x=y=3
print(describe_point(Point(3, 4)))    # Point(3, 4)
```

**`__match_args__` 的作用**：`Point(x, y)` 是位置模式——解释器怎样知道第一个位置参数对应 `x`？答案就是 `__match_args__ = ("x", "y")`。没有它，类模式只能用关键字形式：`case Point(x=0, y=0):`。

实验 16：`__match_args__` 的效果

```python
class WithoutMatchArgs:
    def __init__(self, a, b):
        self.a = a
        self.b = b

class WithMatchArgs:
    __match_args__ = ("a", "b")
    def __init__(self, a, b):
        self.a = a
        self.b = b

obj1 = WithoutMatchArgs(1, 2)
obj2 = WithMatchArgs(1, 2)

# 位置模式需要 __match_args__
try:
    match obj1:
        case WithoutMatchArgs(1, 2):    # TypeError!
            print("matched")
except TypeError as e:
    print(f"WithoutMatchArgs positional: {e}")

# 关键字模式不需要
match obj1:
    case WithoutMatchArgs(a=1, b=2):
        print("WithoutMatchArgs keyword: matched")

# 有 __match_args__ 后位置模式可用
match obj2:
    case WithMatchArgs(1, 2):
        print("WithMatchArgs positional: matched")
```

### 3.1.7 守卫条件

`case pattern if condition:` —— 先匹配模式，再检查守卫，两者都通过才执行分支。

```python
def categorize(numbers):
    match numbers:
        case [x, y] if x > y:
            return f"Descending: {x} > {y}"
        case [x, y] if x < y:
            return f"Ascending: {x} < {y}"
        case [x, y]:
            return f"Equal: {x} = {y}"
        case _:
            return "Not a pair"

print(categorize([5, 3]))   # Descending: 5 > 3
print(categorize([3, 5]))   # Ascending: 3 < 5
print(categorize([3, 3]))   # Equal: 3 = 3
```

**注意**：守卫条件中的变量是模式捕获的变量。如果模式匹配失败，守卫条件不会执行——短路优先。

### 3.2 match vs switch——本质区别

#### 3.2.1 C 的 switch——跳转表 + fall-through

```c
// C 的 switch: 值分派 + 默认 fall-through
switch (x) {
    case 1: printf("one");    // 没有 break, 会 fall-through 到 case 2!
    case 2: printf("two"); break;
    default: printf("other");
}
```

C 的 switch 编译为**跳转表**（当 case 值密集时）或**二分查找树**（当 case 值稀疏时）。jump table 模式下，`switch` 的时间复杂度是 O(1)——直接用 case 值作为数组索引跳转。

C switch 的问题：
1. **fall-through 陷阱**：忘记 `break` 导致逻辑穿透
2. **只支持整数/枚举**：不能匹配字符串、结构体
3. **无解构**：只能做值比较

#### 3.2.2 Rust 的 match——穷尽 + 解构

```rust
// Rust: 穷尽匹配, 编译器强制
match x {
    1 => println!("one"),
    2 => println!("two"),
    _ => println!("other"),    // 删掉这行 → 编译报错!
}
```

Rust 的 match 比 Python 更严格——**编译器强制穷尽性检查**，遗漏的模式会在编译期报错。Python 的 match 只做运行时匹配 + 可选的穷尽警告。

#### 3.2.3 Python 的 match——结构化解构 + 灵活穷尽

Python 选择了一条中间路线：保持了 Rust 的解构能力，但没有 Rust 的编译器强制穷尽——因为 Python 是动态类型语言，编译期无法确定被匹配对象的所有可能结构。`case _:` 是显式的兜底，不是编译器强制的。

| 特性 | C switch | Rust match | Python match |
|:---|:---|:---|:---|
| 匹配基础 | 整数值 | 任意模式 | 任意模式 |
| fall-through | 默认有 | 无 | 无 |
| 解构 | 无 | 有 | 有 |
| 穷尽检查 | 无 | **编译期强制** | 运行时 + 可选警告 |
| 守卫条件 | 无 | 有 | 有 |
| 变量绑定 | 无 | 有 | 有 |
| 编译优化 | 跳转表 O(1) | 编译期穷尽优化 | 顺序比较 O(n) |

### 3.3 match 的字节码实现

实验 17：match/case 的字节码

```python
import dis

def match_simple(x):
    match x:
        case 1:
            return "one"
        case 2:
            return "two"
        case _:
            return "other"

dis.dis(match_simple)
```

输出（Python 3.12，简化）：
```
  2     RESUME 0
        LOAD_FAST x
        MATCH_SUBJECT                     ← 保存匹配目标到专用栈

  3     LOAD_CONST 1
        COMPARE_OP ==                     ← x == 1?
        POP_JUMP_IF_FALSE → (next case)
        RETURN_VALUE "one"

  5     LOAD_CONST 2
        COMPARE_OP ==                     ← x == 2?
        POP_JUMP_IF_FALSE → (next case)
        RETURN_VALUE "two"

  7     RETURN_VALUE "other"              ← 通配符 Case
```

match/case 的实现策略：
1. **`MATCH_SUBJECT`**：将匹配目标保存到"匹配栈"上，供后续 case 共用
2. 每个 case 编译为**一系列比较指令**（`COMPARE_OP`、`CONTAINS_OP` 等）
3. case 匹配成功的路径编译为**变量绑定 + 分支执行**
4. case 匹配失败的路径编译为**跳转到下一个 case**

对于结构化模式（序列模式、映射模式、类模式），字节码更复杂：

```python
def match_sequence(x):
    match x:
        case [a, b]:
            return a + b

dis.dis(match_sequence)
```

输出会包含：
- 匹配前：检查 `isinstance(x, (list, tuple))`（序列类型检查）
- 检查长度：`len(x) == 2`
- 解构绑定：`a = x[0]`, `b = x[1]`

**类模式的实现**使用 `__match_args__` 做位置参数映射：
1. `isinstance(subject, Point)` → 类型检查
2. 从 `__match_args__` 获取属性名 → 按位置取属性值
3. 递归匹配子模式

### 3.4 模式匹配的设计闭环

| 设计选择 | 协议层支撑 | 字节码实现 | 安全性保障 | 代价 |
|:---|:---|:---|:---|:---|
| 非fall-through | case 后隐式跳转 | `JUMP_FORWARD` 跳出匹配 | 消除 switch fall-through 陷阱 | 无法利用 fall-through 简化多值匹配 |
| 变量绑定 | 赋值语义 | `STORE_FAST`/`STORE_NAME` | 解构+绑定一步完成 | 小写名字不能做常量匹配 |
| `__match_args__` | 位置参数→属性名映射 | `LOAD_ATTR` 读取属性 | 类模式简洁 | 需手动定义，容易遗漏 |
| 序列模式 | `__getitem__` + `len()` | `BINARY_SUBSCR` + 序列类型检查 | 鸭子类型匹配 | 跨类型匹配可能意外 |
| 映射模式 | `__getitem__` + `keys()` | `CONTAINS_OP` + `BINARY_SUBSCR` | 只检查指定键 | 额外键被忽略可能遗漏 |
| 守卫条件 | 布尔表达式 | `POP_JUMP_IF_FALSE` | 精细过滤 | 守卫失败后继续匹配其他 case |

## 四、推导式——循环的语法糖

### 4.1 四种推导式

Python 提供四种推导式（comprehension），它们是**循环 + 条件过滤 + 表达式求值**的一体化语法糖：

| 推导式 | 语法 | 返回类型 | 括号 |
|:---|:---|:---|:---|
| 列表推导式 | `[expr for x in iterable if cond]` | `list` | `[ ]` |
| 集合推导式 | `{expr for x in iterable if cond]` | `set` | `{ }` |
| 字典推导式 | `{key: val for x in iterable if cond}` | `dict` | `{ }` |
| 生成器表达式 | `(expr for x in iterable if cond)` | `generator` | `( )` |

实验 18：四种推导式对比

```python
# 列表推导式
squares = [x**2 for x in range(6)]              # [0, 1, 4, 9, 16, 25]
evens   = [x for x in range(10) if x % 2 == 0] # [0, 2, 4, 6, 8]

# 集合推导式
unique_squares = {x**2 for x in [-3, -2, -1, 1, 2, 3]}  # {1, 4, 9}

# 字典推导式
word_lengths = {w: len(w) for w in ["hello", "world", "hi"]}
# {'hello': 5, 'world': 5, 'hi': 2}

# 生成器表达式（惰性!）
gen = (x**2 for x in range(10**10))   # 不会预计算!
print(next(gen))                       # 0
print(next(gen))                       # 1
# 只在需要时计算

# 条件过滤
filtered = [x for x in range(10) if x % 2 == 0 if x % 3 == 0]  # 多个 if
print(filtered)                         # [0, 6]
```

### 4.2 推导式 vs 等价 for 循环

```python
# 推导式
result = [x**2 for x in range(5) if x > 2]

# 等价 for 循环
result = []
for x in range(5):
    if x > 2:
        result.append(x**2)
```

**推导式更快的原因**：
- 推导式的字节码中使用了 `LIST_APPEND` 指令，直接操作栈上的列表对象，**跳过了 `LOAD_ATTR`（查找 `append` 方法） + `CALL_FUNCTION`（调用方法）** 的开销
- 等价 for 循环每次 `result.append(x**2)` 需要：找到 `result` → 获取 `append` → 调用 → 返回

实验 19：性能对比

```python
import timeit

setup = "vals = list(range(10000))"

list_comp = timeit.timeit("[x**2 for x in vals]", setup=setup, number=1000)
for_loop  = timeit.timeit("""
result = []
for x in vals:
    result.append(x**2)
""", setup=setup, number=1000)

print(f"List comprehension: {list_comp:.3f}s")
print(f"For loop + append:  {for_loop:.3f}s")
# List comprehension 通常快 30-50%
```

### 4.3 嵌套推导式

嵌套推导式按**从左到右**的顺序阅读，等价于嵌套 for 循环：

```python
# 展平矩阵
matrix = [[1, 2, 3], [4, 5, 6], [7, 8, 9]]

flat = [x for row in matrix for x in row]
# 等价于:
# flat = []
# for row in matrix:
#     for x in row:
#         flat.append(x)

print(flat)   # [1, 2, 3, 4, 5, 6, 7, 8, 9]

# 带条件的嵌套推导式
# 找出矩阵中所有 > 5 的元素
big = [x for row in matrix for x in row if x > 5]
print(big)    # [6, 7, 8, 9]

# 转置矩阵
transposed = [[row[i] for row in matrix] for i in range(3)]
print(transposed)   # [[1, 4, 7], [2, 5, 8], [3, 6, 9]]
```

### 4.4 推导式的作用域——Python 3 的关键变更高

**Python 2**：推导式变量会泄漏到外部作用域。

**Python 3**：推导式有**独立的作用域**——推导内部的变量是局部的，不会影响外部。

实验 20：推导式的作用域隔离

```python
# Python 3: 推导式变量不泄漏
x = "outer"
result = [x**2 for x in range(3)]
print(result)   # [0, 1, 4]
print(x)        # "outer" — x 没有被推导式修改!

# Python 2 中: print(x) 会输出 2 (最后一次迭代的值)

# 生成器表达式同样隔离
y = "outer"
gen = (y for y in range(3))
print(list(gen))  # [0, 1, 2]
print(y)          # "outer" — 隔离

# 但赋值表达式 (walrus operator) 可以"返回"值
result = [(z := i, z**2) for i in range(3)]
print(result)   # [(0, 0), (1, 1), (2, 4)]
print(z)        # 2 —walrus 操作符的变量在外部可见!
```

#### 4.4.1 字节码层面的作用域隔离

推导式被编译为**独立的代码对象**——在字节码层面，推导式相当于一个匿名函数调用。

实验 21：推导式的代码对象

```python
import dis

def make_list():
    return [x**2 for x in range(3)]

# 查看函数的常量表
print(make_list.__code__.co_consts)
# (None, <code object <listcomp> at ...>, 'range')

# 推导式有自己的代码对象!
listcomp_code = make_list.__code__.co_consts[1]
print(listcomp_code.co_varnames)
# ('x', '.0')   — x 是推导变量, .0 是临时迭代器

# 反汇编推导式自己的字节码
dis.dis(listcomp_code)
#   1     LOAD_FAST .0 (迭代器)
#         FOR_ITER → (end)
#         STORE_FAST x
#         LOAD_FAST x
#         BINARY_OP **
#         LIST_APPEND 2       ← 直接追加到结果列表, 不走 append 方法
#         JUMP_BACKWARD → FOR_ITER
#   end   RETURN_VALUE
```

**关键发现**：
1. 推导式是一个**独立代码对象**（`<listcomp>`），有自己的 `co_varnames`、`co_consts`
2. 推导式内部使用 `LIST_APPEND` 指令，而非 `append()` 方法调用——这是性能优势的来源
3. 推导式通过函数调用机制执行，自然获得独立作用域——这是 Python 3 作用域隔离的底层原因

### 4.5 推导式的设计闭环

| 设计选择 | 实现 | 优势 | 代价 |
|:---|:---|:---|:---|
| 一体化语法 | `[expr for x in iter if cond]` | 声明式 > 命令式，compact | 复杂推导式可读性差 |
| 独立代码对象 | 推导式编译为 `<listcomp>` 函数 | 作用域隔离，不污染外部 | 无法在推导体内用 yield/await（3.6 前） |
| `LIST_APPEND` 指令 | 直接操作栈上列表 | 比调用 `append()` 快 30-50% | 只限列表推导式，其他推导式用各自的指令 |
| 生成器表达式惰性 | 返回 generator | 内存 O(1) | 只能迭代一次 |
| 嵌套推导式从左到右 | 等价嵌套 for 循环 | 扁平化、转置一行搞定 | 超过两层难读懂 |

## 五、常见陷阱

### 陷阱 1：for/else 的语义反直觉

**误解**：else 在循环条件为假时执行（类似 if/else）。

**实际**：else 在循环**没有被 break 中断时**执行——包括循环正常结束和空迭代。

```python
# 误解: "else 在条件为假时执行" → 错误!
for i in range(5):
    pass
# else 会执行! —— 但 range(5) 的"条件"从未为"假"

# 正确理解: "else 在没有 break 时执行"
for i in range(5):
    if i == 10:        # 永远不触发
        break
else:
    print("no break")  # 执行! 因为 break 从未触发

for i in range(5):
    if i == 3:
        break
else:
    print("no break")  # 不执行! 因为 break 触发了
```

**替代写法**（如果不习惯 for/else）：

```python
# 用标志变量代替 for/else
found = False
for i in items:
    if condition(i):
        found = True
        break
if not found:
    handle_not_found()

# 或用函数 + return 代替
def find(items):
    for i in items:
        if condition(i):
            return i
    return None  # 隐式"else"
```

### 陷阱 2：迭代中修改列表

**问题**：在 `for` 循环中添加/删除列表元素，会导致跳过元素或索引错误。

```python
# 陷阱: 删除时跳过元素
nums = [1, 2, 2, 3, 4]
for x in nums:
    if x == 2:
        nums.remove(x)     # 删除后, 后续元素前移, 迭代器跳过下一个!
print(nums)                # [1, 2, 3, 4] — 还有一个 2 没删掉!

# 正确做法1: 列表推导式创建新列表
nums = [1, 2, 2, 3, 4]
nums = [x for x in nums if x != 2]
print(nums)                # [1, 3, 4]

# 正确做法2: 迭代副本
nums = [1, 2, 2, 3, 4]
for x in nums[:]:          # nums[:] 创建副本, 迭代副本, 修改原列表
    if x == 2:
        nums.remove(x)
print(nums)                # [1, 3, 4]

# 正确做法3: 反向迭代删除
nums = [1, 2, 2, 3, 4]
for i in range(len(nums) - 1, -1, -1):
    if nums[i] == 2:
        del nums[i]
print(nums)                # [1, 3, 4]
```

**底层原因**：`for x in nums:` 的迭代器内部维护一个索引 `i`，每次 `__next__()` 返回 `nums[i]` 然后 `i += 1`。当你在循环中删除 `nums[i]`，后面的元素前移一位，但 `i` 仍然 `+= 1`，导致跳过了原来在 `i+1` 位置的元素。

### 陷阱 3：可变循环变量的闭包捕获

**问题**：在循环中创建闭包（lambda 或嵌套函数），所有闭包共享同一个循环变量的**最终值**。

```python
# 陷阱: 所有 lambda 都返回 4
funcs = []
for i in range(5):
    funcs.append(lambda: i)      # 捕获的是变量 i, 不是 i 的当前值!

print([f() for f in funcs])      # [4, 4, 4, 4, 4]

# 修复1: 默认参数绑定当前值
funcs = []
for i in range(5):
    funcs.append(lambda i=i: i)  # i=i 在定义时求值, 绑定到默认参数

print([f() for f in funcs])      # [0, 1, 2, 3, 4]

# 修复2: 用闭包工厂
def make_func(i):
    return lambda: i

funcs = [make_func(i) for i in range(5)]
print([f() for f in funcs])      # [0, 1, 2, 3, 4]

# 修复3: 推导式本身在 Python 3 中有独立作用域
funcs = [lambda i=i: i for i in range(5)]
print([f() for f in funcs])      # [0, 1, 2, 3, 4]
```

**底层原因**：Python 的闭包捕获的是**变量**（cell 引用），而非**值**。所有 lambda 共享同一个 `i` 变量的 cell，当循环结束后 `i = 4`，所有 lambda 看到的都是 4。默认参数 `i=i` 在函数定义时求值，创建了一个局部变量 `i`（默认参数的值），每个 lambda 有自己独立的 `i`。

### 陷阱 4：链式比较的中间值求值

**问题**：`a < b < c` 中 `b` 只求值一次——当 `b` 有副作用时，行为与展开写法不同。

```python
class Counter:
    def __init__(self, start):
        self.count = start
    def __lt__(self, other):
        return self.count < other
    def __repr__(self):
        return str(self.count)

# 陷阱: 链式比较中 b 只求值一次
calls = 0
def evil():
    global calls
    calls += 1
    return 5

# 链式: evil() 只调用一次
calls = 0
result = 3 < evil() < 10
print(f"Chained: calls={calls}, result={result}")  # calls=1

# 展开: evil() 可能调用两次
calls = 0
result = 3 < evil() and evil() < 10
print(f"Expanded: calls={calls}, result={result}")  # calls=2 (3<5 为 True, 继续求值)

# 这个差异在 b 有副作用时 (如修改数据库、发送网络请求) 非常重要
```

### 陷阱 5：match/case 中的大小写陷阱

**问题**：case 中的小写名字是变量捕获，不是值比较。想匹配常量值必须用大写或加点号。

```python
RED, GREEN, BLUE = 1, 2, 3

def describe_color(c):
    match c:
        case RED:              # 陷阱! 这不是匹配 1, 而是变量捕获!
            return "red captured"
        case _:
            return "other"

# 所有输入都会匹配第一个 case!
print(describe_color(99))      # "red captured" — 99 被捕获到 RED 变量!

# 修复: 用大写 + 点号引用常量, 或用守卫条件
class Color:
    RED = 1
    GREEN = 2
    BLUE = 3

def describe_color_fixed(c):
    match c:
        case Color.RED:        # 点号引用 = 常量比较
            return "red"
        case Color.GREEN:
            return "green"
        case Color.BLUE:
            return "blue"
        case _:
            return "other"

print(describe_color_fixed(1))   # "red"
print(describe_color_fixed(99))  # "other"
```

## 六、自测题目

**题目 1**：以下代码输出什么？解释原因。

```python
x = 0
if x:
    print("A")
elif x == 0:
    print("B")
else:
    print("C")
```

**题目 2**：以下代码中，`result` 的值是什么？为什么？

```python
result = []
for i in range(5):
    if i == 2:
        continue
    if i == 4:
        break
    result.append(i)
else:
    result.append("done")

print(result)
```

**题目 3**：以下代码输出什么？解释 `match` 的匹配行为。

```python
def classify(data):
    match data:
        case {"type": "error", "code": code}:
            return f"Error {code}"
        case {"type": "warning"}:
            return "Warning"
        case {"type": t, **rest}:
            return f"Type={t}, rest={rest}"
        case _:
            return "Unknown"

print(classify({"type": "error", "code": 404, "detail": "not found"}))
print(classify({"type": "info", "msg": "hello"}))
```

---

<details>
<summary>参考答案</summary>

**题目 1**：输出 `B`。`x = 0` 是 falsy 值，所以 `if x:` 为假，跳到 `elif x == 0:`，此时 `x == 0` 为 `True`，执行 `print("B")`。关键点：truthiness 为假不等于 `== 0` 为假——`0` 的 truthiness 是 False，但 `0 == 0` 是 True。这就是为什么 PEP 8 推荐用 `if x is not None:` 而非 `if x:` 来检查非空——当 `0` 是合法值时，truthiness 会误判。

**题目 2**：输出 `[0, 1, 3]`。逐次迭代：
- `i=0`：通过两个 if，`append(0)`
- `i=1`：通过两个 if，`append(1)`
- `i=2`：`continue` 跳过，不 append
- `i=3`：通过两个 if，`append(3)`
- `i=4`：`break` 退出循环

由于循环被 `break` 中断，`else` 子句不执行，`"done"` 不会被添加。`continue` 不影响 else 的执行——else 只关心"是否有 break"。

**题目 3**：第一次调用输出 `Error 404`。`{"type": "error", "code": 404, "detail": "not found"}` 匹配 `case {"type": "error", "code": code}:` —— `"type"` 键存在且值为 `"error"`，`"code"` 键存在且值 `404` 绑定到 `code`，额外的 `"detail"` 键被忽略（映射模式的特性）。第二次调用输出 `Type=info, rest={'msg': 'hello'}`。前两个 case 不匹配（`"type"` 不是 `"error"` 或 `"warning"`），第三个 case `{"type": t, **rest}` 匹配——`t` 捕获 `"info"`，`rest` 捕获剩余键值对 `{'msg': 'hello'}`。

</details>

## 七、控制流的解释力——20个疑惑统一回溯

理解 Python 控制流的根基——真值协议、迭代器协议、模式匹配协议——不是记住几条语法规则，而是获得一个**统一的解释框架**：表面上千差万别的 Python 行为，回溯到协议层面，就不再是散落的知识点，而是同一个根上长出的枝叶。

下表汇总了常见疑惑，统一标注其控制流根因：

| # | 表象疑惑 | 控制流根因 | 本文章节 |
|:--|:---|:---|:---|
| 1 | 为什么 `if []:` 为假而 `if [0]:` 为真？ | 真值协议：`__len__() → 0` 为假，`__len__() → 1` 为真；`0` 是合法元素，不影响容器真值 | §1.1 |
| 2 | 为什么 `and`/`or` 返回操作数而非 `True`/`False`？ | 短路求值 + Python 设计哲学：返回决定值意味着 `or` 可作默认值运算符，`and` 可作守卫运算符 | §1.2 |
| 3 | 为什么 `a < b < c` 中 `b` 只求值一次？ | 链式比较的编译器特殊处理：中间值缓存在求值栈上，不等价于展开形式 | §1.5 |
| 4 | 为什么 Python 没有 C 风格 `for(init;cond;incr)`？ | 迭代器协议优先：for 消费 `__iter__()`/`__next__()`，比索引更通用、更安全 | §2.1 |
| 5 | 为什么 `for x in lst:` 不能在循环中获取索引？ | for 只消费迭代器的 `__next__()`，无索引概念；需用 `enumerate()` 将元素包装为 `(index, element)` 元组 | §2.1 |
| 6 | 为什么迭代器只能用一次？ | 迭代器协议的设计：`__next__()` 消费一个元素后前进，耗尽后抛出 `StopIteration`，不会重置 | §2.1 |
| 7 | 为什么 `for/else` 的 else 在正常结束时执行？ | else 语义来自"break 是异常退出"——没有 break 说明循环正常结束，执行 else 是"没有异常"的分支 | §2.3 |
| 8 | 为什么 `break` 只退出最内层循环？ | 字节码层面，break 编译为跳转到当前循环的结束偏移，不携带层级信息 | §2.3 |
| 9 | 为什么 `range(10**10)` 不耗尽内存？ | range 是惰性序列（非迭代器），`__len__` 预计算，`__getitem__` 按公式生成元素 | §2.4 |
| 10 | 为什么 `10**9 in range(10**10)` 是 O(1)？ | range 的 `__contains__` 做数学判断（`(x-start)%step == 0` 且在范围内），不遍历 | §2.4 |
| 11 | 为什么 `match/case` 不需要 `break`？ | match 不是 switch——每个 case 是独立分支，无 fall-through 语义，编译器自动插入跳转 | §3.1 |
| 12 | 为什么 `case RED:` 是变量捕获而非值比较？ | 模式匹配的设计：小写名字 = 变量捕获（destructuring），点号/大写 = 常量比较（dispatch） | §3.1 |
| 13 | 为什么映射模式忽略额外键？ | 设计选择：映射模式只检查"是否有指定键"，类似 `dict.get()` 的语义；若要精确匹配需用守卫条件 | §3.1 |
| 14 | 为什么推导式变量不影响外部作用域？ | 推导式编译为独立代码对象（`<listcomp>`），通过函数调用执行，自然获得独立局部作用域 | §4.4 |
| 15 | 为什么推导式比等价 for 循环快？ | 推导式使用 `LIST_APPEND` 指令直接操作栈上列表，跳过了 `LOAD_ATTR`（查 `append`）+ `CALL_FUNCTION`（调用）的开销 | §4.2 |
| 16 | 为什么在循环中修改列表会跳过元素？ | 列表迭代器内部维护索引 `i`，删除元素后后续前移但 `i` 仍 `+=1`，导致跳过 | §5 陷阱2 |
| 17 | 为什么 lambda 捕获循环变量后都返回最后一值？ | 闭包捕获的是变量（cell）而非值，所有 lambda 共享同一个 `i` 的 cell，循环结束后 `i` 为最终值 | §5 陷阱3 |
| 18 | 为什么 `while True` + `break` 比 `do-while` 更 Pythonic？ | Python 没有 `do-while`，`while True:` + 条件 `break` 是等价惯用法，且更灵活（break 可出现在任何位置） | §2.2 |
| 19 | 为什么 `None` 在布尔上下文中为假？ | 真值协议：`None` 是单例空值，`PyObject_IsTrue()` 对 `Py_None` 特殊返回 0 | §1.1 |
| 20 | 为什么 `bool(0)` 是 `False` 而 `bool(0j)` 也是 `False`？ | 真值协议：数值类型通过 `__bool__()` → `nb_bool` 槽位，零值统一返回假，不管是 int、float 还是 complex | §1.1 |

每一个疑惑都不是独立的知识点——它们的答案都回溯到**三个协议**：**真值协议**（`__bool__`/`__len__` → 决定条件的真假）、**迭代器协议**（`__iter__`/`__next__` → 驱动循环的推进）、**模式匹配协议**（`__match_args__`/`__getitem__` → 实现结构的解构）。Python 的控制流不是建立在跳转指令之上的，而是建立在这三个协议之上的——**协议是控制流的元语言：理解它，其他一切是从它推出的定理，而非需要分别记忆的公理**。
