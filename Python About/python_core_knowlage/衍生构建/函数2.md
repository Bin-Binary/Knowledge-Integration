**实验 22：外层函数的 co_cellvars**

```python
def outer():
    x = 42
    y_unused = 99     # inner 没引用, 不会成为 cell
    
    def inner():
        return x
    
    return inner

print(f"outer co_cellvars: {outer.__code__.co_cellvars}")     # ('x',)
print(f"inner co_freevars: {outer().__code__.co_freevars}")   # ('x',)
print(f"y_unused 是否在 cellvars: {'y_unused' in outer.__code__.co_cellvars}")  # False
```

**只有被内层函数引用的外层变量才变成 Cell 变量**——`y_unused` 虽然也是 `outer` 的局部变量，但没有被内层引用，所以它保持为普通的 `LOAD_FAST` 局部变量，不会转化为 Cell。

**实验 23：用 ctypes 读取 Cell 对象的内存**

```python
import ctypes

class PyCellObject(ctypes.Structure):
    _fields_ = [
        ("ob_refcnt", ctypes.c_ssize_t),
        ("ob_type", ctypes.c_void_p),
        ("ob_ref", ctypes.c_void_p),     # 指向 cell_contents 的 PyObject*
    ]

def make_closure():
    captured = 42
    def inner():
        return captured
    return inner

f = make_closure()
cell = f.__closure__[0]
cell_addr = id(cell)

py_cell = PyCellObject.from_address(cell_addr)
print(f"Cell ob_ref    (hex) = {hex(py_cell.ob_ref)}")
print(f"captured value (id)  = {id(42)}")
print(f"cell.cell_contents   = {cell.cell_contents}")
print(f"ob_ref matches id(42): {py_cell.ob_ref == id(42)}")
```

Cell 对象的 `ob_ref` 字段指向值的 `PyObject` 地址——与 `id(cell_contents)` 一致。Cell 就是一个薄间接层：**"局部变量 → Cell → 实际值"**，多一次指针解引用，换来的是变量的堆上生命周期。

### 4.2 nonlocal 与闭包修改

§4.1 的闭包场景中，内层函数读取外层变量是自然的（`LOAD_DEREF` 读取 `cell_contents`）。但如果内层函数想要**修改**外层变量呢？

**不加 nonlocal：赋值创建新的 L 层变量，遮蔽 Cell**

```python
def outer():
    x = 42
    
    def inner():
        x = 99          # 没有 nonlocal，这是创建 L 层新变量
        print(f"inner x = {x}")     # 99 — L 层
        return x
    
    result = inner()
    print(f"outer x = {x}")         # 42 — Cell 中的值不变
    return result

outer()
```

**加上 nonlocal：赋值修改 Cell 的 cell_contents**

```python
def outer_mut():
    x = 42
    
    def inner():
        nonlocal x
        x = 99          # STORE_DEREF 修改 Cell
        print(f"inner x = {x}")
        return x
    
    inner()
    print(f"outer x = {x}")         # 99 — Cell 被修改，外层可见
    return x

outer_mut()
```

**实验 24：nonlocal 的字节码验证**

```python
import dis

def without_nonlocal():
    x = 42
    def inner():
        x = 99
        return x
    return inner

def with_nonlocal():
    x = 42
    def inner():
        nonlocal x
        x = 99
        return x
    return inner

print("=== 不加 nonlocal ===")
dis.dis(without_nonlocal())

print("\n=== 加上 nonlocal ===")
dis.dis(with_nonlocal())
```

输出对比：

```
=== 不加 nonlocal ===
  3           0 LOAD_CONST               0 (99)
              2 STORE_FAST               0 (x)      ← STORE_FAST: 局部变量赋值
  4           4 LOAD_FAST                0 (x)
              6 RETURN_VALUE

=== 加上 nonlocal ===
  3           0 LOAD_CONST               0 (99)
              2 STORE_DEREF              0 (x)      ← STORE_DEREF: Cell 赋值
  4           4 LOAD_DEREF               0 (x)
              6 RETURN_VALUE
```

**多层闭包的 nonlocal 链**：

```python
def level1():
    x = 1
    def level2():
        y = 2
        def level3():
            nonlocal x     # 跨越 level2, 修改 level1 的 Cell
            x = 10
            nonlocal y     # 修改 level2 的 Cell
            y = 20
        level3()
        print(f"level2: x={x}, y={y}")    # x=10 (level1的Cell), y=20 (level2的Cell)
    level2()
    print(f"level1: x={x}")               # x=10

level1()
```

`nonlocal x` 从 `level3` 的直接外层（`level2`）开始搜索，`level2` 中没有 `x`，继续上溯到 `level1` 的 Cell——找到后绑定。Cell 链使多层嵌套闭包的变量共享成为可能。

### 4.3 闭包的应用模式

#### 工厂函数

```python
def make_adder(n):
    def adder(x):
        return x + n        # n 被闭包捕获
    return adder

add5 = make_adder(5)
add10 = make_adder(10)

print(add5(3))    # 8
print(add10(3))   # 13

print(f"add5.__closure__[0].cell_contents = {add5.__closure__[0].cell_contents}")  # 5
print(f"add10.__closure__[0].cell_contents = {add10.__closure__[0].cell_contents}") # 10

print(f"add5.__code__ is add10.__code__: {add5.__code__ is add10.__code__}")
# True — 共享同一个 PyCodeObject, 不同的 Cell 绑定了不同的 n
```

这就是 "Function = Code + Context" 的极致体现：同一份代码，通过不同的 Cell 绑定，表现出不同的行为。

#### 状态封装（无类的状态机）

```python
def make_counter(start=0, step=1):
    count = start
    def counter():
        nonlocal count
        count += step
        return count
    counter.reset = lambda: setattr(counter, '__reset', True) or reset_inner()
    def reset_inner():
        nonlocal count
        count = start
    counter.reset = reset_inner
    return counter

c = make_counter(10, 5)
print(c())   # 15
print(c())   # 20
c.reset()
print(c())   # 15 — 重置后
```

闭包提供了一种**不使用类**即可封装可变状态的方式。Cell 对象就是实例属性——只是它不在 `__dict__` 中，而在 `__closure__` 的 Cell 里。

#### 回调携带上下文

```python
def make_callback(user_id, callback_type):
    def callback(event_data):
        print(f"[{callback_type}] user={user_id}, data={event_data}")
    return callback

cb1 = make_callback(42, "login")
cb2 = make_callback(99, "logout")

cb1({"ip": "10.0.0.1"})    # [login] user=42, data={'ip': '10.0.0.1'}
cb2({"ip": "10.0.0.2"})    # [logout] user=99, data={'ip': '10.0.0.2'}
```

闭包让回调函数天然携带了创建时的上下文——这在 GUI 编程（事件处理）、网络编程（连接回调）、异步编程（完成回调）中极为常见。

#### 晚绑定陷阱

这是闭包**最经典的陷阱**——闭包捕获的是**变量（Cell 引用）**，而非**值**：

**实验 25：晚绑定陷阱——循环中的 lambda**

```python
funcs = []
for i in range(5):
    funcs.append(lambda: i)

print([f() for f in funcs])    # [4, 4, 4, 4, 4] — 不是 [0, 1, 2, 3, 4]!
```

原因：所有 lambda 都捕获了**同一个变量 `i` 的 Cell**。循环结束后 `i = 4`，五个 lambda 通过 `LOAD_DEREF` 读取 Cell 时，`cell_contents` 已经是 4。

```python
for j, f in enumerate(funcs):
    if f.__closure__:
        print(f"lambda{j}.__closure__[0].cell_contents = {f.__closure__[0].cell_contents}")
# 全部输出 4
```

**修复：使用默认参数捕获当前值**

```python
funcs_fixed = []
for i in range(5):
    funcs_fixed.append(lambda i=i: i)     # i=i 在定义时求值，绑定到 func_defaults

print([f() for f in funcs_fixed])        # [0, 1, 2, 3, 4]

for j, f in enumerate(funcs_fixed):
    print(f"lambda{j}.__defaults__ = {f.__defaults__}")
# lambda0.__defaults__ = (0,)
# lambda1.__defaults__ = (1,)
# lambda2.__defaults__ = (2,)
# ...
```

`i=i` 利用了默认参数在**定义时求值**的特性（§2.2），将当前循环值"固化"到 `func_defaults` 中——这是默认参数绑定时机从陷阱变为工具的经典案例。

**修复2：使用工厂函数**

```python
def make_func(n):
    return lambda: n      # n 是每次调用 make_func 的新 Cell

funcs_factory = [make_func(i) for i in range(5)]
print([f() for f in funcs_factory])    # [0, 1, 2, 3, 4]
```

每次 `make_func(i)` 调用创建一个**新的闭包**，`n` 是一个新的 Cell——不同 Cell 之间互不干扰。

### 4.4 闭包与对象——殊途同归

闭包和对象都是"代码 + 状态"的封装方式。事实上，它们在表达能力上是等价的：

```python
# 闭包实现
def make_point_closure(x, y):
    def get_x(): return x
    def get_y(): return y
    def move(dx, dy):
        nonlocal x, y
        x += dx; y += dy
        return (x, y)
    return type('Point', (), {
        'get_x': get_x, 'get_y': get_y, 'move': move
    })()

# 类实现
class PointClass:
    def __init__(self, x, y):
        self._x, self._y = x, y
    def get_x(self): return self._x
    def get_y(self): return self._y
    def move(self, dx, dy):
        self._x += dx; self._y += dy
        return (self._x, self._y)

pc = make_point_closure(1, 2)
pcl = PointClass(1, 2)
print(pc.get_x(), pc.move(3, 4))     # 1, (4, 6)
print(pcl.get_x(), pcl.move(3, 4))   # 1, (4, 6)
```

| 对比维度 | 闭包 | 对象 |
|:---|:---|:---|
| 状态存储 | Cell 对象（`__closure__`） | 实例属性（`__dict__` / `__slots__`） |
| 状态访问 | `LOAD_DEREF`（指针解引用） | `LOAD_ATTR`（属性查找） |
| 方法共享 | 每个闭包实例有自己的函数对象 | 类的所有实例共享方法 |
| 继承 | 不支持 | 支持（MRO） |
| 自省 | 困难（Cell 不直观） | 容易（`dir()`、`vars()`） |
| 适用场景 | 少量状态 + 简单逻辑 | 大量状态 + 复杂行为 |

## 五、lambda——匿名函数的边界

### 5.1 lambda 的本质

`lambda` 是 Python 中创建匿名函数的语法。它创建的也是一个 `PyFunctionObject`，与 `def` 创建的函数对象在运行时完全相同，唯一区别是没有绑定到一个具名变量：

```python
add = lambda x, y: x + y

# 等价于:
def add(x, y):
    return x + y

# 但 lambda 的 __name__ 是 '<lambda>'
print(add.__name__)         # '<lambda>'
print(add.__qualname__)     # 'add' 或 '<lambda>' 取决于是否绑定到变量
```

**实验 26：lambda 与 def 的字节码对比**

```python
import dis

lambda_add = lambda x, y: x + y

def def_add(x, y):
    return x + y

print("=== lambda ===")
dis.dis(lambda_add)
print("\n=== def ===")
dis.dis(def_add)
```

输出几乎完全相同——两者的 `PyCodeObject` 中的字节码一样，都是 `LOAD_FAST 0`、`LOAD_FAST 1`、`BINARY_ADD`、`RETURN_VALUE`。lambda 不是什么特殊的语法结构，它就是**def + return 的单行缩写**。

### 5.2 lambda 的限制与边界

| 特性 | `def` | `lambda` |
|:---|:---|:---|
| 多条语句 | 支持 | 不支持（只允许单个表达式） |
| 赋值语句 | 支持 | 不支持（可用海象运算符 `:=` 部分 workaround） |
| 文档字符串 | 支持 | 不支持 |
| 类型注解 | 支持 | 不支持（参数注解支持，返回值注解不支持） |
| `__name__` | 函数名 | `'<lambda>'` |
| traceback 可读性 | 好（显示函数名） | 差（显示 `<lambda>`） |

```python
# lambda 中的海象运算符——有限的状态表达
data = [1, 2, 3, 4, 5]
result = list(map(lambda x: (y := x**2, y + 1)[1], data))
print(result)    # [2, 5, 10, 17, 26]
```

### 5.3 何时使用 vs 何时避免

**适合使用 lambda 的场景**：

```python
sorted(items, key=lambda x: x.age)                    # 简单的排序键
list(map(lambda x: x**2, range(10)))                 # 简单的变换
filter(lambda x: x > 0, values)                      # 简单的过滤
defaultdict(lambda: 0)                               # 简单的工厂
```

**应该避免 lambda 的场景**：

```python
# 反模式1: 复杂逻辑
process = lambda data: [transform(x) for x in data if validate(x) and not exclude(x)]
# → 应该用 def, 可读性、可调试性、可文档化

# 反模式2: 带副作用的 lambda
results = []
mapper = lambda x: (results.append(x), x*2)[1]  # 丑陋的副作用 hack
# → 应该用 def 明确表达意图

# 反模式3: 赋名 lambda
square = lambda x: x**2
# → 既然赋名了, 为什么不用 def square(x): ... ?
```

### 5.4 lambda 的闭包行为

lambda 的闭包机制与 def 完全一致——都是 Cell 对象 + `LOAD_DEREF`/`STORE_DEREF`：

```python
def make_lambda():
    x = 42
    return lambda: x     # 捕获 x

fl = make_lambda()
print(fl())                                   # 42
print(fl.__closure__[0].cell_contents)        # 42
print(fl.__code__.co_freevars)                # ('x',)
```

晚绑定陷阱对 lambda 同样有效（参见 §4.3），修复方式也相同（默认参数 `i=i` 或工厂函数）。

## 六、内置函数——工具箱

Python 的内置函数不是"对象的附属方法"，而是通过 `ob_type` 槽位统一分派的**协议函数**。这种设计让内置函数对任何实现了相应协议的类型一视同仁。

### 6.1 协议分派机制

```
调用 len(obj):
  1. 内置 len()  → PyObject_Size(obj)
  2. PyObject_Size → obj->ob_type->tp_as_sequence->sq_length
  3. 如果 sq_length 为 NULL → 尝试 tp_as_mapping->mp_length
  4. 如果都为 NULL → TypeError: object of type has no len()
  
调用 iter(obj):
  1. 内置 iter() → PyObject_GetIter(obj)
  2. PyObject_GetIter → obj->ob_type->tp_iter
  3. 如果 tp_iter 为 NULL → 尝试 tp_as_sequence->sq_item (旧式迭代)
  4. 如果都为 NULL → TypeError: object is not iterable
```

**实验 27：内置函数的协议分派**

```python
class MyContainer:
    def __len__(self):
        return 42
    
    def __iter__(self):
        return iter([1, 2, 3])
    
    def __getitem__(self, index):
        return [10, 20, 30][index]

c = MyContainer()
print(len(c))       # 42 — 调用 c.__len__()
print(list(c))      # [1, 2, 3] — 调用 c.__iter__()
print(c[0])         # 10 — 调用 c.__getitem__(0)
```

| 内置函数 | 对应协议方法 | C 层槽位 | 语义 |
|:---|:---|:---|:---|
| `len(obj)` | `obj.__len__()` | `sq_length` / `mp_length` | 容器大小 |
| `iter(obj)` | `obj.__iter__()` | `tp_iter` | 获取迭代器 |
| `next(itr)` | `itr.__next__()` | `tp_iternext` | 迭代器推进 |
| `hash(obj)` | `obj.__hash__()` | `tp_hash` | 哈希值 |
| `bool(obj)` | `obj.__bool__()` / `__len__()` | `nb_bool` / `sq_length` | 真值判断 |
| `repr(obj)` | `obj.__repr__()` | `tp_repr` | 官方字符串表示 |
| `str(obj)` | `obj.__str__()` | `tp_str` | 非官方字符串表示 |

### 6.2 函数式工具

```python
from functools import reduce

data = [1, 2, 3, 4, 5]

print(list(map(lambda x: x**2, data)))           # [1, 4, 9, 16, 25]
print(list(filter(lambda x: x > 3, data)))       # [4, 5]
print(reduce(lambda a, b: a + b, data))          # 15

print(list(enumerate(data)))                      # [(0,1), (1,2), (2,3), (3,4), (4,5)]
print(list(zip(data, "abcde")))                   # [(1,'a'), (2,'b'), (3,'c'), (4,'d'), (5,'e')]

print(all([True, True, False]))                   # False
print(any([True, True, False]))                   # True

print(min(data), max(data), sum(data))            # 1, 5, 15
print(sorted([3, 1, 4, 1, 5, 9]))                # [1, 1, 3, 4, 5, 9]
print(sorted("hello", key=str.lower, reverse=True))  # ['o', 'l', 'l', 'h', 'e']
```

**设计闭环**：为什么 `len`/`sorted`/`map` 是函数而不是方法？

在 Java 中，`list.size()` 是方法；在 Python 中，`len(list)` 是函数。这不是历史遗留，而是有意的设计：

1. **协议一致性**：`len()` 对 list、dict、str、set、自定义容器一视同仁——都是调用 `__len__()`。如果 `len` 是方法，那么 `int` 有 `bit_length()`、`str` 有 `len()` 属性、自定义类型有 `length()` 方法——命名不统一，协议无法统一。
2. **鸭子类型的保障**：`len(x)` 只要求 `x` 实现 `__len__()`，不要求 `x` 继承任何基类。方法调用（`x.len()`）暗示"类型拥有这个方法"的隶属关系，而函数调用暗示"对象满足这个协议"的能力关系。
3. **内置函数→ C 层槽位的直接分派**：`len(obj)` 在 C 层面直接查 `sq_length` 槽位，绕过了 Python 属性查找的开销——比 `obj.__len__()` 少一次属性查找。

## 七、常见陷阱

### 陷阱 1：可变默认参数（最经典的陷阱）

```python
def register(user, users=[]):
    users.append(user)
    return users

print(register("Alice"))    # ['Alice']
print(register("Bob"))      # ['Alice', 'Bob'] — 共享同一 list!
```

**原因**：默认值 `[]` 在 `def` 时创建一次，存储在 `func_defaults` 中，所有调用共享。

**避免**：

```python
def register(user, users=None):
    if users is None:
        users = []
    users.append(user)
    return users

print(register("Alice"))    # ['Alice']
print(register("Bob"))      # ['Bob']
```

### 陷阱 2：闭包的晚绑定（循环变量捕获）

```python
funcs = [lambda: i for i in range(5)]
print([f() for f in funcs])    # [4, 4, 4, 4, 4]
```

**原因**：lambda 捕获的是变量 `i` 的 Cell 引用，而非值。循环结束后 `i = 4`。

**避免**：

```python
funcs = [lambda i=i: i for i in range(5)]      # 默认参数固化当前值
print([f() for f in funcs])    # [0, 1, 2, 3, 4]
```

### 陷阱 3：忘记 global 声明

```python
count = 0

def increment():
    count += 1     # UnboundLocalError!
    return count
```

**原因**：`count += 1` 包含赋值，编译器将 `count` 标记为局部变量，但 `LOAD_FAST` 时局部 `count` 尚未初始化。

**避免**：

```python
count = 0
def increment():
    global count
    count += 1
    return count
```

### 陷阱 4：`from module import *` 遮蔽内建名称

```python
from some_module import *   # 如果 some_module 定义了 list, dict 等

def process(data):
    result = list(data)      # 可能调用的不是 builtins.list!
    return result
```

**原因**：`from ... import *` 将模块中所有名字倒入 G 层，如果与 B 层的内建名冲突，按 LEGB 规则 G 先于 B，内建函数被遮蔽。

**避免**：

1. 永远不要使用 `from module import *`
2. 如果必须导入多个名字，显式列出：`from some_module import foo, bar`
3. 使用 `__all__` 限制模块导出名

### 陷阱 5：闭包中修改可变对象与 nonlocal 的混淆

```python
def outer():
    items = [1, 2, 3]
    
    def inner():
        items.append(4)      # OK: 修改对象, 不改变绑定
        items = [99]         # UnboundLocalError! 赋值改变了绑定, 需要 nonlocal
    
    inner()

outer()
```

**原因**：`items.append(4)` 是方法调用，不涉及名字重新绑定，`LOAD_DEREF` 读取 Cell 后调用其方法即可。而 `items = [99]` 是赋值，编译器根据"赋值即局部"规则将 `items` 标记为局部变量，导致 `LOAD_FAST` 失败。

**避免**：理解 `修改对象` 和 `重新绑定变量名` 的区别——前者不需要 `nonlocal`，后者需要。

```python
        x = "local"
        print(x)
    g()

f()
```

**题目 3**：以下代码中 `f.__defaults__[0]` 最终的值是什么？写出推导过程。

```python
def f(a, b=[]):
    b.append(a)
    return b

r1 = f(1)
r2 = f(2, [])
r3 = f(3)
print(f.__defaults__[0])
```

---

<details>
<summary>参考答案</summary>

**题目 1**：输出 `10, 11, 12`。`base=i` 使用了默认参数在定义时求值的特性——每次循环 `def f` 执行时，`base` 的默认值被固化为当前 `i` 的值（0, 1, 2），存储在各自函数对象的 `__defaults__` 中。这与晚绑定陷阱恰好相反：默认参数捕获值，闭包捕获变量。

**题目 2**：`UnboundLocalError: local variable 'x' referenced before assignment`。在 `g` 函数中，存在赋值语句 `x = "local"`，编译器将 `x` 标记为 `g` 的局部变量。因此 `g` 中所有对 `x` 的引用（包括 `print(x)` 那一行）都编译为 `LOAD_FAST`。执行到 `print(x)` 时，`LOAD_FAST` 找到局部槽位为 NULL（尚未赋值），触发 `UnboundLocalError`。解决方法：在 `g` 中声明 `nonlocal x`，编译器会改用 `LOAD_DEREF`/`STORE_DEREF`。

**题目 3**：`f.__defaults__[0]` 最终值为 `[1, 3]`。推导：
- `f(1)`：不传 `b`，使用默认值 `[]`，`b.append(1)` → 默认值变为 `[1]`，返回 `[1]`。
- `f(2, [])`：显式传入 `[]`，创建了一个**新的 list**，`b.append(2)` → 这个新 list 变为 `[2]`，不影响默认值。默认值仍为 `[1]`。
- `f(3)`：不传 `b`，使用默认值 `[1]`，`b.append(3)` → 默认值变为 `[1, 3]`，返回 `[1, 3]`。

关键：`f(2, [])` 传入的是独立的 list，与 `func_defaults[0]` 无关；`f(1)` 和 `f(3)` 共享同一个默认 list。

</details>

## 九、函数与作用域的解释力——N个疑惑统一回溯

理解函数对象和 LEGB 作用域的最大收益，是获得一个**统一的解释框架**：表面上千差万别的 Python 函数行为，回溯到 `PyFunctionObject` 的内部字段 + `PyFrameObject` 的栈帧机制 + `PyCellObject` 的闭包单元 + LEGB 的字节码实现，就不再是散落的知识点，而是同一个根上长出的枝叶。

| # | 表象疑惑 | 底层根因 (PyFunctionObject / LEGB / Cell) | 本文章节 |
|:--|:---|:---|:---|
| 1 | 为什么可变默认参数在调用间共享状态？ | 默认值在 `def` 时求值一次，存入 `func_defaults` 元组，所有调用共享同一 `PyObject` | §2.2 |
| 2 | 为什么 `f(2, [])` 不影响默认值但 `f(1)` 影响？ | 显式传参创建新对象绑定到 `f_locals`，不涉及 `func_defaults`；不传参时从 `func_defaults` 取出共享对象 | §2.2 |
| 3 | 为什么循环中的 lambda 全部返回最后一个值？ | 闭包捕获**变量**（Cell 引用）而非**值**，所有 lambda 共享同一 Cell，循环结束后 `cell_contents` = 最后值 | §4.3 |
| 4 | 为什么 `lambda i=i: i` 可以修复晚绑定陷阱？ | 默认参数在 `def` 时求值，`i=i` 将当前循环值固化到 `func_defaults`，绕过了 Cell 的晚绑定 | §2.2, §4.3 |
| 5 | 为什么函数内赋值同名的全局变量报 `UnboundLocalError`？ | 编译器发现赋值语句，将变量标记为局部→`LOAD_FAST`，但在赋值前读取时槽位为 NULL→`UnboundLocalError` | §3.2 |
| 6 | 为什么 `global x` 声明让赋值修改模块变量？ | `global` 声明后，编译器将 `x` 的读写改为 `STORE_GLOBAL`/`LOAD_GLOBAL`，直接操作 `f_globals`（模块 `__dict__`） | §3.2 |
| 7 | 为什么 `nonlocal x` 让内层函数修改外层变量？ | `nonlocal` 声明后，编译器将 `x` 的读写改为 `STORE_DEREF`/`LOAD_DEREF`，通过 Cell 修改 `cell_contents` | §4.2 |
| 8 | 为什么局部变量比全局变量快？ | 局部变量用 `LOAD_FAST`（数组索引 O(1)），全局用 `LOAD_GLOBAL`（dict 查找 O(1) 均摊但常数更大） | §3.3 |
| 9 | 为什么闭包变量在函数返回后仍然存活？ | 变量存入 `PyCellObject`（堆上），Cell 的引用计数由闭包函数的 `__closure__` 元组持有，独立于栈帧 | §4.1 |
| 10 | 为什么同一份代码可以产生行为不同的函数（工厂函数）？ | `Function = Code + Context`：同一 `PyCodeObject` + 不同的 `func_defaults`/`func_closure` = 不同行为 | §1.1, §4.3 |
| 11 | 为什么 `def` 每次执行都创建新的函数对象？ | `def` 是运行时语句，`MAKE_FUNCTION` 字节码在堆上新建 `PyFunctionObject` | §1.2 |
| 12 | 为什么 `len()` 是内置函数而非方法？ | `len(obj)` → `sq_length` 槽位分派，保证协议一致性，避免各类型命名不统一的 `x.len()` / `x.size()` / `x.length()` | §6.1 |
| 13 | 为什么闭包只能读外层变量，修改需要 `nonlocal`？ | Python 的"赋值即局部"规则：赋值默认在 L 层创建新变量，`nonlocal` 显式覆盖此规则 | §3.2, §4.2 |
| 14 | 为什么 `items.append(4)` 不需要 `nonlocal` 但 `items = [99]` 需要？ | `.append()` 是方法调用（修改对象，不改变绑定），`= [99]` 是赋值（改变名字绑定，触发"赋值即局部"） | §7 陷阱5 |
| 15 | 为什么 `from module import *` 可能导致 `list()` 行为异常？ | `import *` 将名字倒入 G 层，LEGB 规则中 G 先于 B，遮蔽 `builtins.list` | §7 陷阱4 |
| 16 | 为什么装饰器能修改函数的行为？ | 装饰器在 `MAKE_FUNCTION` 后、`STORE_NAME` 前拦截函数对象，替换为新函数或修改 `func_*` 属性 | §1.2 |
| 17 | 为什么函数可以有自己的 `__dict__`？ | `PyFunctionObject` 有 `func_dict` 字段，允许动态添加属性（如 `f.custom_attr = value`） | §1.1 |
| 18 | 为什么 `nonlocal` 不能跨越模块级变量？ | `nonlocal` 只搜索 E 层（外层函数的 Cell），模块级变量在 G 层，需用 `global` 而非 `nonlocal` | §3.2 |
| 19 | 为什么 `LOAD_NAME` 是最慢的查找指令？ | `LOAD_NAME` 执行完整 LEGB 搜索（逐层 dict 查找），而 `LOAD_FAST`/`LOAD_GLOBAL` 只查固定一层 | §3.3 |
| 20 | 为什么递归深度有上限？ | 每次递归调用创建新 `PyFrameObject`，栈帧占用内存，`sys.setrecursionlimit()` 限制帧数量防止栈溢出 | §1.3 |

每一个疑惑都不是独立的知识点——它们的答案都回溯到 `PyFunctionObject` 的 "Code + Context" 结构（代码对象共享、上下文私有绑定）、`PyFrameObject` 的 `f_localsplus` 数组（局部变量的 O(1) 访问 vs 全局的 dict 查找）、`PyCellObject` 的堆上间接引用（闭包变量跨越栈帧存活）、以及编译器对变量作用域的静态分类（决定使用哪条 `LOAD_*`/`STORE_*` 字节码）。

函数与作用域模型就是 Python 行为的执行引擎：**理解它，其他一切——默认参数陷阱、闭包晚绑定、作用域遮蔽、性能差异——都是从它推出的定理，而非需要分别记忆的公理**。
