# Python核心基础（六）：迭代的哲学——迭代器/生成器/推导式的统一世界观

## 引言

C++ STL 的迭代器是指针的泛化——5 种分类（Input/Forward/Bidirectional/Random Access/Contiguous）构成严格的能力层级，编译器在模板实例化时检查你传的迭代器是否满足算法要求的 category。Java 的 `Iterator<E>` 用 `hasNext()` + `next()` 的配对方法驱动遍历，但 `Iterator` 与 `Iterable` 是独立的接口层次，`for-each` 语法糖只认 `Iterable`。Rust 的 `Iterator` trait 将惰性求值和组合子（`map`/`filter`/`fold`）做到极致，所有权系统保证了迭代期间的数据安全，`for` 循环底层调用 `IntoIterator::into_iter`——但 trait 的孤儿规则限制了跨 crate 的迭代器扩展。Go 没有泛型迭代器（1.23 之前），用 channel + `range` 实现并发迭代，代价是每个迭代都要分配一个 goroutine。

Python 做了一个足够激进的选择：**迭代是一个协议（protocol），不是一个类型层次**。

`__iter__` + `__next__`，两个双下方法，就是迭代的全部契约。没有 category 标签，没有 `hasNext()` 的状态查询，没有 trait 的编译期约束——只要你的对象在运行时能响应这两个方法，它就是可迭代的。生成器（`yield`）让编写迭代器从"手动维护状态机"变成了"写一个函数即可"。推导式（comprehension）让最常见的 `map`+`filter` 模式获得了函数式语言的表达力，同时保持 Python 的可读性。三者共享同一条底层通道：迭代器协议。

**协议简明的代价**：没有编译期 category 检查，你无法在类型层面区分"只能读一次的输入迭代器"和"可以反复遍历的随机访问迭代器"；`StopIteration` 异常不是 `next()` 的返回值而是控制流机制，这意味着在错误的时间抛出 `StopIteration` 会产生极其隐蔽的 bug（PEP 479 正是为此而生）；迭代器的一次性语义（one-shot）让 `list(it)` 这种"物化"操作暗中耗尽迭代器，后续的 `list(it)` 只能得到空列表——这不是 bug，而是协议的推论，但理解它需要你回溯到"迭代器与可迭代对象的区别"这个根源。

更进一步：生成器在 Python 中有双重角色。PEP 255 引入生成器时，动机仅为"让迭代器写法更简单"；PEP 342 增加 `send`/`throw`/`close` 后，生成器变成了"可以双向通信的协程"；PEP 380 的 `yield from` 又让生成器具备了委托能力——这是协程调度的基础。当 asyncio 用 `async def` + `await` 取代了生成器协程（PEP 492），生成器回归了迭代器的本职，但 `yield from` 的语义已经渗入 `async for` 的实现——理解异步迭代，首先要理解同步迭代。

本文的线索：从 `__iter__` + `__next__` 的 C 层分派开始，追踪 `for` 循环到字节码的操作码，进入 `PyGenObject` 的内部看到 yield 如何将栈帧挂起，再回到语法层分析推导式如何编译为独立的代码对象，最后用 itertools 证明"迭代器的组合艺术"。一路上你会亲手运行 `ctypes` 和 `dis.dis` 实验，看到 Python 的迭代机制在最底层如何运行——然后，你会明白为什么这个协议看似简陋，实则自洽。

### 四种语言的迭代模型对比

| 维度 | C++ STL | Java | Rust | Python |
|:---|:---|:---|:---|:---|
| **核心抽象** | 5 类迭代器（tag dispatch） | `Iterator<E>` 接口 | `Iterator` trait | `__iter__` + `__next__` 协议 |
| **结束检测** | `it == end`（哨兵值） | `hasNext()` 返回 bool | `next()` 返回 `Option<T>` | `next()` 抛 `StopIteration` |
| **类型安全** | 编译期 category 检查 | 编译期接口检查 | 编译期 trait 约束 + 所有权 | 运行时 duck typing |
| **可重启** | 容器重新 `begin()` | 容器重新 `iterator()` | 容器重新 `into_iter()` | 容器重新 `iter()` |
| **一致性保证** | 禁止迭代中修改（UB） | `ConcurrentModificationException` | 借用规则编译阻止 | 运行时行为未定义（陷阱源） |
| **组合性** | 算法 + 迭代器适配器 | Stream API | 迭代器适配子（`map`/`filter`） | itertools + 生成器管道 |
| **协程能力** | C++20 协程（`co_yield`） | 无原生支持 | Generator（nightly） | `yield` + `send`/`throw`/`close` |

**逐一展开对比**：

**C++ STL 迭代器**：5 种 category 不是文档约定，而是编译期类型标签——`std::input_iterator_tag`、`std::forward_iterator_tag` 等。算法通过 tag dispatch 选择最高效的实现：`std::advance` 对 RandomAccessIterator 用 `it += n`（O(1)），对 InputIterator 只能用 `++it` 循环 n 次（O(n)）。代价是泛型代码的错误信息极其晦涩——传错迭代器 category，你可能面对 200 行的模板实例化错误。Python 没有这个分层能力：`next()` 永远是 O(1) 的单步推进，`list(it)` 永远是 O(n) 的逐步拉取——不管底层数据结构是否支持随机访问。

**Java Iterator**：`hasNext()` + `next()` 的配对看似更安全——你永远不用担心"取值时突然抛异常"。但 `hasNext()` 和 `next()` 之间的状态一致性是一个微妙问题：如果两个线程交替调用 `hasNext()` 和 `next()`，或者在 `hasNext()` 返回 true 后、`next()` 调用前容器被修改，行为是未定义的。Python 用 `StopIteration` 单方法协议避免了这个问题——状态查询和取值合二为一，不存在"hasNext 说过有但 next 取不到"的窗口。代价是异常开销：`StopIteration` 的抛出/捕获比返回 `None` 或哨兵值贵，但 CPython 对此做了专门优化（`FOR_ITER` 内联检查 `StopIteration`，不走完整的异常处理路径）。

**Rust Iterator**：`trait Iterator { fn next(&mut self) -> Option<Self::Item>; }`——`Option<T>` 是代数类型，`Some(value)` 表示有值，`None` 表示结束。加上所有权系统：`for x in collection` 消耗 `collection`（通过 `IntoIterator::into_iter`），迭代期间无法再获取 `collection` 的引用——编译器保证了迭代中不会修改容器。Python 无法做到这一点——`for x in lst` 不消耗 `lst`，`lst` 仍然可用，这意味着迭代中修改容器是运行时检查不到的。

**Go channel**：Go 1.22 之前没有泛型迭代器，`for range` 只能用于 slice/map/channel/string。Go 1.23 引入了 `func(yield func(V) bool)` 风格的迭代器函数，但本质上是回调模式——与 Python 的 `__iter__`/`__next__` pull 模式相反，Go 的迭代器函数是 push 模式（迭代器主动 push 值给 yield 回调）。push 模式在某些场景更高效（避免了每步的函数调用开销），但控制流更复杂——`break` 退出循环时需要通过 yield 返回 false 通知迭代器停止。

**Python 的激进之处**：没有类型层次的约束，协议的实现成本最低（两个方法），但类型安全的防线也从编译期退到了运行时。这意味着迭代器的错误使用（耗尽后重用、迭代中修改容器）只能在运行时暴露——但同样因为协议简明，**任何对象都可以零成本成为可迭代对象**，没有"你必须继承某个基类"的门槛。这是鸭子 types 的哲学极致：能力即类型，协议即契约。

## 一、迭代器协议——最小化的鸭子协议

### 1.1 `iter()` 与 `next()` 的 C 层分派

Python 的迭代始于两个内置函数。但它们不是魔法——每一个都在 C 层有明确的分派路径。

**`iter(obj)`** 的分派：

```
iter(obj)  →  PyObject_GetIter(obj)
    ├── 检查 obj->ob_type->tp_iter 是否非 NULL
    │   ├── 是: 调用 tp_iter(obj) → 返回迭代器对象
    │   └── 否: 走 "序列协议" 后备路径
    │       ├── 检查 obj->ob_type->tp_as_sequence->sq_item 是否非 NULL
    │       │   ├── 是: 创建 seqiter 对象（包装 __getitem__ 调用）
    │       │   └── 否: 抛出 TypeError: '...' object is not iterable
    │       └── seqiter 内部: 从 index=0 开始，调用 __getitem__(i)
    │           ├── 返回值: 正常产出
    │           └── IndexError: 转换为 StopIteration
    └── 返回的迭代器对象必须满足: tp_iternext 非空
```

**`next(it)`** 的分派：

```
next(it)  →  PyIter_Next(it)
    ├── 调用 it->ob_type->tp_iternext(it)
    │   ├── 返回非 NULL: 产出值，增加引用计数
    │   └── 返回 NULL:
    │       ├── 检查是否有异常设置
    │       │   ├── StopIteration: 清除异常，返回 NULL（正常结束）
    │       │   └── 其他异常: 传播该异常
    │       └── 无异常（罕见）: 返回 NULL
    └── 等效 Python: it.__next__()
```

关键细节：

1. **`tp_iter` 优先于 `sq_item`**：如果类型同时定义了 `__iter__` 和 `__getitem__`，`iter()` 总是调用 `__iter__`。这是设计上的明确优先级——迭代器协议是首要的，序列协议是向后兼容的后备。

2. **`seqiter` 对象**：当类型只有 `__getitem__` 没有 `__iter__` 时，`PyObject_GetIter` 创建一个内部的 `seqiterobject`，其 `tp_iternext` 实现为：调用 `__getitem__(0)`，`__getitem__(1)`，`__getitem__(2)`，...，直到 `IndexError`。这个对象你从 Python 层看不到，但它是向后兼容的关键——旧式的序列类（只有 `__getitem__`）也能被 `for` 遍历。

3. **`tp_iternext` vs `__next__`**：`tp_iternext` 是 C 层的直接函数指针，效率最高；`__next__` 是 Python 层的方法，通过 MRO 查找后间接调用。对于内置类型（list/dict/set/str），迭代器的 `next()` 直接走 `tp_iternext`，不需要属性查找。

**实验 1：用 `ctypes` 观察 `tp_iter` 和 `tp_iternext` 槽位**


**Iterable vs Iterator 的定义**：

- **Iterable**：实现了 `__iter__()` 方法的对象。`__iter__()` 必须返回一个 Iterator。
- **Iterator**：同时实现了 `__iter__()` 和 `__next__()` 方法的对象。`__iter__()` 返回 `self`，`__next__()` 返回下一个值或抛出 `StopIteration`。

```python
from collections.abc import Iterable, Iterator

# Iterable 的 __subclasshook__: 只检查 __iter__
print(Iterable.__subclasshook__(type([1,2,3])))   # True
print(Iterable.__subclasshook__(type(42)))         # False

# Iterator 的 __subclasshook__: 检查 __iter__ + __next__
it = iter([1,2,3])
print(isinstance(it, Iterator))      # True
print(isinstance([1,2,3], Iterator)) # False — list 没有 __next__
```

`collections.abc.Iterator` 的实现极其简练：

```python
class Iterator(Iterable):
    __slots__ = ()
    @abstractmethod
    def __next__(self):
        raise StopIteration
    def __iter__(self):
        return self
    @classmethod
    def __subclasshook__(cls, C):
        # 只检查方法是否存在, 不要求继承关系
        if cls is Iterator:
            return _check_methods(C, "__iter__", "__next__")
        return NotImplemented
```

`__subclasshook__` 做的事情：不检查 MRO，不检查 `isinstance`——只检查类型 `C` 上有没有 `__iter__` 和 `__next__` 方法。这是鸭子类型在 ABC 中的正式化：**能力即身份**。

### 1.2 `for` 循环的迭代器协议实现

`for x in iterable:` 不神秘——它是 `iter()` + `while` + `next()` + `StopIteration` 的语法糖：

```python
# for x in iterable:   等价于:
_iter = iter(iterable)       # 1. 获取迭代器
while True:
    try:
        x = next(_iter)      # 2. 获取下一个值
    except StopIteration:    # 3. 正常结束
        del _iter            # 4. 清理迭代器引用
        break
    # 循环体
    ...
```

**字节码层面的 `for` 循环**：

```python
import dis

def for_loop(lst):
    for x in lst:
        print(x)

dis.dis(for_loop)

# 输出 (Python 3.10+):
#   2           0 LOAD_FAST                0 (lst)
#               2 GET_ITER                           ← iter(lst)
#               4 FOR_ITER               14 (to 20)  ← 循环头: next(it) 或跳转
#               6 STORE_FAST               1 (x)     ← x = next(it)
#
#   3           8 LOAD_GLOBAL              1 (print)
#              10 LOAD_FAST                1 (x)
#              12 CALL_FUNCTION            1
#              14 POP_TOP
#              16 JUMP_BACKWARD            7 (to 4)   ← 跳回 FOR_ITER
#
#              18 END_FOR                             ← Python 3.12+: 清理迭代器
#          20 >> RETURN_VALUE
```

关键操作码：

| 操作码 | 作用 | C 层对应 |
|:---|:---|:---|
| `GET_ITER` | `TOS = iter(TOS)` | `PyObject_GetIter(v)` |
| `FOR_ITER` | 尝试 `next(TOS)`，成功则 push 值，失败（StopIteration）则 pop 迭代器并跳转 | `PyIter_Next(v)` + 异常检查 |
| `STORE_FAST` | 将栈顶值存入局部变量 | 无特殊 |
| `JUMP_BACKWARD` | 无条件跳回循环头 | 无特殊 |
| `END_FOR` | Python 3.12+：迭代结束时清理迭代器 | DECREF 迭代器 |

**Python 3.12 的变化**：3.12 之前，`FOR_ITER` 在 `StopIteration` 时直接弹出迭代器并跳转；3.12 引入 `END_FOR` 操作码，将"清理迭代器"和"跳转"分离——这让整个循环的字节码布局更清晰，也更容易被优化器（specializing adaptive interpreter）识别和处理。

**为什么 `for` 不只用 `__getitem__`**：

Python 有两个遍历协议：
1. **迭代器协议**：`__iter__` → 返回迭代器 → `__next__` → StopIteration
2. **序列协议**：`__getitem__` + `__len__`（可选），从索引 0 开始递增调用

`iter()` 的选择逻辑（见 1.1 节）：`__iter__` 优先。如果类型定义了 `__iter__`，即使也定义了 `__getitem__`，`iter()` 也只调用 `__iter__`。

```python
class Dual:
    def __iter__(self):
        print("__iter__ called")
        return iter([1, 2, 3])

    def __getitem__(self, index):
        print(f"__getitem__({index}) called")
        if index < 3:
            return index + 10  # 返回 10, 11, 12
        raise IndexError

for x in Dual():
    print(f"  got: {x}")

# 输出:
# __iter__ called          ← __iter__ 被调用, __getitem__ 被忽略
#   got: 1
#   got: 2
#   got: 3
```

**实验 2：手动模拟 `for` 循环 + 序列协议迭代**

```python
# 实验2a: 手动 iter/next 循环
lst = [10, 20, 30]
it = iter(lst)           # 获取迭代器
print(type(it))          # <class 'list_iterator'>

print(next(it))          # 10
print(next(it))          # 20
print(next(it))          # 30
# print(next(it))        # StopIteration — 耗尽

# 实验2b: 只有 __getitem__ 的序列协议
class SeqOnly:
    def __init__(self, data):
        self.data = data
    def __getitem__(self, index):
        if index < len(self.data):
            return self.data[index]
        raise IndexError

s = SeqOnly([100, 200, 300])
# isinstance(s, Iterable) → True! 因为 __subclasshook__ 也检查 __getitem__
for x in s:
    print(x)
# 100  200  300 — for 循环使用 seqiter 包装器

# 实验2c: 同时有 __iter__ 和 __getitem__
class Both:
    def __iter__(self):
        print("  [__iter__]")
        return iter(['a', 'b'])
    def __getitem__(self, i):
        print(f"  [__getitem__({i})]")
        if i < 2: return chr(ord('x') + i)
        raise IndexError

print("Testing Both protocol:")
for x in Both():         # 只走 __iter__
    print(f"  → {x}")

# 输出:
# Testing Both protocol:
#   [__iter__]
#   → a
#   → b
```

**序列协议的局限**：`__getitem__` 遍历只能按整数索引递增，不能处理非序列集合（如 dict 的键，树的节点，无限数据流）。而且 `__getitem__` 的语义是"按索引取值"，将遍历语义强加在索引语义上是概念混叠——这正是 `__iter__` 被引入的原因。

### 1.2a 内置迭代器的 C 层结构

CPython 为每种内置容器实现了专用的迭代器类型，它们不共享代码，各自优化：

```
listiterobject                          ← list 的迭代器
├── [PyObject 头部: ob_refcnt + ob_type]
├── it_seq      (PyListObject*)  ← 指向被迭代的列表
├── it_index    (Py_ssize_t)     ← 当前索引 (0, 1, 2, ...)
└── it_seqlen   (Py_ssize_t)     ← 快照长度 (用于检测并发修改)

dict_keyiterator                       ← dict 的 key 迭代器
├── [PyObject 头部]
├── di_dict      (PyDictObject*) ← 指向被迭代的字典
├── di_pos       (Py_ssize_t)    ← 哈希表中的当前位置
├── di_len       (Py_ssize_t)    ← 剩余元素数
└── di_values    (PyObject**)    ← 值数组 (紧凑 dict)

setiterobject                          ← set 的迭代器
├── [PyObject 头部]
├── si_set       (PySetObject*)  ← 指向被迭代的集合
├── si_pos       (Py_ssize_t)    ← 哈希表中的当前位置
└── si_len       (Py_ssize_t)    ← 剩余元素数
```

**`listiterobject` 的 `tp_iternext` 实现**（简化伪代码）：

```c
static PyObject *
listiter_next(listiterobject *it)
{
    PyListObject *seq = it->it_seq;
    if (seq == NULL)
        return NULL;                          // 已耗尽
    // 检测并发修改: 如果列表长度变化, 抛出异常或行为未定义
    // CPython 的实现: 只在 it_index >= it_seqlen 时停止
    if (it->it_index < PyList_GET_SIZE(seq)) {
        PyObject *item = PyList_GET_ITEM(seq, it->it_index);
        ++it->it_index;
        Py_INCREF(item);
        return item;
    }
    it->it_seq = NULL;                        // 标记耗尽
    Py_DECREF(seq);
    return NULL;                              // 触发 StopIteration
}
```

注意这里的关键设计：`it_seq` 直接持有列表的指针（不是拷贝），`it_index` 是简单的递增索引。这意味着：

1. **迭代期间列表可以修改**——但行为是未定义的。如果列表增长了，新加入的元素可能被遍历到；如果缩短了，`it_index` 可能越界。这就是陷阱 4（迭代时修改容器）的 C 层根因。

2. **`it_seqlen` 的角色**：CPython 某些版本用 `it_seqlen` 记录列表创建时的长度快照，如果迭代中发现列表长度不匹配，可以提前终止。但这不是严格的 fail-fast（Java 那种），只是"尽力检测"。

3. **内存效率**：`listiterobject` 只有一个指针 + 两个整数 ≈ 24 字节。遍历 100 万元素的列表，迭代器本身只占 24 字节——不会随着列表大小增长。

**实验 2a-ranking：用 `ctypes` 观察迭代器内部状态**

```python
import ctypes
import sys

# 间接方法: 通过迭代器的 __reduce__ 查看内部状态
lst = [10, 20, 30, 40]
it = iter(lst)

# 列表迭代器有 __reduce__ 方法, 暴露内部状态
print(it.__reduce__())  # (<class 'list_iterator'>, ([10, 20, 30, 40],), 0)
#                              类型                    绑定的列表          当前索引
# __reduce__ 返回的第三个元素就是 it_index!

next(it)  # 取走 10
print(it.__reduce__())  # (... , 1)  ← 索引推进到 1

next(it)  # 取走 20
print(it.__reduce__())  # (... , 2)  ← 索引推进到 2

# 字典迭代器
d = {'x': 1, 'y': 2, 'z': 3}
dit = iter(d)
print(type(dit).__name__)              # dict_keyiterator
# dict 迭代器没有 __reduce__, 但可以通过 __length_hint__ 看剩余数
print(dit.__length_hint__())           # 3
next(dit)
print(dit.__length_hint__())           # 2
```

**`seqiterobject` —— `__getitem__` 的包装器**：

当类型只有 `__getitem__` 没有 `__iter__` 时，`PyObject_GetIter` 创建的内部迭代器类型：

```c
// Objects/iterobject.c (简化)
typedef struct {
    PyObject_HEAD
    PyObject *it_seq;     // 被迭代的序列对象
    Py_ssize_t it_index;  // 当前索引, 从 0 开始
} seqiterobject;

static PyObject *
seqiter_next(seqiterobject *it)
{
    // 等价于: it_seq[it_index]
    PyObject *result = PyObject_GetItem(it->it_seq, PyLong_FromSsize_t(it->it_index));
    if (result != NULL) {
        it->it_index++;
        return result;
    }
    // IndexError → StopIteration
    if (PyErr_ExceptionMatches(PyExc_IndexError)) {
        PyErr_Clear();
        return NULL;  // 触发 StopIteration
    }
    // 其他异常传播
    return NULL;
}
```

与 `listiterobject` 的区别：
- `listiterobject` 直接通过 `PyList_GET_ITEM` C 宏访问数组元素，O(1)，无 Python 层调用
- `seqiterobject` 通过 `PyObject_GetItem` 间接调用 `__getitem__`，每次都要构建 `int` 参数、做属性查找、调用 Python 方法——**慢得多**

这就是为什么内置类型（list/dict/set/str/tuple/range）都实现了 `__iter__` 而不是依赖 `__getitem__`——C 层直接访问比 Python 层间接调用快 5-10 倍。

### 1.3 迭代器的耗尽与一次性

迭代器是一个**有状态**的对象：它记住"当前走到哪了"。一旦走到终点（抛出 `StopIteration`），它就永久耗尽——再调用 `next()` 只会立刻抛 `StopIteration`。

```python
it = iter([1, 2, 3])
print(list(it))   # [1, 2, 3] — 物化迭代器
print(list(it))   # [] — 已耗尽, 无值可产
```

这不是 bug。迭代器的语义是"一次性游标"——就像文件指针读到了 EOF，你不会期望再 `read()` 出内容，除非 `seek(0)` 重新定位。但迭代器没有 `seek`——要重新遍历，你必须从**可迭代对象**重新获取一个**新的迭代器**：

```python
lst = [1, 2, 3]            # 可迭代对象 (Iterable)
it1 = iter(lst)            # 第一个迭代器
list(it1)                   # [1, 2, 3]
it2 = iter(lst)            # 第二个迭代器 (从 lst 重新创建)
list(it2)                   # [1, 2, 3] — 新迭代器不受 it1 影响
```

**`iter(iterator)` 返回 `self`**：

这是一个微妙但关键的设计：对迭代器调用 `iter()`，返回的是它自己：

```python
it = iter([1, 2, 3])
print(iter(it) is it)   # True
```

为什么？因为迭代器的 `__iter__` 方法返回 `self`。在 C 层，`Iterator` 类型的 `tp_iter` 槽位直接返回 `self`（增加引用计数后），而不是创建一个新的迭代器包装器。

这个设计的意图：**迭代器本身就是可迭代的**。这样，接受 `Iterable` 的函数可以放心调用 `iter(obj)`——如果 `obj` 已经是迭代器，`iter()` 不会多此一举地包装；如果 `obj` 是可迭代对象，`iter()` 创建新迭代器。`iter()` 是幂等的（对迭代器而言）。

```python
def consume(iterable):
    """接受 Iterable 或 Iterator, 统一处理"""
    it = iter(iterable)   # 如果已是 Iterator, 返回 self
    for x in it:
        print(x)

it = iter([1, 2, 3])
consume(it)               # 正常工作: iter(it) is it
consume([1, 2, 3])        # 正常工作: iter(list) 创建新 list_iterator
```

**实验 3：迭代器耗尽行为与 `iter(it) is it`**

```python
# 实验3a: 耗尽后继续调用 next
it = iter([1, 2])
print(next(it))           # 1
print(next(it))           # 2
try:
    next(it)              # StopIteration
except StopIteration as e:
    print(f"StopIteration: value={e.value}")  # value=None (默认)

# 再次调用 next — 仍然 StopIteration (不会恢复)
try:
    next(it)
except StopIteration:
    print("Still exhausted")  # Still exhausted

# 实验3b: iter(it) 返回 self
it = iter([1, 2, 3])
print(iter(it) is it)     # True

# 与 list 对比
lst = [1, 2, 3]
it1 = iter(lst)
it2 = iter(lst)
print(it1 is it2)         # False — 每次创建新迭代器

# 实验3c: len() 对耗尽迭代器无意义
import sys
it = iter([1, 2, 3])
print(sys.getsizeof(it))  # 迭代器本身很小 (32 字节左右)
# 迭代器没有 __len__, 因为它不知道自己还有多少元素

# 实验3d: 迭代器 != 可迭代对象 (重要区别)
class Repeat:
    """可迭代对象: 每次迭代产生相同的序列"""
    def __init__(self, n):
        self.n = n
    def __iter__(self):
        return iter(range(self.n))

r = Repeat(3)
print(list(r))    # [0, 1, 2]
print(list(r))    # [0, 1, 2] — 可迭代对象可以反复迭代!

# 对比: 如果 Repeat.__iter__ 返回 self 并实现 __next__
class RepeatOnce:
    """错误示范: 把自身当迭代器"""
    def __init__(self, n):
        self.n = n
        self.i = 0
    def __iter__(self):
        return self        # ← 返回 self 而非新迭代器
    def __next__(self):
        if self.i < self.n:
            val = self.i
            self.i += 1
            return val
        raise StopIteration

r = RepeatOnce(3)
print(list(r))    # [0, 1, 2]
print(list(r))    # [] — 耗尽了! 因为 iter(r) is r, 不是新迭代器
```

**设计模式：可迭代对象 vs 迭代器分离**：

```python
# 正确模式: Iterable 和 Iterator 分离
class Countdown:
    """Iterable: 负责创建迭代器"""
    def __init__(self, start):
        self.start = start
    def __iter__(self):
        return CountdownIterator(self.start)

class CountdownIterator:
    """Iterator: 负责维护遍历状态"""
    def __init__(self, start):
        self.current = start
    def __iter__(self):
        return self
    def __next__(self):
        if self.current <= 0:
            raise StopIteration
        val = self.current
        self.current -= 1
        return val

c = Countdown(3)
print(list(c))   # [3, 2, 1]
print(list(c))   # [3, 2, 1] — 每次创建新的 CountdownIterator
```

这种分离在 C++ 中也是惯例：容器（类似 `Iterable`）的 `begin()`/`end()` 返回迭代器对象（类似 `Iterator`），迭代器本身不负责存储数据。Java 的 `Iterable.iterator()` 也是一个工厂方法，每次返回新的 `Iterator`。Python 的区别仅在：迭代器协议更简明（2 个方法 vs C++ 的 5 个 category + begin/end），但"**可迭代对象与迭代器分离**"的原则是跨语言通用的。

### 1.3a 设计闭环：协议简明性的收益与代价

回顾 §1.1-§1.3，迭代器协议的设计形成了一个自洽的闭环：

**收益闭环**：
1. 协议只需 2 个方法 → 任何类型零成本成为 Iterable → 标准库和第三方库百花齐放
2. `iter()` 对迭代器幂等 → 统一接口，不需要区分 "传入的是 Iterable 还是 Iterator"
3. `StopIteration` 作为结束信号 → `for` 循环的实现统一为 try/except，不需要状态查询
4. 迭代器一次性 → 推导式/生成器/itertools 共享同一条 pull-based 数据流模型

**代价闭环**：
1. 没有 category → 复杂算法（如二分查找）无法利用随机访问优化 → `bisect` 模块绕过迭代器直接操作序列
2. 一次性语义 → `list(it)` 暗中耗尽迭代器 → 需要理解 "Iterable ≠ Iterator" 才能避开陷阱
3. 异常作为控制流 → `StopIteration` 可能从意外位置逃逸 → PEP 479 引入 `RuntimeError` 转换
4. 无编译期保护 → 迭代中修改容器行为未定义 → 只能在运行时通过编码规范规避

**Python 的哲学选择**：协议简明 > 编译期安全。这个选择与 Python 的整体设计一脉相承——动态类型、鸭子类型、EAFP（Easier to Ask Forgiveness than Permission）都是"运行时发现 > 编译期阻止"的体现。迭代器协议不是这个哲学的例外，而是它最纯粹的实例。

**PEP 纪年表**：

| PEP | 版本 | 内容 | 核心变化 |
|:---|:---|:---|:---|
| PEP 234 | 2.2 | 引入 `iter()` 内置函数和迭代器协议 | 统一遍历方式，`__iter__` 取代 `__getitem__` 作为首选 |
| PEP 255 | 2.2 | 引入生成器（`yield`） | 简化迭代器编写，但生成器只支持 `next()` |
| PEP 342 | 2.5 | 生成器增强（`send`/`throw`/`close`） | 生成器升级为协程，支持双向通信 |
| PEP 380 | 3.3 | `yield from` 语法 | 子生成器委托，简化生成器组合 |
| PEP 479 | 3.7 | `StopIteration` 隐式转换 | 生成器内 `StopIteration` 转为 `RuntimeError`，消除隐蔽 bug |
| PEP 492 | 3.5 | `async/await` + 异步迭代器 | `__aiter__`/`__anext__` 协议，`async for` 语法 |
| PEP 525 | 3.6 | 异步生成器 | `async def` + `yield`，`PyAsyncGenObject` |

## 二、生成器——yield 驱动的状态机

### 2.1 `PyGenObject` 内部结构

生成器是 Python 迭代机制的皇冠——它让"写一个迭代器"的工作量从"手动维护状态类"坍缩为"写一个带 `yield` 的函数"。要理解为什么生成器能做到这一点，必须看 CPython 内部的 `PyGenObject`。

```
PyGenObject                                 ← 继承自 PyObject
├── [PyObject 头部: ob_refcnt + ob_type, 16B]
├── gi_frame    (PyFrameObject*)  8B   ← 挂起的栈帧 (核心!)
├── gi_code     (PyCodeObject*)   8B   ← 代码对象 (就是生成器函数的代码)
├── gi_running  (int)             4B   ← 运行标志 (防重入)
├── gi_yieldfrom(PyObject*)       8B   ← yield from 委托的目标
└── gi_name     (PyUnicodeObject*) 8B  ← 生成器函数名

# Python 3.11+ 栈帧结构变化:
# PyFrameObject 被简化为 "frame object",
# 实际执行状态移入更轻量的 _PyInterpreterFrame
# 但 gi_frame 仍然指向栈帧 (只是内部结构变了)
```

**核心洞察：生成器 = 挂起的栈帧 + 保存的状态**。

普通函数调用时，`CALL_FUNCTION` 创建 `PyFrameObject`，函数执行完毕后栈帧销毁。生成器函数不同：`yield` 时，解释器**不销毁栈帧**，而是将栈帧从调用链中摘下，挂到 `PyGenObject.gi_frame` 上——栈帧上的局部变量、操作数栈、指令指针（`lasti`）全部原样保留。下次 `next(gen)` 时，解释器将这个栈帧重新挂回调用链，从 `lasti + 1` 继续执行。

```python
import dis
import inspect

def simple_gen():
    x = 1
    yield x
    x = 2
    yield x
    return "done"

g = simple_gen()

# 生成器对象内部
print(type(g))                          # <class 'generator'>
print(g.gi_code is simple_gen.__code__) # True — 共享代码对象

# 栈帧信息
frame = g.gi_frame
print(frame.f_lasti)   # -1 (尚未开始执行)
print(frame.f_locals)  # {}  (还没有局部变量)

next(g)                 # 执行到 yield x, 挂起
print(g.gi_frame.f_lasti)    # 2 (yield 对应的字节码偏移)
print(g.gi_frame.f_locals)   # {'x': 1}

next(g)                 # 恢复, 执行到第二个 yield
print(g.gi_frame.f_lasti)    # 更新
print(g.gi_frame.f_locals)   # {'x': 2}

try:
    next(g)             # 执行 return "done", 抛 StopIteration(value="done")
except StopIteration as e:
    print(e.value)      # "done"

# 生成器关闭后
print(g.gi_frame)       # None — 栈帧已被释放
```

**生成器创建的 C 层过程**：

```
simple_gen()  →  调用生成器函数
    ├── 不执行函数体!           ← 关键: 调用生成器函数只创建对象, 不运行
    ├── 创建 PyGenObject
    │   ├── gi_code = simple_gen.__code__
    │   ├── gi_frame = 新建 PyFrameObject (尚未执行)
    │   ├── gi_running = 0
    │   └── gi_yieldfrom = NULL
    └── 返回 PyGenObject* (即 generator 对象)
```

这里有一个关键点：**调用生成器函数不执行函数体**。普通函数调用 = 创建帧 + 执行帧 + 返回值；生成器函数调用 = 只创建帧 + 返回生成器对象，帧的执行延迟到第一次 `next()`。

验证这一点：

```python
def gen_with_print():
    print("Body started!")    # 什么时候打印?
    yield 1
    print("After first yield")

g = gen_with_print()          # 不会有任何输出!
print(type(g))                # <class 'generator'> — 已经返回了
# "Body started!" 还没打印

next(g)                       # 现在: Body started! → yield 1 → 挂起
# 输出: Body started!
# 返回: 1
```

### 2.2 `yield` ——暂停与恢复

**yield 的语义**：

```python
def gen():
    received = yield 42       # yield 产出 42, 暂停, 等待 send() 传入值
    print(f"Received: {received}")
    yield received * 2
```

分解 `yield 42` 的执行过程：

```
1. 计算 yield 后的表达式 (42)
2. 将 42 作为当前 yield 的产出值 (给 next()/send() 的返回值)
3. 保存当前栈帧状态:
   - f_lasti = 当前字节码偏移 + 跳过 POP_TOP
   - 局部变量原样保留在栈帧上
4. 将 gi_frame 从调用链摘下
5. 返回 42 给调用者
6. (挂起, 等待 next()/send() 恢复)
```

**对应字节码**：

```python
import dis

def gen():
    x = yield 1
    yield x + 1

dis.dis(gen)

# Python 3.11:
#   2           0 LOAD_CONST               0 (None)
#               2 YIELD_VALUE              0     ← 暂停, 产出 1 (注意: 常量 1 实际由前面的 RESUME 准备)
#               4 RESUME                   3     ← 恢复后的起点
#               6 STORE_FAST               0 (x) ← x = send() 传入的值
#
#   3           8 LOAD_FAST                0 (x)
#              10 LOAD_CONST               1 (1)
#              12 BINARY_OP                0 (+)
#              16 YIELD_VALUE              0     ← 暂停, 产出 x+1
#              18 RESUME                   3
#              20 POP_TOP                       ← 丢弃 send() 传入的值 (因为后面没有接收)
#              22 RETURN_CONST            1 (None)  ← 隐式 return None
```

Python 3.11+ 对生成器字节码做了重要改版：引入 `YIELD_VALUE` + `RESUME` 操作码替代旧的 `YIELD_VALUE` + `POP_TOP`。`RESUME` 是新的操作码，既用于生成器恢复，也用于协程恢复——这让生成器和协程的字节码路径统一了起来。

**生成器的状态转换**：

```
              next()/send(None)
  [创建] ──────────────────────────► [执行中]
  GEN_CREATED                       GEN_RUNNING
       │                                │
       │ 首次 next()                    │ yield → 挂起
       │                                ▼
       │                          GEN_SUSPENDED
       │                                │
       │                                │ next()/send(value)
       │                                │ → 恢复执行
       │                                │
       │                                │ return / StopIteration
       │                                ▼
       └──────────────────────────► GEN_CLOSED
                                  (gi_frame = None)
```

```python
import inspect

def gen():
    yield 1
    yield 2

g = gen()
print(inspect.getgeneratorstate(g))  # GEN_CREATED — 尚未启动

next(g)                               # 执行到 yield 1
print(inspect.getgeneratorstate(g))  # GEN_SUSPENDED — 挂起

# 获取状态也可以看 gi_frame
print(g.gi_frame is not None)         # True — 有栈帧

next(g)                               # 执行到 yield 2
print(inspect.getgeneratorstate(g))  # GEN_SUSPENDED

next(g)                               # 函数结束, return None → StopIteration
print(inspect.getgeneratorstate(g))  # GEN_CLOSED
print(g.gi_frame)                     # None — 栈帧已释放
```

**实验 4：`gi_frame` 检查与 `send()` 双向通信**

```python
def two_way():
    first = yield "hello"       # 产出 "hello", 等待接收
    second = yield first * 2    # 产出 first*2, 等待接收
    yield second * 3            # 产出 second*3

g = two_way()

# 启动生成器 (必须用 next() 或 send(None))
result1 = next(g)
print(result1)                  # "hello" — yield 产出的值

# 检查栈帧
print(f"f_lasti={g.gi_frame.f_lasti}")
print(f"f_locals={g.gi_frame.f_locals}")  # {} — first 还没赋值

# 发送值给 yield
result2 = g.send(10)
print(result2)                  # 20 — first=10, yield 产出 10*2

print(f"f_locals={g.gi_frame.f_locals}")  # {'first': 10}

result3 = g.send(5)
print(result3)                  # 15 — second=5, yield 产出 5*3

try:
    next(g)                     # 函数结束
except StopIteration:
    pass
```

### 2.3 `send` / `throw` / `close` ——生成器的控制协议

PEP 342 为生成器增加了三个方法，使其从"单向产出器"升级为"双向通信协程"：

**`send(value)`**：

- 恢复生成器执行，`value` 成为当前 `yield` 表达式的值
- 首次启动必须用 `send(None)` 或 `next()`（因为第一个 yield 还没有"等待接收"的位置）
- 等价于 `next()`：`next(g)` ≡ `g.send(None)`

```
调用者                         生成器
  │                              │
  │  g.send(10)                  │
  │ ───────────────────────────► │
  │                              │  yield 表达式的值 = 10
  │                              │  继续执行...
  │                              │  遇到下一个 yield
  │  ←────────────────────────── │
  │  返回 yield 产出的值          │  (挂起)
```

**`throw(type[, value[, traceback]])`**：

- 在当前 `yield` 挂起点抛出指定异常
- 生成器可以选择捕获该异常并继续运行，或让它传播出去

```python
def catching_gen():
    try:
        x = yield "ready"
    except ValueError as e:
        print(f"Caught: {e}")
        yield "recovered"
    yield "after recovery"

g = catching_gen()
next(g)                           # "ready"
g.throw(ValueError, "test error") # Caught: test error → "recovered"
next(g)                           # "after recovery"
```

**`close()`**：

- 向生成器发送 `GeneratorExit` 异常
- 生成器如果捕获了 `GeneratorExit`，应该清理资源后重新抛出或直接返回
- 如果生成器不处理 `GeneratorExit`，它会传播出来但被 `close()` 捕获（不报错）
- **关键规则**：生成器不允许在 `GeneratorExit` 后 yield 新值（会触发 `RuntimeError`）

```python
def with_cleanup():
    try:
        yield 1
        yield 2
    finally:
        print("Cleaning up")

g = with_cleanup()
next(g)           # 1
g.close()         # Cleaning up — finally 块被执行
print(g.gi_frame) # None — 已关闭
```

**`yield from` ——子生成器委托**（PEP 380）：

`yield from expr` 做了三件关键事情：
1. 将 `next()`/`send()` 的调用**透传**给子生成器
2. 将子生成器的 `yield` 产出值**直接**传递给调用者
3. 将 `throw()`/`close()` 也**透传**给子生成器

```python
def sub_gen():
    result = yield "sub-1"
    yield f"sub-2(got {result})"
    return "sub-return"

def main_gen():
    received = yield from sub_gen()
    yield f"main: sub returned {received}"

g = main_gen()
print(next(g))      # "sub-1" — 来自 sub_gen
print(g.send("X"))  # "sub-2(got X)" — send 透传到 sub_gen
print(next(g))      # "main: sub returned sub-return" — sub_gen 的 return 值赋给 received
```

在 C 层，`yield from` 的实现通过 `PyGenObject.gi_yieldfrom` 字段：当生成器执行 `yield from sub`，`gi_yieldfrom` 被设置为子生成器对象。后续的 `send()`/`throw()`/`close()` 会递归委托给 `gi_yieldfrom`，直到子生成器完成——其 `return` 值成为 `yield from` 表达式的值。

**实验 5：协程式的 ping-pong 通信**

```python
def coroutine():
    total = 0
    while True:
        x = yield total        # 产出当前 total, 接收新值 x
        if x is None:
            break              # None 作为终止信号
        total += x

g = coroutine()
next(g)           # 启动, 返回 0 (初始 total)
print(g.send(10)) # 10 — total=0+10, yield 10
print(g.send(20)) # 30 — total=10+20, yield 30
print(g.send(5))  # 35 — total=30+5, yield 35
g.close()

# 这个模式是协程的雏形:
# 发送值 → 生成器处理 → 产出结果 → 再发送值 → ...
# asyncio 的协程在语义上沿用了这个模式 (由事件循环驱动)
```

### 2.4 生成器 vs 迭代器——关系与区别

```python
from collections.abc import Iterator, Iterable

def gen_func():
    yield 1
    yield 2

g = gen_func()

# 生成器是迭代器
print(isinstance(g, Iterator))     # True
print(hasattr(g, '__iter__'))      # True
print(hasattr(g, '__next__'))      # True
print(iter(g) is g)                # True

# 生成器额外的能力 (普通迭代器不一定有)
print(hasattr(g, 'send'))          # True
print(hasattr(g, 'throw'))         # True
print(hasattr(g, 'close'))         # True
print(hasattr(g, 'gi_frame'))      # True
```

| 维度 | 自定义迭代器类 | 生成器函数 |
|:---|:---|:---|
| **实现成本** | 需要手写 `__iter__` + `__next__` + 状态变量 | 只需 `yield`，状态自动保存 |
| **状态保存** | 手动管理实例变量 | 自动保存在 `gi_frame` 的局部变量中 |
| **协议成员** | `__iter__` + `__next__` | `__iter__` + `__next__` + `send` + `throw` + `close` |
| **可重启** | 可以（重新实例化类） | 可以（重新调用函数创建新生成器） |
| **代码对象** | 独立方法的代码对象 | 整个函数体是一个代码对象 |
| **调试** | 有完整的类结构可以检查 | `gi_frame` 提供栈帧信息，更灵活 |
| **协程能力** | 无 | `send/throw/close` 支持双向通信 |

**核心结论**：每个生成器都是迭代器，但不是每个迭代器都是生成器。生成器是迭代器的**超集**——它自动获得状态保存和协程能力，代价是你无法对生成器内部状态做精细控制（与手写迭代器类相比）。

### 2.4a 何时用手写迭代器，何时用生成器？

这是一个实际工程中的选择问题。决策规则：

**用生成器**：
- 状态逻辑可以用函数体的控制流自然表达（循环、条件、递归）
- 需要协程能力（`send`/`throw`/`close`，虽然 asyncio 时代已不推荐用生成器做协程）
- 一次性使用的简单迭代器

**用手写迭代器类**：
- 需要多次重启（每次 `__iter__` 返回一个独立的 Iterator 实例）
- 需要在迭代器上暴露额外方法（如 `peek()`、`skip()`、`reset()`）
- 需要精细的生命周期控制（如迭代器持有文件句柄或数据库游标，需要 `__del__`）
- 复杂状态不适合用单个函数的局部变量表达

```python
# 案例: 需要 peek 能力的迭代器
class PeekableIterator:
    """支持 peek(预看下一个值而不消费) 的迭代器"""
    def __init__(self, iterable):
        self._it = iter(iterable)
        self._cache = None
        self._has_cache = False

    def __iter__(self):
        return self

    def __next__(self):
        if self._has_cache:
            val = self._cache
            self._has_cache = False
            self._cache = None
            return val
        return next(self._it)

    def peek(self, default=None):
        """预看下一个值, 不消费"""
        if not self._has_cache:
            try:
                self._cache = next(self._it)
                self._has_cache = True
            except StopIteration:
                return default
        return self._cache

# 使用
it = PeekableIterator([1, 2, 3])
print(it.peek())   # 1 — 预看但不消费
print(next(it))    # 1
print(next(it))    # 2
print(it.peek())   # 3
print(next(it))    # 3
```

这种 `peek()` 能力，纯生成器无法提供——因为生成器的状态隐藏在 `gi_frame` 内部，你无法"偷看"下一个 yield 的值。这是手写迭代器类的不可替代场景。
