# Python核心基础（二）：基本类型深度解析

## 引言

在C中，`int` 是4字节的原始数据，`float`是8 字节的IEEE 754浮点，`char`是1字节的整数——它们直接映射到CPU寄存器和内存地址，没有对象头，没有引用计数，没有类型指针。Java 将基本类型分成两套世界：`int`/`long`/`double` 是原始类型（栈上分配，无对象开销），`Integer`/`Long`/`Double` 是包装类（堆上分配，16 字节对象头 + 有效载荷）——程序员必须在性能与统一之间手动切换。Go 坚持值语义，`int64` 就是 8 字节，没有继承，没有装箱，`interface{}` 才需要间接寻址。Rust 更彻底：`i32`/`f64`/`bool` 都是栈上的定宽数据，`Box<i32>` 才是堆分配——所有权系统取代了引用计数，零成本抽象是核心信条。

Python 做了一个足够激进的决定：**连 `int` 都是完整的 `PyObject`**。

一个值为 `0` 的整数，在 C 中占 4 字节，在 Java 中占 4 字节（原始类型）或 16 字节（`Integer` 包装），在 Go 中占 8 字节，在 Rust 中占 4 字节——而在 Python 中，它占 **28 字节**：16 字节的 `ob_refcnt + ob_type` 头部 + 12 字节的 digit 数组（即使值为 0 也至少分配一个 digit 槽位）。更令人震惊的是，Python 的整数不是定宽的——它是**任意精度**的，`2**1000` 不会溢出，代价是 28 + 4 × ceil(1000/30) = 160 字节的内存占用。`float` 相对克制，24 字节（16 字节头部 + 8 字节 `double`），但仍是 C 中 `double` 的 3 倍。`str` 更是重量级：空字符串 49 字节，每个 ASCII 字符加 1 字节，每个中文字符加 4 字节——而 C 中同样内容只需要 `strlen + 1`。

统一的代价一目了然：**基本类型的内存开销是 C 的 3-7 倍**。但换回的是什么？一个**完全统一的类型系统**——`type(42)`、`type(3.14)`、`type("hello")`、`type(True)`、`type(None)` 走的是同一条代码路径，调用的是同一个 `ob_type` 解引用，享有的是同一套 `PyTypeObject` 槽位协议。反射、鸭子类型、运算符重载、动态分派——这些在对基本类型"特殊对待"的语言中需要绕道实现的机制，在 Python 中是对象模型的自然推论。

更深层的收益是**任意精度整数**。C 的 `int` 会溢出——`INT_MAX + 1` 是未定义行为，编译器可以任意优化掉溢出检查。Java 的 `int` 会静默回绕——`Integer.MAX_VALUE + 1` 变成 `Integer.MIN_VALUE`，不抛异常。Go 的 `int` 同样回绕。Rust 的 `i32::MAX + 1` 在 debug 模式 panic，在 release 模式回绕。只有 Python 给了一个简单承诺：**整数运算永远数学正确**。这个承诺的根因不是"Python 更好"，而是对象模型的直接推论——既然每个整数都是 `PyObject`，`ob_digit` 数组的长度就是可变的，溢出时 `realloc` 一个更长的 `digit` 数组即可，无需担心栈溢出或寄存器宽度。

本文将逐一拆解 Python 的七个基本类型——`int`、`float`、`str`、`bool`、`None`、`bytes`、`bytearray`——从 CPython 的 C 结构体出发，用可运行的代码和字节级内存图，追踪每个类型的**内存布局、运算分派、类型协议与设计决策**。你将看到 `ob_type` 的槽位如何决定 `+` 对 `int` 和 `str` 走完全不同的路径，`ob_refcnt` 如何让小整数池和字符串驻留成为安全的优化，以及 `PyTypeObject` 的继承链如何让 `bool` 既是 `int` 的子类又是 `True`/`False` 的单例——这一切都回溯到《Python核心基础（一）：对象模型》建立的 `PyObject` 统一契约。

### 基本类型在对象模型中的位置

在《对象模型》中，我们建立了"一切皆 `PyObject`"的认知框架。基本类型不是这个框架的例外，而是它最极端的体现——它们是最简单的 `PyObject`，也是最"不可接受"的开销：为了统一性，Python 甚至给 `bool`（本质上 1 bit 的信息）分配了 28 字节的完整对象。

```
PyObject (16B, 所有对象共用的头部契约)
├── ob_refcnt  (8B)  ← 引用计数, 基本类型也参与
└── ob_type    (8B)  ← 类型指针, 指向 PyTypeObject
    │
    ├── int  → PyLongObject  (16B头部 + 变长digit数组)
    ├── float → PyFloatObject (16B头部 + 8B double)
    ├── str  → PyUnicodeObject (24B PyVarObject头部 + 变长字符数据)
    ├── bool → PyBoolObject (16B头部 + 固定digit[0]=0或1)
    ├── None → PyNoneObject (仅16B头部, 无有效载荷)
    ├── bytes → PyBytesObject (24B PyVarObject头部 + ob_shash + 变长字节数据)
    └── bytearray → PyByteArrayObject (24B头部 + ob_alloc + 变长缓冲区)
```

每一个基本类型的对象，都戴着同一顶16字节的帽子，通过`ob_type`连接到自己的`PyTypeObject`，拥有`tp_hash`/`nb_add`/`sq_concat` 等操作槽位——与 `list`、`dict`、自定义 class 完全同构。基本类型不是"特殊的基本"，而是"最简单的对象"。

## 一、整数 int
### 1.1 PyLongObject——任意精度的 C 实现

Python的整数在CPython中由`PyLongObject`实现，它是`PyObject`的直接子结构（不经过`PyVarObject`，因为int不需要`ob_size`来记录元素个数——digit数组的长度信息已经编码在对象自身的`tp_basicsize`和分配大小中）：

```c
// CPython Include/longobject.h (简化)
typedef struct _longobject {
    PyObject_VAR_HEAD          // ob_refcnt(8B) + ob_type(8B) + ob_size(8B)
    digit ob_digit[1];         // 变长 digit 数组, 每个digit 30-bit, 占 4B
} PyLongObject;

// 其中 digit 的定义 (32位系统上):
typedef uint32_t digit;
#define PyLong_SHIFT 30        // 每个 digit 用 30 bit
#define PyLong_BASE (1 << PyLong_SHIFT)  // 2^30 = 1073741824
```

等等——前面引言说 int 不经过 `PyVarObject`，为什么这里用了 `PyObject_VAR_HEAD`？这是一个微妙但重要的事实：**`PyLongObject` 确实用了 `PyVarObject` 的头部（包含 `ob_size`），但 `ob_size` 在此处记录的不是"元素个数"的语义，而是 digit 数组的长度**。更精确地说，`ob_size` 的**绝对值**表示 digit 数组有多少个有效 digit，**符号**表示整数的正负——`ob_size > 0` 为正数，`ob_size < 0` 为负数，`ob_size == 0` 表示值为 0。

```
PyLongObject 内存布局 (64位系统):

值 = 0:
┌───────────────────────────────────────────────────┐
│ ob_refcnt = 1                        (8 字节)     │
│ ob_type   → <class 'int'>            (8 字节)     │
│ ob_size   = 0                        (8 字节)     │ ← 0 个 digit, 但仍分配了空间
│ ob_digit[0] = 0 (未使用)             (4 字节)     │ ← C 结构体至少有1个元素的声明
│ (对齐填充)                           (4 字节)     │
└───────────────────────────────────────────────────┘
总大小: 16 + 8 + 4 + 4(对齐) = 28 字节  ← sys.getsizeof(0) 验证

值 = 1:
┌───────────────────────────────────────────────────┐
│ ob_refcnt = 1                        (8 字节)     │
│ ob_type   → <class 'int'>            (8 字节)     │
│ ob_size   = 1                        (8 字节)     │ ← 1 个 digit
│ ob_digit[0] = 1                      (4 字节)     │
│ (对齐填充)                           (4 字节)     │
└───────────────────────────────────────────────────┘
总大小: 28 字节  ← sys.getsizeof(1) 验证

值 = 2**30 - 1 = 1073741823 (最大单digit正数):
┌───────────────────────────────────────────────────┐
│ ob_refcnt = 1                        (8 字节)     │
│ ob_type   → <class 'int'>            (8 字节)     │
│ ob_size   = 1                        (8 字节)     │
│ ob_digit[0] = 0x3FFFFFFF (1073741823) (4 字节)    │ ← 30 bit 全 1
│ (对齐填充)                           (4 字节)     │
└───────────────────────────────────────────────────┘
总大小: 28 字节 — 与值为1时一样!

值 = 2**30 = 1073741824 (需要2个digit):
┌───────────────────────────────────────────────────┐
│ ob_refcnt = 1                        (8 字节)     │
│ ob_type   → <class 'int'>            (8 字节)     │
│ ob_size   = 2                        (8 字节)     │ ← 2 个 digit
│ ob_digit[0] = 0                      (4 字节)     │ ← 低位: 2**30 mod 2**30 = 0
│ ob_digit[1] = 1                      (4 字节)     │ ← 高位: 2**30 / 2**30 = 1
└───────────────────────────────────────────────────┘
总大小: 16 + 8 + 4*2 = 32 字节  ← sys.getsizeof(2**30) 验证

值 = -1:
┌───────────────────────────────────────────────────┐
│ ob_refcnt = 1                        (8 字节)     │
│ ob_type   → <class 'int'>            (8 字节)     │
│ ob_size   = -1                       (8 字节)     │ ← 负数! ob_size < 0
│ ob_digit[0] = 1                      (4 字节)     │ ← 数值部分的存储与正1相同
│ (对齐填充)                           (4 字节)     │
└───────────────────────────────────────────────────┘
总大小: 28 字节 — PyLongObject 不用补码, 用 ob_size 符号表示正负
```

**关键设计决策：为什么选 30-bit 而非 32-bit digit？**

CPython 选择每个 digit 用 30 位（在 32 位平台上）或 30 位（在 64 位平台上同样 30 位），而非完整的 32 位。这不是浪费，而是**运算溢出缓冲**的工程设计：

- 两个 30-bit digit 相加，结果最多 31 位，仍然可以放入一个 `uint32_t`——无需进位传播的特殊处理
- 两个 30-bit digit 相乘，结果最多 60 位，放入一个 `uint64_t`——无需 128 位中间类型
- 如果使用 32-bit digit，加法可能产生 33 位溢出，乘法需要 64 位中间类型且仍需溢出检查——每次运算都需要额外的溢出判断

2 bit 的"浪费"换回了每次算术运算不需要溢出检查的性能收益——这是经典的**空间换时间**权衡。

**实验 1：用 ctypes 直接读取 PyLongObject 的 ob_digit**

```python
import ctypes
import sys

class PyLongObject(ctypes.Structure):
    _fields_ = [
        ("ob_refcnt", ctypes.c_ssize_t),
        ("ob_type", ctypes.c_void_p),
        ("ob_size", ctypes.c_ssize_t),       # ob_size 的绝对值 = digit 数量
        ("ob_digit", ctypes.c_uint32 * 1),   # 至少1个digit
    ]

def read_long_digits(n):
    addr = id(n)
    size = sys.getsizeof(n)
    digit_count = (size - 24) // 4  # 减去头部24B, 每4B一个digit
    class DynLong(ctypes.Structure):
        _fields_ = [
            ("ob_refcnt", ctypes.c_ssize_t),
            ("ob_type", ctypes.c_void_p),
            ("ob_size", ctypes.c_ssize_t),
            ("ob_digit", ctypes.c_uint32 * digit_count),
        ]
    obj = DynLong.from_address(addr)
    digits = list(obj.ob_digit)
    return obj.ob_size, digits

ob_size, digits = read_long_digits(0)
print(f"值=0:   ob_size={ob_size}, digits={digits}")

ob_size, digits = read_long_digits(42)
print(f"值=42:  ob_size={ob_size}, digits={digits}")

ob_size, digits = read_long_digits(2**30)
print(f"值=2**30: ob_size={ob_size}, digits={digits}")
# ob_size=2, digits=[0, 1]  ← 低位=0, 高位=1

ob_size, digits = read_long_digits(2**30 - 1)
print(f"值=2**30-1: ob_size={ob_size}, digits={digits}")
# ob_size=1, digits=[1073741823]  ← 0x3FFFFFFF, 单digit最大值

ob_size, digits = read_long_digits(-1)
print(f"值=-1:  ob_size={ob_size}, digits={digits}")
# ob_size=-1, digits=[1]  ← 负数的ob_size为负, digit值与正数相同

ob_size, digits = read_long_digits(2**100)
print(f"值=2**100: ob_size={ob_size}, digits={digits[:4]}...")
# ob_size=4, 100/30≈3.33, 需要4个digit
```

这个实验直接从内存中读出了 `ob_digit` 的原始值，验证了 30-bit 分段存储和 `ob_size` 的符号语义。注意 `2**30` 需要 2 个 digit，而 `2**30 - 1` 只需 1 个 digit——跨越 `2**30` 边界时内存从 28 字节跳到 32 字节。

### 1.2 任意精度——Python 选择了"永远数学正确"

C 的 `int` 是 32 位定宽，`INT_MAX + 1` 是未定义行为——编译器可以合法地假设溢出不会发生，从而优化掉安全检查。Java 的 `int` 是 32 位定宽，`Integer.MAX_VALUE + 1` 静默回绕为负数，不抛异常。Go 的 `int` 在 64 位系统上是 64 位，但仍会回绕。Rust 在 debug 模式会对溢出 panic，但 release 模式回绕。

Python 选择了完全不同的路：**整数不做定宽，运算永不溢出**。

```python
import sys

x = 2**63 - 1   # C中 long long 的最大值
print(f"2**63-1 = {x}")
print(f"sys.getsizeof(x) = {sys.getsizeof(x)}")  # 36 — 2个digit

y = x + 1       # C中会溢出, Python中只是多分配一个digit
print(f"2**63   = {y}")
print(f"sys.getsizeof(y) = {sys.getsizeof(y)}")  # 36 — 仍2个digit

z = 2**1000
print(f"2**1000 有 {len(str(z))} 位十进制")
print(f"sys.getsizeof(2**1000) = {sys.getsizeof(z)}")  # 160
```

**内存大小随值的增长公式**：

```
sys.getsizeof(n) = 24 + 4 * ceil(max(bit_length(|n|), 1) / 30)
                        │     │
                        │     └── 每个30-bit digit占4字节
                        └── 头部: ob_refcnt(8) + ob_type(8) + ob_size(8) = 24
```

**实验 2：验证整数大小随值的阶梯增长**

```python
import sys

for i in range(0, 65, 10):
    if i == 0:
        n = 0
    else:
        n = 2**i - 1  # 刚好在 i bit 范围内
    size = sys.getsizeof(n)
    digits = (i + 29) // 30 if i > 0 else 1
    print(f"2**{i:2d}-1 = bit_length={n.bit_length():3d}, "
          f"sizeof={size:3d}B, 预期digit数={digits}")

# 输出:
# 2** 0-1 = bit_length=  0, sizeof= 28B, 预期digit数=1
# 2**10-1 = bit_length= 10, sizeof= 28B, 预期digit数=1
# 2**20-1 = bit_length= 20, sizeof= 28B, 预期digit数=1
# 2**30-1 = bit_length= 30, sizeof= 28B, 预期digit数=1
# 2**40-1 = bit_length= 40, sizeof= 32B, 预期digit数=2
# 2**50-1 = bit_length= 50, sizeof= 32B, 预期digit数=2
# 2**60-1 = bit_length= 60, sizeof= 36B, 预期digit数=3
```

每次跨越 30 bit 边界，`sizeof` 增加 4 字节——完美验证了 30-bit digit 分段存储。

**跨语言对比：整数的溢出行为**

| 语言 | 类型 | 位数 | 溢出行为 | 内存开销 |
|:---|:---|:---|:---|:---|
| C | `int` | 32 | 未定义行为 | 4 字节 |
| C | `long long` | 64 | 未定义行为 | 8 字节 |
| Java | `int` | 32 | 静默回绕 | 4 字节 |
| Java | `BigInteger` | 任意 | 不溢出 | 64+ 字节（对象头 + int[]） |
| Go | `int` | 64 | 回绕 | 8 字节 |
| Go | `math/big.Int` | 任意 | 不溢出 | 32+ 字节 |
| Rust | `i32` | 32 | debug panic, release 回绕 | 4 字节 |
| Python | `int` | 任意 | 不溢出 | 28+ 字节 |

Python 没有像 Java 那样把"基本整数"和"大整数"分成两套类型——只有 `int`，它自动处理任意精度。这回溯到对象模型的设计哲学：**统一性 > 效率**。在 Java 中，`int + int` 和 `BigInteger.add()` 是不同的 API、不同的语法、不同的心智模型；在 Python 中，`1 + 1` 和 `2**1000 + 1` 是同一个 `nb_add` 槽位，同一个操作符，同一条代码路径——唯一的区别是底层 digit 数组的长度。

### 1.3 小整数池 [-5, 256]——预创建 + 缓存

如果每次使用 `0` 或 `1` 都在堆上分配 28 字节的 `PyLongObject`，内存和性能的开销将无法接受。CPython 在解释器启动时预创建了 [-5, 256] 范围内的所有整数对象，缓存在一个全局数组 `small_ints` 中，此后的访问直接返回缓存对象的指针——无需分配，无需初始化，只需 `INCREF`。

```c
// CPython Objects/longobject.c (简化)
#ifndef NSMALLPOSINTS
#define NSMALLPOSINTS 257    // 0 到 256
#endif
#ifndef NSMALLNEGINTS
#define NSMALLNEGINTS 5      // -1 到 -5
#endif

static PyLongObject *small_ints[NSMALLNEGINTS + NSMALLPOSINTS];
// 总共 262 个预创建的 int 对象

// 获取整数 n 的流程:
PyObject *PyLong_FromLong(long n) {
    if (-NSMALLNEGINTS <= n && n < NSMALLPOSINTS) {
        // 命中小整数池: 直接返回缓存对象 + INCREF
        PyObject *op = (PyObject *)(small_ints[n + NSMALLNEGINTS]);
        Py_INCREF(op);
        return op;
    }
    // 不在池中: 分配新 PyLongObject
    return _PyLong_New(n);
}
```

**为什么是 [-5, 256]？**

- **负数端 -5**：Python 内部少量使用负数常量（如 `-1` 表示错误、`-2` 表示未找到），-5 到 -1 覆盖了 CPython 运行时最常见的哨兵值
- **正数端 256**：0-255 覆盖了单字节值的所有可能（字符编码、字节操作），256 是"长度为 0 到 255"的常见上界。这一范围在 Python 2 时代就已确定，沿用至今

**实验 3：小整数池的对象身份验证**

```python
import sys

# 小整数池内: 同一对象
a = 42; b = 42
print(f"42 is 42: {a is b}")          # True — 缓存命中

a = -5; b = -5
print(f"-5 is -5: {a is b}")          # True — 池的下界

a = 256; b = 256
print(f"256 is 256: {a is b}")        # True — 池的上界

# 小整数池外: 新对象
a = 257; b = 257
print(f"257 is 257 (交互模式): {a is b}")  # 可能为 False (交互模式)
# 注意: 同一代码块中编译器可能做常量折叠, 使 a is b 为 True

a = -6; b = -6
print(f"-6 is -6 (交互模式): {a is b}")    # 可能为 False

# 用 ctypes 验证小整数是同一内存地址
import ctypes
addr_0_first = id(0)
addr_0_second = id(0)
print(f"id(0) 稳定性: {addr_0_first == addr_0_second}")   # True

addr_257_first = id(257)
_ = 257                                    # 再次访问257, 可能获得不同对象
addr_257_second = id(257)
print(f"id(257) 稳定性: {addr_257_first == addr_257_second}")
# 交互模式下可能 False — 不在池中, 每次临时创建
```

**常量折叠对小整数池的干扰**

上面的实验需要区分**两个不同层面的优化**：小整数池是**运行时**的缓存（所有代码块共享），而常量折叠是**编译期**的优化（同一代码块内字面量合并）。两者叠加会让 `is` 的行为更加微妙：

```python
# 交互模式: 每行是一个独立代码块
a = 257    # 代码块1: 创建 257 对象
b = 257    # 代码块2: 可能创建新的 257 对象
print(a is b)   # False (交互模式)

# 函数模式: 整个函数体是一个代码块
def test():
    a = 257
    b = 257
    print(a is b)   # True — 编译器常量折叠, co_consts中只有1个257

test()

# 验证常量折叠
import dis
dis.dis(test)
# 可以看到 a 和 b 都 LOAD_CONST 同一个 257 常量索引
```

### 1.4 整数运算——nb_add 槽位与任意精度加法

当 Python 执行 `a + b`（`a` 和 `b` 都是 `int`），发生的不是一条 CPU 指令，而是一整条分派链：

```
Python: a + b
  ↓
字节码: BINARY_ADD
  ↓
C 层: PyNumber_Add(a, b)
  ↓
查 a->ob_type->tp_as_number->nb_add
  ↓
命中: long_add(a, b)    ← int 类型对象注册的加法实现
  ↓
实现:
  1. 读取 a->ob_digit[] 和 b->ob_digit[]
  2. 从低位到高位逐 digit 相加, 处理进位
  3. 计算结果需要的 digit 数量
  4. 分配新的 PyLongObject, 填入结果 digit
  5. 返回新对象 (int 运算永远返回新对象!)
```

**关键点：`a + b` 不修改 `a` 或 `b`，而是创建新对象**。这不是 Python 层的选择，而是 `int` 不可变性的直接推论——《对象模型》中已分析，内联存储的对象无法原地修改。`ob_digit` 数组内联在 `PyLongObject` 中，长度固定，要"增加"只能创建更大的新对象。

**实验 4：验证整数运算返回新对象**

```python
import sys

a = 42
print(f"a 的 id: {id(a)}, sizeof: {sys.getsizeof(a)}")

b = a + 1
# a=42 在小整数池, b=43 也在小整数池
print(f"b 的 id: {id(b)}, a is b: {a is b}")  # False — 不同对象(即使都在池中)

c = 10**9
d = c + 1
print(f"c 的 id: {id(c)}")
print(f"d 的 id: {id(d)}")
print(f"c is d: {c is d}")    # False — 一定不同, 因值就不同

# 更有趣的: 小整数池内的运算
x = 1
y = x + 1    # y = 2, 小整数池
z = 2
print(f"y is z: {y is z}")    # True — 都命中了小整数池中的同一个 2
```

**大数加法的 digit 级实现**

```python
def simulate_long_add(a_digits, b_digits):
    """模拟 CPython 的 long_add: digit-by-digit 加法"""
    carry = 0
    BASE = 2**30
    result = []
    max_len = max(len(a_digits), len(b_digits))
    for i in range(max_len):
        ai = a_digits[i] if i < len(a_digits) else 0
        bi = b_digits[i] if i < len(b_digits) else 0
        total = ai + bi + carry
        result.append(total % BASE)    # 当前 digit
        carry = total // BASE          # 进位
    if carry:
        result.append(carry)
    return result

# 示例: 2**30 + 2**30 = 2**31
# 2**30 的 digit 表示: [0, 1]
# 相加: [0+0, 1+1] = [0, 2]
result = simulate_long_add([0, 1], [0, 1])
print(f"2**30 + 2**30 的 digit: {result}")  # [0, 2]
# 验证: 0 + 2*2**30 = 2**31, 正确!

# 示例: (2**30-1) + 1 = 2**30
# 2**30-1 的 digit 表示: [0x3FFFFFFF] = [1073741823]
# 1 的 digit 表示: [1]
# 相加: [1073741823 + 1] = [1073741824], 但 1073741824 = 2**30 = BASE
# 所以: 进位, 结果应为 [0, 1]
result = simulate_long_add([0x3FFFFFFF], [1])
print(f"(2**30-1) + 1 的 digit: {result}")  # [0, 1]
```

### 1.5 位运算——任意精度的移位与掩码

位运算是整数操作中最直接接触底层的部分。在 C 中，`i << n` 是一条 CPU 移位指令；在 Python 中，`n << k` 需要在 digit 数组上实现跨 digit 的移位。

```
左移 n << k 的实现:
  1. digit_shift = k // 30     ← 完整 digit 的移位
  2. bit_shift  = k % 30       ← digit 内的比特移位
  3. 结果 digit 数组 = digit_shift 个 0 + 原 digit 逐个左移 bit_shift + 进位拼接

示例: 1 << 30
  1 的 digit: [1]
  digit_shift = 30 // 30 = 1, bit_shift = 0
  结果: [0, 1]  ← digit[0]=0, digit[1]=1, 即 2**30

示例: 1 << 31
  digit_shift = 31 // 30 = 1, bit_shift = 1
  原 digit[0] = 1 = 0b1
  左移1位: 0b10 = 2
  结果: [0, 2]  ← 2 * 2**30 = 2**31
```

**实验 5：位运算的字节级验证**

```python
import sys

for shift in [0, 10, 29, 30, 31, 60, 61]:
    n = 1 << shift
    size = sys.getsizeof(n)
    digits = (shift + 30) // 30
    expected_size = 24 + 4 * max(digits, 1)
    print(f"1 << {shift:3d} = 2**{shift:3d}, sizeof={size:3d}B, "
          f"预期digit数={digits}, 预期size={expected_size}B")

# 输出:
# 1 <<   0 = 2**  0, sizeof= 28B, 预期digit数=1, 预期size=28B
# 1 <<  10 = 2** 10, sizeof= 28B, 预期digit数=1, 预期size=28B
# 1 <<  29 = 2** 29, sizeof= 28B, 预期digit数=1, 预期size=28B
# 1 <<  30 = 2** 30, sizeof= 32B, 预期digit数=2, 预期size=32B  ← 跳变!
# 1 <<  31 = 2** 31, sizeof= 32B, 预期digit数=2, 预期size=32B
# 1 <<  60 = 2** 60, sizeof= 36B, 预期digit数=3, 预期size=36B
# 1 <<  61 = 2** 61, sizeof= 36B, 预期digit数=3, 预期size=36B

# Python 整数没有上限 — 位运算也不溢出

```

`.bit_length()` 方法返回整数的二进制表示所需的最少位数（不含符号位），是 `ob_digit` 数组的有效信息量的直接反映——`bit_length(n) = (|ob_size| - 1) * 30 + 最高digit的有效bit数`。

### 1.6 bool 是 int 的子类——True = 1, False = 0

`bool` 是 Python 中最奇特的类型之一：它既是 `int` 的子类（继承了一切数值操作），又是只有两个实例的单例类型（`True` 和 `False`）。

```c
// CPython Include/boolobject.h
typedef struct {
    PyLongObject long_obj;   // 继承 PyLongObject!
} PyBoolObject;
// 注意: PyBoolObject 没有添加任何新字段!
// 它就是 PyLongObject, 只是 ob_type 指向 bool 而非 int
```

```
PyBoolObject (True) 的内存布局:
┌──────────────────────────────────────────────────┐
│ ob_refcnt = 很多(全局共享)            (8 字节)    │
│ ob_type   → <class 'bool'>           (8 字节)    │ ← 注意: 指向 bool, 不是 int!
│ ob_size   = 1                        (8 字节)    │
│ ob_digit[0] = 1                      (4 字节)    │ ← 数值=1
│ (对齐填充)                           (4 字节)    │
└──────────────────────────────────────────────────┘

PyBoolObject (False) 的内存布局:
┌──────────────────────────────────────────────────┐
│ ob_refcnt = 很多(全局共享)            (8 字节)    │
│ ob_type   → <class 'bool'>           (8 字节)    │
│ ob_size   = 0                        (8 字节)    │ ← 不同于 int 0 的 ob_size=0
│ ob_digit[0] = 0 (未使用)             (4 字节)    │ ← 数值=0
│ (对齐填充)                           (4 字节)    │
└──────────────────────────────────────────────────┘
```

**实验 6：bool 继承 int 的验证**

```python
# bool 是 int 的子类
print(issubclass(bool, int))      # True
print(True.__class__.__mro__)     # (bool, int, object)

# True 的数值行为
print(True + 1)                   # 2     — nb_add 继承自 int
print(True * 5)                   # 5     — nb_multiply 继承自 int
print(False + 1)                  # 1
print(int(True))                  # 1     — True 就是 1
print(int(False))                 # 0     — False 就是 0

# 但 True 不完全等同于 1
print(True == 1)                  # True  — 值相等
print(True is 1)                  # False — 不同对象! ob_type 不同
print(type(True))                 # <class 'bool'>
print(type(1))                    # <class 'int'>

# isinstance 的微妙之处
print(isinstance(True, int))      # True  — bool 是 int 的子类
print(isinstance(True, bool))     # True  — 也是 bool
print(isinstance(1, bool))        # False — int 不是 bool 的子类

# id 不同
print(id(True), id(1))            # 不同 — True 是独立对象
print(id(False), id(0))           # 不同

# 1 + True 的分派: int.__add__ 发现右操作数是 bool(int子类), 处理兼容
print(1 + True)                   # 2
```

**为什么 Python 不让 `True` 和 `1` 是同一个对象？**

这涉及类型安全的核心原则：`type(True)` 应该返回 `<class 'bool'>` 而非 `<class 'int'>`。如果 `True is 1`，那么 `type(True)` 必须返回 `int`，bool 类型就在对象层面消失了——`isinstance(True, bool)` 将返回 `False`，这违反了直觉和类型系统的一致性。所以 Python 创建了两个独立的单例 `True` 和 `False`，它们的 `ob_type` 指向 `bool`（`int` 的子类），`ob_digit` 值分别为 1 和 0。

**实验 7：True 和 1 的分派路径差异**

```python
# 虽然值相同, 但类型不同
print(f"True == 1: {True == 1}")              # True — 值比较, int.__eq__ 处理
print(f"True is 1: {True is 1}")              # False — id 不同

# 类型检查时区分
def process(value):
    if type(value) is bool:
        return "布尔标志"
    elif type(value) is int:
        return "整数计数"
    return "其他"

print(process(True))               # "布尔标志"
print(process(1))                  # "整数计数"
print(process(2))                  # "整数计数"

# 序列化时区分 (JSON: True → true, 1 → 1)
import json
print(json.dumps(True))            # "true"
print(json.dumps(1))               # "1"
```

**设计闭环**：

```
bool 继承 int (因)
  → True == 1, False == 0 (效果)
    → bool 能参与整数运算: True + 1 == 2 (直接效果)
      → 但 type(True) ≠ type(1) (约束: 类型安全要求 bool 独立)
        → True is not 1 (推论: 身份不同)
          → isinstance(True, int) True, isinstance(1, bool) False (不对称)
            → JSON 序列化区分 True/1, type() 检查区分 (下游影响)
```

bool 继承 int 是 Python 2 时代 `True`/`False` 只是整数别名（`True = 1; False = 0`）的进化残留——在 Python 3 中，`bool` 成了正式的类，但保持了与 `int` 的兼容性。这个设计让 `sum([True, False, True])` 自然返回 `2`，但也在类型系统引入了不对称——这是**向后兼容**与**类型精确性**之间的权衡。

## 二、浮点数 float

### 2.1 PyFloatObject——16 字节头部 + 8 字节 double

浮点数是基本类型中最"规矩"的——它没有变长数组，没有任意精度，只是一个固定 24 字节的对象，头部 16 字节 + 一个 C `double`（8 字节）。

```c
// CPython Include/floatobject.h
typedef struct {
    PyObject_HEAD           // ob_refcnt(8B) + ob_type(8B)
    double ob_fval;         // 8 字节 IEEE 754 双精度浮点
} PyFloatObject;
```

```
PyFloatObject 内存布局 (64位系统):

值 = 0.0:
┌───────────────────────────────────────────────────┐
│ ob_refcnt = 1                        (8 字节)     │
│ ob_type   → <class 'float'>          (8 字节)     │
│ ob_fval   = 0.0                      (8 字节)     │
└───────────────────────────────────────────────────┘
总大小: 24 字节  ← sys.getsizeof(0.0) 验证

值 = 3.14:
┌───────────────────────────────────────────────────┐
│ ob_refcnt = 1                        (8 字节)     │
│ ob_type   → <class 'float'>          (8 字节)     │
│ ob_fval   = 3.14 (IEEE 754 编码)     (8 字节)     │
└───────────────────────────────────────────────────┘
总大小: 24 字节 — 无论值多大, float 永远 24 字节!
```

**跨语言对比：浮点数的内存开销**

| 语言 | 类型 | 有效载荷 | 对象头 | 总计 |
|:---|:---|:---|:---|:---|
| C | `double` | 8 字节 | 0 | 8 字节 |
| Java | `double` (原始) | 8 字节 | 0 | 8 字节 |
| Java | `Double` (包装) | 8 字节 | 16 字节 | 24 字节 |
| Go | `float64` | 8 字节 | 0 | 8 字节 |
| Rust | `f64` | 8 字节 | 0 | 8 字节 |
| Python | `float` | 8 字节 | 16 字节 | 24 字节 |

Python 的 `float` 与 Java 的 `Double` 包装类大小完全一致——都是 16 字节对象头 + 8 字节 `double`。区别在于：Java 中 `double` 是默认选择（`Double` 是被迫使用的），Python 中只有 `float`（即 `double`），不存在"基本/包装"的分裂。

**实验 8：浮点数的固定大小**

```python
import sys

for v in values:
    print(f"float({v!r}): sizeof={sys.getsizeof(v)}B")
# 全部 24 字节! 无论值多大, float 永远24B
```

**float 的自由列表**

与 int 不同，CPython 为 float 实现了一个**自由列表（free list）**而非小整数池。当 float 对象被回收（`ob_refcnt == 0`），它不会立即归还内存，而是放入一个长度为 100 的链表缓存中。下次创建 float 时优先从链表取用，避免 `malloc`/`free` 的系统调用开销。

```python
import sys

# 连续创建和丢弃 float, 验证自由列表
def test_float_freelist():
    ids = []
    for _ in range(5):
        f = 1.0
        ids.append(id(f))
        del f
    # 自由列表使得连续创建的 float 可能复用同一内存
    print(f"IDs: {ids}")
    print(f"是否有重复: {len(ids) != len(set(ids))}")

test_float_freelist()
```

注意：自由列表不是小整数池——小整数池中的对象**永远存活**（`ob_refcnt` 永远 > 0），自由列表中的对象**可以被回收**，只是内存块被缓存复用。这意味着 `id(x)` 对小整数有确定性（始终相同），对 float 没有。

### 2.2 IEEE 754 双精度——8 字节中的宇宙

Python 的 `float` 底层就是 C 的 `double`，即 IEEE 754 双精度浮点数。这 8 字节（64 bit）被分成三段：

```
IEEE 754 double (64 bit):
┌──────┬──────────────┬──────────────────────────────────────────────────┐
│ 符号S│ 指数E (11bit) │ 尾数M (52bit)                                    │
│ 1bit │              │                                                  │
└──────┴──────────────┴──────────────────────────────────────────────────┘

值 = (-1)^S × 2^(E-1023) × 1.MMMMM...M   (规格化数, E≠0且E≠2047)
值 = (-1)^S × 2^(-1022) × 0.MMMMM...M   (非规格化数, E=0, M≠0)
值 = 0                                    (E=0, M=0)
值 = ±∞                                   (E=2047, M=0)
值 = NaN                                  (E=2047, M≠0)

关键参数:
  指数偏移 = 1023
  指数范围: -1022 到 1023 (规格化)
  尾数精度: 53 bit (含隐含的1, 52 bit显式存储)
  十进制精度: ≈15-17 位有效数字
  最小正值: ≈2.225e-308
  最大正值: ≈1.798e+308
```

**实验 9：用 struct 查看 float 的二进制表示**

```python
import struct
import sys

def float_to_hex(f):
    """将 float 的 IEEE 754 二进制表示转为十六进制"""
    packed = struct.pack('<d', f)   # little-endian double
    return packed.hex()

def float_bits(f):
    """显示 float 的符号、指数、尾数"""
    packed = struct.pack('<d', f)
    bits = int.from_bytes(packed, 'little')
    sign = (bits >> 63) & 1
    exponent = (bits >> 52) & 0x7FF
    mantissa = bits & ((1 << 52) - 1)
    return sign, exponent, mantissa

# 常见值的 IEEE 754 编码
test_values = [0.0, -0.0, 1.0, 2.0, 0.5, 3.0, 0.1, 0.3, float('inf'), float('-inf'), float('nan')]

for v in test_values:
    s, e, m = float_bits(v)
    hex_repr = float_to_hex(v)
    if e == 0 and m == 0:
        kind = "零"
    elif e == 0x7FF and m == 0:
        kind = "无穷"
    elif e == 0x7FF:
        kind = "NaN"
    elif e == 0:
        kind = "非规格化"
    else:
        kind = f"值=(-1)^{s} × 2^{e-1023} × 1.{m:052b}"
    print(f"{v!r:>15s}: hex={hex_repr}, S={s}, E={e:011b}({e}), M={m:052b}, {kind}")

# 输出:
#            0.0: hex=0000000000000000..., S=0, E=00000000000(0), M=000...0, 零
#           -0.0: hex=0000000000000080..., S=1, E=00000000000(0), M=000...0, 零
#            1.0: hex=000000000000f03f..., S=0, E=01111111111(1023), M=000...0, 值=1.0
#            2.0: hex=0000000000000040..., S=0, E=10000000000(1024), M=000...0, 值=2.0
#            0.5: hex=000000000000e03f..., S=0, E=11111111110(1022), M=000...0, 值=0.5
#            0.1: hex=...
```

### 2.3 为什么 0.1 + 0.2 ≠ 0.3

这是浮点数最经典的困惑，而答案完全在 IEEE 754 的编码中——**0.1 在二进制中是无限循环小数**。

```
十进制 0.1 = 1/10 = 二进制 0.0001100110011001100110011... (无限循环)
                          └─── 0011 无限重复 ───┘

用 IEEE 754 double 存储 (53 位精度):
  0.1 ≈ 0.0001100110011001100110011001100110011001100110011010  (截断+舍入)
      = 1.1001100110011001100110011001100110011001100110100 × 2^(-4)

实际存储的值:
  sign=0, exponent=1019(=1023-4), mantissa=1001100110011001100110011001100110011001100110011010
  = 0.1000000000000000055511151231257827021181583404541015625

同理:
  0.2 = 0.1 × 2, 也是无限循环, 实际存储:
       = 0.200000000000000011102230246251565404236316680908203125

0.1 + 0.2 的 double 运算结果:
       = 0.3000000000000000444089209850062616169452667236328125

而 0.3 的实际存储:
       = 0.299999999999999988897769753748434595763683319091796875

两个值不相等! (差约 5.55e-17)
```

**实验 10：0.1 + 0.2 ≠ 0.3 的精确验证**

```python
import struct
import decimal

# 直接查看
print(f"0.1 + 0.2 = {0.1 + 0.2}")
print(f"0.3       = {0.3}")
print(f"0.1 + 0.2 == 0.3: {0.1 + 0.2 == 0.3}")  # False

# 高精度查看实际值
print(f"\n0.1 的精确值: {decimal.Decimal(0.1)}")
# Decimal('0.1000000000000000055511151231257827021181583404541015625')

print(f"0.2 的精确值: {decimal.Decimal(0.2)}")
# Decimal('0.200000000000000011102230246251565404236316680908203125')

print(f"0.3 的精确值: {decimal.Decimal(0.3)}")
# Decimal('0.299999999999999988897769753748434595763683319091796875')

print(f"0.1+0.2 的精确值: {decimal.Decimal(0.1 + 0.2)}")
# Decimal('0.3000000000000000444089209850062616169452667236328125')

# 为什么 0.1 的表示不精确?
# 分数 1/10 的二进制展开: 1/10 = 1/16 + 1/32 + 1/256 + 1/512 + ...
# = 0.0001 1001 1001 1001... (0011 循环)
# IEEE 754 截断到 52 位尾数, 舍入误差就此产生
```

**这不是 Python 的 bug，而是 IEEE 754 的数学必然**——任何使用 IEEE 754 的语言（C/Java/Go/Rust/JS）都会遇到同样的问题。Python 与它们的区别只在于：`print` 默认会舍入到 17 位有效数字，所以你在 Python 中看到了 `0.30000000000000004`，而在 C 的 `printf("%.17g", 0.1 + 0.2)` 中也会看到同样的结果。
