# opencode v1.15.10 实体粗筛 —— 工具生态

> 主导维度：**边界**（工具的本质是跨越系统边界的 I/O 代理：文件系统、Shell 进程、网络请求、子 Agent 会话——每条工具都是一条控制权转移通道）
> SOP 顺序：边界 → 时序 → 结构 → 实体
> 合并规则：同一类型、≤2 维只有 1-2 行、共享强配对/继承、独立成卡不增加关系边

╔═══════════════════════════════════════════════════════════╗
║  【工具】Tool定义与调用 — Def + Info + Context + ExecuteResult + InvalidArgumentsError ║
║  编号: E_TOOL_01 | 来源: tool.ts:22-75                     ║
╚═══════════════════════════════════════════════════════════╝

【定义】 工具系统的类型框架：Tool.Def 是完全解析的可执行工具规格，Tool.Info 是延迟初始化的工具声明，Tool.Context 是每次调用的执行沙箱，ExecuteResult 是执行产出，InvalidArgumentsError 是参数校验失败的类型化错误。五者共同构成工具从定义 → 初始化 → 调用 → 产出的完整生命周期类型。

【边界】★★★ Tool.Def.execute 是工具与外部世界的唯一接触点，所有边界跨越均在此发生——文件系统读写、Shell 进程 spawn、HTTP 请求、子 Agent 启动；Tool.Context.abort(AbortSignal) 从外部取消执行；Tool.Context.ask() 跨越权限审批边界；ExecuteResult.attachments 携带文件引用跨越内存/磁盘边界。

【时序】Tool.Info.init() → 调用 init 工厂函数 → 返回 Effect<DefWithoutID> → 注入 id → 产出 Tool.Def → ToolRegistry 注册。
工具调用：Tool.Context 构造(携带 sessionID, messageID, agent, abort, callID, extra) → Tool.Def.execute(context, args) → 参数校验(Schema.Decoder) → 失败则抛出 InvalidArgumentsError { tool, detail } → 被上游 Try/Catch 匹配 → 反馈给 LLM 修正参数；成功 → 执行业务逻辑 → 返回 ExecuteResult { title, metadata, output, attachments }。
Truncate 包装：output 超出限制 → tool.ts wrap 逻辑调用 Truncate.Service.output() → 写入磁盘 → 返回截断预览 + 磁盘路径。

【结构】五类型管线：Tool.Info(声明层) → Tool.Def(执行层) → Tool.Context(上下文层) → ExecuteResult(产出一层) + InvalidArgumentsError(错误层)。
Tool.Def 持有 execute 闭包 → 内部捕获外部作用域变量(如 Truncate.Service、Ripgrep.Service)。
ExecutionContext: sessionID + messageID → Session 关联；agent → Agent.Info 权限绑定；abort → AbortController.signal 取消链；metadata() → 动态元数据注入；ask() → Permission.Service 桥接。

【实体】Tool.Def { id(string), description(string), parameters(Schema.Decoder — Effect Schema), jsonSchema(JSON Schema), execute(fn: (ctx:Context, args:Params)→Effect<ExecuteResult>), formatValidationError(fn) }
Tool.Info { id(string), init(() → Effect<DefWithoutID>) } — 延迟工厂，DefWithoutID = Omit<Tool.Def, "id">
Tool.Context { sessionID(SessionID), messageID(MessageID), agent(Agent.Info), abort(AbortSignal), callID(string), extra(Record), messages(MessageV2[]), metadata(()→Record), ask()→Permission.Request }
ExecuteResult { title(string), metadata(Record), output(string), attachments?(FilePart[]) }
InvalidArgumentsError { tool(string), detail(string) } — extends Error

【内部关联】
- Tool.Info.init() --[产出]--> Tool.Def
- Tool.Def.execute() --[消费]--> Tool.Context
- Tool.Def.execute() --[产出]--> ExecuteResult
- Tool.Def.execute() --[抛出]--> InvalidArgumentsError
- Tool.Context.ask() --[委托]--> Permission.Service.ask()
- ExecuteResult.attachments --[引用]--> MessageV2.FilePart(同步创建)
- tool.ts wrap 逻辑 --[调用]--> Truncate.Service

【示例】
```typescript
// tool.ts:53-63 — 工具定义
const grepTool: Tool.Def = {
  id: "grep",
  description: "基于 ripgrep 的正则内容搜索",
  parameters: Schema.Struct({ pattern: Schema.String(), path: Schema.optional(Schema.String()) }),
  execute: async (ctx, args) => {
    const results = await RipgrepService.search(args.pattern, args.path)
    return { title: `Found ${results.length} matches`, output: results.join("\n"), metadata: {} }
  }
}
```

║  【工具】ToolRegistry — 中央工具注册表                      ║
║  编号: E_TOOL_02 | 来源: registry.ts:82-110               ║
╚═══════════════════════════════════════════════════════════╝

【定义】 中央工具注册表，聚合内置工具、MCP 外部工具、Plugin 自定义工具、Skill 加载工具，解析模型适配工具列表，是 LLM.Service 与工具生态的唯一桥接点。

【边界】★★★ 外部工具发现跨越文件系统边界（Glob.scan 扫描工具文件）；MCP 工具发现跨越进程/网络边界（StdioClientTransport / HTTP SSE → MCP 服务器 → tools/list）；Plugin 工具注入跨越第三方扩展边界；tools(model) 过滤跨越模型能力边界（部分工具不支持某些模型）。

【时序】初始化：注册内置工具(函数 → Tool.Info) → 扫描 Plugin 工具(Plugin.Hooks.tool.definition) → 扫描 MCP 工具(MCP.Service.tools) → 扫描文件系统工具 → 全量 Tool.Def 就绪。
调用时：ids() → 返回所有工具 ID 数组；all() → 返回所有 Tool.Def 实例；named(name) → 按 ID 查找 Tool.Def；tools(model) → 按模型能力过滤 → 返回 Tool.Def[] → 传入 LLM.Service.stream()。
模型适配：部分模型不支持 parallel tool calls / 特定参数 → tools(model) 内部排除不兼容工具。

【结构】聚合器模式：ToolRegistry 持有 Map<id, Tool.Def> + 多源发现管道。依赖链：Config.Service(文件系统工具路径) → Plugin.Service(Hooks.tool.definition) → MCP.Service(tools/list) → Skill.Service(loadSkill 工具)。
每源工具注入后统一校验：id 去重 → Schema 兼容性检查 → 注册到中央 Map。

【实体】ToolRegistry { ids()→string[], all()→Tool.Def[], named(name:string)→Tool.Def|undefined, tools(model:ModelID)→Tool.Def[] }

【内部关联】
- ToolRegistry --[聚合]--> Tool.Def[](内置 + 文件系统 + MCP + Plugin + Skill)
- ToolRegistry --[依赖]--> Config.Service(文件系统工具路径)
- ToolRegistry --[依赖]--> Plugin.Service(Hooks.tool.definition)
- ToolRegistry --[依赖]--> MCP.Service(MCP tools/list)
- ToolRegistry --[依赖]--> Skill.Service(loadSkill 工具)
- ToolRegistry.tools() --[被调用]--> LLM.Service.stream()(注入工具列表)
- ToolRegistry.named() --[被调用]--> Tool.Def 执行入口

【示例】
```typescript
// registry.ts:82-110 — 工具注册表使用
const tools = registry.tools("claude-sonnet-4-20250514")
// → [read, edit, write, shell, task, grep, glob, webfetch, question, todowrite, skill, ...MCP工具, ...Plugin工具]
const grepDef = registry.named("grep")
// → Tool.Def{ id:"grep", execute:fn, ... }
```

║  【工具】文件操作工具族 — read + edit + write                ║
║  编号: E_TOOL_03 | 来源: read.ts, edit.ts, write.ts        ║
╚═══════════════════════════════════════════════════════════╝

【定义】 文件系统操作工具三件套：read 读取文件/目录并支持文本/图片/PDF/二进制检测，edit 执行精确字符串替换并预览 diff，write 创建或覆盖文件。edit 与 write 同构（均操作文件内容），三者共享文件路径解析和 LSP 集成。

【边界】★★★ read 的三种核心边界：(1) Node.js fs/promises 读取文本 + Buffer 检测二进制 → 操作系统文件系统；(2) LSP.touchFile() → 通知 LSP 服务器文件已被读取（跨进程边界）；(3) assertExternalDirectoryEffect → 检查文件是否在工作区外（安全边界）；(4) 图片/PDF 检测 → 返回 FilePart(mime+base64) 非纯文本（媒体边界）。edit 的关键边界：(1) 文件锁(原子写) → 互斥边界；(2) BOM 感知读写 → 编码边界；(3) diff 预览生成 → 用户确认边界；(4) post-edit LSP/Formatter/Bus 通知 → 集成边界。write 边界：与 edit 共享文件锁 + 路径校验，额外：content 必须非空，filePath 必须绝对路径。

【时序】read 执行流：接收 filePath/offset/limit → 路径解析（相对→绝对） → 文件类型检测(Buffer 采样判断文本/二进制/图片/PDF) → 文本类：fs.readFile → slice(offset, offset+limit) → 返回文本 output + 行号映射；图片/PDF 类：fs.readFile → base64 编码 → 返回 FilePart[] attachments + 文本占位 output；目录类：fs.readdir → 返回文件列表文本。
edit 执行流：接收 filePath/oldString/newString/replaceAll → 文件锁获取(写互斥) → 读取文件内容 → BOM 检测处理 → 字符串替换(oldString→newString, replaceAll 为全量替换) → 生成 diff → 原子写入(临时文件 + rename) → LSP 文件变更通知 → Formatter 触发 → Bus 发布 FileChanged 事件 → 返回 diff output。
write 执行流：接收 content/filePath → 路径绝对化校验 → 目录存在性检查 → 文件锁 → 原子写入 → LSP/Bus 通知 → 返回成功 output。

【结构】三工具共享文件路径解析模块(相对→绝对 + 工作区根目录)、文件锁机制(原子写入)、LSP 集成(touchFile/文档变更通知)。read 独有：文件类型检测器(文本/二进制/图片/PDF 判别)、偏移量化器(行号→字节偏移映射)。edit 独有：BOM 感知层、diff 生成器、replaceAll 批量模式。write 独有：content 非空校验、仅写入模式。三工具均产出 ExecuteResult { title, output, attachments } 到 LLM 流。

【实体】read 参数 { filePath(string), offset?(number), limit?(number) } — offset/limit 从 1 计数
edit 参数 { filePath(string), oldString(string), newString(string), replaceAll?(boolean) } — oldString 必须精确匹配
write 参数 { content(string), filePath(string) } — filePath 必须为绝对路径

【内部关联】
- read/edit/write --[共享]--> 文件路径解析模块
- read/edit/write --[共享]--> 文件锁机制
- read --[通知]--> LSP.touchFile()
- edit/write --[通知]--> LSP 文档变更
- edit/write --[通知]--> Formatter
- edit/write --[发布]--> Bus.FileChanged
- edit/write --[使用]--> BOM 检测模块
- read --[调用]--> assertExternalDirectoryEffect(安全校验)
- edit.diff --[展示]--> 用户确认 UI

【示例】
```typescript
// read.ts — 读取文件
const result = await readTool.execute(ctx, { filePath: "src/app.ts", offset: 1, limit: 100 })

// edit.ts — 精确替换
const result = await editTool.execute(ctx, {
  filePath: "src/app.ts",
  oldString: "const port = 3000",
  newString: "const port = parseInt(process.env.PORT || '3000')",
  replaceAll: false
})
// → output 包含 diff 预览

// write.ts — 创建文件
const result = await writeTool.execute(ctx, {
  filePath: "C:/project/newfile.ts",  // 必须绝对路径
  content: "export const hello = 'world'"
})
```

║  【工具】Shell工具 — 命令执行 + 权限作用域                   ║
║  编号: E_TOOL_04 | 来源: shell.ts                          ║
╚═══════════════════════════════════════════════════════════╝

【定义】 操作系统 Shell 命令执行工具，通过 tree-sitter 解析命令结构实现细粒度权限作用域（如仅允许 npm run * 而禁止 rm -rf），由 ChildProcessSpawner 管理子进程生命周期，支持工作目录、超时和流式输出。

【边界】★★★ ChildProcessSpawner.spawn() 跨越操作系统进程边界（创建子进程 → PID 管理）；ShellID 追踪每次命令调用的唯一标识（进程关联边界）；命令输出流跨越 stdout/stderr 管道边界（异步流式读取）；tree-sitter 命令解析跨越 AST 语法边界（Bash/PowerShell 语法树）；权限匹配 ShellID 跨越安全审批边界；timeout 参数跨越子进程生命周期边界（SIGTERM → SIGKILL 升级）。

【时序】shell 执行流：接收 command/cwd/timeout → tree-sitter 解析命令为 AST → 提取命令语义（如 npm run test → 命令名: npm, 子命令: run, 参数: test） → Permission.evaluate("shell", 命令语义, ...) → allow: 继续 / deny: 拒绝 / ask: 用户审批 → 构造 spawn 参数(ShellID, cwd, env) → ChildProcessSpawner.spawn(command, {cwd, env, timeout}) → 异步读取 stdout/stderr 流 → 逐 chunk 返回 → 进程结束 → 收集 exit code → 合并 stdout+stderr → ExecuteResult { output: 合并输出, metadata: {exitCode, shellID} }。
Truncate 包装：输出过大 → Truncate.Service.output() → 磁盘写入 → 截断预览 → 返回预览 + 完整路径。

【结构】Shell 工具链：Command String → tree-sitter Parser(Bash/PowerShell 语法) → AST → Permission.Scope(命令+子命令+参数) → Permission.evaluate → ChildProcessSpawner(OS 子进程管理) → StreamReader(stdout/stderr) → ExecuteResult。
ShellID 作为品牌字符串绑定每次执行，用于权限持久化（PermissionTable 关联 ShellID）。
ChildProcessSpawner 封装 Node.js child_process.spawn，管理进程生命周期（启动/超时杀/异常清理）。

【实体】shell 参数 { command(string), cwd?(string), timeout?(number) }
ShellID = string & { readonly _brand: "ShellID" }
ChildProcessSpawner 接口 { spawn(cmd, opts)→ChildProcess }
tree-sitter 解析产物 { command(string), subcommand?(string), args(string[]), flags(Record) }

【内部关联】
- shell --[调用]--> tree-sitter Parser(命令解析)
- shell --[调用]--> Permission.evaluate("shell", scope)
- shell --[调用]--> ChildProcessSpawner.spawn()
- shell --[关联]--> ShellID(权限持久化键)
- shell --[关联]--> PermissionTable(shell + ShellID pattern)
- shell 输出 --[包装]--> Truncate.Service.output()

【示例】
```typescript
// shell.ts — 执行命令
const result = await shellTool.execute(ctx, {
  command: "npm run test -- --coverage",
  cwd: "/project",
  timeout: 120000  // 2 分钟
})
// → tree-sitter 解析: { command:"npm", subcommand:"run", args:["test", "--", "--coverage"] }
// → Permission.evaluate("shell", "npm run test") → allow
// → spawn("npm", ["run", "test", "--", "--coverage"], { cwd, timeout })
```

║  【工具】Task工具 — 子 Agent 调度与并行执行                  ║
║  编号: E_TOOL_05 | 来源: task.ts                           ║
╚═══════════════════════════════════════════════════════════╝

【定义】 子 Agent 调度工具，启动独立 Session 绑定 subagent 模式 Agent，支持同步（阻塞等待子任务完成）或后台（异步执行）模式，是 opencode 并行多步骤任务执行的核心调度原语。

【边界】★★★ 子 Session 创建跨越会话隔离边界（独立 SessionID + 独立 MessageV2 链 + 独立上下文窗口）；子 Agent 绑定跨越 Agent 切换边界（主 Agent = build，子 Agent = general/explore）；background 模式跨越同步/异步边界（主线程不等待子任务完成）；Bus 事件跨越父子会话通信边界（子任务完成通知）；子工具调用权限跨越双层 Permission 边界（子 Agent.Info.permission + 父 Session.permission 双层覆盖）。

【时序】task 执行流：接收 description/prompt/subagent_type/task_id/background → Permission.evaluate("task", subagent_type, ...) → 过滤可用子 Agent → 创建子 Session(Session.Service.create({agent:subagent_type, parentID:parentSessionID, ...})) → 注入 prompt → 构造子会话独立消息上下文 → 启动子 LLM.Service.stream() → 子 Agent 在独立上下文中执行多轮工具调用。
同步模式(sync)：子 LLM stream → 等待完成(finish event) → 收集子会话 output → 合并到父会话为 SubtaskPart → 返回 ExecuteResult { output: 子任务产出 }。
后台模式(background)：创建子 Session → 异步启动 stream → 立即返回 ExecuteResult { output: "background task started" } → 子会话持续运行 → 完成时发布 Bus.SubtaskCompleted → 父会话 UI 更新。
可选 resume：携带 task_id 恢复已有子任务 → 继续执行。

【结构】Task 工具是会话层的拓扑分支器：父 Session(K) → 子 Session 1..N。每个子 Session 是独立会话实体，持有独立 Agent.Info、独立 MessageV2[]、独立 LLM 上下文。父子会话通过 parentID 外键关联（SessionTable.parent_id → SessionTable.id），子会话结果通过 SubtaskPart 回传父会话消息链。background 模式下子会话生命周期独立于父会话。

【实体】task 参数 { description(string), prompt(string), subagent_type(string — "general"|"explore"|other subagent name), task_id?(string), background?(boolean) }

【内部关联】
- task --[调用]--> Permission.evaluate("task", subagent_type)
- task --[调用]--> Agent.Service(过滤 subagent)
- task --[调用]--> Session.Service.create(parentID)
- task --[调用]--> LLM.Service.stream(子会话)
- task --[产出]--> SubtaskPart(同步模式)
- task --[发布]--> Bus.SubtaskCompleted(后台模式)
- task --[关联]--> SessionTable(parent_id FK)

【示例】
```typescript
// task.ts — 同步子任务：让 explore Agent 搜索代码库
const result = await taskTool.execute(ctx, {
  description: "搜索所有使用 JWT 的文件",
  prompt: "Find all files that import or use jsonwebtoken",
  subagent_type: "explore"
})
// → 子 Session 创建 → explore Agent 使用 grep/glob/read 工具 → 结果返回

// 后台任务：并行启动多个子 Agent
await taskTool.execute(ctx, {
  description: "后台运行测试",
  prompt: "Run the full test suite",
  subagent_type: "general",
  background: true
})
// → 立即返回，子 Agent 在后台继续执行
```

╔═══════════════════════════════════════════════════════════╗
║  【工具】搜索工具族 — grep + glob                           ║
║  编号: E_TOOL_06 | 来源: grep.ts, glob.ts                  ║
╚═══════════════════════════════════════════════════════════╝

【定义】 基于 ripgrep 引擎的代码搜索工具对：grep 执行正则内容搜索返回匹配行及上下文，glob 执行文件模式匹配返回文件路径列表。两者共享 Ripgrep.Service 底层引擎，因结构高度相似（参数→引擎→结果）且各自独立维度 ≤2 行，合并为一个工具族。

【边界】★★★ 两者均跨越 ripgrep 二进制进程边界（调用 rg 命令行工具 → 子进程 stdout）；路径搜索跨越文件系统边界（递归目录遍历）；pattern 参数跨越正则表达式解析边界（regex 语法错误 → 上游处理）；.gitignore 遵守跨越版本控制忽略规则边界（ripgrep 内置）。

【时序】grep 执行流：接收 pattern/path/include → 构造 rg 命令参数（--json 输出、--context 行数、--max-count 限制） → Ripgrep.Service.search(pattern, path, include) → spawn rg 进程 → 解析 JSON 行输出 → 格式化匹配为 {file, line, column, text} → 返回 ExecuteResult { output: 格式化文本 }。
glob 执行流：接收 pattern/path → Ripgrep.Service.files(pattern, path) → spawn rg --files → 收集 stdout 行 → 按修改时间排序 → 返回 ExecuteResult { output: 文件路径列表 }。

【结构】共享底层：Ripgrep.Service { search(pattern, path, include?)→Match[], files(pattern, path)→string[] }。grep 是内容级搜索（语义匹配），glob 是文件名级搜索（模式匹配）。两者参数集几乎正交：grep 多一个 include(文件类型过滤) 参数。Ripgrep.Service 封装 rg 二进制调用（子进程管理 + JSON 解析），统一了错误处理（rg 不存在 → 报错，无匹配 → 空结果）。

【实体】grep 参数 { pattern(string — 正则表达式), path?(string — 搜索目录), include?(string — 文件类型过滤如 "*.ts") }
glob 参数 { pattern(string — glob 模式), path?(string — 搜索目录) }

【内部关联】
- grep --[调用]--> Ripgrep.Service.search()
- glob --[调用]--> Ripgrep.Service.files()

║  【工具】网络+交互工具族 — webfetch + question + todowrite   ║
║  编号: E_TOOL_07 | 来源: webfetch.ts, question.ts, todo.ts  ║
╚═══════════════════════════════════════════════════════════╝

【定义】 用户交互工具三件套：webfetch 获取并转换网页内容为 Markdown/Text/HTML，question 发起交互式多问题提问，todowrite 更新会话任务列表。三者因各自维度偏薄且均为"非文件非进程"的外部信息获取/交互通道，合并为一个工具族。

【边界】★★★ webfetch：(1) HttpClient HTTP/HTTPS 请求跨越网络边界 → 目标服务器；(2) TurndownService HTML→Markdown 转换跨越格式边界；(3) URL 合法性校验跨越安全边界（禁止 SSRF/localhost 访问）；(4) timeout 跨越网络超时边界。question：(1) Question.Service.ask() 跨越用户交互边界（TUI 提问界面 / Server WebSocket）；(2) 多问题并行展示跨越 UI 渲染边界。todowrite：(1) Todo.Service.update() 跨越数据库持久化边界（TodoTable INSERT/UPDATE）；(2) 任务状态流转 (pending→in_progress→completed) 跨越状态管理边界。

【时序】webfetch 执行流：接收 url/format/timeout → URL 校验(协议+域名白名单) → HttpClient.fetch(url, {timeout, redirect:"follow"}) → 获取 HTML/Text → format="markdown" → TurndownService.turndown(html) → 生成 Markdown → 截断(超长内容) → ExecuteResult { output: markdown }。
question 执行流：接收 questions(Question.Prompt[]) → 构造交互界面 → Question.Service.ask(questions) → 用户填入答案 → 返回 ExecuteResult { output: JSON.stringify(answers) }。
todowrite 执行流：接收 todos(Todo[]) → Todo.Service.update(sessionID, todos) → UPSERT TodoTable → 返回 ExecuteResult { output: "Tasks updated" }。

【结构】三者共享"非代码变更的外部交互"语义。webfetch 是外向网络获取，question 是内向用户获取，todowrite 是状态管理更新。Question.Prompt = { question(string), type("text"|"select"|"confirm"), options?(string[]) }。Todo = { content(string), status("pending"|"in_progress"|"completed"), priority(number), position(number) }。TodoTable 列：session_id FK, content, status, priority, position → 由 Todo.Service 管理 CRUD。

【实体】webfetch 参数 { url(string), format?("text"|"markdown"|"html"), timeout?(number) }
question 参数 { questions: Question.Prompt[] } — Question.Prompt { question, type, options? }
todowrite 参数 { todos: Todo[] } — Todo { content, status, priority, position }

【内部关联】
- webfetch --[调用]--> HttpClient
- webfetch --[调用]--> TurndownService(HTML→Markdown)
- question --[调用]--> Question.Service.ask()
- todowrite --[调用]--> Todo.Service.update()
- Todo.Service --[写入]--> TodoTable(UPSERT)
- Question.Service --[展示]--> TUI 交互界面

【示例】
```typescript

  url: "https://example.com/docs",
  format: "markdown"
})
// → HTTP GET → HTML → TurndownService → Markdown output

// question.ts — 提问

})
// → TUI 展示下拉选择 → 用户选择 "PostgreSQL" → output: [{"answer":"PostgreSQL"}]
```

║  【工具】Truncate.Service — 输出尺寸管理                    ║
║  编号: E_TOOL_08 | 来源: truncate.ts                       ║
╚═══════════════════════════════════════════════════════════╝

【定义】 工具输出尺寸管理服务，当工具执行产出超过字符限制时，将完整输出写入磁盘并返回截断预览，同时提供清理接口回收临时文件。被 tool.ts wrap 逻辑统一调用，是所有工具输出的最后一公里。

【边界】★★★ write(text) 跨越内存→磁盘边界（将超大输出写入临时文件）；limits() 跨越配置边界（从 Config 读取输出截断阈值）；cleanup() 跨越磁盘资源管理边界（清理过期临时文件）。

【时序】工具执行 → ExecuteResult output → wrap 逻辑检查 output.length > limits().maxChars → 若超出：Truncate.Service.write(output) → 生成临时文件路径 → 写入全量内容 → Truncate.Service.output(text) → 计算截断点 → 返回 { truncated: 截断预览, fullPath: 磁盘路径 } → 替换 ExecuteResult.output 为截断预览 + "完整输出已保存至 {path}" 提示；若未超出：原样返回。
清理：定时/关闭时 → cleanup() → 遍历临时文件目录 → 删除过期文件。

【结构】Truncate.Service 是单例服务，持有临时文件目录路径。write() 使用 Node.js fs.createWriteStream 写文件 → 返回路径。output() 使用字符截断（非字节截断）保留前后各 limits().preview 字符 → 中间省略。limits() 读取 Config.Info.tool_output.maxChars/preview → 可动态配置。
工具链位置：Tool.Def.execute() [产出 ExecuteResult] → tool.ts wrap 逻辑 [调用 Truncate.Service] → [返回修改后的 ExecuteResult] → 流式返回 LLM。

【实体】Truncate.Service { cleanup()→void, write(text:string)→path(string), output(text:string)→{truncated:string, fullPath?:string}, limits()→{maxChars:number, preview:number} }

【内部关联】
- tool.ts wrap 逻辑 --[调用]--> Truncate.Service.write()/output()
- Truncate.Service.limits() --[读取]--> Config.Info.tool_output
- Truncate.Service --[写入]--> 临时文件目录(磁盘)
- Truncate.Service.cleanup() --[删除]--> 过期临时文件

【示例】

║  【Plugin】Plugin体系 — Service + Hooks + PluginInput + Loader ║
║  编号: E_TOOL_10 | 来源: plugin/index.ts:58-152           ║

【定义】 插件生命周期管理系统：Plugin.Service 管理内置认证插件 + 外部 npm 插件的安装、加载和钩子触发，Hooks 定义可拦截的生命周期点(tool.definition/chat.system.transform/config/event)，PluginInput 是每个插件的初始化上下文，Plugin Loader 处理外部插件的 npm 安装 → 加载 → 兼容性检查 → 入口导出的完整管道。

【边界】★★★ 外部插件加载跨越 npm 包管理边界（npm install → node_modules → require）；Plugin Loader 阶段（install/load/compatibility/entry）跨越文件系统和运行时动态加载边界；PluginInput.serverUrl 跨越网络边界（插件可能发起 HTTP 请求）；Hooks.experimental.chat.system.transform 跨越 system prompt 修改边界（第三方注入）；RuntimeFlags.disableDefaultPlugins 跨越用户配置控制边界；认证插件（CodexAuth/CopilotAuth/GitlabAuth/...）跨越外部 OAuth 服务边界。

【时序】初始化流：Plugin.Service.init() → 加载内置认证插件(除非 RuntimeFlags.disableDefaultPlugins) → 扫描外部插件配置 → 调用 Plugin Loader。
外部插件加载管道：install(若未安装 → npm install 插件包) → load(从 node_modules 加载包入口 → require/import) → compatibility(检查包版本与 opencode 兼容性) → entry(调用包导出的 setup 函数 → 传入 PluginInput) → 注册 Hooks → 插件就绪。
钩子触发流：运行时某事件发生 → Plugin.Service.trigger(name, input, output) → 查找注册了该 hook name 的插件列表 → 按注册顺序依次执行钩子函数（确定性执行，无优先级） → 每个钩子接收 input → 返回 transformed output → 传递给下一个钩子 → 最终 output 返回给调用者。
Hook 点：tool.definition(工具注册时拦截，可新增/修改/删除工具定义)；experimental.chat.system.transform(每次 LLM 调用前拦截 system prompt)；config(配置加载后拦截)；event(全局事件监听)。

【结构】Plugin.Service 是事件驱动架构：初始化阶段构建插件列表 → 运行时触发钩子链。Hooks 对象是插件注册的回调集合，每个 Hook 是一个 EventEmitter 风格的注册表。PluginInput 是依赖注入容器：将 opencode 内部服务（Config/Project/Workspace/Storage）安全暴露给插件。内置插件是 opencode 自身提供的认证提供者插件集(8个)，外部插件是用户安装的 npm 包。

【实体】Plugin.Service { trigger(name:string, input:any, output:any)→Promise<any>, list()→PluginHook[], init()→void }
Plugin.Hooks { tool?:{definition(fn)}, experimental?:{chat?:{system?:{transform(fn)}}}, config?(fn), event?(fn), ... }
Plugin.PluginInput { client(OpencodeClient), project(ProjectInfo), worktree(WorktreeInfo), directory(string), experimental_workspace:{register(fn)}, serverUrl(string?) }
Plugin Loader 阶段 { install, load, compatibility, entry }
内置插件 = { CodexAuth, CopilotAuth, GitlabAuth, PoeAuth, Cloudflare, Azure, DigitalOcean, Xai }

- Plugin.PluginInput --[暴露]--> OpencodeClient(内部 API 子集)
