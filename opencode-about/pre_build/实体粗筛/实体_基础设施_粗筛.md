╔═══════════════════════════════════════════════════════════╗
║  【Provider】Provider体系 — Service + ID体系 + Model + SDK + SSE ║
║  编号: E_INFRA_01 | 来源: provider.ts:40-125, provider/schema.ts:5-30 ║
╚═══════════════════════════════════════════════════════════╝

【定义】 AI 模型提供者统一管理层：Provider.Service 负责 18+ 内置 SDK 的懒加载、模型实例化与解析、认证凭证注入，ProviderID/ModelID 通过品牌类型系统保证类型安全，Provider.Model 封装 LanguageModelV3 实例（来自 Vercel AI SDK）及成本和能力元数据，SSE 超时包装保护流式读取可靠性。

【结构】★★★ 四层塔式依赖：
①品牌类型层(底部)：ProviderID(品牌字符串，"opencode"|"anthropic"|"openai"|"google"|...共18+) → ModelID(品牌字符串，"claude-sonnet-4-20250514"|"gpt-4o"|...) → 类型安全保证，防止 ID 混淆。
②SDK 注册层：内置 SDK 提供者懒加载 Map<ProviderID, ()=>SDK>[18+条目] → OpenAI SDK、Anthropic SDK、Google Generative AI、AWS Bedrock、Groq、Mistral、Together、Fireworks、DeepSeek、xAI、Perplexity、Cohere、Azure OpenAI、Cerebras、Cloudflare、DigitalOcean、Google Vertex AI、OpenRouter → 首次 getModel() 时初始化对应 SDK 单例。
③Service 层(中间)：Provider.Service { getModel, getLanguage, getProvider, defaultModel, models, info } → 核心解析器：ProviderID + ModelID → LanguageModelV3 实例；认证注入：从 Auth.Service 获取 API Key → 注入 SDK 客户端；能力查询：models(providerID)→Model[]（列出该提供者的所有可用模型）。
④Model 层(顶部)：Provider.Model { id(ModelID), providerID(ProviderID), model(LanguageModelV3 — AI SDK 实例), cost(token定价), context(上下文窗口大小), capabilities(能力集:vision/tool_calls/streaming/...)} → 被 LLM.Service 直接消费用于流式调用。
SSE 超时包装：provider.ts:40-86 — wrapSSE(res:Response, ms:number, ctl:AbortController) → 对 SSE fetch 响应施加读超时 → 超时则 abort → 保护调用方不永远挂起。

【实体】ProviderID = string & { readonly _brand: "ProviderID" } — well-known 常量 18+
ModelID = string & { readonly _brand: "ModelID" }
Provider.Model { id(ModelID), providerID(ProviderID), model(LanguageModelV3), cost:{input,output,cacheRead,cacheWrite}(每1K tokens定价), context:{input,output}, capabilities:Set<string> }
Provider.Service { getModel(modelID, providerID)→Provider.Model, getLanguage(model)→LanguageModelV3, getProvider(providerID)→ProviderInfo, defaultModel()→{providerID, modelID}, models(providerID)→ModelSummary[], info(providerID)→ProviderInfo }
SSE 超时包装 { wrapSSE(res:Response, ms:number, ctl:AbortController)→AsyncIterable<SSEChunk> }

【时序】模型解析流：LLM.Service.stream() → providerID + modelID → Provider.Service.getModel(modelID, providerID) → 检查 SDK 是否已加载 → 未加载则导入 SDK 包(lazy load) → 根据 providerID 调用对应 SDK 的 createModel 工厂 → 实例化 LanguageModelV3 → 包装为 Provider.Model(附加 cost/context/capabilities 元数据) → 返回。
SSE 超时流：HTTP Response → SSE 流读取 → 每个 chunk → 重置计时器 → 若 N ms 内无新 chunk → AbortController.abort() → 流结束 → 错误向上传播。
认证注入：Provider.Service.getModel() 内 → Auth.Service.getCredentials(providerID) → 获取 API Key/Token → 设置到 SDK 客户端配置 → SDK 内部携带 Authorization header。

【边界】SDK 懒加载跨越 npm 包动态导入边界（Top-level await import 或 require）；所有 AI SDK 调用跨越网络边界（HTTP → AI API 端点）；认证凭证注入跨越安全边界（API Key 敏感信息）；SSE 超时包装跨越网络可靠性边界（网络中断/服务器卡死 → abort 保护）；模型能力查询跨越第三方文档一致性边界（SDK 声明的能力 vs 实际支持的能力）。

【内部关联】
- Provider.Service.getModel() --[调用]--> Auth.Service.getCredentials()
- Provider.Service.getModel() --[产出]--> Provider.Model
- Provider.Model --[包装]--> LanguageModelV3(AI SDK)
- Provider.Model --[被消费]--> LLM.Service.stream()
- Provider.Service.defaultModel() --[读取]--> Config.Info.model.small_model
- wrapSSE() --[应用于]--> 提供者 HTTP 客户端
- SDK 注册表(Map) --[懒加载]--> 各 AI SDK npm 包

║  【MCP】MCP体系 — Service + 传输层 + 状态 + Resource + 工具转换 ║
║  编号: E_INFRA_02 | 来源: mcp/index.ts:4-186              ║
╚═══════════════════════════════════════════════════════════╝

【定义】 Model Context Protocol 集成层：MCP.Service 管理外部 MCP 服务器的完整生命周期（启动/连接/标准化/工具发现/OAuth 认证），支持三种传输层（STDIO 子进程 / SSE HTTP / StreamableHTTP），将外部 MCP 工具转换为 opencode 兼容的 AI SDK 工具定义，通过 MCP Resource 暴露模型上下文资源。

【结构】★★★ 五层依赖栈：
①传输层(底部)：STDIO(StdioClientTransport — 子进程 stdin/stdout JSON-RPC) | SSE(SSEClientTransport — HTTP Server-Sent Events) | HTTP(StreamableHTTPClientTransport — HTTP 请求/响应) → 统一抽象为 Transport 接口。
②状态机层：MCP 服务器连接状态 = StatusConnected | Disabled | Failed | NeedsAuth | NeedsClientRegistration → 判别联合类型，每个状态携带各自上下文。状态变迁：初始化 → Connected(工具可用) / Disabled(配置禁用) / Failed(连接失败+错误信息) / NeedsAuth(需 OAuth 认证) / NeedsClientRegistration(需客户端注册)。
③协议层：JSON-RPC 2.0 over Transport → tools/list(发现工具) | resources/list(发现资源) | prompts/list(发现提示模板) + 对应的 call/read/get 调用方法。
④Service 层(中间)：MCP.Service → 管理多个 MCP 服务器实例 → 每个实例持有 transport + client + state → 统一对外暴露 tools/resources/prompts 列表。
⑤转换层(顶部)：convertMcpTool(mcpTool, client, timeout?) → 将 MCP SDK 的工具定义(JSON Schema + name + description) 转为 opencode Tool.Def(Effect Schema + execute 闭包) → 注册到 ToolRegistry。
MCP Resource：外部服务器暴露的只读上下文资源 { name, uri, description, mimeType, client } → 可作为 LLM 上下文注入。

【实体】MCP 传输类型 = StreamableHTTPClientTransport | SSEClientTransport | StdioClientTransport
MCP 状态 = { type:"connected" } | { type:"disabled" } | { type:"failed", error:Error } | { type:"needs_auth", authUrl:string } | { type:"needs_client_registration", ... }
MCP Resource { name(string), uri(string), description(string), mimeType(string), client(Client) }
MCP.Service { servers:MCPInstance[], start(id)→void, stop(id)→void, tools(id)→Tool.Def[], resources(id)→MCPResource[], prompts(id)→Prompt[] }
convertMcpTool { (mcpTool:McpToolDefinition, client:Client, timeout?:number)→Tool.Def }

【时序】服务器启动流：MCP.Service.start(serverId) → 读取 Config.Info.mcp[serverId] → 确定传输类型 → 创建对应 Transport 实例 → STDIOSpawn(子进程) / HTTPConnect(建立连接) → JSON-RPC initialize 握手 → 获取服务器能力 → OAuth 流程(若 NeedsAuth: 弹出授权 URL → 用户确认 → 交换 Token) → ClientRegistration(若 NeedsClientRegistration: 注册客户端) → 状态 → Connected。
工具发现流：server.state=Connected → client.request("tools/list") → 获取工具列表 JSON → 每个工具调用 convertMcpTool() → 包装 execute 闭包(内部调用 client.callTool(name, args)) → 返回 Tool.Def[]。
工具调用流：LLM → LLM.Service → Tool.Def.execute(ctx, args) → 闭包内部 → mcpClient.callTool(toolName, args) → Transport.send(JSON-RPC request) → 等待响应 → 返回 ExecuteResult。
资源注入流：MCP.Service.resources(id) → client.request("resources/list") → 返回 Resource[] → LLM 可引用 URI 注入上下文。

【边界】STDIO Transport 跨越操作系统进程边界（子进程 spawn → stdin/stdout 管道 → 进程生命周期管理）；SSE/HTTP Transport 跨越网络边界（TCP/HTTP → 外部 MCP 服务器端点）；OAuth 认证跨越安全边界（用户浏览器授权 → Token 交换）；JSON-RPC 序列化跨越协议边界（请求/响应格式一致性）；convertMcpTool 跨越 Schema 转换边界（JSON Schema → Effect Schema）；ToolRegistry 跨越工具注册边界（外部工具注入）。

【内部关联】
- MCP.Service --[读取]--> Config.Info.mcp[](服务器配置)
- MCP.Service --[使用]--> Transport(三种类型)
- MCP.Service --[调用]--> Auth.Service(OAuth 流程)
- convertMcpTool --[产出]--> Tool.Def
- MCP.Service.tools() --[注入]--> ToolRegistry
- MCP.Resource --[注入]--> LLM context
- MCP.Service --[发布]--> Bus(MCP 状态变更事件)

【示例】
```typescript
// mcp/index.ts:157-186 — MCP 工具转换
const opencodeTool = convertMcpTool(mcpTool, client, 30000)
// → Tool.Def { id: "mcp_servername_toolname",
//               execute: async (ctx, args) => {
//                 const result = await client.callTool({ name: "toolname", arguments: args })
//                 return { output: result.content[0].text, ... }
//               }}

// 三种传输层示例配置：
// STDIO:  { command: "npx", args: ["-y", "@modelcontextprotocol/server-filesystem", "/path"] }
// SSE:    { url: "http://localhost:8080/sse" }
// HTTP:   { url: "http://localhost:8080/mcp" }
```

║  【Config】Config体系 — Info + Service + 合并 + 远程配置     ║
║  编号: E_INFRA_03 | 来源: config.ts:49-200+               ║
╚═══════════════════════════════════════════════════════════╝

【定义】 多层配置管理系统：Config.Info 是 opencode 完整配置模式(opencode.json/jsonc)，Config.Service 负责从全局/工作区/本地三层加载并深度合并配置，支持远程 URL 配置加载和 ${VAR}/${env:VAR} 变量替换，指令数组（instructions）通过 Set 去重拼接。

【结构】★★★ 三层配置来源 + 合并管道：
①源层：全局配置(~/.config/opencode/opencode.json)、工作区配置(project_root/opencode.json)、本地配置(project_root/.opencode/opencode.json) + 可选远程 URL → 均通过 JSON Schema 校验。
②合并层：mergeConfig(ConfigA, ConfigB)→Config → 深度合并 JSON 对象(嵌套字段递归合并) + mergeConfigConcatArrays → 数组字段(如 instructions) 拼接而非覆盖 → instructions 用 Set 去重。
③远程配置层：substituteWellKnownRemoteConfig({value, dir, source, env}) → ${VAR} → 从环境变量或内置变量替换；${env:VAR} → 从 process.env 替换。
④Service 层(顶部)：Config.Service { get()→Config.Info(返回当前缓存的合并配置), directories()→配置目录路径列表, waitForDependencies()→确保远程配置等依赖就绪, set(k,v)→局部更新 } → 依赖 Auth/Env/AppFileSystem/Account 获取各层配置源。
Config.Info 完整模式字段涵盖: shell(Terminal 配置), logLevel, server(端口/地址), command(自定义命令), skills, reference, plugin, model(默认模型), small_model(小型模型), default_agent, agent(Agent 定义数组), provider(Provider 配置), permission(全局权限), instructions(全局指令数组), tool_output(输出截断配置), experimental(实验性功能开关)...

【实体】Config.Info { shell, logLevel, server, command, skills, reference, plugin, model(ModelID), small_model(ModelID), default_agent(string), agent(Agent.Info[]), provider(ProviderConfig[]), permission(Ruleset), instructions(string[]), tool_output:{maxChars, preview}, experimental:Record, ... }
Config.Service { get()→Config.Info, directories()→string[], waitForDependencies()→Promise<void>, set(k:string, v:any)→void }
mergeConfig<T>(base:T, override:T)→T — 深度合并函数
mergeConfigConcatArrays<T>(base:T, override:T)→T — 数组拼接合并
substituteWellKnownRemoteConfig({value, dir, source, env})→string — 变量替换函数

【时序】配置加载流：Config.Service.get() 首次调用 → directories() 确定配置目录列表 → 遍历目录 → fs.readFile("opencode.json"|"opencode.jsonc") → JSONC/JSON 解析 → JSON Schema 校验 → 递归 mergeConfig(当前累积配置, 新配置) → instructions 通过 mergeConfigConcatArrays 拼接 → 远程 URL → HTTP GET → substituteWellKnownRemoteConfig 替换变量 → JSON 解析 → mergeConfig 合并 → 缓存最终 Config.Info → 返回。
set(k, v) 流：set("default_agent", "plan") → 局部更新内存缓存 → 不写回文件(仅运行时生效) → 通知依赖方(Bus)。
依赖就绪流：waitForDependencies() → 等待远程配置加载完成 → 等待 Auth 就绪 → 等待 Env 初始化 → resolve。

【边界】多层文件系统读取跨越磁盘 I/O 边界（全局/工作区/本地三个目录 → opencode.json）；远程 URL 配置加载跨越网络边界（HTTP GET → 外部配置服务器）；变量替换 ${VAR}/${env:VAR} 跨越环境变量边界；JSON Schema 校验跨越数据格式一致性边界；Auth/Account/Env/AppFileSystem 依赖跨越外部服务注入边界。

【内部关联】
- Config.Service.get() --[读取]--> 全局/工作区/本地 opencode.json
- Config.Service.get() --[读取]--> 远程 URL(可选)

- Config.Service --[依赖]--> AppFileSystem
- Config.Service --[依赖]--> Account

╔═══════════════════════════════════════════════════════════╗
║  【Storage】数据库体系 — Client + Transaction + 全量表Schema  ║
║  编号: E_INFRA_04 | 来源: db.ts:92-198, session.sql.ts:24-110 ║
╚═══════════════════════════════════════════════════════════╝

【定义】 单例 SQLite 持久化层：Database.Client 是基于 Bun SQLite + Drizzle ORM 的单例连接管理器（WAL 模式），Database.transaction 提供带行为控制的事务管理（deferred/immediate/exclusive），五大表（SessionTable/MessageTable/PartTable/TodoTable/PermissionTable）构成完整的数据持久化 Schema，通过 EffectBridge.bind 桥接 Drizzle 同步 API 到 Effect 异步世界。

【结构】★★★ 自底向上四层：
①存储层(底部)：Bun SQLite 单例 $client → WAL 模式(WAL journal + synchronous NORMAL) → Global.Path.data 定位 DB 文件路径 → 自动迁移(Drizzle migrations)。
②ORM 层：Drizzle ORM Schema 定义 → 五张核心表(SessionTable/MessageTable/PartTable/TodoTable/PermissionTable) → JSON 列(SeesionTable.data / MessageTable.data / PartTable.data) 存储序列化对象 → 外键约束(session_id → SessionTable, message_id → MessageTable) → 索引定义。
③事务层：Database.transaction(behavior, fn) → 支持 deferred(延迟锁)/immediate(立即 RESERVED 锁)/exclusive(排他锁) → 通过 LocalContext 检测并嵌套已有事务（避免重复 BEGIN） → EffectBridge.bind 将同步 Drizzle API 包装为 Effect 可调用函数。
④Client 层(顶部)：Database.Client → 单例模式($client 全局唯一) → initialize() 执行迁移 → get() 获取 Drizzle 实例 → close() 关闭连接 → 被 Session.Service / Permission.Service / Todo.Service 等上层服务消费。

【实体】Database.Client { get()→DrizzleClient, close()→void, $client(Bun.SQLite) }
Database.transaction { <T>(behavior:"deferred"|"immediate"|"exclusive", fn:(tx)=>T)→T }
SessionTable { id(SessionID PK), slug(string unique), title(string), agent(string), model(JSON), data(JSON — Session.Info序列化), timestamps(created_at, updated_at) }
MessageTable { id(MessageID PK), session_id(FK→SessionTable), data(JSON — MessageV2序列化), timestamps }
PartTable { id(PartID PK), message_id(FK→MessageTable), session_id, data(JSON — Part子类型序列化), timestamps }
TodoTable { session_id(FK→SessionTable), content(string), status("pending"|"in_progress"|"completed"), priority(number), position(number) — 复合主键(session_id, position) }
PermissionTable { session_id(FK→SessionTable), permission(string), pattern(string), action("allow"|"deny") — 复合主键(session_id, permission, pattern) }

【时序】数据库初始化流：Database.Client 首次使用 → 查找 Global.Path.data 下的 SQLite 文件 → 不存在则创建 → 执行 Drizzle migrations(CREATE TABLE IF NOT EXISTS...) → 设置 WAL 模式 → $client 就绪。
写操作流：Session.Service.create() → Database.transaction("immediate", tx => { INSERT INTO SessionTable ... }) → tx 内获取立即锁 → INSERT 执行 → 提交 → 锁释放。
读操作流：Session.Service.children(parentID) → Database.Client.get() → db.select().from(SessionTable).where(eq(...)) → Drizzle 生成 SQL → Bun SQLite 执行 → 返回行数据 → 反序列化 JSON 列。
事务嵌套流：外层已有事务 → Database.transaction() 通过 LocalContext 检测到 → 不创建新事务 → 直接在上层事务中执行 fn → 确保写操作的原子性。
Effect 桥接流：EffectBridge.bind(db.query) → 将同步 db.query() 包装为 Effect(()=>db.query()) → 在 Effect Runtime 中调用 → 返回 Effect<T>。

【边界】Bun SQLite 调用跨越原生 C 库边界（libsqlite3 → 操作系统文件 I/O）；WAL 模式跨越文件系统并发边界（WAL 文件 → shared memory → checkpoint）；Drizzle ORM 抽象跨越 SQL 编译边界（TypeScript Schema → SQL DDL/DML）；数据库文件存储位置跨越文件系统路径边界（Global.Path.data）；Close() 跨越连接生命周期边界（文件句柄释放）。

【内部关联】
- Database.Client --[持有]--> Bun SQLite $client
- Database.Client --[使用]--> Drizzle ORM
- Database.Client --[依赖]--> Global.Path.data(文件路径)
- Database.transaction --[桥接]--> EffectBridge.bind
- SessionTable --[外键关联]--> MessageTable ← PartTable
- SessionTable --[外键关联]--> TodoTable + PermissionTable
- Session.Service --[消费]--> Database.Client(所有 CRUD)
- Permission.Service --[消费]--> Database.Client(PermissionTable 读写)

【示例】

║  【Effect】EffectBridge.Shape — Effect↔Promise 桥接        ║
║  编号: E_INFRA_05 | 来源: effect/bridge.ts:7-12           ║
╚═══════════════════════════════════════════════════════════╝

【定义】 Effect 代码与外部 Promise 世界的桥接层：将 Effect 代码通过 promise() 转为标准 Promise（给外部调用者）、通过 fork() 作为 Fiber 独立执行、通过 run() 同步运行并返回结果、通过 bind() 将同步函数包装为 Effect 可调用函数。是 opencode 内部 Effect 框架与 TypeScript 原生异步生态的互操作层。

【结构】★★★ 桥接方向双向：
①Effect → Promise(对外)：promise(effect)→Promise<T> — 将 Effect 程序提交到 Effect Runtime → 等待完成 → resolve Promise；fork(effect)→Fiber — 将 Effect 作为 Fiber 提交到 Runtime → 立即返回 Fiber 引用（不等待完成）→ 可通过 Fiber 取消/等待。
②Effect ← 外部(对内)：run(effect)→T — 同步运行 Effect 程序 → 阻塞等待完成 → 返回结果；bind(fn)→boundFn — 将普通函数包装为 Effect 可调用函数 → 在 Effect Generator 中直接调用。
核心消费者：Plugin tools(外部工具实现可能是 Effect 程序)、DB transactions(Drizzle 同步 API bind 为 Effect)、Bus subscriptions(订阅回调可能是 Effect 程序)。

【实体】EffectBridge.Shape { promise<T>(effect:Effect<T>):Promise<T>, fork<T>(effect:Effect<T>):Fiber<T>, run<T>(effect:Effect<T>):T, bind<Args, T>(fn:(...args:Args)=>T):(...args:Args)=>Effect<T> }

【时序】promise() 流：外部调用 promise(effect) → Effect Runtime 获取当前 Scope → effect 提交到 Runtime → Runtime 调度执行 effect → 若 effect 包含 yield*(await) 则挂起 → 等待 → 完成 → Runtime 将结果传给 Promise resolve → Promise.then() 回调触发。
fork() 流：fork(effect) → Runtime 创建新 Fiber → Fiber 独立运行 → 立即返回 Fiber 引用 → 调用方持有 Fiber → 可调用 Fiber.interrupt() 取消 → 可调用 Fiber.await() 等待完成。
bind() 流：bind(db.query) → 返回 function*(...args) { return db.query(...args) } → 可在 Effect Generator 中 yield* 调用 → Runtime 执行时遇到 yield* → 调用原始函数 → 结果注入 Generator。

【边界】Effect.effect/promise 跨越异步模型边界（Effect 结构化并发 vs Promise 非结构化并发）；fork 跨越生命周期边界（Fiber 独立于调用方，需显式管理）；bind 跨越同步/异步边界（同步函数包装为 Effect 生成器）；Runtime 调度跨越执行模型边界（Effect Fiber vs JavaScript 事件循环）。

【内部关联】
- EffectBridge.promise() --[提交]--> Effect Runtime
- EffectBridge.bind() --[包装]--> Drizzle/同步函数
- EffectBridge --[被调用]--> Plugin tools(外部工具注册)
- EffectBridge --[被调用]--> DB.transaction(bind Drizzle API)
- EffectBridge --[被调用]--> Bus subscriptions

【示例】
```typescript
// effect/bridge.ts:7-12 — 桥接使用
// Effect → Promise: 将内部 Effect 暴露给外部
const result = await EffectBridge.promise(effectProgram)

// bind: 将同步函数转为 Effect 兼容
const boundQuery = EffectBridge.bind(db.select().from(SessionTable))
// boundQuery 可在 Effect Generator 中 yield* 调用

// fork: 后台执行 Effect
const fiber = EffectBridge.fork(backgroundEffect)
// ... do other work ...
await fiber.await() // 等待后台任务完成
```

║  【Effect】InstanceState — 作用域缓存抽象                  ║
║  编号: E_INFRA_06 | 来源: effect/instance-state.ts:8-13  ║
╚═══════════════════════════════════════════════════════════╝

【定义】 目录/工作区级别的作用域缓存抽象：将服务实例与文件系统路径关联，当上下文（目录切换、工作区变更）改变时自动失效缓存并重建，提供 make/get/use/useEffect/has/invalidate 六种缓存操作原语。被 Bus、Permission、Agent、ToolRegistry、Skill 等服务用于避免跨工作区状态污染。

【结构】★★★ 缓存组织模式：
①键结构：ScopedCache → 以 directory(工作目录路径) 或 workspace(工作区标识) 作为 Scope Key → 每个 Scope 下维护一个数据 Map → 多个 ScopedCache 实例共存（按数据类型隔离）。
②操作集：make(scope, [constructor]) → 若 scope 未缓存 → 调用 constructor 创建新实例 → 存入缓存 → 返回实例；get(scope) → 查缓存 → 命中返回 / 未命中返回 undefined；use(scope, factory) → 存在则返回 + 重置失效计时器 / 不存在则 factory 创建 + 缓存；useEffect(scope, factory) → 同 use 但返回 Effect 包装；has(scope) → boolean 检查缓存存在性；invalidate(scope) → 清除 scope 下所有缓存 → 下次访问触发重建。
③消费者：Bus.Service(每工作区独立事件总线)、Permission.Service(每目录独立权限状态)、Agent.Service(每目录独立 Agent 实例)、ToolRegistry(每工作区独立工具注册表)、Skill.Service(每目录独立技能列表)。

【实体】InstanceState { cache<T>(ScopedCache<T>): { make(scope, constructor?)→T, get(scope)→T|undefined, use(scope, factory)→T, useEffect(scope, factory)→Effect<T>, has(scope)→boolean, invalidate(scope)→void } }

【时序】make 流：服务初始化 → make(directory, () => new Service()) → 检查 scope 缓存 → 未命中 → 执行 constructor → 存入 ScopedCache → 返回新实例 → 后续同 scope 的 get/use 直接返回。
invalidate 流：工作区切换事件 → 检测 directory/workspace 变更 → invalidate(old_scope) → 清除旧缓存 → 引用释放 → 依赖旧 scope 的服务在下一次 access 时通过 use/make 重建。
use 流：每轮请求 → use(scope, factory) → 命中：返回缓存实体 + 刷新失效计时器(若实现 TTL) → 未命中：factory() 创建+缓存+返回。

【边界】缓存失效跨越文件系统路径变更边界（directory 切换 → 缓存失效 → 服务重建）；ScopedCache 存储跨越内存管理边界（缓存增长 → 内存压力 → 需及时 invalidate）；多 ScopedCache 共存跨越作用域隔离边界（每个服务类型的缓存独立，但都基于 directory/workspace 作 key）。

【内部关联】
- InstanceState.cache() --[被调用]--> Bus.Service(每工作区独立)
- InstanceState.cache() --[被调用]--> Permission.Service(每目录独立)
- InstanceState.cache() --[被调用]--> Agent.Service
- InstanceState.cache() --[被调用]--> ToolRegistry
- InstanceState.cache() --[被调用]--> Skill.Service
- InstanceState.invalidate() --[触发于]--> 工作区/目录切换事件

【示例】
```typescript
// effect/instance-state.ts:8-13 — 缓存使用模式
const toolRegistryCache = InstanceState.cache<ToolRegistry>()

// 首次访问工作区 A
const registryA = toolRegistryCache.make("/projectA", () => new ToolRegistry("/projectA"))
// → 创建并缓存

// 同工作区再次访问
const same = toolRegistryCache.get("/projectA")
// → 返回缓存实例（same === registryA）

// 切换到工作区 B
toolRegistryCache.invalidate("/projectA") // 清除旧缓存
const registryB = toolRegistryCache.make("/projectB", () => new ToolRegistry("/projectB"))
// → 创建新实例，旧实例释放
```

║  【Bus】Bus体系 — Service + BusEvent 事件总线              ║
║  编号: E_INFRA_07 | 来源: bus/index.ts, bus/bus-event.ts  ║
╚═══════════════════════════════════════════════════════════╝

【定义】 内部发布/订阅事件总线：Bus.Service 提供类型化事件定义和跨模块发布/订阅能力，BusEvent 通过 BusEvent.define(name, schema) 定义事件名称 + Schema 的双元组，被权限请求、会话更新、项目变更、MCP 状态变化等模块用于解耦通信。

【结构】★★★ 两层定义 + 发布订阅模式：
①Event 定义层：BusEvent.define(name, schema) → 返回 TypedEvent → 承载事件名称(string 标签) + Schema(Effect Schema 或 JSON Schema，用于运行时类型校验)。事件类型示例：PermissionRequested(权限请求)、SessionUpdated(会话更新)、ProjectChanged(项目/工作区变更)、McpStatusChanged(MCP 服务器状态变化)、FileChanged(文件变更)、SubtaskCompleted(子任务完成)。
②Service 层：Bus.Service → 每个工作区独立实例(通过 InstanceState 缓存) → publish(event, payload) → 通知所有 subscribe(event, callback) 的监听器 → callback(payload) 按注册顺序执行 → 支持 Effect Bridge 绑定(订阅回调可为 Effect 程序)。
事件定义在 bus/bus-event.ts 中集中声明，各模块在 import 时注册监听器，运行时 publish 触发通知链。

【实体】BusEvent = BusEvent.define(name:string, schema:Schema)→{ name, schema, publish(payload):void }
Bus.Service { publish<T>(event:BusEvent<T>, payload:T)→void, subscribe<T>(event:BusEvent<T>, callback:(payload:T)=>void)→Unsubscribe }

【时序】定义 → 订阅 → 发布 三部曲：
①模块 A 定义事件：const SessionUpdated = BusEvent.define("session:updated", SessionUpdateSchema)
②模块 B 订阅：BusService.subscribe(SessionUpdated, (payload) => { /* 更新 UI */ })
③模块 A 发布：Session.Service.update() 完成后 → BusService.publish(SessionUpdated, { sessionID, changes })
④通知流：Bus.Service 查找 SessionUpdated 的所有订阅 → 按注册顺序遍历 callback 数组 → 每个 callback(payload) → 若 callback 是 Effect 程序 → EffectBridge.fork() 异步执行 → 不阻塞发布者。
取消订阅：subscribe 返回 Unsubscribe 函数 → 调用后从监听器列表移除 → 后续 publish 不再通知。

【边界】跨模块通信跨越模块隔离边界（Agent/Session/Permission/MCP/CLI 等模块通过 Bus 松耦合通信）；publish 到 subscribe 跨越调用栈边界（发布者不感知订阅者，无返回值）；订阅回调内的 Effect 执行跨越 Effect Runtime 边界（EffectBridge.fork 独立调度）；工作区隔离跨越 InstanceState 缓存边界（不同工作区有独立 Bus 实例）。

【内部关联】
- Permission.Service.ask() --[发布]--> Bus.PermissionRequested
- Session.Service.update() --[发布]--> Bus.SessionUpdated
- MCP.Service --[发布]--> Bus.McpStatusChanged
- edit/write 工具 --[发布]--> Bus.FileChanged
- Task 工具(后台) --[发布]--> Bus.SubtaskCompleted
- TUI/CLI/Server --[订阅]--> Bus.SessionUpdated/PermissionRequested/FileChanged(UI 刷新)
- Bus.Service --[依赖]--> InstanceState(每工作区独立)
- Bus.Service --[依赖]--> EffectBridge(订阅回调的 Effect 执行)

【示例】
```typescript
// bus/bus-event.ts — 事件定义
const SessionUpdated = BusEvent.define("session:updated", Schema.Struct({
  sessionID: Schema.String(),
  changes: Schema.Record(Schema.String(), Schema.Any())
}))

// 订阅：TUI 监听会话更新以刷新界面
BusService.subscribe(SessionUpdated, ({ sessionID, changes }) => {
  refreshUI(sessionID, changes)
})

// 发布：Session.Service 更新后通知
await SessionService.update(sessionID, { title: "New Title" })
BusService.publish(SessionUpdated, { sessionID, changes: { title: "New Title" } })
// → 触发 TUI 的 refreshUI 回调
```
