# opencode v1.15.10 实体粗筛 —— 核心机制

> 主导维度：**时序**（核心挑战是追踪用户请求 → Agent 调度 → LLM 流式处理 → 工具执行 → 会话累积 → 压缩的完整控制流）
> SOP 顺序：时序 → 边界 → 结构 → 实体
> 合并规则：同一功能域、≤2 维只有 1-2 行、共享强配对/继承、独立成卡不增加关系边

║  【Agent】Agent体系 — Info + 预置Agent实例                ║
║  编号: E_CORE_01 | 来源: agent.ts:29-203                  ║
╚═══════════════════════════════════════════════════════════╝

【定义】 Agent 是 AI 助手的身份与行为配置单元，通过 mode 判别联合（primary/subagent/all）决定交互形态，绑定模型、权限、提示和运行参数，四预置实例（build/plan/general/explore）共享同一结构体按字段差异化行为。

【时序】★★★ Agent 选择与注入流：用户切换 Tab → CLI/TUI 发送 Agent.Name → Session 绑定 Agent.Info → LLM.Service.stream() 读取 model/provider/permission → 构建 system prompt 时注入 Agent.prompt → 工具调用时 Tool.Context.ask() 读取 Agent.permission 构造 Permission.Request → 权限评估后执行/拒绝/询问。
预置 Agent 差异流：build(全权限，mode=primary) → 每次工具调用权限预通过；plan(编辑拒绝，仅允许 .opencode/plans/ 写入) → edit/write 工具 → Permission.evaluate 命中 deny → 阻断；general(mode=subagent) → task 工具内部启动子会话 → 独立上下文；explore(mode=subagent, prompt=PROMPT_EXPLORE) → 仅只读工具可见。

【边界】Agent.Info 依赖 Config.Service 从 opencode.json 的 agent 字段加载配置定义（JSON Schema 校验边界）；LLM.Service.stream() 消费 model/provider 字段跨越网络边界调用 AI API；Permission.evaluate 消费 permission(Ruleset) 字段跨越用户审批边界；hidden 字段控制 CLI 可见性。

【结构】Agent.Info 是扁平配置结构体 → mode 是判别联合类型（"primary" 可交互顶层 / "subagent" 被 Task 调度 / "all" 两者皆可）。四预置 Agent 实例均为 Agent.Info 值的常量声明，无继承关系。permission 字段类型为 Permission.Ruleset(Rule[])，嵌入权限规则集。options 字段承载 Agent 级自定义扩展参数。
层级关系：Agent.Info(配置) --被管理--> Agent.Service --被注入--> Session --被消费--> LLM.Service --被评估--> Permission.evaluate

【实体】Agent.Info { name(string), description(string), mode("primary"|"subagent"|"all"), native(boolean, 是否内置不可删除), hidden(boolean, 是否在 UI 中隐藏), topP(number), temperature(number), color(string), permission(Ruleset), model(ModelID), variant(string), prompt(string), options(Record), steps(number) }
预置实例差异字段: build{name:"build", mode:"primary", native:true, 无permission(全允许)}; plan{name:"plan", mode:"primary", permission:edit→deny 除 .opencode/plans/}; general{name:"general", mode:"subagent"}; explore{name:"explore", mode:"subagent", prompt:PROMPT_EXPLORE}

【内部关联】
- Agent.Info --[被管理]--> Agent.Service.get()/list()
- Agent.Info.permission --[被消费]--> Permission.evaluate()
- Agent.Info.model --[被解析]--> Provider.Service.getModel()
- Agent.Info.prompt --[被注入]--> LLM.Service.stream()
- Agent.Info.mode="subagent" --[被过滤]--> Permission.evaluate("task", name)
- build/plan --[互斥切换]--> Tab/Session 绑定

【示例】
```typescript
// agent.ts:130-143 — build Agent 声明
const build: Info = {
  name: "build",
  mode: "primary",
  native: true,
  // 无 permission → 所有工具允许
}

// agent.ts:145-166 — plan Agent 声明
const plan: Info = {
  name: "plan",
  mode: "primary",
  permission: [{ permission: "edit", pattern: "*", action: "deny" },
                { permission: "edit", pattern: ".opencode/plans/**", action: "allow" }]
}
```

║  【Agent】Agent.Service — Agent 管理 + Subagent 过滤 + 动态生成 ║
║  编号: E_CORE_02 | 来源: agent.ts:52-78, registry.ts:307  ║
╚═══════════════════════════════════════════════════════════╝

【定义】 Agent 管理服务契约，提供 Agent.Info 的 CRUD 查询、Subagent 权限过滤和 LLM 驱动的动态 Agent 生成（GeneratedAgent），是 Agent 配置的运行时入口。

【时序】★★★ list() → 从 Config.Service 读取所有 Agent.Info → 过滤 hidden → 返回公开 Agent 列表；get(name) → 按 name 键查找 Agent.Info Map → 返回 Info 或 undefined；defaultInfo() → 返回 Config 中标记为 default_agent 的 Agent.Info；defaultAgent() → 返回 default_agent 名称字符串。
Subagent 调度流：task 工具 → Permission.evaluate("task", name, agent.permission) → 过滤 subagent 模式 Agent → 启动子 Session → 注入子 Agent.Info。
动态生成流：generate({description}) → 构造 LLM 提示 → 调用 LLM.Service.stream() → 解析响应 → 产出 GeneratedAgent{identifier, whenToUse, systemPrompt} → 转为 Agent.Info 候选。

【边界】依赖 Config.Service(get 查询 agent 配置)、Auth.Service(身份验证)、Plugin.Service(agent 相关钩子)、Skill.Service(技能注入)、Provider.Service(模型解析)；generate() 跨越 LLM 调用边界（AI API 网络请求）。

【结构】Agent.Service 是服务接口契约 → 聚合 Config/Auth/Plugin/Skill/Provider 五大依赖。Subagent 过滤路径：Agent.Info.mode === "subagent" → Permission.evaluate("task", name, permission) → 结果 allow → 可用子 Agent 列表。GeneratedAgent 是 LLM 输出物 → 非持久化 → 仅当前会话生命周期。

【实体】Agent.Service { get(name:string)→Info|undefined, list()→Info[], defaultInfo()→Info, defaultAgent()→string, generate({description:string})→GeneratedAgent }
GeneratedAgent { identifier(string), whenToUse(string), systemPrompt(string) }

【内部关联】
- Agent.Service.list() --[读取]--> Config.Info.agent[]
- Agent.Service.generate() --[调用]--> LLM.Service.stream()
- Agent.Service --[被调用]--> task 工具(Permission 过滤 Subagent)
- Agent.Service --[产出]--> Agent.Info(GeneratedAgent → Info 转换)
- Permission.evaluate("task", name) --[过滤]--> Agent.Info.mode="subagent"

【示例】
```typescript
// Agent 列表获取
const agents = await AgentService.list()
// → [build, plan, general, explore, ...自定义 Agent]

// 动态 Agent 生成
const generated = await AgentService.generate({
  description: "安全代码审查专家，专注于 OWASP Top 10"
})
// → { identifier:"security-reviewer", whenToUse:"...", systemPrompt:"..." }
```

║  【Session】Session数据模型 — Info + Tokens + Summary + Model + ID体系 ║
║  编号: E_CORE_03 | 来源: session.ts:161-228, schema.ts:7-25 ║
╚═══════════════════════════════════════════════════════════╝

【定义】 Session 是单次对话的完整可序列化状态容器，携带身份标识（SessionID/MessageID/PartID 三品牌类型）、模型绑定、Token 用量计数器、文件变更摘要和回退快照，实现会话状态的持久化与恢复。

【时序】★★★ 会话诞生：用户启动对话 → Session.Service.create({agent, model, directory}) → 生成 SessionID(品牌字符串) → INSERT SessionTable → 分配初始 Session.Model → 初始化空 Tokens/Summary。
会话累积：每轮 LLM 交互 → Tokens.input/output/reasoning 累加 → Summary.additions/deletions/files 更新 → Session.Info 整体 UPDATE SessionTable。
会话查询：MessageID(前缀"msg") 作为 Part 聚合外键 → PartID(前缀"prt") 作为 PartTable 主键 → 三 ID 链形成 Consumer/Producer 引用链。
会话终结：用户关闭/删除 → Session.Service.remove(id) → DELETE SessionTable CASCADE → 清除子会话引用。

【边界】Session.Info 序列化为 JSON → 存入 SQLite SessionTable.data 列（数据库边界）；SessionID/MessageID/PartID 作为 SQLite 外键跨表引用；revert 字段持有快照引用跨越 Storage/文件系统边界。

【结构】Session.Info 是顶级聚合对象，嵌入三个子结构：Session.Tokens(用量统计)、Session.Summary(变更摘要)、Session.Model(模型绑定)。SessionID(品牌字符串包装，全局唯一主键)、MessageID(前缀"msg"+品牌标记)、PartID(前缀"prt"+品牌标记) 三种 ID 类型通过品牌类型系统保证类型安全，避免 ID 混淆。
表结构对应：SessionTable(id:SessionID PK, slug, title, agent, model, data:JSON) ← MessageTable(id:MessageID PK, session_id FK, data:JSON) ← PartTable(id:PartID PK, message_id FK, session_id, data:JSON)

【实体】Session.Info { id(SessionID), slug(string), projectID, directory(string), parentID(SessionID?), title(string), agent(string), model(Session.Model), version, summary(Session.Summary), cost, tokens(Session.Tokens), share, time, permission(Ruleset), revert }
Session.Tokens { input(number), output(number), reasoning(number), cache:{read(number), write(number)} }
Session.Summary { additions(number), deletions(number), files(number), diffs(FileDiff[]) }
Session.Model { id(ModelID), providerID(ProviderID), variant(string?) }
SessionID = string & { readonly _brand: "SessionID" }
MessageID = string & { readonly _brand: "MessageID", _prefix: "msg" }
PartID = string & { readonly _brand: "PartID", _prefix: "prt" }

【内部关联】
- Session.Info --[聚合]--> Session.Tokens + Summary + Model
- Session.Info.id(SessionID) --[外键引用]--> MessageTable.session_id
- MessageID --[外键引用]--> PartTable.message_id
- Session.Info.revert --[引用]--> Snapshot 快照
- Session.Info.permission --[被评估]--> Permission.evaluate()

【示例】
```typescript
// session.ts:208-228 — Session.Info 结构
const session: Session.Info = {
  id: "sess_abc123" as SessionID,
  title: "修复登录页面 Bug",
  agent: "build",
  model: { id: "claude-sonnet-4-20250514" as ModelID, providerID: "anthropic" as ProviderID },
  tokens: { input: 15420, output: 3200, reasoning: 500, cache: { read: 8000, write: 2000 } },
  summary: { additions: 45, deletions: 12, files: 3, diffs: [...] },
  permission: [...]
}
```

║  【Session】Session.Service — 会话生命周期管理               ║
║  编号: E_CORE_04 | 来源: session.ts                         ║
╚═══════════════════════════════════════════════════════════╝

【定义】 会话生命周期管理服务，提供创建、更新、删除、压缩、回退、提示构建和子会话查询的完整 CRUD + 流操作，是会话状态的唯一写入口。

【时序】★★★ create({agent, model, parentID?}) → 生成 SessionID → 构造 Session.Info → INSERT SessionTable → 发布 Bus.SessionCreated → 返回 Session.Info。
update(id, patch) → 部分合并 Session.Info → UPDATE SessionTable → 发布 Bus.SessionUpdated → 触发 UI 刷新。
compact(id) → 读取 Session 消息历史 → 计算溢出范围 → 调用 LLM 生成摘要 → 创建 CompactionPart → 标记压缩锚点 → 更新 Session.Info → 发布 Bus.SessionCompacted。
revert(id, messageID) → 查找 messageID 位置 → DELETE 该消息及所有后继 Part/Message → 恢复 Session 状态 → 发布 Bus.SessionReverted。
children(parentID) → SELECT SessionTable WHERE parent_id = parentID → 返回子会话列表。
prompt(id) → 构建完整消息上下文 → 拼接 system prompt + messages → 返回纯文本或结构化提示。

【边界】所有写操作跨越数据库事务边界（Database.Client / Drizzle ORM / SQLite WAL 模式）；compact() 跨越 LLM 调用边界（摘要生成 API 请求）；事件发布跨越 Bus 边界（跨模块通知）；revert() 跨越 Storage 边界（快照数据恢复）。

【结构】Session.Service 是外观层 → 聚合 Database.Client(CRUD 持久化)、Bus.Service(事件发布)、Snapshot(回退快照)、Storage(文件存储)、LLM.Service(压缩摘要) 五个依赖。无状态服务：每次调用从 Database 读取最新状态，不维护内存缓存。

【实体】Session.Service { create(NewSession)→Session.Info, update(id:SessionID, patch:Partial<Session.Info>)→void, remove(id:SessionID)→void, compact(id:SessionID)→CompactionResult, revert(id:SessionID, messageID:MessageID)→void, prompt(id:SessionID)→string, children(parentID:SessionID)→Session.Info[] }

【内部关联】
- Session.Service.create() --[写入]--> SessionTable(INSERT)
- Session.Service.update() --[写入]--> SessionTable(UPDATE)
- Session.Service.compact() --[触发]--> LLM.Service.stream()(摘要生成)
- Session.Service.compact() --[产出]--> CompactionPart
- Session.Service --[发布]--> Bus.Service(SessionCreated/Updated/Compacted/Reverted)
- Session.Service.revert() --[触发]--> Snapshot.restore()

【示例】
```typescript
// 创建新会话
const sess = await SessionService.create({
  agent: "build",
  model: { id: "claude-sonnet-4-20250514", providerID: "anthropic" }
})

// 压缩长会话
await SessionService.compact(sess.id)  // 自动生成摘要压缩历史

// 回退到指定消息
await SessionService.revert(sess.id, "msg_xxx")
```

║  【Session】MessageV2.Part体系 — 消息多态内容单元            ║
║  编号: E_CORE_05 | 来源: message-v2.ts:60-220+             ║
╚═══════════════════════════════════════════════════════════╝

【定义】 MessageV2.Part 是消息内容的多态载荷单元，通过判别联合类型（TextPart | ReasoningPart | FilePart | SnapshotPart | PatchPart | AgentPart | CompactionPart | SubtaskPart | ToolPart）统一封装文本、推理、文件、快照、补丁、Agent切换、压缩标记、子任务和工具调用九种语义载体，配合 OutputFormat 控制 LLM 输出结构。

【时序】★★★ Part 写入流：LLM stream 产出一组事件 → 按事件类型构造对应 Part 子类型 → 每个 Part 序列化为 JSON → INSERT PartTable（message_id FK, session_id, data JSON）。
Part 读取流：查询消息历史 → SELECT PartTable WHERE message_id = ? ORDER BY created_at → 反序列化 JSON → 判别 type 字段 → 还原为联合类型实例 → 渲染到 UI/拼接 LLM context。
ToolPart 特化流：LLM 返回 tool_use → ToolPart 构造 → Tool.Def.execute() → ExecuteResult → 可能产出 FilePart(Base64 图片附件) → 追加到消息流。

【边界】Part 序列化为 JSON 存入 SQLite PartTable.data 列（数据库边界）；FilePart.url 引用 Storage 存储路径或外部 URL；ToolPart 携带 tool_call_id 跨越 Tool.Def.execute() 边界；OutputFormat.JsonSchema 对 LLM API 施加结构化输出约束（跨 AI API 边界）。

【结构】MessageV2.Part 是 tagged union → 公共字段 { type(discriminant), time, metadata } + 各子类型特有字段。MessageV2 聚合 Part[] 数组，一条 Message 可包含多个 Part（如 text + tool_call 组合）。
OutputFormat 独立于 Part 体系：是 LLM 请求级控制参数 { type:"text"|"json_schema", schema? }，非 Part 子类型，但影响 TextPart 的内容格式。
文件引用链：FilePart.source(FilePartSource) → 可能的 FilePartSource 包括：url、base64、local_path、generated → ExecuteResult.attachments 可产出 FilePart 追加到流。

【实体】TextPart { type:"text", text(string), synthetic(boolean), ignored(boolean), time, metadata } — 主要文本载体，synthetic 标记系统生成，ignored 标记不计入 LLM 上下文。
ReasoningPart { type:"reasoning", text(string), metadata, time } — LLM 推理链输出（如 Claude extended thinking）。
FilePart { type:"file", mime(string), filename(string), url(string), source(FilePartSource), time } — 图片/PDF 等文件附件。
SubtaskPart { type:"subtask", prompt(string), description(string), agent(string), model(Session.Model) } — 子任务调度负载。
CompactionPart { type:"compaction", ... } — 压缩标记，替代被折叠的历史消息段。
OutputFormat { type:"text"|"json_schema", schema?(JSONSchema) }

【内部关联】
- MessageV2 --[包含]--> Part[] (1:N 聚合)
- Part --[序列化]--> PartTable.data(JSON)
- ToolPart --[引用]--> Tool.Def.id
- FilePart --[被引用]--> ExecuteResult.attachments
- CompactionPart --[产出]--> Compaction 进程
- SubtaskPart --[触发]--> Task 工具启动子会话

【示例】
```typescript
// message-v2.ts:97-111 — TextPart
const part: TextPart = {
  type: "text",
  text: "我来分析这段代码...",
  synthetic: false,  // LLM 自然生成
  ignored: false,    // 计入 LLM 上下文窗口
  time: { start: 1717200000, end: 1717200050 }
}

// 带工具调用的消息: [ReasoningPart, ToolPart, TextPart]
const msg = [reasoningPart, toolPart, textPart]
```

║  【核心机制】LLM.Service — LLM 流式编排中心                 ║
║  编号: E_CORE_06 | 来源: llm.ts:56-57                      ║
╚═══════════════════════════════════════════════════════════╝

【定义】 LLM.Service 是 AI 模型流式编排中心，负责 Provider 解析、工具绑定、认证注入、权限过滤和 Plugin 钩子调用，将系统上下文转换为 AI SDK 兼容的流式请求，产出 LLMEvent 事件流供上层消费。

【时序】★★★ stream(input:StreamInput) → ①解析 model/provider → Provider.Service.getModel(modelID, providerID) → 获取 LanguageModelV3 实例；②构建请求参数：system prompt(Agent.prompt + instructions), messages(MessageV2[]→AI SDK format), tools(ToolRegistry.tools(model)→经 Permission.evaluate 过滤); ③注入认证：Auth.Service.getCredentials(providerID); ④Plugin 钩子：experimental.chat.system.transform 变换 system prompt; ⑤发起流式调用：provider.doStream(params) → SSE/HTTP chunk 迭代; ⑥逐 chunk 处理：text_delta → 累积文本, tool_call → 收集参数, reasoning → 推理块; ⑦finish → 产出完整 message + usage stats → 返回 Stream 结束。
权限过滤子流：ToolRegistry.tools(model) → 获取全量工具列表 → Permission.evaluate(tool.id, pattern, agentRuleset, sessionRuleset) → 移除 deny 工具 → ask 工具标记需要审批 → 仅 allow 工具直接绑定到 LLM 请求。

【边界】provider.doStream() 跨越网络边界（HTTP/SSE → AI API 端点 openai/anthropic/google/...）；Auth.Service 注入 API Key 跨越认证安全边界；Plugin.Hooks.system.transform 跨越扩展性边界（第三方修改 system prompt）；SSE 超时包装(provider.ts:40-86) 跨越网络可靠性边界。

【结构】LLM.Service 是编排层（无状态）→ 聚合 Provider.Service(SDK 实例化)、Auth.Service(凭证)、Config.Service(模型配置)、Plugin.Service(变换钩子)、Permission.evaluate(工具过滤) 五个依赖。StreamInput 是请求参数聚合体，Stream<LLMEvent> 是响应流抽象。LLMEvent 是判别联合 = TextDelta | ToolCall | Reasoning | Finish | Error。
工具绑定链：Tool.Def → AI SDK Tool 格式转换 → LanguageModelV3.tools 参数 → LLM API 请求体 tools 字段。

【实体】LLM.Service { stream(input:StreamInput)→Stream<LLMEvent> }
StreamInput { model(ModelID), provider(ProviderID), messages(MessageV2[]), tools(Tool.Def[]), system(string), outputFormat(OutputFormat), session(Session.Info), agent(Agent.Info), abort(AbortSignal) }
LLMEvent = TextDelta({text, messageID}) | ToolCall({id, name, args}) | Reasoning({text}) | Finish({usage, stopReason})

【内部关联】
- LLM.Service.stream() --[调用]--> Provider.Service.getModel()
- LLM.Service.stream() --[调用]--> Auth.Service.getCredentials()
- LLM.Service.stream() --[过滤]--> Permission.evaluate()(工具权限)
- LLM.Service.stream() --[触发]--> Plugin.Hooks.system.transform
- LLM.Service.stream() --[产出]--> MessageV2.TextPart + ReasoningPart + ToolPart
- LLM.Service --[被调用]--> Session.Service.compact()(摘要生成)

【示例】
```typescript
// llm.ts:56-57 — 流式调用
const stream = LLMService.stream({
  model: "claude-sonnet-4-20250514" as ModelID,
  provider: "anthropic" as ProviderID,
  messages: sessionMessages,
  tools: registry.tools("claude-sonnet-4-20250514"),
  system: agent.prompt,
  outputFormat: { type: "text" },
  session, agent, abort
})
for await (const event of stream) {
  // 处理 TextDelta / ToolCall / Reasoning / Finish
}
```

║  【核心机制】Compaction — 上下文窗口压缩管理                  ║

【定义】 上下文窗口管理机制，当会话消息历史超过 LLM 上下文限制（溢出检测）时，自动触发摘要生成或消息折叠，将超限的历史消息段替换为 CompactionPart 压缩标记，维持会话连续性且不丢失语义上下文。

【时序】★★★ 压缩触发检测：每次 LLM.Service.stream() 前 → 计算当前消息总 tokens(输入 + 历史) → 与 model.context.limit 比较 → 若溢出：auto(true) 则自动触发 → 或 overflow(true) 标记强制触发。
压缩执行：定位压缩锚点(tail_start_id: MessageID，保留尾部 N 条消息) → 提取需压缩的消息段 → 构造 LLM 摘要请求("请总结以下对话") → LLM.Service.stream(摘要 prompt) → 产出摘要文本 → 创建 CompactionPart(携带摘要文本 + 被压缩消息引用) → 更新 Session.Info.summary → 从消息历史移除被压缩的原始 Part → 追加 CompactionPart 到消息链。
非溢出场景：用户手动触发压缩 → compact(id) → 同上流程但无需溢出检测。

【边界】压缩摘要生成跨越 LLM 调用边界（实际发送 AI API 请求生成摘要）；压缩结果持久化跨越数据库边界（SessionTable.data 和 PartTable INSERT/UPDATE）；CompactionPart 的引用链跨越消息历史一致性边界（被压缩的消息 ID 链）。

【结构】Compaction 关联 Session.Info → 控制参数：auto(是否自动压缩)、overflow(是否因溢出触发)、tail_start_id(保留尾部消息的起始 MessageID)。产出 CompactionPart 作为特殊 Part 类型，携带摘要文本和被折叠段的元信息。
Session 生命周期中的压缩位置：正常交互 → Tokens 累加 → 溢出检测点(每次 stream 前) → 压缩 → 恢复交互。

【实体】Compaction { auto(boolean), overflow(boolean), tail_start_id(MessageID|undefined) }
CompactionPart { type:"compaction", summary(string), compactedMessageIDs(MessageID[]), ... }（推断字段）

【内部关联】
- Compaction --[触发于]--> LLM.Service.stream()（上下文溢出检测）
- Compaction --[触发]--> LLM.Service.stream()（摘要生成子请求）
- Compaction --[产出]--> CompactionPart
- Compaction --[更新]--> Session.Info.summary
- Compaction --[被触发]--> Session.Service.compact()
- CompactionPart --[替代]--> 被压缩的 MessageV2.Part[]

【示例】
```typescript
// 自动压缩：当 tokens 超过模型限制时
// 系统自动执行:
// 1. 计算溢出
// 2. 压缩前50条消息为摘要
// 3. 消息链变为: [CompactionPart(摘要), ...保留的最后20条消息]
// 4. LLM 读到 CompactionPart 作为上下文
```

║  【Permission】Permission体系 — 权限规则引擎 + 交互审批 + 持久化 ║
║  编号: E_CORE_08 | 来源: permission/index.ts:19-304       ║
╚═══════════════════════════════════════════════════════════╝

【定义】 工具使用安全网关，通过有序规则匹配引擎（Rule + Ruleset）评估每条工具调用（allow/deny/ask），结合交互式审批（Request→Reply 生命周期）和会话级持久化（PermissionTable），实现多源规则合并和用户意图驱动的访问控制。

【时序】★★★ 规则评估流：工具调用 → Tool.Context.ask() 构造 Permission.Request { id, sessionID, permission, patterns[], metadata, always[], tool } → Permission.evaluate(permission, pattern, ...rulesets) → 遍历 agentRuleset + sessionRuleset(后者覆盖前者) → 正则匹配 pattern 字段 → 返回最后匹配的 Rule.action。
action=allow → 直接执行工具。
action=deny → 返回拒绝 → 工具不执行 → 反馈给 LLM。
action=ask → 发送 Request → Permission.Service.ask() → 发布 Bus.PermissionRequested → TUI/Server 渲染审批界面 → 用户选择 Reply。
审批持久化流：用户 select Reply → reply("once"|"always"|"reject") → "once" 仅本次有效 → "always" UPSERT PermissionTable(session_id, permission, pattern, action) → 下次同 permission+pattern 自动通过 → "reject" 拒绝本次执行 → 反馈给 LLM。
多源合并流：Permission.merge(agentRuleset, sessionRuleset, ...) → 委托 PermissionV2.merge → 长 Ruleset 拼接 → 重复 permission+pattern → 后者覆盖前者。

【边界】ask() 跨越用户交互边界（TUI 终端提示 / Server WebSocket 推送）；reply("always") 跨越数据库持久化边界（PermissionTable INSERT/UPDATE）；用户决策跨越确定性边界（系统无法预测用户意图）；Bus 发布跨越模块通信边界。

【结构】三层架构：
①Rule 层(原子)：Permission.Rule { permission, pattern, action } — 单条匹配规则，action ∈ {allow, deny, ask}。
②Ruleset 层(集合)：Permission.Ruleset = Rule[] — 有序规则数组，附着于 Agent.Info.permission + Session.Info.permission。后覆盖前：遍历时最后匹配的 rule 胜出。
③Service 层(交互)：Permission.Service { ask(AskInput)→void, reply(ReplyInput)→void, list()→Request[] } — 管理审批生命周期；Permission.evaluate(permission, pattern, ...rulesets)→Rule — 纯函数引擎；Permission.merge(...rulesets)→Ruleset — 合并器。

【实体】Permission.Rule { permission(string — 如 "edit"/"shell"/"task"), pattern(string — glob 模式匹配文件路径/命令), action("allow"|"deny"|"ask") }
Permission.Ruleset = Rule[] — 有序规则数组
Permission.Request { id(PermissionID), sessionID(SessionID), permission(string), patterns(string[]), metadata(Record), always(string[]), tool(Tool.Def) }
Permission.Reply = "once" | "always" | "reject" — 判别联合类型
Permission.Service { ask(input:AskInput)→void, reply(input:ReplyInput)→void, list()→Request[] }
Permission.evaluate = (permission, pattern, ...rulesets:Ruleset[]) → Rule | undefined
Permission.merge = (...rulesets:Ruleset[]) → Rule[]

【内部关联】
- Permission.evaluate() --[消费]--> Agent.Info.permission + Session.Info.permission
- Tool.Context.ask() --[构造]--> Permission.Request
- Permission.Service.ask() --[发布]--> Bus.PermissionRequested
- Permission.reply("always") --[写入]--> PermissionTable(UPSERT)
- Permission.merge() --[组合]--> Ruleset[]
- Permission.evaluate --[委托]--> PermissionV2.evaluate(底层引擎)
- Permission.merge --[委托]--> PermissionV2.merge

【示例】
```typescript
// 定义 Agent 权限
const agentRuleset: Ruleset = [
  { permission: "edit", pattern: "*", action: "deny" },
  { permission: "edit", pattern: ".opencode/plans/**", action: "allow" },
  { permission: "shell", pattern: "npm run *", action: "ask" },
]

// 工具调用时评估
const rule = Permission.evaluate("edit", "src/app.ts", agentRuleset, sessionRuleset)
// → action="deny" (匹配 pattern:"*")

// 用户审批流程
await PermissionService.ask({ id, sessionID, permission: "shell", patterns: ["npm run test"] })
// → TUI 显示审批提示 → 用户选择 "always"
await PermissionService.reply({ id, reply: "always" })
// → PermissionTable 写入: { session_id, permission:"shell", pattern:"npm run *", action:"allow" }
```
